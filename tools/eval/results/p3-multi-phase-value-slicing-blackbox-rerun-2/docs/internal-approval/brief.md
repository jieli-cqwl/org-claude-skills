# Brief: 内部审批系统

功能名: internal-approval | 产出时间: 2026-04-12

## 业务背景与根问题
目前审批主要靠聊天工具和表格流转，申请、结果和历史记录分散，导致申请人和审批人都很难追踪一笔申请到底卡在哪一步。根问题不是“再做一个审批入口”，而是先把申请提交、审批结果和历史记录收口成可追踪的闭环。

## 目标与成功标准

| 目标 | 成功标准 | 度量方式 |
|------|---------|---------|
| Phase 1 跑通审批闭环 | 员工可提交申请，审批人可通过或驳回，申请人和管理员可查看审批记录，当前状态始终清晰 | 关键流程 E2E 通过率，人工追问次数下降 |
| Phase 2 补主动通知 | 审批结果变化后，申请人能收到企业微信通知 | 通知送达率，未送达可追踪率 |
| Phase 3 提供管理报表 | 管理员能查看审批统计结果 | 报表打开成功率，统计结果可复核 |

## 关键假设

| 假设 | 不成立时的后果 | 验证方式 |
|------|--------------|---------|
| 审批人角色和权限可明确配置 | 审批处理无法判断谁能处理哪一单 | 进入设计前确认角色矩阵 |
| 审批记录需要完整落库 | 历史追踪与审计无法成立 | 设计阶段核对记录字段清单 |
| 企业微信通知可在后续接入 | Phase 1 不会被外部集成阻塞 | 将接入条件放入待设计决策 |
| 报表统计口径需要先收口 | 统计结果可能前后不一致 | 设计阶段确认维度与刷新口径 |

## 用户角色与核心场景
- 作为员工，我希望提交审批申请并随时查看处理结果，这样我不用反复找人问进度。
- 作为审批人，我希望能直接处理待办申请并写下通过或驳回结果，这样审批动作能留下明确记录。
- 作为管理员，我希望查看全量审批记录和后续统计报表，这样我能追踪流程和做管理分析。

## 业务术语

| 术语 | 定义 | 备注 |
|------|------|------|
| 审批申请 | 一次需要审批的业务请求 | 包含提交人、提交时间、当前状态 |
| 审批结果 | 审批人对申请做出的处理结论 | 取值至少包括待处理、通过、驳回 |
| 审批记录 | 可追踪的历史留痕 | 需要包含提交人、审批人、时间、处理结果、驳回原因 |
| 当前状态 | 一笔申请此刻处于的审批阶段 | 需要对申请人和管理员可见 |

## 业务对象

| 对象 | 说明 | 关键状态/属性 |
|------|------|---------------|
| 审批申请 | 申请人提交的一条审批单 | 申请编号、提交人、提交时间、当前状态 |
| 审批结果 | 审批人对申请的处理动作 | 待处理、通过、驳回、处理人、处理时间、驳回原因 |
| 审批记录 | 历史查询和追踪载体 | 申请人、审批人、时间、结果、备注 |

## 当前业务流程
员工通过聊天工具发起审批，审批人可能在聊天、表格或私下沟通中处理，结果和历史记录分散在不同地方，后续追踪依赖人工询问。

## 目标业务流程
员工提交审批申请后，审批人可处理并给出通过或驳回结果，系统记录处理人、时间和原因；申请人和管理员都能查看记录，当前状态始终明确。后续再扩展企业微信通知和统计报表。

## 范围 / 本期不交付

| 类型 | 内容 |
|------|------|
| 范围 | 提交审批申请、审批处理（通过/驳回）、查看审批记录、查看当前状态 |
| 本期不交付 | 企业微信通知、统计报表、多级会签、复杂 SLA 规则、驳回后自动重新提交 |

## 业务规则
- 申请提交成功后，状态必须进入“待处理”。
- 审批处理只能由有权限的审批人执行。
- 审批通过或驳回时，必须记录审批人、时间和处理结果。
- 审批驳回时，必须记录驳回原因并在记录中可见。
- 申请人可以查看自己的审批记录，管理员可以查看全量审批记录。

## MVP 最小闭环说明
- 最小闭环包含哪些 UNIT：UNIT-1、UNIT-2、UNIT-3
- 关键路径（按依赖顺序）：UNIT-1 → UNIT-2 → UNIT-3
- 逐项不可移除论证：
  - 移除 UNIT-1 则：员工无法发起申请，后续审批没有对象可处理。
  - 移除 UNIT-2 则：申请只能提交不能结论，根问题“结果难追踪”仍未解决。
  - 移除 UNIT-3 则：申请人和管理员无法查看历史，闭环没有“可追踪”出口。
