# UNIT-2: 审批处理通过或驳回

**优先级**: MVP

## 优先级依据
没有审批处理，申请只能提交不能形成结论，根问题“结果难追踪”仍未解决。

## 背景
审批人需要能在系统里直接处理待办申请，避免结果继续散落在聊天和表格里。

## 需求描述
提供对待处理申请的审批能力，审批人可以给出通过或驳回结果，并留下可追踪记录。

## 功能闭环定义
- 输入/触发: 审批人打开一条待处理申请并选择通过或驳回
- 核心行为: 系统校验审批权限，写入审批结果、处理人、处理时间；若驳回则写入原因；状态更新为通过或驳回
- 可观察结果: 申请状态改变，记录页可看到处理结果、处理人和时间

## 验收标准

### 正常场景
- AC-U2-01: 审批人对待处理申请选择通过 → 系统记录通过结果，状态更新为已通过
- AC-U2-02: 审批人对待处理申请选择驳回并填写原因 → 系统记录驳回结果和原因，状态更新为已驳回

### 异常场景
- AC-U2-03: 非授权用户尝试处理申请 → 系统拒绝操作，并提示无权限

### 边界条件
- AC-U2-04: 同一申请已被处理后再次提交审批动作 → 系统拒绝重复处理，并保留首个有效结果

## 业务规则（如有）
- 只有有权限的审批人可以处理待办申请。
- 驳回时必须记录原因，且记录在后续查询中可见。

## 依赖
- 依赖 UNIT: UNIT-1
- 依赖业务对象: 审批申请、审批结果
- 受影响方: 审批记录查询、后续通知

## 排除项
- 多级会签
- 企业微信通知发送细节
- 重新提交驳回申请
