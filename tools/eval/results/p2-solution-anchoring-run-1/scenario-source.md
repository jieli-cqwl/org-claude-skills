# P2 Run 1 Scenario Source

- 场景 ID: `p2-solution-anchoring`
- 执行日期: `2026-04-12`
- 用户首句: `我想做一个权限矩阵配置中心，最好像竞品那样有角色树和批量授权。`

## 模拟共创输入

- S2 根问题澄清:
  - 真实痛点是新项目开权限依赖平台管理员手工配置，速度慢且事后难追溯。
  - `角色树` 和 `批量授权` 不是必须，只是用户受竞品启发给出的方案示例。
- S3 目标与成功标准:
  - 项目管理员能看清某个角色拥有哪些资源权限。
  - 一次常规授权调整最好在 5 分钟内完成。
  - 变更后能追溯是谁改的。
- S4 语义收口:
  - 角色是项目内角色，不是公司统一身份角色。
  - 资源是系统里的功能模块和数据范围。
- S5 范围与规则:
  - 本期先覆盖项目级角色的查看和调整。
  - 不做跨项目继承、组织架构同步、复杂审批流。
  - 每次权限调整都要留下操作人、时间、变更前后差异。
- S6 Phase 决策:
  - 核心闭环可以先做一个 Phase。
  - 树形可视化和批量操作不要求同一期上线。
- S7 UNIT 拆解:
  - 最少覆盖查看当前权限、执行权限调整、留存变更记录三件事。
  - 不把 `像竞品的角色树` 当成必做 UNIT。
- S8 AC:
  - 把 `能看清当前权限` 和 `改完后可追溯` 写成可观察结果。
- S9 待设计决策:
  - 权限矩阵的交互形态。
  - 批量调整是否需要单独能力。
- S10 完整性扫描:
  - 项目管理员不能越权修改其他项目的角色权限。

## 本轮评测目标

- 验证 `/product` 是否能把“方案先行”的用户表达还原为“问题先行”的需求基线。
- 验证最终输出是否保留开放设计决策，而不是把 `角色树` / `批量授权` 锁死成需求。
