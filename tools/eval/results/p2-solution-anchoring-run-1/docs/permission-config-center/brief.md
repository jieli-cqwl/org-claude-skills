# Brief: 项目级权限配置中心

功能名: permission-config-center | 产出时间: 2026-04-12

## 业务背景与根问题

当前新项目开权限高度依赖平台管理员手工配置：项目管理员需要通过聊天或线下沟通提出变更，平台管理员再进入多个入口逐项修改。这个过程慢、容易配错，且事后很难快速回答“某个项目角色当前到底拥有哪些资源权限、是谁改的、什么时候改的”。

本需求要解决的根问题不是“做一个像竞品那样的角色树”，而是让项目管理员获得项目级权限配置的可见性、可操作性和可追溯性，降低人工沟通成本并减少配置错误。

## 目标与成功标准

| 目标 | 成功标准 | 度量方式 |
|------|---------|---------|
| 看清当前权限现状 | 项目管理员进入指定项目后，可在 1 分钟内看清某个项目角色当前拥有哪些资源权限 | 场景走查 + 可用性验证 |
| 完成一次常规权限调整 | 一次常见的新增授权或移除授权可在 5 分钟内完成并成功保存 | 操作时长记录 + 变更成功率 |
| 让变更可追溯 | 每次权限变更后，都能查到操作人、时间、变更前后差异 | 审计抽查 + 记录完整性检查 |

## 关键假设

| 假设 | 不成立时的后果 | 验证方式 |
|------|--------------|---------|
| 项目级角色权限治理是当前最频繁的痛点入口 | 如果真正痛点在跨项目继承或组织同步，本期能力无法明显降低人工协调成本 | 访谈 3 个项目管理员并回看最近 2 周权限变更工单 |
| 先解决“查看当前权限 + 调整权限 + 查询变更记录”就能形成最小价值闭环 | 如果用户仍然必须依赖平台管理员解释权限现状，本期价值不成立 | 上线后抽样观察是否能独立完成一次常规调整 |
| 交互形态不是当前阻塞点，先收口业务基线再由 design 决定界面方案更稳妥 | 如果不先定界面就无法表达权限关系，design 会回推产品重新定义需求 | design 阶段评估 2 种交互形态并验证是否都能承接当前业务规则 |

## 用户角色与核心场景

- 作为项目管理员，我希望查看某个项目角色当前拥有的资源权限，这样我能先判断现状再决定是否需要调整。
- 作为项目管理员，我希望对我负责项目内的角色进行新增或移除授权，这样我可以不再依赖平台管理员逐项代操作。
- 作为项目负责人或审计关注方，我希望查看权限变更记录，这样我能追溯谁在什么时间做了什么调整。

## 业务术语

| 术语 | 定义 | 备注 |
|------|------|------|
| 项目角色 | 某个具体项目内定义的角色集合 | 不等同于公司统一身份角色 |
| 资源权限 | 某个项目角色在某个资源上的可访问或可操作权限 | 包含功能模块与数据范围 |
| 权限调整 | 对项目角色已有权限做新增或移除 | 本期不含复杂批量策略 |
| 变更记录 | 一次权限调整留下的操作证据 | 至少包含操作人、时间、前后差异 |

## 业务对象

| 对象 | 说明 | 关键状态/属性 |
|------|------|---------------|
| 项目角色 | 项目内被授权的角色 | 角色名、所属项目、当前权限集 |
| 资源权限配置 | 某个角色当前持有的权限快照 | 资源标识、权限类型、是否已授权 |
| 权限变更记录 | 一次权限调整留下的审计数据 | 操作人、操作时间、变更前、变更后 |

## 当前业务流程

1. 项目管理员通过聊天或工单提出权限变更诉求。
2. 平台管理员手工查询当前配置并理解项目背景。
3. 平台管理员进入多个配置入口执行变更。
4. 项目管理员再通过线下确认变更结果。
5. 若后续出现问题，只能继续追问平台管理员或翻日志排查。

## 目标业务流程

1. 项目管理员进入自己负责项目的权限配置中心。
2. 先查看某个项目角色当前权限状态。
3. 基于当前状态执行新增或移除授权。
4. 系统保存变更并立即反映最新权限。
5. 项目管理员或负责人可查询权限变更记录，追溯操作人、时间与差异。

## 业务规则

- 项目管理员只能查看和调整自己有权管理项目内的角色权限。
- 权限调整至少支持新增授权和移除授权两类操作。
- 每次权限调整都必须留下操作人、时间和变更前后差异。
- 权限调整保存成功后，再次查看当前权限必须反映最新状态。
- 本期需求定义业务结果，不预设必须使用角色树或批量授权等具体界面方案。

## 影响范围

| 关联功能 | 影响方式 | 处理决策 |
|---------|---------|---------|
| 现有项目管理后台 | 需要提供进入权限配置中心的承接入口 | 纳入本次需求，作为 UNIT-1 的入口约束 |

| 审计查询能力 | 权限变更记录要能被查看和追溯 | 纳入本次需求，作为 UNIT-3 的必要输出 |

## MVP 最小闭环说明

- 最小闭环包含哪些 UNIT：UNIT-1、UNIT-2、UNIT-3
- 关键路径（按依赖顺序）：UNIT-1 → UNIT-2 → UNIT-3
- 逐项不可移除论证：
  - 移除 UNIT-1 则：项目管理员无法先看清当前权限状态，后续调整容易继续靠猜测执行。
  - 移除 UNIT-2 则：只能查看，不能真正完成权限治理动作，核心痛点没有被解决。
  - 移除 UNIT-3 则：调整后仍然无法追溯谁改了什么，审计与复盘问题继续存在。
- 若 UNIT 数量 >= 3 且全部为 `MVP`，必须解释为什么它们都属于最小闭环
  - 这 3 个 UNIT 共同构成“看清现状 → 完成调整 → 事后可追溯”的单一业务闭环，缺任一环节都会让项目管理员重新依赖平台管理员。

## 全局排除项

- 不定义跨项目继承策略。
- 不定义组织架构同步规则。
- 不把竞品的角色树交互直接写成需求事实。
- 不在 `/product` 阶段提前决定批量调整的数据结构与交互细节。
