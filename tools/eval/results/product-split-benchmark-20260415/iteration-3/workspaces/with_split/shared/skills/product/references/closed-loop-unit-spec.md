# 闭环 UNIT 规格

> /product 生成的语义拆解单元格式定义。

## 模板

```markdown
# UNIT-NNN: [闭环功能标题]

**优先级**: MVP | 增强 | 扩展

## 优先级依据
[为什么属于 MVP / 增强 / 扩展]

## 背景
[业务动机]

## 需求描述
[做什么、为什么]

## 功能闭环定义
- 输入/触发: [什么输入、什么状态或什么动作触发该功能]
- 核心行为: [系统做什么]
- 可观察结果: [外部可见结果是什么]

## 验收标准

> AC 编号格式: `AC-U{UNIT序号}-{序号}`（如 AC-U1-01），由 product 定义权威编号，UNIT 内唯一递增。

### 正常场景
- AC-U1-01: [输入/操作] → [期望输出]

### 异常场景
- AC-U1-02: [输入/操作] → [期望错误/拒绝]

### 边界条件
- AC-U1-03: [边界条件] → [期望行为]

## 业务规则（如有）

## 依赖
- 依赖 UNIT: [UNIT-NNN 列表，无则"无"]
- 依赖业务对象: [业务对象或业务状态，无则"无"]
- 受影响方: [因本 UNIT 变更需同步评估的现有功能/流程，无则"无"]

## 排除项
- [本需求明确不处理的场景]
```

## 质量标准

| 检查项 | 要求 |
|--------|------|
| 标题 | 必须是功能名/能力名，不是“梳理/建模/审计/SOP”等主题名 |
| 优先级 | 必须标注 MVP / 增强 / 扩展，并写明优先级依据 |
| 背景 | 业务动机（非技术动机） |
| 需求描述 | 精确、无歧义 |
| 功能闭环定义 | 必须写清 `输入/触发 -> 核心行为 -> 可观察结果` |
| AC 编号 | 每条验收标准必须有 AC-U{UNIT序号}-{序号} 编号，UNIT 内唯一递增 |
| 正常/异常/边界 | 各 >= 1 个，含输入/操作和可观察结果 |
| 依赖 + 排除项 | 必须显式列出 |

## AC 反例（禁止出现的模糊表达）

| 模糊表达 | 问题 | 改进后 |
|---------|------|--------|
| "快速响应" | 无量化标准 | "请求发出后 500ms 内返回结果" |
| "友好的错误提示" | 主观判断 | "错误提示包含：错误原因 + 建议操作" |
| "及时通知" | 时间不确定 | "状态变更后 3 秒内推送通知" |
| "合理的权限控制" | 标准不明 | "非 admin 角色访问 /admin/* 返回 403" |
| "高可用" | 无 SLA 定义 | "月度可用率 >= 99.9%" |
| "高性能" | 无基准值 | "P99 延迟 <= 200ms，QPS >= 1000" |
| "良好的用户体验" | 无可测量维度 | "操作步骤 <= 3 步，页面加载 <= 1s" |
| "安全地处理" | 标准不明 | "输入经过转义处理，输出不包含原始用户输入" |

## 拆分规则

- 一个 UNIT 只表达一个闭环功能，不允许把多个独立功能拼在一起。
- 若一个 UNIT 内出现多个独立触发、多个独立结果、或多个下游实现入口，必须继续拆分。
- 若 3 个及以上 UNIT 全部标为 `MVP`，PRD 必须额外解释”为什么这些 UNIT 一起构成最小闭环”。

## 拆分粒度对标案例

| 场景 | 拆为 1 个 UNIT | 拆为多个 UNIT | 判断依据 |
|------|---------------|--------------|---------|
| 单实体 CRUD（用户管理） | 共享同一触发入口（管理页面）、同一数据对象 | 创建/编辑有独立复杂校验逻辑、删除有级联影响 | 触发入口和核心行为是否真正独立 |
| 列表 + 详情 + 搜索 | 列表是入口，详情和搜索是同一页面的子功能 | 搜索有独立的复杂筛选逻辑 | 是否有独立的异常/边界场景 |
| 导入 + 导出 | 同一数据对象的双向操作 | 导入有复杂校验/冲突处理、导出有格式选择/异步生成 | 核心行为复杂度是否对称 |
| 审批流程 | 提交→审批→结果 是单一闭环 | 多级审批每级有独立规则、驳回有独立回退逻辑 | 是否存在多个独立决策点 |
