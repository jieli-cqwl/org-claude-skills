结论：**阻断，不能直接把“换来源系统 + 重新设计 approval state model”塞进当前计划。**

原因很明确：
- 这不是 tech-lead 的改写权限范围。它已经触发了 **产品范围变更** 和 **架构决策变更**。
- 按 skill 硬门禁，`/tech-lead` 只能把**已确认**的产品、架构、测试输入转成实施计划，不能替代上游 owner 重新定义目标。
- 当前现场只给了口头变更，没有新的 canonical 输入，因此 **不能写 tasks.json，也不能冻结计划版本**。

**必须补齐的上游输入**
- `product-manager`：确认是否真的把来源系统替换纳入本 Phase，新的范围边界是什么。
- `designer` / 架构 owner：确认 approval state model 的新决策、状态机边界、迁移/兼容策略。
- `test-designer`：补齐对应的新测试义务和验收断言。

**当前应返回的用户决策包**
- 选项 1：只做原始冻结范围的“增加逾期提醒”，把系统替换和 state model 重构移出本轮。
- 选项 2：接受本轮范围扩大，但先回流补齐产品/架构/测试确认，再重新出计划。
- 选项 3：暂停，等上游输入冻结后再继续。

**下一步**
1. 先让用户确认：这两个变更是“新需求”还是“原需求的澄清”。
2. 若是新需求，回流 product-manager / designer / test-designer。
3. 等 canonical 输入齐了，再重新做 preflight 和 WBS 分解。
