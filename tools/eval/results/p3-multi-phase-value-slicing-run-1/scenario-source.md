# P3 Run 1 Scenario Source

- 场景 ID: `p3-multi-phase-value-slicing`
- 执行轮次: `run-1`
- 执行日期: `2026-04-12`
- 用户首句: `我们要做一个内部审批系统，本期至少要能提交申请、审批通过或驳回、查看审批记录；后面还想接企业微信通知和统计报表。`

## 本轮验证重点

- `/product` 是否会把“提交申请 + 审批处理 + 查看记录”收成一个可独立交付的价值闭环。
- 后续能力是否会被合理拆到后续 Phase，而不是为了追求对称把功能平均切组。
- `/product` 是否只定义 Phase 价值边界，而不会越界写成项目排期、任务批次或人员安排。

## 模拟共创输入摘录

- S2:
  - 当前审批依赖聊天工具和表格，记录分散，状态难追踪。
  - 首先要解决的是让申请、审批结果和历史记录都可追踪。
- S3:
  - Phase 1 完成后，员工能提交申请，审批人能通过或驳回，申请人和管理员都能查看记录。
- S5:
  - 本期不做企业微信通知、不做统计报表、不做多级会签和复杂 SLA。
- S6:
  - “提交申请 + 审批处理 + 查看记录”必须是 Phase 1 的完整闭环。
  - 企业微信通知和统计报表可以分别放到后续 Phase。
- S7:
  - 后续 Phase 只说明新增价值，不要在 `/product` 展开任务批次或人员安排。
- S9:
  - 企业微信通知的触发与失败补偿机制，以及统计报表的维度与刷新方式，都留给 design。

## 本轮想回答的问题

- `product` 的 `S6 Phase 切片` 是否真按业务价值做切分。
- 它是不是会把“交付节奏”写成“实施编排”，从而越过产品边界。
