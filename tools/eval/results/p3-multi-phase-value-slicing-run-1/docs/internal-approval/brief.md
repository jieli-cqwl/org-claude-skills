# Brief: 内部审批系统

功能名: internal-approval | 产出时间: 2026-04-12

## 业务背景与根问题

当前内部审批主要依赖聊天工具、共享表格和人工追问。申请发出后，申请人经常不知道当前到底卡在哪一步；审批人处理过什么、为什么驳回、是否已完成，也缺少统一可查询的记录。问题的核心不是“少了通知或报表”，而是最基础的审批闭环还没有在系统里被完整沉淀下来。

因此，本需求要先解决的根问题是：让审批申请、审批处理结果和审批记录形成一条可追踪的业务闭环。只有这个闭环成立后，通知和统计报表才有承接价值；如果闭环本身都不稳定，提前做通知或报表只会放大噪音。

## 目标与成功标准

| 目标 | 成功标准 | 度量方式 |
|------|---------|---------|
| 建立基础审批闭环 | 员工可提交审批申请，审批人可通过或驳回，申请人和管理员可查看记录 | 场景走查 + 闭环完成率 |
| 让审批状态可追踪 | 任一申请在处理中都能看到当前状态与最终结果，不再依赖线下追问 | 状态可见性抽查 + 用户反馈 |
| 为后续增强能力建立稳定基线 | Phase 1 完成后，通知与报表能力可在不改写核心审批语义的前提下继续扩展 | 后续 Phase 承接成本评估 |

## 关键假设

| 假设 | 不成立时的后果 | 验证方式 |
|------|--------------|---------|
| 先把“提交申请 + 审批处理 + 查看记录”做完整，就能解决当前最主要的审批痛点 | 如果用户仍然需要大量线下追问状态，说明首期闭环切得不对 | 上线后抽样观察审批状态追问量是否下降 |
| 企业微信通知不是首期刚需，而是建立在核心审批闭环上的增强能力 | 如果没有通知就无法驱动审批动作，Phase 1 价值会被削弱 | 访谈审批人和申请人，确认首期可接受的提醒方式 |
| 统计报表更适合建立在稳定记录数据之上 | 如果核心记录模型不稳定，过早做报表会导致指标口径反复返工 | Phase 1 完成后复核记录字段是否已满足报表分析需要 |

## 用户角色与核心场景

- 作为申请人，我希望提交一笔审批申请，并在之后随时看到当前状态和处理结果，这样我不用反复线下追问。
- 作为审批人，我希望查看待处理申请并执行通过或驳回，这样我能在系统内完成审批动作。
- 作为管理员或业务负责人，我希望查看审批记录，这样我能回溯某笔申请是谁提交、谁处理、何时处理、结果如何。

## 业务术语

| 术语 | 定义 | 备注 |
|------|------|------|
| 审批申请 | 由申请人提交、等待处理的业务对象 | 至少包含提交人、申请内容、当前状态 |
| 审批结果 | 审批人对申请给出的处理结论 | 至少包含通过、驳回两类结果 |
| 审批记录 | 一笔申请从提交到处理全过程留下的可查询信息 | 至少包含提交时间、处理时间、处理人、结果 |
| 企业微信通知 | 状态变化后向相关人推送提醒 | 属于后续增强能力 |
| 统计报表 | 基于审批记录生成的汇总分析视图 | 属于后续增强能力 |

## 业务对象

| 对象 | 说明 | 关键状态/属性 |
|------|------|---------------|
| 审批申请 | 审批流程的核心业务实体 | 申请编号、申请人、申请内容、当前状态 |
| 审批处理结果 | 一次审批动作形成的结果 | 审批人、处理时间、通过/驳回、驳回原因 |
| 审批记录 | 申请全过程的可追踪记录 | 申请时间、处理时间、处理结果、关联人 |

## 当前业务流程

1. 员工通过聊天工具或表格发起审批诉求。
2. 审批人在线下看到消息后自行处理。
3. 申请人通过聊天继续追问是否已审批。
4. 需要复盘时，再去找消息记录或人工整理表格。

## 目标业务流程

1. 申请人在系统内提交审批申请。
2. 审批人在系统内查看并处理申请，给出通过或驳回结果。
3. 申请人和管理员在系统中查看申请记录和当前状态。
4. 在核心流程稳定后，再通过通知和报表扩展使用效率与分析能力。

## 业务规则

- 审批申请至少有待处理、通过、驳回三种状态。
- 审批人对申请的处理结果只能是通过或驳回。
- 审批被驳回时，申请人需要能在记录中看到驳回原因。
- 本期只定义业务闭环与 Phase 价值边界，不在 `/product` 阶段安排实施批次或并行计划。
- 企业微信通知和统计报表必须建立在稳定的审批记录之上，不能反向决定 Phase 1 的业务边界。

## 影响范围

| 关联功能 | 影响方式 | 处理决策 |
|---------|---------|---------|
| 员工身份体系 | 申请人和审批人身份需要被系统识别 | 纳入本次需求，作为申请与处理的身份前提 |
| 审批记录存储能力 | 审批状态和处理结果需要被持久化并可查询 | 纳入本次需求，作为 Phase 1 的核心基线 |
| 企业微信集成能力 | 未来通知能力依赖外部消息通道 | 延后到 Phase 2，在本期只保留业务承接点 |
| 数据分析能力 | 未来报表依赖稳定记录数据 | 延后到 Phase 3，在本期只保留业务承接点 |

## MVP 最小闭环说明

- 最小闭环包含哪些 UNIT：UNIT-1、UNIT-2、UNIT-3
- 关键路径（按依赖顺序）：UNIT-1 → UNIT-2 → UNIT-3
- 逐项不可移除论证：
  - 移除 UNIT-1：审批流程没有系统内入口，闭环无法开始。
  - 移除 UNIT-2：申请无法被处理，核心审批价值不成立。
  - 移除 UNIT-3：处理结果不可追踪，申请人与管理员仍需线下追问。
- 若 UNIT 数量 >= 3 且全部为 `MVP`，必须解释为什么它们都属于最小闭环
  - 它们分别对应“发起、处理、追溯”三段最短审批链路，任何一段缺失都会让审批状态重新回到线下追问。
