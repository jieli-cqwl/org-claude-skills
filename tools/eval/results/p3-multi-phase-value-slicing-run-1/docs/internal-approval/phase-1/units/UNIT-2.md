# UNIT-2: 处理审批申请

**优先级**: MVP

## 优先级依据

如果申请不能在系统内被处理，审批系统就只是一个登记入口，核心业务价值无法成立。

## 背景

当前审批处理依赖线下消息确认，处理结果和原因缺少统一记录，申请人也难以知道结果。

## 需求描述

提供审批处理能力，让审批人能够在系统内对待处理申请执行通过或驳回，并形成明确的处理结果。

## 功能闭环定义

- 输入/触发: 审批人查看一条待处理申请并执行通过或驳回
- 核心行为: 系统保存审批结果、更新申请状态，并在驳回时保留驳回原因
- 可观察结果: 申请状态被更新为“通过”或“驳回”，且结果可被后续记录查询承接

## 验收标准

> AC 编号格式: `AC-U{UNIT序号}-{序号}`（如 AC-U1-01），由 product 定义权威编号，UNIT 内唯一递增。

### 正常场景

- AC-U2-01: 审批人对一条待处理申请执行通过 → 系统保存处理结果并将申请状态更新为“通过”

### 异常场景

- AC-U2-02: 无审批权限的用户尝试处理一条待处理申请 → 系统拒绝处理并明确提示权限不足

### 边界条件

- AC-U2-03: 审批人驳回一条申请并填写原因 → 系统保存驳回结果，申请记录中可见驳回原因

## 业务规则（如有）

- 审批结果只允许通过或驳回。
- 驳回时必须记录驳回原因。

## 依赖

- 依赖 UNIT: UNIT-1
- 依赖业务对象: 审批申请、审批结果
- 受影响方: 审批记录存储能力

## 排除项

- 不处理企业微信通知。
- 不处理多级审批分支。
