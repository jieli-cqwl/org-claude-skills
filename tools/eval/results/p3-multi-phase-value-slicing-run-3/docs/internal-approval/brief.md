# Brief: 内部审批工作台

功能名: internal-approval | 产出时间: 2026-04-12

## 业务背景与根问题

内部审批目前存在三个连续断点：申请提交入口分散、审批处理结果不透明、审批历史难查询。用户后续还想接企业微信通知和统计报表，但这些都建立在一个前提之上：审批主链路本身必须先在系统中形成稳定闭环。否则通知只会把混乱状态更快地推送出去，报表也只会放大不稳定数据。

因此，当前最合理的切片方式不是把“申请、审批、记录、通知、报表”平均分成几组，而是先保证“提交申请 → 处理审批 → 查看记录”这条主链路能独立交付业务价值，然后再把通知和报表作为后续增量能力承接进去。

## 目标与成功标准

| 目标 | 成功标准 | 度量方式 |
|------|---------|---------|
| 打通审批主链路 | 申请人能提交申请，审批人能通过或驳回，申请人和管理员都能查看记录 | 场景走查 + 闭环完成率 |
| 提升审批状态透明度 | 任一申请都能在系统中看到当前状态和最终结果 | 状态可见性抽查 |
| 让后续增强能力有稳定承接点 | 首期完成后，通知和报表都可在不改写审批语义的前提下继续扩展 | 承接成本评估 |

## 关键假设

| 假设 | 不成立时的后果 | 验证方式 |
|------|--------------|---------|
| 首期只做审批主链路，就足以解决当前最主要痛点 | 如果没有通知就无法驱动审批动作，首期切片可能不成立 | 访谈申请人和审批人，确认首期可接受的使用方式 |
| 通知能力适合作为建立在主链路之上的第二阶段增强 | 如果通知需求压倒主链路需求，说明切片顺序需要调整 | 观察 Phase 1 样本是否仍需大量线下追问 |
| 报表价值需要建立在稳定记录模型之上 | 如果记录模型不稳定，报表口径会不断返工 | Phase 1 完成后复核记录字段是否已稳定 |

## 用户角色与核心场景

- 作为申请人，我希望提交审批申请并查看当前状态，这样我不用再反复线下追问。
- 作为审批人，我希望在系统里完成审批处理，这样我能直接给出通过或驳回结果。
- 作为管理员或负责人，我希望查看审批记录，这样我能追溯一笔审批的来龙去脉。

## 当前业务流程

1. 申请人通过聊天或表格提出审批。
2. 审批人在线下处理。
3. 申请人继续追问审批进度。
4. 管理员需要人工整理审批历史。

## 目标业务流程

1. 申请人在系统中提交审批申请。
2. 审批人在系统中处理审批。
3. 申请人和管理员在系统中查看审批记录。
4. 核心流程稳定后，系统再增加通知和报表能力。

## 业务规则

- 审批状态至少包括待处理、通过、驳回。
- 驳回结果必须保留驳回原因。
- Phase 1 的业务目标是主链路闭环，不是提醒增强或数据分析。
- Phase 2 和 Phase 3 只承接新增价值，不改变首期主链路定义。
- `/product` 阶段只定义交付价值，不负责项目实施编排。

## 影响范围

| 关联功能 | 影响方式 | 处理决策 |
|---------|---------|---------|
| 员工身份体系 | 申请人和审批人身份需要被识别 | 纳入本次需求，作为主链路前提 |
| 审批记录存储能力 | 申请状态和处理结果需要被持久化并可查询 | 纳入本次需求，作为首期基线 |
| 企业微信集成能力 | 通知阶段依赖外部消息通道 | 延后到 Phase 2，仅保留承接点 |
| 数据分析能力 | 报表阶段依赖稳定记录数据 | 延后到 Phase 3，仅保留承接点 |

## MVP 最小闭环说明

- 最小闭环包含哪些 UNIT：UNIT-1、UNIT-2、UNIT-3
- 关键路径（按依赖顺序）：UNIT-1 → UNIT-2 → UNIT-3
- 逐项不可移除论证：
  - 移除 UNIT-1：审批主链路没有起点。
  - 移除 UNIT-2：审批无法在系统中被处理。
  - 移除 UNIT-3：审批结果不可追溯，用户仍需线下追问。
- 若 UNIT 数量 >= 3 且全部为 `MVP`，必须解释为什么它们都属于最小闭环
  - 因为它们对应审批主链路最短的“发起、处理、追溯”三段业务链条，缺失任一环都不能独立交付价值。

| 阶段 | 关键提问 | 用户回应 | 对产品的影响 |
