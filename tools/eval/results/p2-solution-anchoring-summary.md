# P2 Summary: 方案先行型模糊需求

日期：2026-04-12

## 场景目标

验证 `/product` 在用户首句明显带着方案暗示时，是否仍然能够：

- 先回到真实业务问题，而不是顺着“角色树 / 批量授权”直接写需求。
- 把 MVP 收敛成业务闭环，而不是把候选方案全部并入首期。
- 把应该留给 design 的问题保留在 `待设计决策`，而不是在产品阶段越权裁决。

## 三次运行的稳定信号

1. 根问题都稳定收敛到“项目级权限治理闭环缺失”

- 三次运行都没有把 `角色树` 或 `权限矩阵` 直接当成需求标题或核心业务问题。
- 根问题稳定落在：看不清当前权限、常规调整依赖平台管理员、变更后难追溯。

2. MVP 边界都稳定收敛到同一个三段式闭环

- 三次运行都把首期核心范围收敛为：
  - 查看当前权限
  - 调整权限
  - 查询变更记录
- `批量调整`、`复杂视图`、`跨项目继承`、`组织同步` 都没有被误收进首期核心范围。

3. 设计决策边界基本稳定

- 三次运行都把“如何展示权限现状”和“批量能力是否独立存在”保留在 `待设计决策`。
- 没有出现直接替 design 指定角色树、矩阵表或其他固定交互形态的情况。

## 这轮能证明什么

- 当前 `product` skill 至少在这个高价值场景里，**具备抵抗方案锚定的能力**。
- 就结果样本看，`product` 现在更像“问题发现与需求收口器”，而不是“用户说什么方案就整理什么文档”的工具。

## 这轮还不能证明什么

- 这 3 次仍属于人工 replay 产物，不等于黑盒独立 agent 的自然分布结果。
- 现已补上 `problem-discovery-grader`、`phase-slicing-quality-grader` 和 `process-lightness-grader`，可以分别观察是否把竞品方案退回到根问题、是否克制地保持单 Phase、以及整体收口是否过重；但仍不能替代黑盒独立执行证据。
- 三次运行结论一致，说明路径可复现；但还不足以证明真实线上执行里也会稳定如此。

## 当前判断

基于 P2，目前更合理的判断是：

- **还不能说 `product` 的主定义错了。**
- 更接近真实的问题是：**缺少足够强的运行证据来证明它在更多场景下也能稳定做对。**

## 下一步建议

1. 转到 `P3: multi-phase value slicing`

- 继续验证 `product` 是否只是做“价值切片”，还是已经越界成“交付节奏 owner”。

2. 在 P2/P3 之后继续补真实执行证据

- 建议优先让独立 agent 跑 3 轮保留 transcript
- 再把 transcript 里的偏移点映射回当前 3 个 grader

3. 暂时不要基于 P2 去大改 `product` 主定义

- 现阶段更稳的做法是先继续取证，再决定改定义、改内容质量准绳，还是改流程轻重。
