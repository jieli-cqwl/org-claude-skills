**推荐 UNIT 草案**
推荐 UNIT：`UNIT-1 审批配置发布闭环`

裁决理由：审批配置能力的最小闭环不是“能编辑配置”，而是“有权限的业务管理员从配置输入到发布生效，并能看到配置状态；无效配置被阻断”。这样 `/design` 能判断业务影响面，`/test-design` 能直接映射正常、异常、边界验收。

- 输入 / 触发：有权限的业务管理员为 Phase 1 指定审批场景新建或修改审批配置，并提交保存或发布。
- 核心行为：系统按已确认业务规则校验审批对象、审批人范围、必填项、生效状态和冲突配置；有效配置可保存/发布，无效配置被明确阻断。
- 可观察结果：管理员看到配置状态为“已保存 / 已发布 / 未生效 / 被阻断”，后续审批流程使用当前有效配置；无权限或非法配置不会误生效。
- Priority：`P0`
- Priority Basis：审批配置是审批流程可执行的前置条件；若配置不可发布或状态不可观察，下游审批流无法稳定设计和验收。

**Integration Context**
只包含业务上下文，不包含文件、接口、组件、数据库或架构方案。

- business_modules：审批配置管理、角色权限、审批流程触发、配置状态可见性。
- protected_behaviors：未发布配置不得影响真实审批；无权限用户不得创建、修改或发布配置；已有有效审批配置不能被无提示覆盖；Director 已锁定的 Phase 1 范围和业务规则不得被改写。
- cross_unit_dependencies：依赖已确认的审批对象范围、审批角色范围、审批流程消费有效配置的业务约定。
- business_constraints：本 UNIT 只定义 WHAT 层配置行为；配置如何存储、如何路由、如何被审批流读取交给 `/design`。

**AC 草案**
`AC-U1-01 正常：有效配置可发布并可观察`
- example_input：管理员为一个 Phase 1 审批场景选择有效审批对象、审批人范围和生效状态，并提交发布。
- expected_result：配置状态变为“已发布”，管理员能看到配置摘要；后续审批场景使用该有效配置。
- boundary_case：配置先保存为草稿时，不影响真实审批流程。
- failure_mode：发布成功但后续审批仍使用旧配置，视为不可接受失败。

`AC-U1-02 异常：无权限用户不能发布配置`
- example_input：无审批配置权限的用户尝试创建、修改或发布审批配置。
- expected_result：操作被阻断，用户看到无权限结果；现有有效配置不发生变化。
- boundary_case：用户只有查看权限时，只能查看配置状态，不能保存或发布。
- failure_mode：无权限用户造成配置变更或误发布，视为不可接受失败。

`AC-U1-03 边界：配置不完整或冲突时不得生效`
- example_input：配置缺少审批人范围，或与同一审批场景的已发布配置发生业务冲突。
- expected_result：系统阻断发布，指出需要修正的业务项；配置不得进入“已发布”状态。
- boundary_case：同一审批场景已有有效配置时，新配置必须有明确替换或不生效结果 `[?]`。
- failure_mode：不完整或冲突配置被发布并影响真实审批，视为不可接受失败。

**Verification Plan**
- functional：以有权限管理员提交完整审批配置；观察配置进入“已发布”并可被审批场景识别。对应 `AC-U1-01`。
- permission：以无权限用户尝试发布配置；观察操作被阻断且现有配置不变。对应 `AC-U1-02`。
- boundary/risk：提交缺失审批人或冲突的配置；观察发布被阻断、错误原因可见、真实审批不受影响。对应 `AC-U1-03`。
