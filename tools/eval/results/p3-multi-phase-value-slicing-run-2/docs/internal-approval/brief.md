# Brief: 内部审批平台

功能名: internal-approval | 产出时间: 2026-04-12

## 业务背景与根问题

内部审批目前依赖聊天工具、表格和人工追问，导致三件事同时失真：申请入口不统一、处理过程不透明、处理结果难追溯。用户虽然提到了企业微信通知和统计报表，但那是建立在审批主链路已经稳定之后的增强诉求，不是当前最先需要解决的根问题。

因此，这个需求的正确切入点应该是“先让审批主链路在系统里闭合”，也就是让申请提交、审批处理和审批记录查询成为一个独立可交付的首期闭环。只有这个闭环成立后，后续的通知和报表才不会变成放大噪音的附加层。

## 目标与成功标准

| 目标 | 成功标准 | 度量方式 |
|------|---------|---------|
| 让审批主链路在线闭合 | 申请人能提交申请，审批人能处理结果，申请人和管理员能查看记录 | 场景走查 + 闭环完成率 |
| 让审批状态透明 | 任一申请都能在系统中看到当前状态和最终结果 | 状态可见性抽查 |
| 为后续提醒与分析能力建立稳定基线 | 首期完成后，通知和报表可以在不重写审批语义的前提下继续扩展 | 后续承接成本评估 |

## 关键假设

| 假设 | 不成立时的后果 | 验证方式 |
|------|--------------|---------|
| 首期最重要的价值是让审批主链路闭合，而不是先做通知或报表 | 如果没有通知就无法驱动处理动作，首期切片可能过窄 | 访谈申请人和审批人，确认首期可接受的提醒方式 |
| 将通知和报表拆到后续 Phase 不会破坏首期独立价值 | 如果首期没有这些能力就无法使用，Phase 切片失真 | 在 Phase 1 样本中复核是否仍需大量线下追问 |
| 审批记录一旦稳定沉淀，就足以支撑后续通知和报表 | 如果记录模型不稳定，后续 Phase 会反复返工 | Phase 1 完成后检查记录字段是否满足后续承接需求 |

## 用户角色与核心场景

- 作为申请人，我希望在系统里发起审批并看到后续状态，这样我不用持续线下追问。
- 作为审批人，我希望在系统里处理待审批事项，这样我能直接完成通过或驳回。
- 作为管理员或负责人，我希望查看审批记录，这样我能回溯某笔审批的提交、处理与结果。

## 业务术语

| 术语 | 定义 | 备注 |
|------|------|------|
| 审批申请 | 由申请人发起、等待处理的业务对象 | 至少包含提交人、内容、当前状态 |
| 审批结果 | 审批人对申请给出的处理结论 | 至少有通过、驳回 |
| 审批记录 | 申请从提交到处理全过程的可查询信息 | 至少含时间、处理人、结果 |
| 企业微信通知 | 基于审批状态变化的主动提醒能力 | 延后到后续 Phase |
| 统计报表 | 基于审批记录的分析能力 | 延后到后续 Phase |

## 业务对象

| 对象 | 说明 | 关键状态/属性 |
|------|------|---------------|
| 审批申请 | 审批流程的核心业务实体 | 申请编号、申请人、状态 |
| 审批处理结果 | 一次审批动作形成的业务结论 | 审批人、处理时间、结果、驳回原因 |
| 审批记录 | 可查询的审批全流程信息 | 提交时间、处理时间、当前状态 |

## 当前业务流程

1. 申请人通过聊天或表格提出审批诉求。
2. 审批人在线下消息里处理。
3. 申请人继续线下追问处理结果。
4. 管理员需要人工拼接审批历史。

## 目标业务流程

1. 申请人在系统内提交审批申请。
2. 审批人在系统内处理通过或驳回。
3. 申请人和管理员在系统中查看申请记录。
4. 核心链路稳定后，再增加通知和报表能力。

## 业务规则

- 审批状态至少包含待处理、通过、驳回。
- 驳回时必须能记录并查询驳回原因。
- Phase 1 只负责审批主链路，不承担通知和报表职责。
- 后续 Phase 只在前一阶段稳定后承接新增价值，不反向定义首期边界。
- `/product` 只定义交付价值和边界，不负责实施排期。

## 影响范围

| 关联功能 | 影响方式 | 处理决策 |
|---------|---------|---------|
| 员工身份体系 | 申请人和审批人身份必须被系统识别 | 纳入本次需求，作为主链路前提 |
| 审批记录存储能力 | 状态和处理结果需要被持久化并可查询 | 纳入本次需求，作为 Phase 1 基线 |
| 企业微信集成能力 | 后续通知能力依赖外部消息通道 | 延后到 Phase 2，仅保留业务承接点 |
| 数据分析能力 | 后续报表依赖稳定记录数据 | 延后到 Phase 3，仅保留业务承接点 |

## MVP 最小闭环说明

- 最小闭环包含哪些 UNIT：UNIT-1、UNIT-2、UNIT-3
- 关键路径（按依赖顺序）：UNIT-1 → UNIT-2 → UNIT-3
- 逐项不可移除论证：
  - 移除 UNIT-1：审批闭环没有系统起点。
  - 移除 UNIT-2：申请无法被系统内处理，首期价值不成立。
  - 移除 UNIT-3：处理结果不可追溯，用户仍需线下追问。
- 若 UNIT 数量 >= 3 且全部为 `MVP`，必须解释为什么它们都属于最小闭环
  - 这三项对应审批主链路的“发起、处理、追溯”三个最短环节，缺任一项都不能算独立交付价值。

## 共创摘要

| 阶段 | 关键提问 | 用户回应 | 对产品的影响 |
|------|---------|---------|------------|
| 根问题澄清 | `这套审批系统第一步最应该先解决什么？` | 最先要解决的是申请、审批结果和历史记录可追踪 | 把首期起点锁在审批主链路 |
| 目标与成功标准对齐 | `Phase 1 做成后，用户具体能完成什么？` | 申请人能提交申请，审批人能通过或驳回，申请人和管理员都能查看记录 | 明确首期独立价值 |
| 语义/范围收口 | `核心对象和首期排除项是什么？` | 核心对象是申请、结果、记录；本期不做通知、报表、多级会签和复杂 SLA | 锁定首期边界 |
| Phase 规划 | `通知和报表该不该进入第一期？` | 都可以后续加，不要混入第一期 | 确定 Phase 1/2/3 的价值切片 |
| PRD/UNIT 与 AC | `首期闭环最少缺不了哪些能力？` | 提交申请、审批处理、查看记录缺一不可 | 形成 Phase 1 的 3 个 MVP UNIT |
| 待设计决策/完整性 | `哪些问题现在先别拍板，要留给 design？` | 通知触发/补偿和报表维度/刷新都留给 design | 保留实现空间，不越权到设计 |
| 交付确认 | `如果按这个 Phase 结构交给下游，是否已经回答了你真正的问题？` | 可以，只要别在这里展开实施排期 | 确认当前 Phase 边界和交接方式 |
