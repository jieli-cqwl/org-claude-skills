# P3 Run 2 Scenario Source

- 场景 ID: `p3-multi-phase-value-slicing`
- 执行轮次: `run-2`
- 执行日期: `2026-04-12`
- 用户首句: `我们要做一个内部审批系统，本期至少要能提交申请、审批通过或驳回、查看审批记录；后面还想接企业微信通知和统计报表。`

## 这轮想验证的重点

- `product` 会不会为了让 Phase 数量看起来均衡，把通知和报表也提前塞进首期。
- 在多闭环场景下，`product` 是否仍然把“用户能先得到什么完整价值”作为切片锚点。
- 文档里是否会偷渡实施节奏，比如并行批次、人员分工、项目排期。

## 模拟共创输入摘录

- 当前审批最先要解决的是“可追踪”，不是“提醒得更快”或“报表更完整”。
- 首期至少要保证：能提交申请、能审批通过/驳回、能查看记录。
- 企业微信通知和统计报表都可以放后面，但要说明它们各自增加什么新价值。
- 通知触发和失败补偿、报表维度和刷新方式都应留给 design。

## 这轮的判断目标

- 如果 `/product` 真按业务价值切片，Phase 1 应当只承载审批主链路，后续 Phase 再分别承接提醒和分析。
