# Brief: 项目级权限治理工作台

功能名: permission-config-center | 产出时间: 2026-04-12

## 业务背景与根问题

新项目开权限时，项目管理员往往只能先找平台管理员说明诉求，再由后者进入多个配置入口逐项修改。整个链路里最突出的三个问题是：项目管理员自己看不清当前权限状态、一次普通调整依然依赖人工代操作、变更完成后又缺少足够直接的追溯证据。

因此，本需求真正要解决的不是“缺少竞品式角色树”，而是项目级权限治理的透明度、操作效率和变更可追溯性不足。用户提到的角色树和批量授权，只能被视为候选方案，不应在产品阶段直接固化为需求事实。

## 目标与成功标准

| 目标 | 成功标准 | 度量方式 |
|------|---------|---------|
| 提升权限现状可见性 | 项目管理员进入对应项目后，可在 1 分钟内判断某角色当前拥有的资源权限 | 场景演练 + 任务完成时长 |
| 降低常规调整成本 | 一次常规的新增或移除授权可在 5 分钟内完成，不再依赖平台管理员代操作 | 操作时长抽样 + 自助完成率 |
| 建立变更追溯能力 | 每次权限变更后，都能查到操作人、时间和变更差异 | 审计抽查 + 记录完整性检查 |

## 关键假设

| 假设 | 不成立时的后果 | 验证方式 |
|------|--------------|---------|
| 当前最痛的权限治理场景发生在项目级角色，而不是更高层级的继承关系 | 如果真实高频问题在跨项目继承，本期价值会被削弱 | 回看最近权限相关工单并访谈项目管理员 |
| 先打通“看现状 + 做调整 + 查记录”就足以构成一个可交付的最小闭环 | 如果项目管理员仍然需要找平台管理员解释状态，本期闭环不成立 | 试运行后观察是否能独立完成一次常规调整 |
| 交互形态仍有多种可行方案，产品阶段不宜直接锁定角色树或矩阵形态 | 如果 design 无法在现有业务定义下展开，会回推产品补充缺失信息 | design 阶段对比至少两种交互方案并验证是否满足当前规则 |

## 用户角色与核心场景

- 作为项目管理员，我希望先看清某个项目角色当前已授权的资源权限，这样我能判断是否真的需要调整。
- 作为项目管理员，我希望直接完成项目内角色权限的新增或移除，这样我不用继续依赖平台管理员代操作。
- 作为项目负责人或审计关注方，我希望查询权限变更历史，这样我能快速追溯责任与差异。

## 业务术语

| 术语 | 定义 | 备注 |
|------|------|------|
| 项目角色 | 某个具体项目内部使用的角色 | 不等同于公司统一身份角色 |
| 资源权限 | 角色在特定资源上的访问或操作权限 | 资源既可能是功能模块，也可能是数据范围 |
| 权限调整 | 对角色现有权限执行新增或移除 | 本期不包含复杂批量策略 |
| 变更记录 | 一次权限调整留下的追溯信息 | 至少包含操作人、时间、前后差异 |

## 业务对象

| 对象 | 说明 | 关键状态/属性 |
|------|------|---------------|
| 项目角色 | 承载项目内权限的角色实体 | 角色名、所属项目、当前权限集 |
| 资源权限配置 | 某角色当前拥有的权限快照 | 资源标识、权限类型、是否生效 |
| 权限变更记录 | 权限调整后的审计证据 | 操作人、操作时间、变更前、变更后 |

## 当前业务流程

1. 项目管理员提出权限查看或调整诉求。
2. 平台管理员人工查询当前配置。
3. 平台管理员进入不同配置入口执行修改。
4. 项目管理员通过线下沟通确认结果。
5. 发生异常时，再回头追问平台管理员或翻日志。

## 目标业务流程

1. 项目管理员进入自己负责项目的权限治理工作台。
2. 先查看某个角色当前权限现状。
3. 基于现状执行新增或移除授权。
4. 系统保存变更并刷新当前状态。
5. 用户可在记录页追溯谁在什么时候做了什么改动。

## 业务规则

- 项目管理员只能查看和修改自己有权限管理的项目角色。
- 本期权限调整只覆盖新增授权和移除授权。
- 每次权限调整都必须留存操作人、时间和前后差异。
- 调整成功后，再次查看当前权限时必须看到最新状态。
- 具体交互方案在 design 阶段裁决，产品阶段只定义业务目标与约束。

## 影响范围

| 关联功能 | 影响方式 | 处理决策 |
|---------|---------|---------|
| 现有项目管理后台 | 需要提供进入权限治理工作台的承接入口 | 纳入本次需求，作为查看与调整入口前提 |
| 权限存储能力 | 权限调整结果需要落库并可重新读取 | 纳入本次需求，由 design 明确数据读写方案 |
| 审计查询能力 | 变更记录需要支持被查询和追溯 | 纳入本次需求，作为 UNIT-3 必要输出 |

## MVP 最小闭环说明

- 最小闭环包含哪些 UNIT：UNIT-1、UNIT-2、UNIT-3
- 关键路径（按依赖顺序）：UNIT-1 → UNIT-2 → UNIT-3
- 逐项不可移除论证：
  - 移除 UNIT-1：项目管理员仍然无法先判断当前权限现状，调整动作会继续盲目。
  - 移除 UNIT-2：只能看不能改，核心治理问题没有被真正解决。
  - 移除 UNIT-3：调整后仍然缺少追溯证据，审计和复盘问题继续存在。
- 若 UNIT 数量 >= 3 且全部为 `MVP`，必须解释为什么它们都属于最小闭环
  - 这三个 UNIT 连成“看清现状 → 完成调整 → 留下证据”的单一业务链路，缺少任何一环都会重新把用户推回人工协同。

## 共创摘要

| 阶段 | 关键提问 | 用户回应 | 对产品的影响 |
|------|---------|---------|------------|
| 根问题澄清 | `你提到角色树和批量授权，是因为缺少这些界面，还是因为现在权限治理太难？` | 真正难的是项目管理员看不清、改不动、改完也难追溯 | 把问题定义从“界面缺失”转回“治理链路缺口” |
| 目标与成功标准对齐 | `如果做成了，你最在意什么结果？` | 要能看清现状、快速完成常规调整、变更后可追溯 | 明确业务目标与验证指标 |
| 语义/范围收口 | `角色、资源、调整分别指什么，本期先做到哪？` | 角色是项目内角色；资源是功能模块和数据范围；本期不做跨项目继承和组织同步 | 锁定术语并压住范围 |
| Phase 规划 | `树形展示和批量操作要不要抢进第一期？` | 不要，先把一个能独立交付的治理闭环跑通 | 保持单 Phase，避免过度扩张 |
| PRD/UNIT 与 AC | `最小闭环最少缺不了哪些能力？` | 查看现状、执行调整、查询记录都缺一不可 | 得出 3 个 MVP UNIT，并要求 AC 可观察 |
| 待设计决策/完整性 | `哪些问题现在不要拍板，应该交给 design？` | 交互呈现方式和批量能力是否独立都留给 design；越权修改必须阻断 | 形成 2 个 DD，并补齐权限边界 |
| 交付确认 | `如果按这个基线交下去，是否已经回答了你真正的问题？` | 可以，前提是不把竞品交互形式写死 | 确认当前基线可交接 |
