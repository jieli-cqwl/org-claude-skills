# 执行备注

## 1. 本次如何判断 Phase 边界

本次按 `/product` 的 S6 规则，用“交付价值是否独立”而不是“功能数量是否均分”来切 Phase：

- Phase 1 定义为“提交申请 + 审批处理 + 查看记录”，因为它单独就能解决根问题“审批不可追踪”。
- 企业微信通知不影响闭环是否成立，它解决的是“主动触达”增强价值，所以放入 Phase 2。
- 统计报表建立在审批记录沉淀之后，解决的是“汇总观察”增强价值，所以放入 Phase 3。

## 2. 为什么 Phase 1 需要 3 个 MVP UNIT

Phase 1 包含 `UNIT-1 / UNIT-2 / UNIT-3`，三者共同构成最小闭环：

- 去掉 `UNIT-1`，员工无法发起申请，流程无法开始。
- 去掉 `UNIT-2`，申请不能被处理，流程停在待处理，无法形成结果。
- 去掉 `UNIT-3`，即使提交和审批存在，申请人与管理员仍无法追踪历史与当前状态，根问题没有被真正解决。

因此这 3 个 UNIT 都属于 MVP，而不是可随意删减的增强项。

## 3. 本次关键审查点

- 是否把通知、报表误塞进 Phase 1。
- 是否在 `/product` 里提前写企业微信接入方案或报表刷新方案。

- 是否把“驳回原因可见”和“无权限访问”补成直接可验证 AC。
