# Brief: 内部审批系统

功能名: internal-approval | 产出时间: 2026-04-12

## 业务背景与根问题

当前内部审批依赖聊天工具和表格流转，申请入口、审批结果与历史记录分散，导致申请人、审批人与管理员都难以判断某笔申请当前卡在哪一步。  
本期要优先解决的根问题是：让审批申请、审批结果和历史记录可追踪，形成可独立交付的审批闭环。

## 目标与成功标准

| 目标 | 成功标准 | 度量方式 |
|------|---------|---------|
| 建立可追踪的审批闭环 | 员工能提交申请，审批人能给出通过或驳回结果 | 抽取一笔申请，能完整走通“提交 -> 审批 -> 状态变更” |
| 让结果与历史可见 | 申请人与管理员都能查看审批记录，且能看到当前状态 | 抽取一笔已处理与一笔待处理申请，均能看到状态与历史信息 |
| 降低线下追问 | 申请进度不再依赖聊天追问确认 | 对同一笔申请，申请人可直接在记录中查看状态和处理结果 |

## 关键假设

| 假设 | 不成立时的后果 | 验证方式 |
|------|--------------|---------|
| 单审批闭环先跑通，就能显著改善“结果难追踪”问题 | 若闭环上线后用户仍需频繁线下追问，说明记录或状态展示不够 | 上线后抽样访谈申请人与管理员，确认是否仍需依赖线下追问 |
| 企业微信通知不是 Phase 1 的必要条件 | 若没有通知就导致审批结果长期无人关注，说明通知不应后置 | 观察 Phase 1 运行后是否因为缺少主动触达产生明显漏处理 |
| 统计报表可以建立在 Phase 1 的审批记录基础上后续补齐 | 若记录结构不足以支持后续汇总，说明 Phase 1 数据沉淀定义不完整 | 在 design 阶段审查记录字段与状态是否足以支持报表需求 |

## 用户角色与核心场景

- 作为员工，我希望提交审批申请，这样审批流程可以正式开始并留下可追踪记录。
- 作为审批人，我希望查看待处理申请并给出通过或驳回结果，这样申请可以得到明确结论。
- 作为申请人，我希望查看审批状态、处理结果和驳回原因，这样我不需要线下追问进度。
- 作为管理员，我希望查看审批记录，这样可以追踪历史处理情况。

## 业务术语

| 术语 | 定义 | 备注 |
|------|------|------|
| 审批申请 | 员工发起的一笔待审批事项 | 是审批流程的起点 |
| 审批结果 | 审批人对申请给出的状态结论 | 本期仅含待处理、通过、驳回 |
| 审批记录 | 围绕一笔申请沉淀的可查询历史信息 | 至少包含提交人、审批人、时间、处理结果、驳回原因（如有） |
| 当前状态 | 申请在当前时刻对外可见的处理状态 | 用于替代线下追问 |

## 业务对象

| 对象 | 说明 | 关键状态/属性 |
|------|------|---------------|
| 审批申请 | 员工提交的审批请求 | 提交人、提交时间、当前状态 |
| 审批结果 | 审批动作产生的状态结论 | 待处理、通过、驳回、处理时间、审批人 |
| 审批记录 | 一笔申请的历史展示载体 | 提交人、审批人、时间、处理结果、驳回原因 |

## 当前业务流程

员工通过聊天工具或表格发起审批，审批结果散落在聊天记录或人工口头反馈中，历史记录难以统一查看。申请人经常需要线下追问审批进度，管理员也无法快速回溯处理情况。

## 目标业务流程

员工提交审批申请后，系统生成一笔可追踪记录并显示当前状态为“待处理”；审批人对申请执行通过或驳回后，状态立即更新并写入审批记录；申请人与管理员可查看审批历史，若被驳回可直接看到驳回原因。

## 范围 / 本期不交付

| 类型 | 内容 |
|------|------|
| 范围 | 提交审批申请、审批人处理申请、申请人与管理员查看审批记录与当前状态 |
| 本期不交付 | 企业微信通知、统计报表、多级会签、复杂 SLA 规则、驳回后直接重新提交 |

## 业务规则

- 审批结果在本期仅允许为“待处理 / 通过 / 驳回”三种状态。
- 每笔申请提交后必须形成可查询记录，并带有当前状态。
- 审批驳回时，申请人必须能在审批记录中看到驳回原因。
- 无权限用户不能处理不属于其权限范围的审批，也不能查看无权访问的审批记录。
- Phase 1 只要求单审批闭环跑通，不扩展多级会签与复杂流转规则。

## MVP 最小闭环说明

- 最小闭环包含哪些 UNIT：`UNIT-1`、`UNIT-2`、`UNIT-3`
- 关键路径（按依赖顺序）：`UNIT-1 -> UNIT-2 -> UNIT-3`
- 逐项不可移除论证：
  - 移除 `UNIT-1` 则：员工无法发起审批申请，审批流程无法开始。
  - 移除 `UNIT-2` 则：申请不能被审批，无法得到通过或驳回结果。
  - 移除 `UNIT-3` 则：申请人与管理员无法查看状态和历史，根问题“不可追踪”仍未解决。
- 若 UNIT 数量 >= 3 且全部为 `MVP`，必须解释为什么它们都属于最小闭环：
  - `UNIT-1` 负责起点，`UNIT-2` 负责决策结果，`UNIT-3` 负责把过程与结果对外可见。三者分别对应“发起、处理、追踪”三个不可缺失环节，缺少任意一项都不能证明本期目标达成。
