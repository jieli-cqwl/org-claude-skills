# UNIT-3: 查看审批记录

**优先级**: MVP

## 优先级依据

本期根问题是“审批过程不可追踪”。如果不能查看状态和历史，即使提交与审批已发生，用户仍需线下追问，因此记录查询能力属于最小闭环不可缺部分。

## 背景

审批记录分散导致申请人和管理员难以判断当前状态、处理结果和历史轨迹，回溯成本高。

## 需求描述

申请人与管理员需要能够查看审批记录，明确看到申请的当前状态、处理结果、关键参与人和处理时间。若申请被驳回，申请人需要能看到驳回原因。

## 功能闭环定义

- 输入/触发: 申请人或管理员查看一笔审批申请的记录
- 核心行为: 系统根据权限返回该申请的当前状态和历史信息
- 可观察结果: 用户看到提交人、审批人、时间、处理结果；驳回时额外可见驳回原因

## 验收标准

> AC 编号格式: `AC-U{UNIT序号}-{序号}`（如 AC-U1-01），由 product 定义权威编号，UNIT 内唯一递增。

### 正常场景

- AC-U3-01: 申请人查看自己已提交申请的记录 -> 系统展示当前状态、提交人、审批人、处理时间和处理结果
- AC-U3-02: 管理员查看任一审批记录 -> 系统展示该记录的完整历史信息

### 异常场景

- AC-U3-03: 无权限用户查看不属于自己且无管理权限的审批记录 -> 系统拒绝访问，不暴露审批内容

### 边界条件

- AC-U3-04: 申请被驳回后，申请人查看该记录 -> 系统展示状态“驳回”且可见驳回原因

## 业务规则（如有）

- 记录查询必须以权限为前提。
- 驳回原因属于审批记录的可见组成部分。

## 依赖

- 依赖 UNIT: UNIT-1、UNIT-2
- 依赖业务对象: 审批申请、审批结果、审批记录
- 受影响方: 申请人、管理员

## 排除项

- 不支持按复杂筛选条件检索报表化数据。
- 不支持催办、评论、转交等扩展互动能力。
- 不定义驳回后再次提交入口。
