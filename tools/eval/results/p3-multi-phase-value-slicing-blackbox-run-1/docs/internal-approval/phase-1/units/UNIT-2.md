# UNIT-2: 审批人处理申请

**优先级**: MVP

## 优先级依据

只有提交没有审批结果，申请仍然停留在待处理状态，无法证明审批闭环成立，因此审批处理能力属于最小闭环的核心决策点。

## 背景

当前审批结果分散在聊天记录中，申请人无法稳定获知申请是通过还是驳回，也无法形成统一结果留痕。

## 需求描述

审批人需要能够对待处理申请执行通过或驳回操作。系统在处理后更新审批结果、当前状态和审批记录；若驳回，需记录驳回原因，供后续查看。

## 功能闭环定义

- 输入/触发: 审批人对一笔待处理申请执行“通过”或“驳回”
- 核心行为: 系统校验审批权限并写入审批结果
- 可观察结果: 申请状态更新为“通过”或“驳回”，审批记录可见审批人、处理时间、处理结果；驳回时额外可见驳回原因

## 验收标准

> AC 编号格式: `AC-U{UNIT序号}-{序号}`（如 AC-U1-01），由 product 定义权威编号，UNIT 内唯一递增。

### 正常场景

- AC-U2-01: 审批人对待处理申请执行通过 -> 该申请状态更新为“通过”，并在记录中显示审批人、处理时间和处理结果
- AC-U2-02: 审批人对待处理申请执行驳回并填写原因 -> 该申请状态更新为“驳回”，并在记录中显示驳回原因

### 异常场景

- AC-U2-03: 无权限用户尝试处理一笔审批申请 -> 系统拒绝处理，不改变原有审批状态

### 边界条件

- AC-U2-04: 审批人处理完成后立即查看该申请记录 -> 记录中的当前状态与最近一次处理结果保持一致

## 业务规则（如有）

- 本期审批结果仅允许“通过”或“驳回”。
- 驳回时需要可见的驳回原因。

## 依赖

- 依赖 UNIT: UNIT-1
- 依赖业务对象: 审批申请、审批结果、审批记录
- 受影响方: 申请人、审批人、管理员

## 排除项

- 不处理多级审批或会签。
- 不处理审批转交、撤回、催办。
- 不定义企业微信通知的发送逻辑。
