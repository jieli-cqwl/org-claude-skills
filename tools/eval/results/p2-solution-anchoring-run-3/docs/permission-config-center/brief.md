# Brief: 项目角色权限治理中心

功能名: permission-config-center | 产出时间: 2026-04-12

## 业务背景与根问题

用户最初提出“权限矩阵配置中心”和“像竞品那样的角色树、批量授权”，但进一步澄清后可以看到，这些并不是问题本身，而是对解决方案的想象。真实业务困难在于：项目管理员无法直接看清项目角色当前权限；常规权限调整依赖平台管理员代操作；改完以后缺少足够直接的追溯信息。

所以，本需求的根问题应被定义为“项目级权限治理闭环缺失”，而不是“缺少某种竞品式交互”。如果一开始就把角色树写进需求，最终很可能只是复制了界面形式，却没有真正解决治理效率和审计可追溯性问题。

## 目标与成功标准

| 目标 | 成功标准 | 度量方式 |
|------|---------|---------|
| 让项目管理员看清权限现状 | 进入目标项目后，项目管理员可在 1 分钟内判断某角色当前拥有哪些资源权限 | 可用性演练 + 完成时长 |
| 让常规调整可自助完成 | 一次普通新增或移除授权可以在 5 分钟内完成，不再需要平台管理员代执行 | 操作时长抽样 + 自助完成率 |
| 让变更结果可追溯 | 任一权限调整后，都能查到操作人、时间和前后差异 | 审计抽查 + 记录完整性 |

## 关键假设

| 假设 | 不成立时的后果 | 验证方式 |
|------|--------------|---------|
| 项目管理员是当前权限治理链路里最需要被解放的角色 | 如果真正瓶颈不在项目管理员侧，本期价值感知会降低 | 访谈项目管理员并复盘近期权限工单 |
| 一个项目级单 Phase 闭环已经足以验证产品价值 | 如果仍然需要额外平台化能力才能让用户自助完成操作，首期切片过窄 | 试运行后观察是否仍需频繁人工介入 |
| 交互方案存在多种承接可能，不需要在产品阶段直接锁定 | 如果设计空间其实很窄，design 仍可能要求产品补足交互边界 | design 阶段对比方案并验证是否满足业务规则 |

## 用户角色与核心场景

- 作为项目管理员，我希望先看清项目内某个角色的权限现状，这样我能决定接下来是否需要调整。
- 作为项目管理员，我希望在项目范围内自己完成权限新增或移除，这样我不用继续依赖平台管理员代操作。
- 作为项目负责人或审计关注方，我希望在事后追溯权限变更，这样我能知道谁改了什么。

## 业务术语

| 术语 | 定义 | 备注 |
|------|------|------|
| 项目角色 | 某个具体项目内使用的角色 | 不等于公司统一身份角色 |
| 资源权限 | 角色在某个资源上的访问或操作权 | 资源可以是模块，也可以是数据范围 |
| 权限调整 | 对现有权限执行新增或移除 | 本期不含复杂批量策略 |
| 变更记录 | 权限调整产生的追溯证据 | 至少含操作人、时间、前后差异 |

## 业务对象

| 对象 | 说明 | 关键状态/属性 |
|------|------|---------------|
| 项目角色 | 承载项目权限的角色实体 | 角色名、所属项目、当前权限集 |
| 资源权限配置 | 某角色当前的权限快照 | 资源标识、权限类型、授权状态 |
| 权限变更记录 | 调整后形成的审计记录 | 操作人、操作时间、变更前、变更后 |

## 当前业务流程

1. 项目管理员提出权限查看或调整需求。
2. 平台管理员查询当前配置并理解上下文。
3. 平台管理员进入不同入口执行修改。
4. 项目管理员再通过沟通确认是否已生效。
5. 若出现权限问题，需要继续回头追问或翻日志。

## 目标业务流程

1. 项目管理员进入项目角色权限治理中心。
2. 查看目标角色当前权限状态。
3. 基于当前状态执行新增或移除授权。
4. 系统保存变更并展示最新状态。
5. 用户在记录页查看该次变更的责任与差异。

## 业务规则

- 项目管理员只能操作自己有管理权限的项目角色。
- 本期权限调整只覆盖新增与移除两类动作。
- 每次调整都必须留存操作人、时间和前后差异。
- 调整完成后，当前权限视图必须反映最新状态。
- 界面交互形态由 design 裁决，产品阶段只固定业务目标和边界。

## 影响范围

| 关联功能 | 影响方式 | 处理决策 |
|---------|---------|---------|
| 现有项目管理后台 | 需要提供进入权限治理中心的入口 | 纳入本次需求，作为首期入口承接 |

| 审计查询能力 | 需要支持变更记录查看与追溯 | 纳入本次需求，作为记录闭环承接 |

## MVP 最小闭环说明

- 最小闭环包含哪些 UNIT：UNIT-1、UNIT-2、UNIT-3
- 关键路径（按依赖顺序）：UNIT-1 → UNIT-2 → UNIT-3
- 逐项不可移除论证：
  - 移除 UNIT-1：用户仍然无法先理解现状，后续操作缺乏依据。
  - 移除 UNIT-2：只能看不能改，首期无法形成治理动作闭环。
  - 移除 UNIT-3：调整后缺少可追溯证据，审计问题继续存在。
- 若 UNIT 数量 >= 3 且全部为 `MVP`，必须解释为什么它们都属于最小闭环
  - 这三者对应权限治理的最短业务链路：认知当前状态、完成变更、追溯变更结果，缺一不可。

- 不定义组织架构同步规则。
- 不把竞品交互形式等同于需求事实。
- 不在 `/product` 阶段提前决定批量能力的数据结构或界面形态。

## 已排查并排除的潜在问题

> 方法：Pre-mortem — 假设项目 6 个月后失败了，回溯最可能的失败原因。

| 编号 | 潜在问题 | 排查过程 | 排除证据 |
|------|---------|---------|---------|
| EP-001 | 把竞品角色树直接写进 PRD，导致团队围绕界面而不是真实治理问题工作 | 在 S2 主动追问“这是不是必须方案”，用户确认不是 | 根问题回到“看不清、改不动、难追溯” |
| EP-002 | 因为用户主动提到批量授权，就让首期范围过早膨胀 | 在 S6 追问是否必须同一期，用户确认批量能力可延后 | `范围 / 本期不交付` 已延后批量能力 |
| EP-003 | 在产品阶段提前替 design 决定交互方案，压缩后续设计空间 | 在 S9 主动收敛开放问题并保留 DD | `待设计决策` 明确保留了展示方式与批量能力问题 |

## 共创摘要

| 阶段 | 关键提问 | 用户回应 | 对产品的影响 |
|------|---------|---------|------------|
| 根问题澄清 | `你提到权限矩阵和角色树，是因为界面缺失，还是因为现在权限治理本身太难？` | 真正困难是项目管理员现在既看不清，也改不动，改完还难追溯 | 把需求定义从“界面方案”拉回“治理闭环” |
| 目标与成功标准对齐 | `这件事做成后，你最关心的结果是什么？` | 快速看清现状、5 分钟内完成常规调整、变更后能追溯 | 建立成功标准和衡量口径 |
| 语义/范围收口 | `角色、资源、调整这些词在这里分别指什么？哪些先不做？` | 角色是项目内角色；资源含模块和数据范围；本期不做跨项目继承和组织同步 | 锁定术语并约束本期边界 |
| Phase 规划 | `是否必须把批量授权和复杂视图一起放进首期？` | 不需要，先做项目级治理最小闭环 | 确认单 Phase 即可成立 |
| PRD/UNIT 与 AC | `如果只保留最必要能力，哪些一定不能少？` | 查看现状、执行调整、查询记录三者缺一不可 | 形成 3 个核心 UNIT，并约束 AC 必须可观察 |
| 待设计决策/完整性 | `哪些问题现在不宜拍板，应该留给 design？` | 展示方式和批量能力都留给 design；越权调整必须阻断 | 保留设计空间，并补齐权限边界 |
| 交付确认 | `如果下游现在接手，这份基线是否已经回答了你真正的问题？` | 可以，关键是别把竞品界面形式提前写死 | 确认当前 brief/phase/unit 可交接 |
