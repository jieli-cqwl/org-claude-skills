### 关键问题（FAIL 项详述）

#### DR-001：CORS 配置完全缺失

问题：PRD CON-004 已把 CORS 标为 Owner=`design`、状态=KNOWN 的前置约束，但设计文档接口设计、质量属性和关键决策表都没有给出任何 CORS 落地方案。对于使用 httpOnly cookie 的前后端分离架构，这不是实现细节，而是运行条件本身。

影响：FastAPI 默认会拒绝来自 React dev server 的跨域请求，前端在开发环境下无法调用后端 API；同时因为认证依赖 cookie，若后续临时补配置却遗漏 `allow_credentials=True` 或错误使用 `*`，仍然会导致认证链路不可用。这个遗漏会直接阻断设计的可实施性。

修复要求：在设计中补齐 CORS 决策，明确允许的 origin、`allow_credentials=True`、允许的方法和请求头，并说明该配置如何覆盖开发态和生产态的跨域访问。

#### DR-002：SQLite WAL 并发写入声明错误

问题：设计文档把“启用 WAL 模式”直接推导为“支持并发写入、无需额外写锁处理”，这一技术结论不成立。WAL 的价值是提升读写并发，但 SQLite 仍保持单 writer 约束，多并发写场景下依然会出现 `SQLITE_BUSY`。

影响：当前 Phase 1 以读操作为主，短期风险有限；但这条错误结论会被后续 Phase 2 的写路径设计继承，导致开发者对并发写冲突、重试策略和数据库边界做出错误判断，积累隐性技术债。

修复要求：把质量属性中的 WAL 描述改成准确表述，明确“读写可并行、写写仍串行”，并补充当前场景为什么可以接受该约束，以及未来引入写操作时需要重新评估哪些条件。

### 改进建议（WARN 项）

#### DR-003：明确 `/api/reports` 的认证边界（WARN）
安全模型（UNIT-3）的有效性依赖于后端 API 也执行认证校验，而非仅依赖前端路由守卫。前端守卫是 UX 防线，后端校验是安全防线，两者不可互相替代。建议在接口设计中明确声明每个 endpoint 的认证要求，并为 /api/reports 添加后端 JWT 校验依赖项或显式说明其为公开端点的决策理由。

#### DR-004：统一种子数据数量与验证步骤（WARN）
当前矛盾（10条 vs 12条）会导致验证步骤第2条在执行时必然失败，降低了设计文档作为实施参考的可信度。建议将种子数据调整为12条，使分页验证（第1页10条、第2页2条）具有实际可验证性，同时与 PRD 范围章节"种子数据（3用户+10周报）"的描述一致性问题也需要明确（PRD 写10条，设计写12条——需统一）。

#### DR-005：补充 ADR 方案对比（WARN）
当前决策表形式上完整，实质上是结论表而非决策记录。对于 DD-001（JWT 存储）已有一定理由（"内网 CSRF 风险低于 XSS"），但 DD-002/DD-004 的理由过于简短。建议至少对 DD-004（路由守卫）补充：为何选择 loader 方案而非全局 auth context 或 PrivateRoute wrapper，因为这直接影响前端组件结构，是实施阶段的关键分叉点。

**贯穿审查透镜评估：Essential vs Accidental 复杂度**

当前设计整体复杂度与问题规模匹配——两表 schema、RESTful API、JWT cookie 均属 Essential 复杂度，无明显 Accidental 过设计。主要问题不在于"引入了不必要的复杂度"，而在于两处遗漏（CORS、认证边界）和一处技术错误（WAL 声明），这些会在实施阶段造成不必要的返工成本。
