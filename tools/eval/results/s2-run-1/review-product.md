### 关键问题（FAIL 项详述）

#### P-001: CORS 配置缺失（FAIL）

**业务意图偏离程度：严重**

PRD CON-004 是一项明确的前置约束，要求设计阶段产出 CORS 配置方案。该约束的根因是：前后端分离架构中，React dev server（通常运行在 localhost:5173 或 localhost:3000）与 FastAPI 后端（通常运行在 localhost:8000）端口不同，浏览器的同源策略会阻止所有跨域 API 请求。

设计文档定义了三个 API endpoint（POST /api/auth/login、GET /api/reports、GET /api/auth/me），但完全没有说明如何配置 FastAPI 的 CORSMiddleware。这意味着：

- 用户体验影响：在没有 CORS 配置的情况下，前端登录请求会被浏览器直接拦截（CORS 错误），用户将看到登录失败，整个平台无法使用。这直接破坏了 PRD 的核心目标——"提供集中的周报阅读入口"。
- 需求覆盖完整性：PRD 的5个待设计决策（DD-001 至 DD-005）在设计中均有回应，但 PRD 前置约束 CON-004 作为设计必须承接的需求被完全遗漏。CON-004 标注 Owner 为"design"，意味着这是设计文档的交付责任。

**验证方式**：全文搜索设计文档，"CORS"、"跨域"、"CORSMiddleware"、"allow_origins"等关键词均不存在。

#### P-002: 验证步骤与种子数据数量矛盾（FAIL）

**业务意图偏离程度：严重**

PRD 范围章节明确规定种子数据为"3用户+10周报"，设计文档种子数据章节也写明"10条 status=published 的周报"。然而验证步骤第2条声称有"12条已发布周报"并需要验证"分2页展示（第2页2条）"。

这一矛盾的业务影响是：

- 错误的验收基准：开发者按照10条种子数据实现，QA 按照验证步骤检查，将看到与预期不符的结果（只有1页而非2页），可能误判功能存在 bug。
- 分页功能无法验证：10条数据无法触发分页（每页10条，10条=1页），这意味着 PRD R4（"分页每页10条"）和 UNIT-2 的核心功能（"支持分页浏览"）在当前种子数据下根本无法通过验证步骤被验证。

**验证方式**：设计文档种子数据节："10条 status=published 的周报"；验证步骤节第2条："12条已发布周报分2页"。两处数字直接矛盾。

### 改进建议（WARN 项）

#### P-003: SQLite WAL 并发写入描述不准确（WARN）

当前 Phase 1 范围内没有写操作（登录为读操作，首页为查询操作），因此该错误描述不影响当前业务意图的实现。但应修正记录，原因如下：

- 后续 Phase 将引入周报发布/编辑/删除的写操作（CRUD）；届时如设计团队引用该错误描述作为并发安全依据，可能导致实际并发写入问题被低估。
- 准确描述：WAL 模式下，并发读性能得到改善（读写可并行执行），但写入操作依然串行化（同一时间只有一个 writer）。对于 10-50 人的内网团队场景，写冲突概率低，风险在可接受范围，但应如实陈述，而非声称"支持并发写入"。
