# P3 Summary: 多闭环功能的 Phase 切片

日期：2026-04-12

## 场景目标

验证 `/product` 在一个天然包含“核心闭环 + 后续增强”的需求里，是否能够：

- 先把首期收敛成可独立交付的业务闭环；
- 把通知、报表等增强能力拆到后续 Phase；
- 在文档里只保留 Phase 的价值边界，而不越界成实施排期或项目编排。

## 三次运行的稳定信号

1. Phase 1 都稳定收敛到同一个审批主链路闭环

- 三次运行都把首期边界稳定收敛为：
  - 提交审批申请
  - 审批通过或驳回
  - 查看审批记录
- 没有出现把通知或报表提前塞进首期的情况。

2. 通知与报表都稳定被拆成后续独立价值 Phase

- 企业微信通知稳定收敛为“状态提醒增强”。
- 统计报表稳定收敛为“基于稳定审批记录的分析能力”。
- 两者都没有被简单并成“第二期剩余功能包”，而是各自具备独立价值说明。

3. `/product` 没有明显越界成实施编排

- 三次运行都只写了 `Phase` 的入口条件、出口条件、交付价值与 UNIT 映射。
- 没有写任务批次、里程碑拆分、并行策略、人员安排等项目管理信息。

## 这轮能证明什么

- 当前 `product` skill 在这个场景里，**具备按业务价值切片 Phase 的能力**。
- 至少就当前样本看，它没有明显把 `Phase` 用成项目计划批次，而是把它当成了“价值交付边界”。

## 这轮还不能证明什么

- 这 3 次仍然是人工 replay，不等于黑盒独立运行的自然分布。
- 现已补上 `problem-discovery-grader`、`phase-slicing-quality-grader` 和 `process-lightness-grader`，能覆盖“问题发现”“Phase 切片质量”“整体收口轻重”；但三次结果仍来自人工 replay，不等于黑盒自然分布。
- 三次运行都切成了 3 个 Phase，说明路径稳定；但还不足以证明这是所有类似需求的最佳切法。

## 当前判断

基于 P2 + P3，现阶段更合理的判断是：

- **`product` 的主定义暂时不需要大改。**
- 当前更像是：它在“问题发现”和“价值切片”上都已经能做出相对合理的结果，但我们还缺更强、更自动化的证据来证明“稳定性”和“质量上限”。

## 下一步建议

1. 补黑盒独立执行证据

- 建议优先让独立 agent 运行 P1/P2/P3，并保留完整 transcript
- 再看人工 replay 与黑盒执行是否存在系统偏差

2. 再跑 `P1: clear-single-phase`

- 用来验证流程是否在简单需求上显得过重。
- 如果 P1 暴露出明显的“机械追问 / 过度 Phase 化”，那我们就能更有把握地说问题主要在“流程负担”，而不是定义错误。

3. 暂时不要基于 P2/P3 直接大改 skill 定义

- 现在更值得做的是把评测体系补强，让后续任何“改定义、改质量规则、改流程轻重”的动作都能被证据验证。
