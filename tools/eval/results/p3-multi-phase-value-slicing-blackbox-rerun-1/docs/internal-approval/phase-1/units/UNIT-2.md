# UNIT-2: 审批通过或驳回

**优先级**: MVP

## 优先级依据
没有审批结果，申请就无法形成闭环，因此这是核心价值的第二步。

## 背景
审批人目前通过聊天或表格人工处理，容易遗漏结果和原因，申请人也无法判断当前进展。

## 需求描述
审批人处理待处理申请时，需要能给出通过或驳回结果；当结果落定后，系统要把审批人、时间、结果和驳回原因完整写入记录。

## 功能闭环定义
- 输入/触发: 审批人打开一条待处理申请并执行通过或驳回操作
- 核心行为: 系统校验审批权限，记录审批动作，更新申请状态为通过或驳回，驳回时保存原因
- 可观察结果: 申请状态发生变化，记录里能看到审批人、处理时间、结果和原因

## 验收标准

> AC 编号格式: `AC-U2-{序号}`

### 正常场景
- AC-U2-01: 审批人对待处理申请点击通过 → 系统记录审批结果，状态变为通过，并显示审批人和处理时间

### 异常场景
- AC-U2-02: 无权限用户尝试处理审批 → 系统拒绝操作并不生成审批结果

### 边界条件
- AC-U2-03: 审批人选择驳回并填写原因 → 系统保存驳回原因，记录中可直接查看

## 业务规则（如有）
- 驳回原因必须保留在审批记录中。
- 本期不做多级会签，也不做驳回后的自动重新提交。

## 依赖
- 依赖 UNIT: UNIT-1
- 依赖业务对象: 审批申请、审批结果
- 受影响方: UNIT-3

## 排除项
- 企业微信通知
- 统计报表
- 多级会签
