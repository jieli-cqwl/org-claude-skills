# Brief: 内部审批系统

功能名: 内部审批系统 | 产出时间: 2026-04-12

## 业务背景与根问题
当前审批通过聊天工具和表格分散处理，申请记录、审批结论和历史追踪不在同一条链路里，导致申请人经常不知道进度卡在哪一步，管理者也难以快速追溯是谁在什么时间做了什么决定。

本期要先解决的根问题是：把审批申请、审批处理结果和历史记录收口到一条可追踪、可查询、可验证的闭环里，先消除“结果不可追踪、状态不可见、历史不完整”这三个核心痛点。

## 目标与成功标准

| 目标 | 成功标准 | 度量方式 |
|------|---------|---------|
| Phase 1 打通核心审批闭环 | 员工能提交申请，审批人能通过或驳回，申请人和管理员能查看记录，当前状态一眼可见 | 用一笔测试申请完成提交、审批和查询全链路，记录中能看到提交人、审批人、时间、结果、原因 |
| Phase 2 补齐审批通知价值 | 审批状态变化后，相关人能在企业微信中收到通知 | 以一笔真实审批结果触发通知，验证收件人可收到与记录一致的消息 |
| Phase 3 补齐统计价值 | 管理者可以查看审批统计报表，获得汇总视图 | 在测试数据下打开报表，能看到可读的统计结果 |

## 关键假设

| 假设 | 不成立时的后果 | 验证方式 |
|------|--------------|---------|
| 本期只需要单级审批闭环，不做多级会签 | 如果存在多级审批需求，Phase 1 的 UNIT 切片要重新拆分 | 通过 S5 范围收口确认 |
| 审批记录必须包含提交人、审批人、时间、结果和驳回原因 | 如果缺少这些字段，无法完成可追踪目标 | 以记录查询结果核对字段是否齐全 |
| 通知和统计都属于后续增强，不应挤占核心闭环 | 如果混入 Phase 1，最小闭环会变宽，交付价值会变散 | 通过 S6 Phase 决策确认 |

## 用户角色与核心场景
- 作为员工，我希望提交审批申请，这样我不用靠聊天反复确认。
- 作为审批人，我希望直接处理待处理申请，这样我可以给出通过或驳回结果。
- 作为申请人或管理员，我希望查看审批记录，这样我能追踪状态和历史。
- 作为管理者，我希望后续查看通知和统计，这样我可以在后续阶段获得更强的管理视角。

## 业务术语

| 术语 | 定义 | 备注 |
|------|------|------|
| 审批申请 | 一次需要审批的业务请求，包含提交人、内容、创建时间和当前状态 | 本期统一按单级审批处理 |
| 审批结果 | 审批人对申请做出的处理结论，至少包含待处理、通过、驳回 | 驳回时必须有原因 |
| 审批记录 | 能回看整笔申请过程的历史信息，至少包含提交人、审批人、时间、结果和原因 | 申请人和管理员可查看 |
| 待处理 | 申请已提交但尚未被审批人处理的状态 | 对外展示的主状态之一 |
| 通过 | 审批结论为同意，申请进入已通过状态 | 作为最终结论展示 |
| 驳回 | 审批结论为不同意，申请进入已驳回状态 | 记录里必须显示原因 |

## 业务对象

| 对象 | 说明 | 关键状态/属性 |
|------|------|---------------|
| 审批申请 | 申请的主业务对象 | 申请ID、提交人、申请内容、创建时间、当前状态 |
| 审批结果 | 一次审批处理动作产生的结论 | 审批人、处理时间、结果、驳回原因 |
| 审批记录 | 申请与审批动作的可追踪历史 | 提交人、审批人、时间、结果、原因、当前状态 |
| 通知事件 | 后续阶段用于企业微信推送的事件对象 | 触发时机、接收人、消息内容、发送状态 |
| 统计报表 | 后续阶段用于管理查看汇总结果的对象 | 统计条件、汇总值、刷新时间 |

## 当前业务流程
申请人在聊天工具里发起申请，审批人再通过聊天或表格接收信息并手工处理，最后由人工回看记录或继续追问。由于申请、处理和历史不在同一处，状态很容易断链。

## 目标业务流程
申请人提交审批申请后，系统生成唯一申请记录并进入待处理状态；审批人直接处理该申请并给出通过或驳回结果；申请人和管理员都能在记录里看到完整历史和当前状态；后续阶段再叠加企业微信通知与统计报表。

## 范围 / 本期不交付

| 类型 | 内容 |
|------|------|
| 范围 | 提交申请、审批通过或驳回、查看审批记录、显示当前状态、显示驳回原因 |
| 本期不交付 | 企业微信通知、统计报表、多级会签、复杂 SLA 规则、驳回后自动重新提交 |

## 业务规则
- 审批流程只按单级审批处理，不引入多级会签。
- 驳回时必须填写驳回原因，并在记录里可见。
- 申请人和管理员可以查看审批记录；审批人只能处理自己有权限的待处理申请。
- 当前状态必须始终可见，不能只靠人工追问确认结果。
- 驳回后是否允许重新提交不在本期范围内。

## MVP 最小闭环说明
- 最小闭环包含哪些 UNIT：UNIT-1、UNIT-2、UNIT-3
- 关键路径（按依赖顺序）：UNIT-1 → UNIT-2 → UNIT-3
- 逐项不可移除论证：
  - 移除 UNIT-1 则：员工无法提交审批申请，后续审批和记录查看没有业务起点
  - 移除 UNIT-2 则：申请无法产生通过/驳回结论，审批闭环无法完成
  - 移除 UNIT-3 则：申请人和管理员无法追踪历史，根问题仍然存在
- 这 3 个 UNIT 都属于最小闭环，因为它们分别覆盖“发起、处理、追踪”三个不可拆的业务动作，缺任一项都会让审批链路断开
