# Brief: 权限配置中心

功能名: permission-config-center | 产出时间: 2026-04-12

## 业务背景与根问题

新项目开权限时，通常要找平台管理员手工改多处配置，处理慢、容易出错，而且改完后很难快速说清某个角色到底拥有哪些资源权限。当前要解决的不是“做一个像竞品那样的角色树”，而是让项目管理员能在一个地方看清、调整并追溯项目内角色权限。

## 目标与成功标准

| 目标 | 成功标准 | 度量方式 |
|------|---------|---------|
| 看清当前权限 | 项目管理员打开某个项目的角色权限页后，能直接看到该角色当前拥有的资源权限和数据范围 | 页面可直接展示当前有效权限，无需翻查配置表 |
| 完成常见调整 | 项目管理员能在一个地方完成新增、移除和查看当前状态等常见权限调整 | 一次常规调整从进入页面到保存完成不超过 5 分钟 |
| 留下可追溯记录 | 每次权限调整都能查到操作人、时间、变更前后差异 | 任一次变更均可在记录中定位到完整审计信息 |
| 限制越权修改 | 项目管理员只能修改自己有权管理的项目 | 非授权项目的查看或修改请求被拒绝 |

## 关键假设

| 假设 | 不成立时的后果 | 验证方式 |
|------|--------------|---------|
| 现有系统已经有项目、角色和资源的基础数据 | 无法直接进入查看/调整闭环，需要先补底层数据治理 | design 阶段确认数据来源和主数据归属 |
| 项目管理员是本期最主要的使用者 | 如果实际使用者不是项目管理员，页面和权限边界会偏掉 | 与业务方确认角色边界和操作范围 |
| 变更留痕可复用现有审计能力或新建审计存储 | 如果没有审计承载，追溯目标无法达成 | design 阶段确认记录落点与查询方式 |

## 用户角色与核心场景

- 作为项目管理员，我希望看清并调整自己项目内某个角色的权限，这样我能更快完成常见授权调整并在事后追溯改动。

## 业务术语

| 术语 | 定义 | 备注 |
|------|------|------|
| 项目内角色 | 仅在单个项目范围内生效的角色，不是公司统一身份角色 | 本期只讨论项目内权限 |
| 资源 | 系统内可授权的功能模块和数据范围 | 具体资源粒度由 design 继续收口 |
| 权限调整 | 对角色执行新增、移除或查看当前状态的动作 | 不包含复杂审批流 |
| 变更记录 | 记录一次权限调整的操作人、时间和变更前后差异 | 供追溯与审计查询 |

## 业务对象

| 对象 | 说明 | 关键状态/属性 |
|------|------|---------------|
| 项目角色 | 项目内可被授权的角色实体 | 角色名、所属项目、当前权限集合 |
| 资源项 | 可被授权的功能或数据范围 | 资源标识、资源类型、可见性 |
| 权限关系 | 角色与资源之间的授权关系 | 生效状态、创建时间、更新时间 |
| 变更记录 | 一次权限调整的审计结果 | 操作人、时间、变更前后差异、目标角色 |

## 当前业务流程

项目管理员提出授权需求后，通常要找平台管理员代为修改多处配置。修改完成后，项目管理员只能通过口头确认或零散日志去反推当前状态，既慢又难追溯。

## 目标业务流程

项目管理员进入权限配置中心后，先查看某角色当前权限，再直接完成新增或移除。系统在保存时自动记录变更人、时间和差异，之后还能按项目、角色或时间查询历史记录。

## 范围 / 本期不交付

| 类型 | 内容 |
|------|------|
| 范围 | 本期只做项目级角色的查看、调整和变更记录查询，支持项目管理员完成常见授权闭环。 |
| 本期不交付 | 不做跨项目继承规则，不做组织架构同步，不做复杂审批流，不把竞品里的角色树和批量授权当作必做能力。 |

## 业务规则

- 项目管理员只能调整自己有权管理的项目，不能越权修改其他项目的角色权限。
- 角色是项目内角色，不是公司统一身份角色。
- 权限调整至少包含新增、移除和查看当前状态三种动作。
- 每次权限调整都必须留下操作人、时间、变更前后差异。
- 本期不引入复杂审批流，变更以直接生效为原则。

## 影响范围

| 关联功能 | 影响方式 | 处理决策 |
|---------|---------|---------|
| 现有项目角色查看页/接口 | 需要展示当前有效权限和空状态，不能只展示静态配置 | 纳入本次需求 |
| 现有权限修改流程 | 需要支持新增、移除、保存和失败回退 | 纳入本次需求 |
| 现有审计/日志查询能力 | 需要承接权限调整的操作人、时间和差异信息 | 纳入本次需求 |
| 项目级权限校验链路 | 需要保证项目管理员只能操作自己有权限的项目 | 纳入本次需求 |

## MVP 最小闭环说明

- 最小闭环包含哪些 UNIT：UNIT-1、UNIT-2、UNIT-3
- 关键路径（按依赖顺序）：UNIT-1 → UNIT-2 → UNIT-3
- 逐项不可移除论证：
  - 移除 UNIT-1 则：用户无法先确认当前角色权限，后续调整没有明确起点。
  - 移除 UNIT-2 则：用户无法完成实际授权调整，根问题仍然存在。
  - 移除 UNIT-3 则：调整后无法追溯谁改了什么，审计目标无法达成。
- 这三个 UNIT 都属于最小闭环，因为它们分别覆盖“看清现状、做出调整、保留追溯”三个必须环节，缺一项都不能独立解决问题。

## 非功能需求

| 编号 | 类别 | 验收标准（输入/操作 → 可观察结果） |
|------|------|-----------------------------------|
| GAC-001 | 安全 | 非授权项目管理员访问查看、调整或查询接口 → 返回 403，且不泄露该项目角色或资源细节 |
| GAC-002 | 审计 | 任一次权限新增/移除保存成功 → 100% 生成可查询的变更记录，记录包含操作人、时间和变更前后差异 |
| GAC-003 | 性能 | 常规项目规模下（角色 <= 100、资源 <= 500）查看或查询请求 → P95 <= 2s；保存一次权限调整 → P95 <= 3s |

## 全局排除项

- 不做跨项目继承规则。
- 不做组织架构同步。
- 不做复杂审批流。
- 不把角色树和批量授权当作本期必做范围。
