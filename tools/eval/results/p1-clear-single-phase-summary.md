# P1 Summary: 清晰需求轻量收口

日期：2026-04-12

## 场景目标

验证 `/product` 在一个边界清晰、天然单闭环的小需求里，是否能够：

- 保持单 `Phase`、单 `UNIT` 的轻量收口；
- 不因为模板存在而机械拆出多个无业务价值的结构层级；
- 把搜索、筛选、编辑、导出、认证改造等明确排除项稳定留在范围外。

## 三次运行的稳定信号

1. 交付结构稳定保持最小形态

- 三次运行都只产出了 `Phase 1`。
- 三次运行都只保留了 `UNIT-1` 作为唯一闭环。
- 三次运行都只留下了 1 个待设计决策：分页采用前端本地分页还是后端分页。

2. 范围边界稳定没有外溢

- 搜索、按作者筛选、编辑、导出都稳定留在非本期范围。
- 认证能力稳定被当作现有依赖复用，没有被拉进当前需求。
- 没有出现“因为需求太简单，所以顺手再加一点”的范围膨胀。

3. 简单需求也能形成可交接基线

- 三次运行都明确了核心业务规则：仅展示 `published` 状态、默认按发布时间倒序、每页 10 条、支持上一页/下一页。
- 三次运行都覆盖了正常浏览、未登录访问、分页边界和空列表提示。
- 从文档结果看，当前 `/product` 在这个场景里没有因为“轻量”而牺牲交接清晰度。

## 这轮能证明什么

- 当前 `product` skill 在这个场景里，**可以稳定保持克制**。
- 至少在清晰小需求上，现有合同并没有表现出“机械走重流程”的明显问题。

## 这轮还不能证明什么

- 这 3 次仍然是手动 replay，不等于黑盒独立运行的自然分布。
- 现已补上 `problem-discovery-grader`、`phase-slicing-quality-grader` 和 `process-lightness-grader`，能分别观察“有没有把需求退回到真实问题”“Phase 粒度是否克制”“整体收口是否过重”；但仍不能直接替代黑盒独立执行证据。
- 因为三个样本的业务边界高度一致，所以它们更能证明“结果可复现”，还不能单独证明“所有简单需求都会同样轻量”。

## 当前判断

基于 `P1 + P2 + P3`，现阶段更稳的判断是：

- **还没有证据支持“`product` 当前主定义明显错误”这个结论。**
- 已证实的问题仍主要是：流程叙事一致性问题，例如之前的序号乱序。
- 更值得继续补强的，是黑盒独立执行证据与真实 transcript 样本。

## 下一步建议

1. 继续补真实执行证据

- 让 agent 独立跑至少 3 轮 `/product`，保留完整 transcript
- 把 transcript 失败标签和当前 3 个 grader 对齐

2. 再考虑是否调整 `product` 主定义

- 如果后续 grader 证明它稳定表现为“资深产品经理式共创”，再改主定义会更稳。
- 如果后续 grader 发现真正问题是“共创负担偏重”，那就优先改流程和质量准绳，而不是先改角色表述。
