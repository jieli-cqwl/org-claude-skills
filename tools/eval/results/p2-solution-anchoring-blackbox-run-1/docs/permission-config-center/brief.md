# Brief: 权限矩阵配置中心

功能名: permission-config-center | 产出时间: 2026-04-12

## 业务背景与根问题
当前新项目开通或调整项目级角色权限时，依赖平台管理员手工修改多处配置，导致常规授权调整效率低、容易配错；调整完成后，项目侧也难以直接看清某个角色实际拥有的资源权限，且事后难以追溯是谁在什么时间改了什么。

## 目标与成功标准

| 目标 | 成功标准 | 度量方式 |
|------|---------|---------|
| 让项目管理员看清当前角色权限 | 项目管理员进入权限配置中心后，可查看某个项目内角色当前拥有的功能模块和数据范围权限 | 在权限查看场景中，角色权限列表一次加载后可直接展示当前授权状态 |
| 提升常规权限调整效率 | 一次常规授权调整可由项目管理员在 5 分钟内独立完成 | 记录从进入调整入口到提交成功的操作时长 |
| 提升权限变更可追溯性 | 每次权限调整后，可查询到操作人、时间、变更前后差异 | 在变更记录查询中可返回完整的审计条目 |

## 关键假设

| 假设 | 不成立时的后果 | 验证方式 |
|------|--------------|---------|
| 项目管理员具备独立维护项目内角色权限的业务责任 | 若实际仍需平台管理员代操作，则配置中心无法降低人工成本 | 上线后统计常规授权调整中项目管理员自主完成占比 |
| 把查看、调整、审计统一到同一入口能显著降低误配和沟通成本 | 若用户仍需跨入口核对权限，效率收益会降低 | 访谈项目管理员并观察调整流程是否仍依赖外部对照表 |
| 本期不做批量能力仍能覆盖高频场景 | 若高频场景主要依赖批量调整，则 MVP 价值不足 | 上线后统计单次调整的平均变更项数与重复操作占比 |

## 用户角色与核心场景
- 作为项目管理员，我希望在一个地方查看某个项目内角色的当前资源权限，这样我能先确认现状再决定是否调整。
- 作为项目管理员，我希望在权限配置中心完成常见的新增和移除权限操作，这样我不必再找平台管理员手工改配置。
- 作为项目管理员或审计相关角色，我希望查询某次权限调整的操作人、时间和变更差异，这样我能追溯问题来源。

## 业务术语

| 术语 | 定义 | 备注 |
|------|------|------|
| 项目内角色 | 仅在单个项目范围内生效的角色定义 | 不等同于公司统一身份角色 |
| 资源 | 系统内可被授权的功能模块和数据范围 | 本期不细分到更复杂对象层级 |
| 权限调整 | 对项目内角色已有权限执行新增、移除或查看当前状态 | 本期不含复杂审批流 |
| 变更记录 | 权限调整后产生的审计条目 | 至少包含操作人、时间、变更前后差异 |

## 业务对象

| 对象 | 说明 | 关键状态/属性 |
|------|------|---------------|
| 项目 | 权限配置发生的业务边界 | 项目标识、可管理人范围 |
| 项目内角色 | 某项目下可被配置权限的角色 | 角色名称、所属项目、当前权限集合 |
| 资源权限项 | 角色可拥有的功能模块或数据范围授权 | 资源标识、授权状态 |
| 权限变更记录 | 一次调整的审计信息 | 操作人、操作时间、变更前、变更后、所属项目、目标角色 |

## 当前业务流程
1. 项目侧提出新增项目或权限调整需求。
2. 平台管理员手工查找并修改多个权限配置点。
3. 调整结果通过口头或零散记录反馈给项目侧。
4. 当出现权限异常时，需要再次人工核对当前角色权限和历史修改记录，成本高且容易缺证据。

## 目标业务流程
1. 项目管理员进入权限配置中心，选择自己有权管理的项目和项目内角色。
2. 系统展示该角色当前拥有的功能模块和数据范围权限。
3. 项目管理员在授权范围内执行新增或移除权限。
4. 系统保存调整结果并生成可查询的变更记录。
5. 项目管理员或审计相关角色可查询变更记录以追溯责任和差异。

## 范围 / 本期不交付

| 类型 | 内容 |
|------|------|
| 范围 | 项目级角色权限查看、项目级角色权限调整、权限变更记录留存与查询 |
| 本期不交付 | 跨项目继承规则、组织架构同步、复杂审批流、竞品角色树交互复刻、批量授权能力 |

## 业务规则
- 项目管理员只能查看和调整自己有权管理的项目，不能越权修改其他项目的角色权限。
- 权限调整至少支持新增权限、移除权限和查看当前状态。
- 每次权限调整必须生成变更记录，至少包含操作人、时间、变更前后差异。
- 变更记录的展示形态不是产品阶段结论，可由 design 决定是列表、时间线或其他交互。

## 影响范围

| 关联功能 | 影响方式 | 处理决策 |
|---------|---------|---------|
| 项目管理员权限配置流程 | 原先依赖平台管理员手工处理，现改为部分自助化 | 纳入本次需求 |
| 权限审计与问题追溯流程 | 原先缺少统一查询入口，需要引入标准变更记录查询能力 | 纳入本次需求 |
| 跨项目继承规则 | 与本期项目级权限独立，但容易被误认为同范围 | 排除（本期不做跨项目继承） |
| 组织架构同步 | 属于外部集成能力，复杂度高且非根问题最小闭环所必需 | 排除（另立需求） |

## MVP 最小闭环说明
- 最小闭环包含哪些 UNIT：UNIT-1、UNIT-2、UNIT-3
- 关键路径（按依赖顺序）：UNIT-1 → UNIT-2 → UNIT-3
- 逐项不可移除论证：
  - 移除 UNIT-1 则：项目管理员无法先看清角色当前权限，仍需依赖人工核对，误配风险不降。
  - 移除 UNIT-2 则：用户只能看不能改，无法解决“调整效率低”的核心问题。
  - 移除 UNIT-3 则：权限调整后无法追溯操作人与差异，根问题中的“事后难审计”无法解决。
- 这 3 个 UNIT 都属于 MVP，因为它们共同构成“看清现状 → 完成调整 → 查询追溯”的最小业务闭环，缺少任一环都无法完整验证本次需求是否真正解决根问题。

## 非功能需求

| 编号 | 类别 | 验收标准（输入/操作 → 可观察结果） |
|------|------|-----------------------------------|
| GAC-001 | 性能 | 项目管理员进入某角色的权限查看页并请求当前权限数据 → 10 秒内返回完整权限状态，且页面不出现“数据未知”占位 |
| GAC-002 | 安全 | 无该项目管理权限的用户尝试提交权限调整 → 系统拒绝操作并返回明确拒绝结果，目标角色权限保持原状态不变 |
| GAC-003 | 可观测性 | 任意一次权限调整提交成功 → 系统可查询到对应的变更记录，记录包含操作人、时间、变更前、变更后 |

## 全局排除项
- 不定义角色树、矩阵表、时间线等具体交互方案。
- 不定义批量授权的交互和执行逻辑。
- 不覆盖组织架构、公司统一身份角色与跨项目继承。

## 待设计决策

| 编号 | 开放问题 | 为什么必须由 design 决定 | 已知业务约束 | 需要 design 产出的结果 |
|------|---------|---------------------------|-------------|------------------------|
| DD-001 | 权限矩阵的交互形态采用何种呈现方式 | 这是交互复杂度和信息密度的裁决，不应在产品阶段写死为角色树或其他方案 | 必须让项目管理员直接看清某角色当前拥有的功能模块和数据范围权限 | 给出可支撑“看清当前权限”的信息架构和核心交互方案 |
| DD-002 | 批量调整是否需要作为独立能力进入后续阶段 | 需要结合高频场景、复杂度和收益判断，不应因竞品存在而默认纳入 | 本期 MVP 不依赖批量能力即可完成单次常规授权调整 | 给出是否独立立项、纳入哪一阶段、影响哪些流程的判断 |
| DD-003 | 变更记录查询的展示与保留策略如何设计 | 架构审查提示查询性能和记录保留周期仍需设计承接 | 必须支持查询操作人、时间、变更前后差异；展示形式不限 | 给出记录检索方式、默认展示结构、保留周期与性能约束建议 |

## 共创摘要

| 阶段 | 关键提问 | 用户回应 | 对产品的影响 |
|------|---------|---------|------------|
| 根问题澄清 | 角色树和批量授权是不是必须，真正想解决的问题是什么 | 不是必须；真正想解决的是配置效率低、容易配错、事后难审计 | 从“竞品方案”回到“效率/准确性/审计性”根问题 |
| 目标与成功标准对齐 | 做到什么算成功 | 能看清当前权限；常规调整 5 分钟内完成；变更后可追溯是谁改的 | 成功标准落到可观察结果和时长指标 |
| 语义/范围收口 | 角色、资源、权限调整分别指什么；本期范围和审计要求是什么 | 角色是项目内角色；资源是功能模块和数据范围；本期只做项目级查看和调整，记录操作人/时间/前后差异 | 明确术语边界、范围与审计规则 |
| Phase 规划 | 是否需要多 Phase | 核心闭环清晰即可先做一个 Phase，树形和批量操作不是同一期必须 | 采用单 Phase，竞品交互不进入本期 |
| PRD/UNIT 与 AC | 最少要覆盖哪些功能，AC 应如何表达 | 必须覆盖查看当前权限、执行一次权限调整、留存可查询变更记录；不要只写界面形式 | 固化 3 个 MVP UNIT，并用可观察结果写 AC |
| 待设计决策/完整性 | 哪些开放问题留给 design；还有什么边界要补 | 交互形态、批量调整留给 design；项目管理员不能越权修改其他项目 | 补充待设计决策和越权边界 |
| 交付确认 | 是否确认当前需求基线并输出 | 确认，输出最终文件 | 允许形成最终 brief/prd/unit 基线 |
