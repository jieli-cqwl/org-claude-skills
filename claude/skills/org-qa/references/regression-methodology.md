# 回归测试方法论

> 供 /qa 验证-C 阶段引用。确保新功能没有破坏已有功能。

## 1. 变更影响分析

### 步骤

| 步骤 | 方法 |
|------|------|
| 1. 识别变更文件 | `git diff --name-only` 获取本次修改的文件列表 |
| 2. 识别对外影响面 | 基于接口/命令/配置/数据表变更识别受影响功能（黑盒） |
| 3. 评估影响面 | 受影响功能/页面/API 即为影响范围 |
| 4. 标记风险 | 被多方调用的共享模块 = 高风险 |

### 影响范围分级

| 级别 | 标准 | 回归策略 |
|------|------|---------|
| 高 | 修改了共享模块/核心库/数据库 Schema | 全量测试 + 手动核心路径 |
| 中 | 修改了业务模块，受影响功能 >= 3 | 全量测试 |
| 低 | 修改了独立模块，受影响功能 <= 2 | 相关测试 + 冒烟测试 |

## 2. 关联功能识别

| 关联类型 | 识别方法 |
|---------|---------|
| 行为依赖 | 与变更接口/命令共享业务流程的功能 |
| 数据依赖 | 读写了变更涉及的数据库表 |
| 配置依赖 | 使用了变更的配置项 |
| 接口依赖 | 调用了变更的 API 端点 |

## 3. 冒烟测试清单

> 快速验证核心功能未被破坏。

| 检查项 | 验证方式 |
|--------|---------|
| 应用启动 | 服务启动 + 健康检查通过 |
| 核心 CRUD | 创建/读取/更新/删除核心实体 |
| 认证流程 | 登录/登出/Token 刷新 |
| 关键业务流 | 系统最核心的 1-3 个业务操作 |
| 数据完整性 | 核心表的基本查询返回正确 |

## 4. 全量测试套件执行

| 步骤 | 要求 |
|------|------|
| 1. 执行命令 | 使用项目标准测试命令 |
| 2. 结果记录 | 通过数/失败数/跳过数 |
| 3. 失败分析 | 每个失败测试：是新引入还是既有问题 |
| 4. 覆盖评估 | 变更文件的测试覆盖是否充分 |

### 结果分析

| 失败类型 | 处理 |
|---------|------|
| 新引入的失败 | FAIL — 回归 bug |
| 既有的失败（变更前就失败） | 不计入回归 |
| Flaky 测试（间歇失败） | 标记但不计入回归 |

## 5. 数据完整性检查

| 检查项 | 验证方式 |
|--------|---------|
| CRUD 后一致性 | 创建后能查到、修改后反映、删除后查不到 |
| 关联数据 | 父实体操作后子实体状态正确 |
| 约束完整性 | 唯一约束、外键约束、非空约束仍有效 |
