# 审查指引 — tech-lead 阶段特异维度

> 本文件定义 tech-lead 阶段（实施计划）的 2 个特异审查维度。
> 与 `review-guide-base.md` 拼接后传给 Codex，基础维度（一致性/完整性/DECEPTION）在 base 文件中定义，此处不重复。

---

## 特异维度 1: 任务可执行性

- 审查焦点: Task 粒度是否足够直接实施，开发者拿到后能否立即开始
- 判定标准:
  - PASS: 每个 Task 有明确的 AC、文件范围、验收命令，开发者无需猜测
  - WARN: 大部分 Task 可执行，但少量 Task 粒度偏大（可能需要拆分）或 AC 不够具体
  - FAIL: Task 粒度过大（需多日且无法拆分）或缺少 AC/文件范围/验收方法

### 审查检查项

1. 每个 Task 是否有 AC 列表（不是空的）？
2. 每个 Task 是否有明确的文件范围（哪些文件要创建/修改/删除）？
3. AC 是否可验证（有验证命令或明确的完成判定方法）？
4. Task 粒度是否合理（一个 Task 能在合理时间内完成）？
5. 是否有 complexity 标注（S/M/L）且与实际复杂度一致？

## 特异维度 2: 依赖合理性

- 审查焦点: 任务排序、前置依赖、并行可能性
- 判定标准:
  - PASS: 依赖关系清晰，执行顺序合理，无循环依赖，并行策略已考虑
  - WARN: 依赖关系基本正确但部分可优化（如可并行的 Task 被安排为串行）
  - FAIL: 存在循环依赖，或关键前置依赖未声明（如 Task-B 依赖 Task-A 的产出但未标注）

### 审查检查项

1. 每个 Task 的 `depends_on` 是否准确（不多不少）？
2. 是否存在循环依赖（A→B→C→A）？
3. 无依赖关系的 Task 是否可并行执行？
4. 并行安全检查是否已确认（shared_files 无冲突）？
5. 关键路径是否识别（哪些 Task 阻塞后续所有 Task）？
