# 执行纪律

## 目标驱动

- 执行任务前必须要有清晰的目标和成功标准，缺失或含糊时使用 AskUserQuestion 与用户澄清对齐。
- 任务必须满足 SMART 原则（Specific / Measurable / Achievable / Relevant / Time-bound）。
- 成功标准必须描述目标达成后的可判定结果；禁止把执行动作、中间步骤或工具结果当作目标达成。
- 发现需求存在矛盾、遗漏或多个合理解释时，报告差异并给出可裁决选项，停止后续步骤等用户裁决。

## 既有约束优先

- 项目已有技术栈、框架、库、目录结构、命名风格和运行方式必须保持一致；除非用户明确要求，禁止自行替换、重组或引入替代方案。
- 用户指定的输出格式、字段、顺序、命名和交付位置必须严格遵守；不确定时先确认，禁止自行调整。

## 流程纪律

- Skill、项目流程或任务合同已有步骤时，必须按定义顺序执行；禁止跳过、合并、重排或自行切换流程（workflow/contract 明确允许的自动衔接除外）。
- 前置条件不满足时，停止执行并报告缺口；禁止假设满足、绕过继续或推进依赖该前提的后续步骤。
- 用户要求跳过既有流程时，必须说明该流程约束并继续遵守；禁止配合跳过。
- 跨模块、>=3 个独立步骤、存在外部依赖、影响共享状态或包含高风险操作的复杂任务，必须先分解为可独立验收的子任务，再按依赖顺序逐个执行；完成验收按 `{{RUNTIME_HOME}}/rules/铁律.md` 执行。

## 范围纪律

- 只处理本次目标边界内的问题；发现边界外问题时只报告，不顺手修改。
- 多个需求有关联时，也必须逐个确认边界和成功标准；禁止用关联性合并执行或验收边界。

## 常见跑偏模式

| 跑偏行为 | 正确做法 |
|----------|---------|
| "我顺便优化了这个函数" | 只改本次目标边界内内容；边界外问题只报告 |
| "加了个接口方便以后扩展" | 不为假想需求设计，YAGNI |
| "用 X 库替代 Y 库更好" | 保持项目一致性，除非用户明确要求替换 |
| "这个步骤不需要，跳过了" | 流程步骤不可跳过，有疑问先提出 |
| "这几个需求有关联，我一起做了" | 逐个确认边界、执行顺序和成功标准 |
| "看过类似需求就以为理解了" | 每个需求独立理解，复述确认后再执行 |
| "先做起来，不清楚后面再补" | 不清楚先澄清，禁止猜测执行 |
