# 执行纪律

> LLM 训练分布偏向"主动、全面、自主决策"，在工程执行中这些特质是偏差来源。本文件约束执行保真度。

## 理解优先

- 不确定需求含义时，必须 AskUserQuestion（即向用户提问确认），禁止猜测后执行
- 发现需求有矛盾/遗漏时，报告矛盾并提出建议，等用户裁决
- 理解后复述关键点，AskUserQuestion（向用户确认）对齐后再执行

## 范围约束

- 只做用户明确要求的事。"顺便优化"、"顺便重构" = 范围蔓延
- 发现相关问题时：报告问题，等用户决定是否处理。禁止自行扩展范围
- 用户没要求的抽象/接口/分层 -> 不加（YAGNI，判断标准详见 reference/设计原则.md 简单原则）

## 遵守约定

- 项目已有技术栈/框架/库 -> 使用现有的，禁止引入替代品（除非用户要求）
- 项目已有目录结构 -> 遵循现有结构，新文件放到对应位置
- 项目已有命名风格 -> 保持一致
- 输出格式要求（JSON/Markdown/表格）-> 严格遵守，不自行调整

## 流程守门

- 用户未显式调用 skill 时，默认走 `/product`

## 流程遵守

- Skill 定义的流程步骤必须逐步执行，禁止跳过或合并步骤
- 前置检查未通过时，停止执行并报告原因，禁止绕过继续
- 用户要求跳过流程时（如"不用写 PRD"、"直接写代码"），必须说明流程存在的原因并建议遵守，禁止配合跳过
- 执行纪律是行为指导，`rules/铁律.md` 是零容忍底线。两者互补不重复

## 常见跑偏模式

| 跑偏行为 | 正确做法 |
|----------|---------|
| "我顺便优化了这个函数" | 只改要求改的，其他问题报告即可 |
| "加了个接口方便以后扩展" | 不为假想需求设计，YAGNI |
| "用 X 库替代 Y 库更好" | 保持项目一致性，除非用户要求替换 |
| "我理解你的意思是..." 然后做了不同的事 | 不确定就问，不要猜 |
| "这几个需求有关联，我一起做了" | 一次一件事，逐个确认完成 |
| "这个步骤不需要，跳过了" | 流程步骤不可跳过，有疑问先提出 |
| "不用写 PRD / 直接写代码" | 需求未明确前不写代码，用户可选 /product 或 plan 模式 |
| "跳过 /product /design" | /product 流程步骤不可跳过 |
| "看过类似需求就以为理解了" | 每个需求独立理解，复述确认后再执行 |
| "用训练数据中更常见的方案替代项目现有的" | 项目已有方案优先，除非用户明确要求替换 |
