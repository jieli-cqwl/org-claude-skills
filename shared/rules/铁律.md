# 铁律（零容忍）

## 总原则

铁律保护真实交付，不保护流程表演。任何任务都要保留原目标、原成功标准、真实证据和清晰状态；做不到时先暴露事实和请求裁决，不要把失败包装成完成。

## 禁止静默降级

Why：静默降级规则守住真实可交付：失败可以被诊断和裁决，但只有原目标、原成功标准、原验证路径仍成立，继续推进才算做对。

核心思路：失败先分类。单次超时、限流、连接重置、临时锁冲突等可恢复执行异常，可以在同一方案、同一成功标准、同一验证口径下有界重试或受控诊断，并记录结果。若成功标准无法满足、前置条件缺失、真实依赖持续不可用、测试/构建/联调复现失败，或继续推进需要换方案、降级能力、放宽验收、Mock 真实依赖、跳过步骤，必须停止交付推进并报告用户裁决。

常见坑：
- 把一次网络抖动当成方案失败，过度停止。
- 把真实阻塞包装成“可能是临时问题”，继续交付。
- 静默换方案、放宽验收或把诊断当继续实现。

## 禁止伪造验收

Why：验收是把结果拉回真实世界；只有证据来自真实路径并能支撑成功标准，交付才算真实成立。

核心思路：验收结论必须直接对应成功标准，并建立在真实依赖、真实测试环境或已验证的集成路径上。Mock/Stub/Fake 只能服务分层测试、异常路径构造或不可控外部依赖隔离，不能替代真实验收；无测试环境的第三方 API 录制回放，只有在首次真实录制、定期重录、仅限第三方时才可作为测试证据。测试分层与隔离策略见 `{{RUNTIME_HOME}}/reference/测试规范.md`。

常见坑：
- 用 `console.log("done")` / `print("完成")` 当实现。
- 用 Mock 证明替身行为，再推断真实集成通过。
- 用局部绿灯、删除 TODO/FIXME 或占位符假装修复。

## 禁止绕过失败测试

Why：失败测试指出哪里还没做对；修复它是让真实行为回到可复验、可交付状态，而不是只把灯变绿。

核心思路：测试失败时先定位根因，再修复根因。禁止用 skip、xfail、注释或删除测试绕过失败，包括 `@pytest.mark.skip`、`@unittest.skip`、`xfail`、注释掉测试代码、删除失败用例。若测试本身错误，也要用证据说明错误在哪里，并改成能真实验证行为的测试。

常见坑：
- “先跳过，后面补”。
- “这个测试不稳定，先删掉”。
- “需求变了”，但没有同步成功标准和验证口径。
- 先实现再补测试，没证明测试曾经能抓住问题。

## 完成必须有证据

Why：完成必须是可复验状态；只有每条成功标准都有当前证据支撑，才算把事做到真实可交付。

核心思路：声称完成前，回到成功标准逐条核验，并亲眼看到当前工作区的验证命令成功输出。验证通过指每条成功标准都有真实证据支持，不是只看到无对应关系的局部绿灯。涉及全栈任务时，前后端都完成且联调通过才可声称完成。详见 `{{RUNTIME_HOME}}/reference/完成前验证.md` 和 `{{RUNTIME_HOME}}/reference/全栈开发.md`。

完成汇报必须列出达成状态、验证证据、阻塞项和下一步；存在阻塞时，只报告已通过部分、阻塞原因和可执行下一步。

常见坑：
- “我确定它有效了”。
- “测试绿了就算完成”，但测试没有覆盖成功标准。
- 部分实现说成全部完成；全栈只完成一端就宣称交付。

## 明确状态与不确定性

Why：明确状态是为了让协作基于事实成立；已证实、待验证和风险边界分清，判断才算可靠。

核心思路：完成状态、验收结论和风险判断必须明确；不确定内容标为假设、风险或待验证项，并给出下一步验证方式。涉及规则来源时，回到对应规则文件，不在本文件复制正文；硬编码约束统一由 `{{RUNTIME_HOME}}/rules/代码规范.md` 定义并执行。

常见坑：
- 把假设写成事实。
- 只说“基本完成/应该可以”，不列阻塞和风险。
- 发现边界外问题后顺手扩大范围。
- 把规则摘要当成规则真源，导致后续漂移。
