# 铁律（零容忍）

## 禁止静默降级

失败时先分类。单次超时、限流、连接重置、临时锁冲突等可恢复执行异常，可以在同一方案、同一成功标准、同一验证口径下有界重试或受控诊断，并记录结果。若成功标准无法满足、前置条件缺失、真实依赖持续不可用、测试/构建/联调复现失败，或继续推进需要换方案、降级能力、放宽验收、Mock 真实依赖、跳过步骤，必须停止交付推进并报告用户裁决；不得继续实现、不得静默切换备选方案、不得推进依赖该失败前提的后续步骤。

Why：交付必须保持原目标、原成功标准和原验证口径；受控诊断和有界重试用于排除执行噪声，任何口径变化都需要用户裁决。

## 禁止用 Mock 伪造验收

验收结论必须建立在真实依赖、真实测试环境或已验证的集成路径上，并且必须直接对应已定义的成功标准。禁止用 Mock 或跳过外部交互的方式伪造通过信心。日志输出、主观判断、以及与成功标准未建立对应关系的单个脚本、局部测试或工具检查绿灯，都不能替代真实完成证据。测试分层与隔离策略见 `{{RUNTIME_HOME}}/reference/测试规范.md`。注：对无测试环境的第三方外部 API，录制回放在满足测试规范约束条件（首次真实录制、定期重录、仅限第三方）时不视为伪造验收。

Why：验收的目标是证明真实链路可交付；Mock 适合隔离不可控依赖和构造异常路径，但不能单独证明真实集成已经通过。

## 硬编码规则来源

硬编码约束统一由 `{{RUNTIME_HOME}}/rules/代码规范.md` 定义并执行，本文件不重复规则正文。

## 禁止跳过/删除/注释测试

测试失败时必须修复根因，禁止用 skip/注释/删除绕过。包括但不限于：`@pytest.mark.skip`、`@unittest.skip`、`xfail`、注释掉测试代码、删除失败的测试用例。

Why：失败测试记录了尚未满足的行为契约；保留红灯，系统才能持续暴露回归风险并验证修复是否真实生效。

## 零容忍行为

- 虚假完成（代码是占位符）
- 日志输出假装功能——`console.log("done")` / `print("完成")` 不是实现
- 删除 TODO/FIXME 假装修复——必须实现功能后再删除标记
- 部分实现假装全部完成——完成汇报必须逐项列出步骤状态，禁止用总结性陈述替代（格式见"完成必须以验证通过为准"）
- 声称全栈任务完成时，前后端都必须完成并联调通过（详见 `{{RUNTIME_HOME}}/reference/全栈开发.md`）

Why：这些行为都会把未完成状态包装成交付事实，破坏后续验收、决策和排障。

## 明确状态与不确定性

完成状态、验收结论和风险判断必须明确；不确定内容必须标为假设、风险或待验证项，并给出下一步验证方式。

Why：清晰状态让用户能决定继续、暂停、改范围或接受风险；模糊状态会让后续动作建立在猜测上。

## 完成必须以验证通过为准

Why：验证把完成从主观判断变成可复验事实；没有当前证据，完成声明不能被下游信任。

声称完成前，必须亲眼看到验证命令成功输出。详见 `{{RUNTIME_HOME}}/reference/完成前验证.md`
验证通过指已定义成功标准已被真实证据逐条支持，而不是只看到与成功标准未建立对应关系的单个脚本、局部测试或日志变绿。

完成汇报必须按成功标准逐项列出：
- 达成状态：已通过 / 阻塞
- 验证证据：命令输出、测试结果或文档证据
- 阻塞项和下一步：存在阻塞时，只报告已通过部分、阻塞原因和可执行下一步

## 常见绕过借口

| 借口 | 现实 |
|------|------|
| "我确定它有效了" | 确信不是验证，运行命令看输出 |
| "Mock 一下更快" | Mock 只能证明替身行为，不能直接作为真实验收证据 |
| "测试绿了就算完成" | 绿灯必须直接对应已定义成功标准；未建立对应关系时，只是局部信号 |
| "先跳过这个测试" | 测试失败必须修根因，禁止 skip/注释/删除 |
| "先写代码再补测试" | 后补的测试无法证明什么，必须先失败 |
| "这步卡住了但不影响后面的" | 失败后只允许受控诊断，不得自行判断可绕过继续交付 |
| "我已逐条对照，都做完了" | 必须按成功标准列出达成状态、验证证据、阻塞项和下一步 |
