# 交付验收底线

## 失败处理

- 失败后保持原目标、原成功标准和原验证口径；只允许重跑同一口径验证，或做不改变口径的诊断。
- 成功标准、前置条件、真实依赖、测试、构建或联调无法满足时，停止交付并请求用户裁决。
- 继续推进若需要换方案、降级能力、放宽验收、用 Mock 替代真实依赖或跳过步骤，停止交付并请求用户裁决。
- 裁决前只报告已验证事实、阻塞原因和可裁决选项；只允许无副作用采证。

## 验收证据

- 验收结论必须来自真实依赖、真实测试环境或已验证集成路径，并直接对应成功标准；详见 `{{RUNTIME_HOME}}/reference/测试规范.md`。
- Mock/Stub/Fake 只用于隔离不可控依赖或构造异常路径，不能单独证明真实集成通过。
- 无测试环境的第三方 API 可按测试规范用录制回放辅助验证；录制回放不能替代首次真实链路证据。
- 日志、主观判断、单个脚本、局部测试或工具绿灯，只有直接覆盖成功标准时才可作为完成证据。

## 验证失败

- 验证失败时，先定位失败对应的成功标准、AC 或既有行为。
- 目标内失败必须修根因；目标外失败只报告。
- 禁止用 skip、xfail、注释、删除测试或放宽断言绕过失败。

## 真实实现

- 完成状态必须来自真实实现；不得把占位符、只打日志、删除标记但未实现、部分实现或单端完成声明为完成。
- 全栈任务完成必须前后端实现闭合，并通过同一真实用户路径联调；详见 `{{RUNTIME_HOME}}/reference/全栈开发.md`。

## 完成声明

- 声称完成前，必须在当前工作区取得可复验证据；有验证命令时，必须重新执行并看到本次成功输出；详见 `{{RUNTIME_HOME}}/reference/完成前验证.md`。
- 结果不确定时，必须标为假设、风险或待验证，不得写成完成。
- 完成汇报必须逐条对应成功标准：状态（已通过 / 阻塞）、验证证据、阻塞项和下一步。
