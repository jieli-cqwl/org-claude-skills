# 代码规范

> 本文件是代码规范唯一规则源：定义 How（代码怎么写）的可执行约束。
> 规范定义：可判定、可检查、可门禁的代码约束（MUST/SHOULD）。
> 适用范围：非测试业务代码。行为与流程底线见 `rules/铁律.md`。

## MUST（必须遵守）

### 复杂度约束

- 函数：参数 <= 5 个、嵌套 <= 3 层、循环复杂度（CC）<= 10
- 文件：单文件 <= 400 行（超出必须拆分；生成文件/配置映射文件可声明豁免）

### 注释规范

- 文件注释：必须说明文件职责与边界
- 函数注释：必须说明业务意图、关键参数语义或失败条件
- 字段注释：必须说明业务含义，至少包含单位/范围/可空性中的一项
- 注释必须解释意图与约束，禁止空话和代码复述

### 错误处理规范

- 禁止空 catch 块、禁止裸 except
- 错误提示必须用户可理解，禁止暴露堆栈/技术细节
- 所有外部调用（API/DB/文件 IO）必须有超时和错误处理

### 硬编码规范

- 禁止硬编码密钥/Token/密码/Secret，必须从配置或环境变量读取
- 禁止通过字符串拼接、默认值回填等方式绕过密钥配置管理
- 环境特定配置（地址/端口/凭据）必须外置配置化，禁止写死在业务代码

### 死代码规范

- 未使用的导入/变量/函数/字段必须删除
- 注释掉的大段旧实现、不可达分支、废弃占位逻辑禁止长期保留
- 确需保留兼容代码时，必须标注保留原因与失效条件

### 门禁落地原则

- 规则可由自动化门禁按改动范围或全量范围执行
- 具体变量、默认值、缺工具策略与 rollout 节奏见 `reference/代码质量.md` 和实际检查脚本
- 门禁实现必须如实反映本文件规则，禁止以配置名义放宽 MUST 语义

### 复用治理规范

- 新增实现前，必须先收集复用证据，判断是否已有语义一致的候选实现
- 最终选择不复用而新建实现时，必须在代码注释、设计文档或 PR 描述中说明原因
- 复用原则见 `reference/代码复用.md`；证据收集与举证流程见 `reference/复用证据与新建门禁.md`

## SHOULD（强烈建议）

- 函数长度 <= 50 行（可读性优先；超过建议拆分）
- 认知复杂度（CogC）<= 15（分阶段治理，先观测再强制）
- 优先单一职责：一个函数只做一件清晰的事
- 优先早返回：减少深层嵌套，降低理解成本
- 命名即文档：名称应体现业务语义，避免缩写和上下文依赖
- 保持同类问题同类写法，减少项目内风格漂移

## 边界与引用

- 性能与资源效率（批量/N+1/单例/缓存策略）：见 `reference/性能效率.md`
- 复用原则：见 `reference/代码复用.md`
- 新增实现的证据与举证要求：见 `reference/复用证据与新建门禁.md`
- 语言实现建议与检查命令：见 `reference/代码质量.md`（指南，不是规则源）

## 原则映射（软件工程学 + 实践）

| 规范条款 | 工程学依据 | 实践映射 |
|----------|------------|------------------|
| 参数/嵌套/CC 上限 + 函数长度建议 | 控制认知复杂度，降低缺陷率与维护成本 | 主流工程实践优先复杂度度量，行数用于可读性提醒 |
| 强制有效注释（文件/函数/字段） | 让“意图与边界”可传递，减少隐式知识 | Google 风格强调注释解释 why，而非复述 what |
| 禁止空 catch/裸 except | 失败显式化，提升可观测性与可调试性 | 生产工程实践要求错误可追踪、可定位 |
| 禁止硬编码敏感信息与环境配置 | 降低泄露风险与环境耦合，提升可部署性 | 工程实践要求配置外置与密钥管理 |
| 死代码必须清理 | 减少认知噪音与维护成本，降低错误路径误触发概率 | 持续重构实践要求保持代码库可读与可演化 |
| 外部调用必须超时+错误处理 | 故障隔离与韧性设计，避免级联失败 | 大规模服务治理强调超时、重试、降级边界 |
| 注释/复杂度门禁可切换 | 渐进治理，先降低落地阻力再收敛到强约束 | 工程团队普遍采用可配置质量门禁推进规范落地 |
