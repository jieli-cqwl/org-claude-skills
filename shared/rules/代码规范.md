# 代码规范

测试与变更验证见 `{{RUNTIME_HOME}}/reference/测试规范.md`；SHOULD 级质量指南见 `{{RUNTIME_HOME}}/reference/代码质量.md`。

## 总原则

代码规范保护可理解、可验证、可维护、可门禁的工程质量。这里的 MUST 是硬约束真源；reference 只补充细则，不得覆盖或放宽本文件结论。

## MUST（必须遵守）

### 复杂度约束

Why：复杂度约束定义代码做到什么程度才算可维护；读得懂、测得动、能演进，才算把实现做对。

核心思路：函数循环复杂度（CC）<= 10；参数 > 5 个或嵌套 > 3 层时，必须优先简化边界或说明保留理由，禁止为满足数字阈值机械拆出错误抽象。文件 <= 400 行；超出时必须按职责拆分或迁入可豁免载体。仅生成文件、配置映射文件、稳定数据表可豁免，且必须在文件头或门禁配置记录来源、豁免原因和校验方式。

常见坑：
- 为了降低数字，把一个概念拆成多个错误抽象。
- 文件超长却只解释“历史原因”，没有记录豁免来源和校验方式。

### 注释规范

Why：注释要补足代码本身说不出的意图、边界和失败条件；维护者能据此安全修改，代码才算可接手。

核心思路：注释用于解释意图、边界、约束和失败条件。公共边界、复杂业务逻辑、非显然约束必须注释；能从代码直接读出的内容不作为注释对象。

常见坑：
- 注释只翻译代码行为，没有说明业务意图或边界。
- 复杂约束没有注释，后续修改者只能猜。

### 错误处理规范

Why：错误处理定义失败时也要把事做对；用户可理解、调用方可恢复、问题可定位，才算可交付。

核心思路：禁止空 catch 块、禁止裸 except。错误提示必须用户可理解，禁止暴露堆栈/技术细节。所有外部调用（API/DB/文件 IO）必须有超时和错误处理。

常见坑：
- 空 catch 让失败静默消失。
- 把堆栈、SQL、内部服务名直接暴露给用户。
- 只给 API 加超时，漏掉 DB 或文件 IO。

### 硬编码规范

Why：配置治理定义系统离开本机后还能成立的边界；密钥、环境和依赖方向可审计，才算真实可交付。

核心思路：禁止硬编码密钥/Token/密码/Secret，必须从配置或环境变量读取；禁止通过字符串拼接、默认值回填等方式绕过密钥配置管理。环境特定配置（地址/端口/凭据）必须外置配置化，禁止写死在业务代码。禁止跨模块导入模块级常量；跨模块共享常量只有在语义稳定且属于公共契约时提升全局，否则调整依赖方向、保留边界内重复或放到概念拥有方。详细分层与命名见 `{{RUNTIME_HOME}}/reference/硬编码治理规范.md`。

常见坑：
- 用默认值或拼接字符串绕过密钥配置。
- 把模块内部常量抽成全局常量，反而扩大耦合。

### 死代码规范

Why：死代码治理让代码库只保留仍成立的行为；搜索、评审和变更判断指向当前事实，维护才算可靠。

核心思路：未使用的导入/变量/函数/字段必须删除。注释掉的大段旧实现、不可达分支、废弃占位逻辑禁止长期保留。确需保留兼容代码时，必须标注保留原因与失效条件。

常见坑：
- 注释掉旧实现当“备份”。
- 保留不可达分支，却不说明兼容对象和失效条件。

### 性能约束

Why：性能约束定义资源使用做到什么程度才算可交付；用户路径、批处理和大表访问都必须在可控边界内成立。

核心思路：临时文件固定命名 + try/finally 清理，禁止无限累积。大表查询必须分页；涉及用户路径、批处理或高频查询时，必须基于查询路径和执行计划评估索引。异步任务状态持久化到 Redis/DB，必须有超时控制。任何缓存引入必须经用户明确同意。详细指南见 `{{RUNTIME_HOME}}/reference/性能效率.md`。

常见坑：
- 临时文件不清理，靠系统目录兜底。
- 大表查询无分页，缓存未获用户明确同意就引入。

### 门禁落地原则

Why：门禁把 rules 变成可复验的交付边界；配置、脚本和人工判断都守住 MUST，质量结论才算成立。

核心思路：规则可由自动化门禁按改动范围或全量范围执行。具体变量、默认值、缺工具策略与 rollout 节奏见 `{{RUNTIME_HOME}}/reference/代码质量.md` 和实际检查脚本。门禁实现必须如实反映本文件规则，禁止以配置名义放宽 MUST 语义。

常见坑：
- 用配置把 MUST 调成 warn，却仍声称遵守规则。
- 工具缺失时静默跳过，不报告覆盖缺口。

### 复用治理规范

Why：复用治理定义什么时候新写才算对；先确认没有语义一致的现有能力，新增实现才算成立。

核心思路：新增实现前，必须先判断是否已有语义一致的候选实现。最终选择不复用而新建实现时，必须在代码注释、设计文档或 PR 描述中说明原因。复用的目标、判断标准与注意事项见 `{{RUNTIME_HOME}}/reference/代码复用.md`。

常见坑：
- 没查既有实现就新写一套。
- 为了复用拉跨模块内部常量或私有实现，破坏边界。
