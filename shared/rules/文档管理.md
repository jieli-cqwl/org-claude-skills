# 文档管理

## 总原则

文档管理保护当前事实单一真源、可接手、可恢复、可验证；不是为了整理目录好看。路径、registry、归档状态和验证脚本都属于运行契约，不能靠模型印象自由判断。

## 命名

Why：稳定命名让路径身份真实成立；同一个事实源能被 contract、恢复脚本和引用同时找到，接手才算可复验。

核心思路：受管路径必须稳定、语义段明确、同层无同义竞争。受管 feature/task 目录使用 `--` 分隔语义段，例如 `docs/feature--doc-governance--context-recovery`；日期 workset 目录使用 `YYYY-MM-DD-<change>`，日期后的短语内部使用单 `-`，例如 `2026-04-28-test-design-governance`。同一层级不得同时存在语义相同的 `feature-xxx-yyy` 与 `feature--xxx--yyy`。已纳管路径改名必须同步 `contracts/active-doc-scope.yaml`、入站引用、fixtures 和恢复测试。

常见坑：
- 把路径改名当纯文本整理，不同步 registry 和恢复测试。
- 混用 `feature-` 与 `feature--`，制造同义目录竞争。
- 日期目录内部继续使用 `--`，破坏 workset 命名口径。

## 同步

Why：文档同步让同一约束在代码、contracts、工具、测试和文档里都成立；这些证据一致，交付判断才算可靠。

核心思路：行为、规则、contracts、工具或测试任一变化影响同一约束时，相关文档必须同步更新。过时文档指与当前代码、contracts、scope registry、已接受决策或验证工具结果冲突的文档。过时文档若与本次变更属于同一约束、会阻断验证或会误导当前交付，必须在本次变更内修正或归档；边界外过时文档只记录并报告，禁止借机扩大范围。涉及行为或约束变更时，文档同步是完成标准的一部分。

常见坑：
- 只改代码或测试，不改同一约束下的文档。
- 发现边界外过时文档后顺手扩大任务范围。
- 把“文档稍后补”当成已完成。

## 归档

Why：归档定义哪些材料不再属于当前事实源；旧材料退出消费路径，当前上下文才算可交付、可恢复。

核心思路：过时且不再作为当前事实使用的文档必须归档至 `docs/archive/`；默认上下文接手不得读取 `docs/archive/`。归档前必须清理 active docs、tests、fixtures、runtime files 中仍指向该目录的引用；仍被验证或运行消费的材料必须迁入稳定 fixture/reference 位置。受管 feature/task 完成且解除入站引用后，整目录移至 `docs/archive/{feature-or-task}/`。scope registry 纳管的需求归档时，必须把 entry 改为 `legacy`，写入 `archive_ref / archived_at`，并保留可恢复的 `worklog.md`。

常见坑：
- 先移动目录，再想起来清 active 引用。
- archive 里的材料仍被 tests、fixtures 或 runtime files 消费。
- 把 `docs/archive/` 当默认接手资料继续读取。

## 活跃需求接手

Why：活跃需求接手要从可验证 registry 恢复；入口、状态和证据链一致，继续推进才算接在真实成立的任务状态上。

核心思路：活跃需求接手必须从 `contracts/active-doc-scope.yaml` 的 `managed / migrated` 条目开始；未纳管的 `docs/*` 不作为接手候选。`docs/{feature}/worklog.md` 只记录 `handoff_status / state_ref / next_ref` 导航字段；不得复制 PRD、设计、任务或验收全文。standard-chain 的进展真源是 canonical JSON；worklog 只能定位 active canonical artifact，不能替代 canonical 状态。接手、归档恢复和引用可达性必须由 `validate_context_contract.py`、`recover_context.py`、`tools/validate-contracts.sh` 和相关测试证明。

常见坑：
- 把未纳管 `docs/*` 当活跃需求入口。
- 把 worklog 写成 PRD、设计、任务或验收全文。
- 把 worklog 和 canonical JSON 平级，甚至替代 canonical 状态。

## 设计文档

Why：设计文档要让架构事实和执行状态各自成立；稳定决策可复验，后续实现才知道做到什么程度才算对。

核心思路：设计文档只记录“是什么”和“为什么”。checklist、版本待办和执行进度必须写入 plan、任务或状态文档，不得写入设计文档。设计决策和执行状态必须分离，避免接手时把计划进度误读为架构事实。

常见坑：
- 把未完成计划写成设计事实。
- 在设计文档里维护 checklist、版本待办或执行进度。
- 用设计文档替代任务状态文档。
