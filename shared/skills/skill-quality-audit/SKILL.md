# /skill-quality-audit -- Skill QA

/skill-quality-audit is a QA auditor for existing Skills. Given a target Skill, it co-creates a capability effectiveness standard with the user, then evaluates whether the Skill content and supporting mechanisms can make an agent perform that real task reliably.

Goal: maximize discovery of how the Skill can induce an agent to fail in real tasks, preserve unproven capability as risk, and only then tell the maintainer whether the Skill is fit for team use, what is wrong, why it matters, where to repair it, and how to verify the repair.

## HARD-GATE

<HARD-GATE>
Do NOT modify target Skill files, tests, contracts, scripts, runtime entries, or fixtures.
Write only audit output artifacts requested by the user or generated by the default artifact-path rule.
Do NOT return a team-readiness verdict unless the user-confirmed capability effectiveness standard includes file-line `confirmation_evidence`, the confirmed alignment JSON, formal report JSON, and both validators pass.
Do NOT treat repository contract, target Skill self-description, previous audit artifacts, transcripts, recaps, or model inference as a user-confirmed capability effectiveness standard.
`fit` requires `content_behavior_audit` coverage for every confirmed target capability with supported instruction hygiene, attention economy, behavior induction, failure-mode coverage, unproven-risk disposition, and per-field `evidence_checks`.
Do NOT close the audit until scope evidence covers every required surface as checked, absent, or blocked.
Do NOT keep any P0/P1 finding without current `path:line` evidence, supported claim review, severity calibration, impact, repair target, and verification hint.
Do NOT assign E4 unless executed verification has a matching PASS support for that dimension or finding.
</HARD-GATE>

Given a target Skill, co-create the capability effectiveness standard before the validated alignment artifact and formal QA report unless the user explicitly asks for a quick, non-final light scan.

Start by identifying the target Skill package and its current runtime surfaces. Then collect evidence with `Read`, `Glob`, and `Grep`; use Bash only for the alignment validator, report validator, and artifact classifier commands shown in Output Contract.

For the default audit, choose artifact paths automatically, write the alignment JSON with the user-confirmed `capability_effectiveness_standard`, write the report JSON with `content_behavior_audit`, write the Markdown summary, run both validators, and return the verdict with repair handoff. Use `docs/tmp/skill-quality-audit-<target-slug>-alignment.json`, `docs/tmp/skill-quality-audit-<target-slug>-report.json`, and `docs/tmp/skill-quality-audit-<target-slug>-summary.md` unless the user provides paths; if `docs/tmp` or a provided parent directory cannot be created or written, fall back to `/tmp` and record the fallback.

The human projection is a short decision surface, not a second report: recommended real task, success criteria, likely failure modes, unacceptable risks, evidence requirements, and one confirmation question with at most three options. Repository contracts and target Skill self-description can seed the projection, but only current user confirmation recorded as file-line `capability_effectiveness_standard.confirmation_evidence` can produce `capability_effectiveness_standard.co_creation_status: confirmed_with_user`. If confirmation evidence is missing, stop before formal audit.

For a light scan, return only unranked candidate risks and missing evidence. Stop before severity labels, verdicts, readiness decisions, JSON report creation, or validator claims.

When the input is an existing audit artifact, classify it before using it. A valid JSON audit report can be validated directly; a transcript or Markdown recap is only a lead for a fresh audit of the target Skill.

## Workflow Checklist

```text
1. Capability Standard Co-Creation -> 2. Pre-Audit Alignment -> 3. Scope Evidence -> 4. Content And Capability Audit -> 5. Runtime And Validation -> 6. Verdict And Repair Handoff
```

1. **Capability Standard Co-Creation** -- present a one-screen standard for user confirmation; include real task, success criteria, failure modes, unacceptable risks, and evidence requirements.
2. **Pre-Audit Alignment** -- separate target capability claims, current capability profile, evidence, assumptions, gaps, the co-created standard, and user confirmation; validate the alignment JSON before formal audit.
3. **Scope Evidence** -- identify the target Skill package and list every available surface: `SKILL.md`, `agents/openai.yaml`, references, scripts, templates, contracts, test prompts, evals, fixtures, runtime surface, install hooks, gate plan, run-all, focused runner, README, and downstream consumers.
4. **Content And Capability Audit** -- first audit Instruction Contract and Noise/Attention Economy, then audit whether the content induces the agent to satisfy the confirmed standard, ask required confirmations, preserve unknowns, and avoid premature verdicts.
5. **Runtime And Validation** -- verify permissions, implicit invocation policy, deterministic scripts/schema/tests, eval coverage, old-name residue, and install/gate alignment.
6. **Verdict And Repair Handoff** -- run claim review for each P0/P1 candidate, write JSON and summary artifacts, run the validator on the final JSON, then return the verdict and repair handoff.

For P0/P1 candidates, use low-freedom agent-team roles when available: Claim Builder decomposes required premises, Evidence Verifier checks current `path:line` evidence and direct refutations, and Severity Calibrator checks whether the claimed severity actually reaches team use, runtime, output, or downstream impact. These agents do not vote. The main audit keeps only the adjudicated `claim_review` and `severity_calibration`; agent transcripts never enter the final artifact. If agents are unavailable, the main audit must perform the same three checks directly.

## Output Contract

For a light scan, return only:

1. **Non-Final Status**: this is not a team-readiness conclusion.
2. **Candidate Risks**: evidence-backed observations without severity labels.
3. **Missing Evidence**: what would need inspection for a formal audit.

For the default audit, the schemas and validators are the field authority. Write `alignment_json` first, then write `report_json`, set `target_skill` to the target Skill path string, include `capability_effectiveness_standard.confirmation_evidence`, `capability_baseline_ref`, `confirmed_target_capability_ids`, `content_behavior_audit` with per-field `evidence_checks`, and each finding's `confirmed_gap_refs`, run both validators, and return a concise repair handoff in this order:

1. **Alignment**: alignment JSON path, confirmation level, confirmed target capabilities, and any residual unknowns.
2. **Verdict**: `fit`, `conditional`, `unfit`, or `blocked`. If the verdict is a team-use readiness conclusion, state that it is limited to this repository's custom team-use readiness contract and does not represent OpenAI official certification, generic Agent Skills compliance, or readiness for every Skill type outside the tested boundary.
3. **Scorecard**: every dimension as `score / evidence_level / reason`, plus the verdict cap reason.
4. **Content Behavior Audit**: every confirmed target capability as instruction hygiene, attention economy, behavior induction, failure-mode coverage, unproven-risk disposition, evidence refs, and per-field evidence checks for supported statuses.
5. **Scope Evidence**: every required surface as `checked`, `absent`, or `blocked`.
6. **Findings**: ordered by severity. Every finding cites confirmed gap refs; P0/P1 findings also require current `path:line`, `evidence_checks`, `claim_review`, and `severity_calibration`. P2/P3 findings omit those optional fields unless fully populated. A bare filename such as `SKILL.md` is not evidence. Markdown and chat summaries must include each P0/P1 finding's full repository-relative `path:line`, impact, repair target, and verification hint.
7. **Repair Handoff**: grouped file targets for a separate editing window.
8. **Validation**: alignment/report JSON paths and validator PASS output.
9. **Residual Risk**: only items outside the audit scope or blocked by missing evidence.

The JSON report is the artifact of record. A Markdown summary or chat response cannot substitute for it. When validating an existing JSON report file, run:

```bash
python3 shared/skills/skill-quality-audit/scripts/validate_skill_audit_alignment.py <alignment.json>
```

Then run:

```bash
python3 shared/skills/skill-quality-audit/scripts/validate_skill_audit_report.py <report.json>
```

When reviewing an existing audit artifact before trusting it, run:

```bash
python3 shared/skills/skill-quality-audit/scripts/classify_audit_artifact.py <artifact>
```

## Completion Verification

Before calling the audit complete, verify:

- Scope evidence covers every required surface, or records `absent` / `blocked`.
- Alignment JSON validates, target capability claims are separated from current supported capabilities, the capability effectiveness standard is user-confirmed with file-line `confirmation_evidence`, and formal findings trace to confirmed gaps.
- Content behavior audit covers every confirmed target capability with per-field evidence checks before any `fit` verdict.
- Scorecard covers every dimension; `blocked` separates not-scored sentinels from quality scores.
- Instruction Contract and team-use readiness have evidence for the decisive claims.
- Every P0/P1 finding has current `path:line`, `evidence_checks`, supported claim review, severity calibration, impact, repair target, and verification hint.
- Every E4 score has matching PASS `executed_verification.supports` for `dimension:<name>` or `finding:<id>`.
- Every `conditional`, `unfit`, or `blocked` verdict has a concrete next repair action.
- The report never tells this audit run to modify the target Skill.
- The final artifact is clean report content, not a chat transcript.
