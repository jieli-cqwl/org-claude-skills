# 中文晨报写作规范

## 体验目标

用户在早晨打开终端时，核心心态是“确认工具是否可用、今天有没有值得改变的用法”。报告要先降低不确定性，再给行动点，最后保留证据。技术细节服务于决策，不抢占第一屏。

## 心理把关规则

- 先结论后细节：第一屏必须回答更新状态、版本变化、今天要不要改变用法。
- 降低损失感：涉及快捷键、权限、配置、模型、计费、兼容性时，明确“会影响什么”和“如何避开风险”。
- 控制选择负担：行动项最多 3 条，按“今天试用 / 暂不需要 / 需要注意”分组。
- 翻译术语：把 TUI、MCP、sandbox、trace、resume 等词解释成用户任务中的效果。
- 给证据但不压迫：命令输出和来源链接放在中后段，让用户需要时追溯。
- 不制造焦虑：无版本变化时，重点写“已是当前版本”和最近可关注能力，不写成失败。

## 输出模板

```markdown
# AI CLI 更新晨报（YYYY-MM-DD）

## 今日结论

- 状态：<全部更新 / 部分阻塞 / 已是当前版本 / 只检查未更新>
- 版本：Claude Code <before> -> <after>；Codex <before> -> <after>
- 今天最值得关注：<1 句话，面向工作流价值>
- 你接下来可以做：<1-3 条行动>

## 更新证据

| 工具 | 更新前 | 更新后 | 执行命令 | 结果 |
| --- | --- | --- | --- | --- |
| Claude Code | <version> | <version> | `<command>` | <ok/blocked/current> |
| Codex | <version> | <version> | `<command>` | <ok/blocked/current> |

## 变更解读

### <工具>：<变化名称>

- 核心特点：<它新增或改变了什么>
- 解决的问题：<之前的痛点或风险>
- 对你工作流的影响：<更快、更稳、更少打断、更容易协作等>
- 推荐用法：<今天就能怎么用，写成具体动作>
- 注意事项：<快捷键变化、配置开关、兼容性、权限、费用或无风险>

## 今天怎么用

- 今天试用：<最值得马上尝试的 1 条>
- 暂不需要：<知道即可的 1 条>
- 需要注意：<风险或习惯变化；无则写“无”>

## 来源

- <官方 changelog / release notes / package metadata 链接>

## 阻塞项

- <无 / 工具、原因、需要用户确认的动作>
```

## 好坏示例

差：

> Added `/tui` command and `tui` setting.

问题：只搬运原文，没有告诉用户为什么关心、怎么使用。

好：

> 核心特点：Claude Code 增加 `/tui fullscreen`，能在同一会话里切到更稳定的全屏渲染。解决的问题：长会话输出闪烁和滚动干扰。推荐用法：今天做长时间重构或读大段日志时，先输入 `/tui fullscreen`，把会话切到全屏模式。

## 分组口径

把 changelog 条目归入以下用户价值，不按原始顺序堆叠：

| 分组 | 适用变化 | 用户关心点 |
| --- | --- | --- |
| 新能力 | 新命令、新模式、新集成 | 今天多了什么做法 |
| 工作流效率 | 快捷键、恢复会话、编辑器集成 | 是否减少切换和等待 |
| 稳定性修复 | 崩溃、渲染、路径、终端兼容 | 是否减少中断 |
| 安全与配置 | 权限、sandbox、MCP、遥测 | 是否改变边界或默认行为 |
| 兼容与风险 | 安装方式、系统差异、破坏性变更 | 是否需要用户调整习惯 |
