# 测试义务分层方法

## 目标

决定每个测试义务应由开发自测、自动化、QA 冒烟、QA 深测或人工 handoff 承接。分层的目的不是减少测试，而是让每个消费者拿到自己能执行、能举证、能负责的义务。

## 分层原则

先问三个问题：

1. 这个义务最早能在哪个阶段被验证。
2. 这个义务失败时由谁最容易定位和修复。
3. 这个义务需要什么环境、数据、权限和证据。

按答案分配：

- 开发自测：单 Task 内可直接验证的行为、边界、错误处理、数据变换、接口契约。
- 自动化优先：稳定、重复、低人工判断、高回归价值的义务。
- QA 冒烟：关键用户路径、提测准入、跨模块联动、浏览器状态、权限路径。
- QA 深测：探索性、兼容性、端到端旅程、复杂数据准备或人工判断较强的场景。
- Handoff obligation：当前阶段不执行，但必须在 QA 或交付阶段被明确消费的义务。

## 开发消费者视角

开发需要的是可实现和可自测的目标：

- 明确输入、操作和预期结果。
- 明确 assertion target。
- 明确对应 AC 和 design refs。
- 明确失败时是否阻断提交。
- 避免让开发猜 QA 才能判断的浏览器体验或发布风险。

开发自测不替代 QA，但应消除“编码完成后才发现 AC 理解不一致”的风险。

## QA 消费者视角

QA 需要的是可执行验收义务：

- 触发源：来自哪个 AC、风险、设计约束或跨 UNIT 旅程。
- 阶段：冒烟、功能、接口、E2E、回归、NFR 或探索。
- 执行方式：是否必须真实浏览器、真实外部依赖、真实数据链路。
- skip rule：什么条件下允许跳过，跳过后风险由谁承担。
- evidence expectation：截图、日志、接口响应、数据库记录、监控指标或人工记录。

QA handoff 不做 release recommendation；它只冻结 QA 应消费的输入义务。

## Tech-Lead 与 Delivery 消费者视角

`/tech-lead` 需要 test_ref、覆盖关系和 blocking gap，以便拆 task 时不丢验收口径。

`/delivery-owner` 需要知道哪些 gap 阻断交付、哪些 QA obligation 必须在提测后消费、哪些跨 UNIT 义务不能断链。

## 反模式

- 把所有高风险都塞给 E2E。
- 把所有 NFR 都交给 QA “看一下”。
- 用“建议测试”代替必须消费的 obligation。
- 缺少 assertion target，却仍然生成测试用例。
- 有 blocking gap，却继续交给 `/tech-lead`。
