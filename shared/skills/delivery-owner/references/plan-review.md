# Plan Review & Execution Strategy

## 目标

审视完 tasks 后，你对三个问题有清晰判断：

1. **能不能执行** — 基线、输入、资源是否就绪
2. **怎么执行最安全** — 关键路径、排序、隔离策略
3. **哪里最可能出问题** — 风险点和应对方式

## 判断框架

### 可执行性审视

先确认基线完整性：

| Check | PASS | Pause |
| --- | --- | --- |
| Baseline | tasks 冻结且版本一致 | producer、版本、确认状态或 task list 漂移 |
| Task | 每个 task 有 AC、依赖、输入和证据入口 | 任一 task 无法回答谁做、目标是什么、证据是什么 |
| Dependency | 依赖图无环，且可决定串并行策略 | 依赖成环、共享文件或状态会互相踩踏且无隔离方案 |
| QA handoff | `qa_handoff_contract` 和组合义务可验收 | QA 需要猜用户路径或验收标准 |
| Resource | 逻辑角色有可用执行入口，权限、环境和工具可用 | 缺 executor、权限、环境、工具或外部条件未确认 |

任一 check 为 Pause 时暂停给用户，说明缺口、影响和推荐处理。

### 依赖分析

任务间的依赖有三个层次，只看 `depends_on` 会漏掉隐式冲突：

1. **显式依赖** — `depends_on` 声明的直接依赖，最容易识别。
2. **文件依赖** — 多个 task 修改同一文件或同一模块的不同部分。即使没有 `depends_on`，并行修改同一文件会导致合并冲突和反复返工。
3. **状态依赖** — task A 的输出是 task B 的运行前置条件（配置变更、数据迁移、环境状态切换）。这类依赖最隐蔽，在 task 字段中看不到，需要理解任务的运行时效果。

分析方法：列出所有 task 对，标记三类依赖，识别哪些 task 对存在未声明的隐式冲突。

### 关键路径识别

关键路径是从第一个任务到交付完成的最长串行链路——它决定整体交付时间。

识别方式：

1. 从依赖图中找出所有必须串行的链路（显式 + 隐式依赖都算）。
2. 最长的那条就是关键路径。
3. 关键路径上的任何延迟都会直接延迟整体交付；非关键路径有缓冲。

关键路径上的任务需要优先派发、优先验证，风险缓解优先投入。

### 资源竞争检测

多个任务可能争用同一资源：

- **同一文件/模块** — 并行修改产生合并冲突。
- **同一测试环境/端口** — 并行运行互相干扰。
- **同一配置/共享状态** — 并行修改互相覆盖。

识别到资源竞争时，要么串行化竞争任务，要么隔离资源（worktree、独立环境、独立配置）。

### 回滚风险评估

评估每个任务失败时的恢复代价：

- **只影响自己** — 失败后直接修复或丢弃，不影响其他任务。
- **影响下游输入** — 下游任务的输入或环境依赖该任务的输出，失败后下游需要重做。
- **影响全局状态** — 修改数据库 schema、共享配置或基础设施，失败后需要回滚全局状态。

回滚代价高的任务需要更严格的验证门禁，或者在独立环境中先行验证。

### 执行策略

基于以上分析，确定执行策略：

**排序原则 — 风险驱动：**

高不确定性的任务先执行。如果高风险任务失败，早期发现可以调整计划、收窄范围或切换方案；推迟到最后才发现，调整空间已经消失。

| 不确定性 | 关键路径 | 排序 |
| --- | --- | --- |
| 高 | 是 | 最先执行 |
| 高 | 否 | 尽早执行但不阻塞关键路径 |
| 低 | 是 | 按依赖顺序执行 |
| 低 | 否 | 可并行或推迟 |

**隔离原则 — 失败爆炸半径：**

| 失败影响范围 | 策略 |
| --- | --- |
| 只影响自己 | 可与其他任务并行 |
| 影响下游任务的输入/环境 | 先验证成功再释放下游 |
| 影响全局状态 | 独立执行，确认回滚方案后再开始 |

**策略分类：**

- `parallel` — 无依赖（含隐式），文件/状态边界独立，验收可独立判断。
- `serial` — 存在依赖、共享状态、高回滚风险或证据会相互失效。
- `mixed` — 先跑关键路径根任务和高风险任务，再派独立分支。大多数真实场景是 mixed。

## 质量标准

审视完成后，你能回答：

- 关键路径是哪条，路径上每个任务的风险和缓解措施是什么。
- 执行顺序有具体的排序依据（风险等级 + 依赖关系），不是默认全并行。
- 共享资源冲突已识别，每个冲突有处理方案（串行化或隔离）。
- 高不确定性任务的位置反映了风险前置原则。

## 常见模式

| 场景 | 诊断 | 处理 |
| --- | --- | --- |
| 所有任务都没有显式 `depends_on` | 不代表无依赖——检查文件依赖和状态依赖 | 发现隐式依赖就调整为串行或隔离 |
| 一个任务改底层模块，其他任务消费该模块 | 典型的关键路径根节点 | 底层任务先行，验证通过后释放消费方 |
| 两个任务改不同功能但共享测试 fixtures | 测试阶段互相影响的风险 | 串行化测试阶段，或隔离 fixtures |
| 多个任务都标高风险 | 不可能全部最先执行 | 按关键路径优先级排序，非关键路径的高风险任务并行探测 |
| 依赖图有环 | 计划有结构性问题 | 暂停，报告环依赖并建议回流 tech-lead |
| 所有任务都低风险且无依赖 | 最简单的场景 | 全并行，注意 resource 和环境上限 |

## 边界

- 计划本身有结构性问题（scope 矛盾、AC 不可验证、依赖成环）→ 审视能发现，但修复不是 delivery-owner 的职责；暂停给用户，说明影响和建议回流 tech-lead。
- 资源完全不可用 → 不是策略问题，标记 `NEEDS_RESOURCE`。
- 需求变更导致计划失效 → 不在审视范围，需要重新走上游。
