## 检查 1：死规则检测（ERROR 级）

**目标**：发现 paths glob 匹配不到实际文件的规则。

**执行方法**：
1. 读取项目 `.claude/rules/`（或 `.codex/rules/`）中每个 `.md` 文件的 YAML frontmatter
2. 提取 `paths` 字段中的每个 glob 模式
3. 对每个 glob 执行 `find` 或 `glob` 匹配，统计匹配文件数
4. 匹配数为 0 → 输出 ERROR

**输出格式**：
```
[ERROR] <rule-file>.md: paths "{glob}" 匹配 0 个文件
  → 建议：检查 glob 模式是否正确，或该规则是否仍然需要
```

**特殊情况**：
- 无 paths frontmatter 的文件 → 跳过此检查（它是无条件加载的）
- paths 有多个 glob，其中部分匹配、部分不匹配 → 仅对不匹配的 glob 报 ERROR

## 检查 2：重复检测（WARN 级）

**目标**：发现项目级规则与全局规则的内容重复。

**执行方法**：
1. 读取全局 `{{RUNTIME_HOME}}/rules/` 中所有文件
2. 提取关键约束短语（如"禁止硬编码"、"禁止空 catch"、"禁止 SELECT *"等）
3. 在项目级规则文件中搜索相同关键短语
4. 匹配到 → 输出 WARN，展示两侧的具体行，让用户判断是否真正重复

**输出格式**：
```
[WARN]  <project-rule>.md 第{N}行 与全局 <global-rule>.md 第{M}行可能重复
  项目级：{匹配行内容}
  全局级：{匹配行内容}
  → 建议：如果语义相同，删除项目级重复条目
```

**关键词列表**（非穷举，持续积累）：
- 硬编码、密钥、Token、密码
- 空 catch、裸 except
- SELECT *
- 超时、错误处理
- 禁止静默降级、禁止跳过

**注意**：关键词匹配是浅层的，可能有误报。始终展示上下文让用户判断，不自动删除。

## 检查 3：盲区检测（WARN 级）

**目标**：发现项目中有代码目录未被任何规则的 paths 覆盖。

**执行方法**：
1. 收集项目中所有包含代码文件的目录（排除 node_modules、.git、build、dist、target 等）
2. 汇总所有项目级规则的 paths glob
3. 对每个代码目录，检查是否至少有一个 glob 能匹配到该目录下的文件
4. 未被覆盖 → 输出 WARN

**输出格式**：
```
[WARN]  目录 {path}/ 未被任何规则 paths 覆盖（包含 {N} 个代码文件）
  → 建议：确认是否需要覆盖，或属于预期排除
```

**排除目录**（不检查）：
- `node_modules/`、`.git/`、`build/`、`dist/`、`target/`、`vendor/`
- `docs/`、`.github/`、`.vscode/`、`.idea/`
- 仅含配置文件的目录（如只有 `.json`、`.yaml`、`.toml`）

**注意**：并非所有目录都需要规则覆盖。此项为 WARN 级，用户确认"预期排除"即可。

## 检查 4：质量检测（WARN 级）

**目标**：检查规则文件本身的质量。

**检查子项**：

### 4a：缺少 paths frontmatter
```
[WARN]  <rule-file>.md 缺少 paths frontmatter，将无条件加载
  → 建议：项目级规则应绑定文件路径，添加 paths 配置
```

### 4b：模糊表述
检测规则文本中包含"应该"、"建议"、"可以考虑"、"最好"等模糊词汇：
```
[WARN]  <rule-file>.md 第{N}行包含模糊表述："{匹配内容}"
  → 建议：MUST 级规则使用"必须/禁止"，不使用"应该/建议"
```

### 4c：规则数量过多
单个规则文件超过 10 条 MUST 约束：
```
[INFO]  <rule-file>.md 包含 {N} 条约束，建议控制在 5-8 条以内
  → 建议：将细节规范拆分到项目 reference/ 目录
```

## 汇总输出

所有检查完成后，输出汇总行：
```
[OK]    {N} 个规则文件，{M} 个技术域覆盖，{E} 个错误，{W} 个警告
```

如果无任何规则文件：
```
[INFO]  当前项目无 .claude/rules/（或 .codex/rules/），建议运行 /rules-manager init
```
