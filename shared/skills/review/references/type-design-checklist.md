# 类型设计检查清单

> 供 /review 审查-B 设计维度引用（TS/Java 项目额外检查）。

## 1. 不变量识别

| 检查项 | 说明 |
|--------|------|
| 不变量是否明确 | 类型应表达"哪些状态组合是合法的" |
| 不变量是否完整 | 所有业务规则是否都通过类型系统表达 |
| 不变量是否可验证 | 是否能通过构造函数/工厂方法强制验证 |

### 示例
```
// 差：不变量仅靠文档保证
interface Order {
  status: string;  // "pending" | "paid" | "shipped"
  paidAt?: Date;   // 文档说"status=paid 时必须有"
}

// 好：不变量通过类型强制
type Order =
  | { status: "pending" }
  | { status: "paid"; paidAt: Date }
  | { status: "shipped"; paidAt: Date; shippedAt: Date };
```

## 2. 封装评估（1-10 评分）

| 分数 | 标准 |
|------|------|
| 9-10 | 所有内部状态私有，仅通过方法暴露行为，无法构造非法状态 |
| 7-8 | 大部分内部状态封装，少量可直接访问但有文档说明 |
| 5-6 | 混合封装，部分内部状态公开，依赖调用方自律 |
| 3-4 | 贫血模型，几乎所有字段公开，逻辑散布在外部 |
| 1-2 | 纯数据容器，无封装，任何代码可任意修改 |

## 3. 不变量表达清晰度

| 检查项 | PASS 标准 |
|--------|---------|
| 类型即文档 | 读类型定义就能理解合法状态 |
| 非法状态不可表示 | 类型系统阻止非法状态组合的构造 |
| 构造时验证 | 工厂/构造函数验证所有不变量 |
| 修改时保护 | 状态变更方法维护不变量 |

## 4. 常见反模式

| 反模式 | 问题 | 修复方向 |
|--------|------|---------|
| 贫血模型 | 类型只有数据无行为，逻辑散布各处 | 将相关逻辑移入类型方法 |
| 暴露可变内部 | 返回内部数组/对象引用 | 返回副本或不可变视图 |
| 仅靠文档保证不变量 | 运行时无强制，依赖开发者记忆 | 类型系统 + 构造验证 |
| 过度泛化 | `Record<string, any>` 代替具体类型 | 定义精确的类型结构 |
| 可选字段滥用 | 所有字段可选导致运行时空检查泛滥 | 用联合类型表达状态 |
| 字符串类型枚举 | `status: string` 代替 `status: "a" \| "b"` | 使用字面量联合或 enum |

## 5. 评估维度总结

| 维度 | 权重 | 评估方法 |
|------|------|---------|
| 封装 | 30% | 内部状态是否通过访问控制保护 |
| 不变量表达 | 30% | 类型系统是否阻止非法状态 |
| 构造验证 | 20% | 创建时是否验证所有约束 |
| 变更保护 | 20% | 修改操作是否维护不变量 |
