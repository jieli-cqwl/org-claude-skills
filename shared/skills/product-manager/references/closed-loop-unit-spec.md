# 闭环 UNIT 规格

UNIT 是 Manager 层的最小可交付 WHAT 单元。它描述业务输入、行为、可观察结果、验收示例、验证计划和集成约束；不描述文件路径、代码模式、接口形态或技术实现方案。

## 模板

```markdown
# UNIT-NNN: [闭环功能标题]

**优先级**: MVP | 增强 | 扩展

## 优先级依据
[为什么属于 MVP / 增强 / 扩展]

## 背景
[业务动机]

## 需求描述
[做什么、为什么]

## 功能闭环定义
- 输入/触发: [什么输入、什么状态或什么动作触发该功能]
- 核心行为: [系统做什么]
- 可观察结果: [外部可见结果是什么]

## Integration Context（集成上下文）
- 涉及的现有业务模块或功能区域: [如权限、订单、线索等；无则"无"]
- 不可破坏的现有行为: [已有流程、权限、数据口径或用户习惯；无则"无"]
- 跨 UNIT 依赖: [依赖 UNIT、顺序或共享业务对象；无则"无"]
- 业务约束说明: [只写业务约束，不写技术落点]

## 验收标准

### 正常场景
- AC-U1-01
  - AC 描述: [可观察、可验证的行为陈述]
  - 示例输入: [具体输入数据、用户操作或业务状态]
  - 预期结果: [具体输出、状态变化、提示或记录]
  - 边界情况: [边界值或特殊条件下的预期行为]
  - 失败模式: [异常输入或异常状态下的处理方式]

### 异常场景
- AC-U1-02
  - AC 描述: [异常路径的可观察行为]
  - 示例输入: [触发异常的具体输入或状态]
  - 预期结果: [错误提示、拒绝、保留上下文或补救动作]
  - 边界情况: [异常路径的边界条件]
  - 失败模式: [不能接受的失败表现或应被阻止的状态]

### 边界条件
- AC-U1-03
  - AC 描述: [边界条件下的业务行为]
  - 示例输入: [最大/最小/空/重复/临界数据]
  - 预期结果: [可观察结果]
  - 边界情况: [该 AC 覆盖的边界]
  - 失败模式: [超出边界时的处理方式]

## Verification Plan（验证计划）
- 验证类型: [功能验证 / 数据验证 / 流程验证 / 权限验证 / 风险验证]
- 业务操作或场景: [用户或系统执行什么业务动作]
- 预期可观察结果: [页面反馈、状态变化、数据记录、通知或阻断结果]
- 对应 AC / 成功标准 / 风险项: [AC-U1-01 / success_signal / risk-id]
- 说明: [只写业务操作和观察结果，不写命令、测试框架或 Mock 策略]

## 结构化待设计决策
- 决策名称: [需要 /design 裁决的问题]
- 候选选项: [2-3 个业务可接受选项；未知时写待设计补充]
- 约束条件: [来自 Director 或 PM 的业务约束]
- 影响的 UNIT: [UNIT-NNN 列表]
- Design handoff: [交给 /design 裁决的目标，不提前给技术答案]

## 依赖
- 依赖 UNIT: [UNIT-NNN 列表，无则"无"]
- 依赖业务对象: [业务对象或业务状态，无则"无"]
- 受影响方: [需同步评估的现有功能/流程，无则"无"]

## 排除项
- [本需求明确不处理的场景]
```

## 质量标准

| 检查项 | 要求 |
|--------|------|
| 标题 | 必须是功能名/能力名，不是“梳理/建模/审计/SOP”等主题名 |
| 优先级 | 必须标注 MVP / 增强 / 扩展，并写明优先级依据 |
| 功能闭环定义 | 必须写清 `输入/触发 -> 核心行为 -> 可观察结果` |
| Integration Context | 必须写清业务模块、不可破坏行为和跨 UNIT 依赖；不得写技术落点 |
| AC | 正常 / 异常 / 边界各 >= 1，且每条都有示例输入、预期结果、边界情况和失败模式 |
| Verification Plan | 必须写业务操作和可观察结果，不写验证命令或测试框架 |
| 结构化待设计决策 | 有开放设计问题时必须写选项、约束、影响 UNIT 和 design handoff |
| 依赖 + 排除项 | 必须显式列出 |

## 拆分规则

- 一个 UNIT 只表达一个闭环功能
- 若一个 UNIT 出现多个独立触发或多个独立结果，必须继续拆分
- 3 个及以上 UNIT 全部标为 `MVP` 时，必须补 `MVP 最小闭环说明`
- 示例驱动 AC 不能替代 UNIT 闭环定义；两者都要存在
