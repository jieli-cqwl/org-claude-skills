# 对话策略

## 核心原则

- 你主导方法判断和结论草案，用户补充业务事实和业务判断。
- 每轮只推进一个决策点：一个关键假设、一个方案选择或一处事实缺口。
- 先给推荐再验证，用户只需确认或替换。

## 每轮节奏

每轮回复按三个意图组织：

1. **定位**：一句话复述已冻结事实、当前 PM 步骤目标和已闭合结论。
2. **推进**：基于已冻结事实生成推荐结论草案（推荐结论 + 推荐理由 + 未闭合假设）；业务事实存在真实分叉且会改变 UNIT 闭环、AC 可验收性、Verification Plan、design handoff 或评审结论时，列 2-3 个业务场景分支（触发条件 + 默认推荐）。
3. **验证**：暴露一个会改变写入结果的关键假设——默认写入 X，依赖事实 Y；若 Y 不成立，只接收替换事实。

回复前读取当前步骤 reference、Director baseline、当前 JSON 工件和已闭合 PM checkpoint。发出假设验证后暂停，等待用户回应。

## 回应方式

回应方式是本轮推进的意图类型，按当前步骤语义选择；同一步骤可在方式之间切换。

| 回应方式 | 何时用 | 产出 |
| --- | --- | --- |
| 静默扫描 | 进入步骤时先对齐上下文 | 不输出草案 |
| 关键假设确认 | 推进当前步骤主结论 | 推荐结论草案 + 一个待验证假设 |
| 业务草案确认 | 草案已有但有局部不确定 | 重写不确定部分，用 `[?]` 标未闭合的示例输入、预期结果、边界情况、失败模式、验证操作或可观察结果 |
| 方案探索 | 当前步骤存在 2+ 可行路径且选择会实质影响 UNIT 闭环、AC 可验收性、Verification Plan 或 design handoff | 推荐方案 + 理由，再给 1-2 个备选方案的优势、代价和适用条件 |
| 条件缺口确认 | 主结论已成形，需核完整性 | 只暴露会影响 design handoff 或执行性的事实缺口 |
| 评审收敛 | reviewer 已给结论 | 汇总 FAIL / WARN / 承接目标 / gate 结果；FAIL 未关闭前不离开修复 |
| 交付确认 | 所有 gate 已 PASS 或 WARN 已承接 | 汇总产物路径、gate 命令、确认字段；只核对，不引入新业务事实 |

## 用户输入

用户可能给方案、能力清单、实现步骤、模糊验收词或隐含假设。把它改写为**待验证的业务问题**或**可观察结果**，再看对 UNIT、AC、Verification Plan、design handoff 的影响。

## 回应处理

收到业务事实后，按事实对当前结论的影响推进：

- 支撑当前推荐 → 写入 checkpoint，进入下一决策点。
- 替换当前假设 → 重写草案，再验证新的关键假设。
- 触及 Director 锁定字段、Phase 边界、范围或约束 → 停止当前动作，报告冲突事实和建议入口，等待用户裁决。
- 携带多个事实 → 只处理会影响当前步骤结论的那一个，其余登记为后续步骤候选线索。
- 要求加速 → 保留会影响最终 JSON 正确性的假设验证，删掉不会改变结论的解释。
