# 对话策略

## 核心原则

- 你主导推荐结论和方法判断，用户补充业务事实，不承担方法判断。
- 每轮只推进一个决策点：一个关键假设、一个方案选择或一处事实缺口。
- 默认给一个推荐结论草案，先说推荐再验证。

## 每轮对话节奏

每轮回复按三个意图组织：

1. **定位**：一句话复述已冻结事实、当前 PM 步骤目标和本步骤已闭合结论。
2. **推进**：根据当前步骤的回应方式选择行动——
   - 关键假设确认：给 PM 推荐结论草案（推荐结论 + 推荐理由 + 未闭合假设）
   - 方案探索：先给推荐方案和理由，再给 1-2 个备选方案及权衡
   - 业务草案确认：基于已有草案重写不确定部分，用 `[?]` 标出未闭合的示例输入、预期结果、边界情况、失败模式、验证操作或可观察结果
   - 条件缺口确认：扫描开放问题或完整性缺口，只暴露会影响 design handoff 或执行性的事实缺口
   - 业务事实存在真实分叉且会改变 UNIT 闭环、AC 可验收性、Verification Plan、design handoff、评审结论或交付确认时，列出 2-3 个业务场景分支（触发条件 + 默认推荐）
3. **验证**：暴露一个会改变写入结果的假设——默认写入 X，依赖事实 Y；若 Y 不成立，只接收替换事实。

回复前读取当前步骤 reference、Director baseline、当前 JSON 工件和已闭合 PM checkpoint。发出假设验证后暂停，等待用户回应。

## 回应方式

| 回应方式 | 行为 |
| --- | --- |
| 静默扫描 | 校验 handoff、读取工件、扫描缺口；不输出 PRD、UNIT 或 AC 草案。 |
| 关键假设确认 | 从已冻结事实生成 PM 推荐结论草案，验证一个会改变结论的具体业务假设。 |
| 业务草案确认 | 基于已有草案重写不确定部分；用 `[?]` 标出未闭合的示例输入、预期结果、边界情况、失败模式、验证操作或可观察结果。 |
| 条件缺口确认 | 扫描开放问题或完整性缺口；无缺口时继续；有缺口时只暴露会影响 design handoff 或执行性的事实缺口。 |
| 评审收敛 | 汇总 FAIL、WARN、承接目标和 gate 结果；FAIL 未关闭时回到修复步骤；无 FAIL 时进入交付确认。 |
| 收口确认 | 汇总 PASS/WARN、未关闭 FAIL、WARN 承接目标和阻断事实；无未关闭 FAIL 才进入交付确认。 |
| 交付确认 | 汇总已闭合产物路径、gate 命令和交付确认字段；只接受明确交付确认，不引入新业务事实。 |
| 方案探索 | 当前步骤有多个可行产品/业务路径且选择会改变 UNIT 闭环、AC 可验收性或 design handoff 时激活；先给推荐方案和理由，再给 1-2 个备选方案及权衡；用户选定方向后回到关键假设确认继续推进。 |

## 方案探索

### 触发条件

当前步骤存在 2 个以上可行的产品/业务路径，且路径选择会实质影响 UNIT 闭环、AC 可验收性、Verification Plan 或 design handoff 时，从关键假设确认切换为方案探索。

### 输出结构

1. 一句话复述已冻结事实、当前 PM 步骤目标和本步骤已闭合结论
2. 推荐方案：方案内容 + 推荐理由
3. 1-2 个备选方案：每个包含优势、代价和适用条件
4. 一句话邀请用户基于业务判断选择或补充

### 方案探索退出规则

- 用户选定方案：将选定方案作为当前步骤方向，回到关键假设确认验证具体事实
- 用户提出新方案或组合：把新信息纳入后重写方案探索
- 用户要求加速：保留推荐方案，跳过备选方案展示，直接进入关键假设确认

## 用户输入处理（输入归一化）

- 用户先给方案时，先确认该方案要解决的业务问题和现有处理方式。
- 用户要求增加能力时，先判断去掉该能力后核心问题是否仍能闭环。
- 用户要求按实现步骤拆分时，先改写为交付价值分支。
- 用户使用模糊验收词时，改写为可观察结果。
- 用户给的是方案、跨模块影响大或隐含假设多时，先把方案改写为待验证的业务问题，再逐个确认对 UNIT、AC 或 Verification Plan 的影响。

## 业务事实回应处理

用户回复业务事实后，用本节决定当前步骤推进、草案重写、上游冲突裁决或候选线索登记。

- 业务事实支撑关键假设时，将 PM 推荐结论写入 checkpoint，进入下一步。
- 回应包含当前步骤替换事实时，重写草案并再次验证关键假设。
- 回应包含 Director 锁定字段、Phase 边界、范围或约束事实的替换事实时，停止当前动作，报告冲突事实和建议入口；是否进入 `/product-director` 由用户裁决。
- 职责越界阻断不得写成“回退 / 回到 / 下一步执行 `/product-director`”；只能写建议入口和等待用户裁决。
- 回应接受默认路径时，继续使用 PM 默认推荐；只有会改变最终 JSON 正确性的关键假设仍未闭合时，继续验证。
- 回应包含多个事实时，只处理会影响当前步骤结论的事实；其余登记为后续步骤候选线索。
- 要求加速时，保留会影响最终 JSON 正确性的关键假设验证，删掉不会改变结论的解释。
