# Flow 诊断口径

**目标**：AI 按这个流程能像该职责的熟练从业者一样把事办成。

## 裁决标准

1. 真实顺序：步骤符合该职责自然办事顺序。
2. 真实判断：关键决策来自专业工作，而不是文件结构或运行时术语。
3. 真实行动：每一步都是可执行动作，能推进任务。
4. 真实交付：流程终点是用户或下游会消费的结果。
5. 失败路径真实：缺输入、目标冲突、验证失败或越权时知道如何停止或回看。
6. 工程载体服务流程：reference、script、template、schema、eval 和 test 只承载对应动作。
7. 目标闭合：验收时回看最初目标；未闭合时只回到对应环节，不重启全流程。
8. 阶段闸门清楚：共创、策略冻结、执行和验收不能混成一个循环；冻结前只登记策略，不改文件。
9. 流程图无歧义：流程图只表达状态推进、暂停点和分支条件，不重复步骤细节。
10. **定义与实现一致**：流程表里的 Acceptance / Failure state / Consumer 必须在对应的详细步骤、HARD-GATE 或 inline bash 里有落地指令；不得只写在表格里而详细步骤无任何强制语（STOP/拒绝/阻断/fallback 等）。

## 问题信号

- 流程按文件生成顺序写，而不是按办事顺序写。
- 每步只强调产物字段，没有专业判断和行动。
- 先补标准段落，再回头解释为什么需要。
- 单个环节策略确认后就开始创建、修改、删除或迁移文件。
- 把"登记待执行策略"写成"进入执行队列"，导致共创阶段和执行阶段混淆。
- 流程图重复步骤细节，或把同一动作写成多个执行节点。
- 失败路径只有泛化措辞，没有说明回到哪个环节、由谁裁决、重新验证什么。
- **流程表 Failure state 写"Stop / 拒绝 / 阻断"，但详细步骤里找不到对应 STOP/拒绝指令或 HARD-GATE 条目——LLM 实际执行时会跳过阻断。**
- **流程表 Acceptance 写"至少命中 X"，但详细步骤没有校验逻辑或门禁，只在自由文本里隐含要求。**
- **流程表 Consumer 列写"Agent 1-6"，但实际详细步骤只定义了 Agent 1-4——编号与范围不对齐。**

## 交叉核验清单

每个流程表行完成诊断前，在目标文件里执行以下检查：

1. Acceptance 对应的校验逻辑在详细步骤可见（命令、HARD-GATE 或明确判断文字）
2. Failure state 在详细步骤或 HARD-GATE 中有对应的 STOP / 拒绝 / 降级 / 回看指令
3. Consumer 字段中提到的所有编号（Agent N、Step N）在详细步骤内均有定义

任一项不满足则该 Flow 维度必须标为 ISSUE，不得单凭"描述看起来合理"判 PASS。
