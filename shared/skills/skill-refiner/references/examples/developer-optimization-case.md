# Developer 优化成功示例

供你在验收时对照成功样例。

## 成功形态

Developer 优化成功不是因为补了更多标准，而是因为把 Skill 拉回了开发职责的真实办事流程：

1. 理解 Task、AC、Scope。
2. 拆解实现步骤。
3. 按 AC 执行 RED / GREEN / REFACTOR。
4. 自测目标测试、目标回归、静态分析和必要冒烟。
5. 输出可复验的 developer-report。

## 纠偏记录

| 早期偏差 | 用户反馈 | 修正原则 |
| --- | --- | --- |
| 给旧设计打补丁 | “这不是我们最初的目标” | 先回到真实需求和办事流程 |
| 引入无关运行面分层标准 | “彻底删除无关标准” | Skill 不承载无关运行时抽象 |
| 在 SKILL.md 重复字段合同 | “字段形状以 schema/template 为准” | 机器合同放机器真源 |
| 默认解释 hook/gate | “这应该是由 hooks 调用” | 运行时内部不写进执行 SOP |
| 保留旧式资源头说明 | “skill 不是说明书，而是 SOP” | reference 也要按消费关系写 |
| 教 LLM 通用探索命令 | “属于 coding LLM 本来应该具备的能力” | 不写模型通用基础能力 |
| 保留历史备用 Skill 目录 | “彻底删除，相关联的都清理干净” | active 链路必须清理历史残留 |

## 你的评审要点

1. 顶层先问专业职责域，不先问目录结构。
2. 目录结构是工程承载规范，不是内容真源。
3. 按 SR-S2、SR-S3 与 SR-R1~SR-R10 沉淀台账结论；关键假设闭合后再冻结整体策略。
4. 旧文件和旧测试是证据，不是必须保留的目标。
5. 删除和迁移必须覆盖 active 消费者；不能只改主文件。
6. 输出要能被下游复验，不靠口头说明替代证据。
