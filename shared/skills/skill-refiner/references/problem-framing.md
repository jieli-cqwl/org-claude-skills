# 问题定义卡

按需读取本文件，用于把“感觉不对”转成可执行的 Skill 精修判断。

## 判断顺序

1. 先问该内容服务哪个专业职责动作。
2. 再问它映射到 `Skill质量标准.md` 的哪个 G/S/E 维度。
3. 再问哪个文件、字段、脚本、测试或下游流程会消费它。
4. 再问候选信号是否被真实流程和消费者关系支持。
5. 最后判断它应删除、迁移、改写、脚本化、测试化，还是停下确认。

## 问题定义卡

每轮改造前写一张卡：

```text
环节：
质量维度：
裁决层级：
现象：
为什么是问题：
影响对象：
证据定位：
目标形态：
改动范围：
验证方式：
候选信号来源：
停手条件：
```

字段口径：

- 环节：从 Trigger、Responsibility、Input、Flow、Output、Resource、Determinism、Eval、Cleanup、Runtime 中选择。
- 质量维度：使用当前质量标准中的 G0-G2、S1-S8 或 E1-E5。
- 裁决层级：Portable core、First-party hardening 或 Production evidence。
- 现象：可定位到文件、段落、字段、测试或运行链路。
- 为什么是问题：说明它怎样破坏真实办事流程、消费关系、验证或 token 理解。
- 影响对象：Agent、用户、下游 Skill、hook、测试、installer、runtime 或 reviewer。
- 证据定位：优先写单个 repo-local `file:line`；多处证据放到说明里。
- 目标形态：改完后应呈现的职责、顺序、载体和证据。
- 改动范围：本轮会改哪些文件；不写泛化重构范围。
- 验证方式：能证明本轮目标的当前输出、可复查产物、command、静态检查、JSON 校验、测试或人工复核点。
- 候选信号来源：用户反馈、静态 checker、只读 finding、旧测试、引用扫描或运行面证据；静态信号必须复核后才能采纳。
- 停手条件：出现不确定消费者、active runtime 风险或目标冲突时停止。

## 决策表

| 发现 | 决策 |
| --- | --- |
| 无消费者字段、段落或模板 | 删除 |
| 专业方法论过长但会按需使用 | 迁移到 `references/` |
| 确定性检查由文字提醒 LLM 执行 | 迁移到 `scripts/`、schema、hook 或测试 |
| 机器字段在 `SKILL.md` 重复定义 | 迁移到 schema/template，并在 SOP 中只给消费路径 |
| 旧测试只验证旧噪音 | 更新或删除测试 |
| 下游消费者仍依赖旧字段 | 先同步消费者或停下确认 |
| 只是表达偏好，无法证明影响 | 不改 |
| 触及专业职责边界变化 | 停下与用户对齐 |

## 反问

出现以下情况，先停：

- 目标只能表达成“更好看”“更完整”“更像标准”，但没有消费或验证。
- 改动会改变 Skill 的专业职责域。
- 删除内容可能破坏 active hook、installer、catalog、eval 或下游文档。
- 用户反馈和仓库 rules 冲突。
