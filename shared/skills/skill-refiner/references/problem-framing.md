# 问题定义卡

用于把"感觉不对"转成可执行的 Skill 改造判断。

## 判断顺序

1. 为什么是下一刀——它是否比其他候选更直接提升用户成功标准。
2. 服务哪个职责——该内容服务哪个专业职责动作。
3. 谁消费它——哪个文件、字段、脚本、测试或下游流程会消费它。
4. 怎么处理——应删除、迁移、改写、脚本化、测试化，还是停下确认。

## 问题定义卡

每个有问题的维度写一张卡：

```text
现象：
为什么是问题：
目标形态：
改动范围：
验证方式：
停手条件：
```

字段口径：

- 现象：可定位到文件、段落、字段、测试或运行链路。
- 为什么是问题：写出它怎样破坏真实办事流程、消费关系、验证或 token 理解。
- 目标形态：改完后应呈现的职责、顺序、载体和证据。
- 改动范围：本轮会改哪些文件；不写泛化重构范围。
- 验证方式：能证明本轮目标的 command、静态检查、JSON 校验、测试或人工复核点。
- 停手条件：出现不确定消费者、active runtime 风险或目标冲突时停止。

## 决策表

| 发现 | 决策 |
| --- | --- |
| 无消费者字段、段落或模板 | 删除 |
| 专业方法论过长但会被流程步骤使用 | 迁移到 `references/` |
| 确定性检查由文字提醒 LLM 执行 | 迁移到 `scripts/`、schema、hook 或测试 |
| 机器字段在 `SKILL.md` 重复定义 | 迁移到 schema/template，SOP 只给消费路径 |
| 旧测试只验证旧噪音 | 更新或删除测试 |
| 下游消费者仍依赖旧字段 | 把消费者纳入同一候选策略，最终操作留到策略制定，或停下确认 |
| 只是表达偏好，无法证明影响 | 不改 |
| 触及专业职责边界变化 | 停下与用户对齐 |

## 反问

出现以下情况，先停：

- 目标只能表达成"更好看""更完整""更像标准"，但没有消费或验证。
- 无法说明为什么本轮优先级高于其他候选缺口。
- 改动会改变 Skill 的专业职责域。
- 删除内容可能破坏 active hook、installer、catalog、eval 或下游文档。
- 用户反馈和仓库 rules 冲突。
