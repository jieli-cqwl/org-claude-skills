# Skill 精修关键假设验证协议

## 关键假设验证协议

共创的目标是让 Agent 基于已闭合事实给出专业默认判断，并只暴露一个会改变下一步判断的关键假设。

回复前读取当前步骤声明的 reference、`refinement-ledger.json` 中的最新 checkpoint，以及当前步骤已闭合结论。只使用这些材料生成本轮草案；缺少会改变结论的事实时，停在当前步骤验证假设。

## 最小决策包

每个全共创或草案修正暂停点，对用户只输出最小决策包：

- 已闭合事实：当前已经确认、可以作为本步输入的事实。
- 推荐理解：基于已闭合事实的默认专业理解或推荐结论草案。
- 关键假设：只写一个不成立就会改变推荐理解、写入结果、候选策略、验证口径或最终操作的事实。
- 用户动作：请用户确认该假设或给出替换事实；不要求用户选择方法论。

确认卡只是最小决策包的一种表现形式；不得把卡片名称当成流程合同。schema key、ledger 字段和 rubric 字段不得作为用户侧标题，只能写入 `refinement-ledger.json`、`skill-refiner-result.json`、schema、validator、eval 或测试。

## 模式差异

| 模式 | 行为 |
| --- | --- |
| 静默 | 读取、盘点和归纳候选线索；不替用户裁决目标、边界、策略或最终操作。 |
| 全共创 | 从已闭合事实生成推荐理解，验证一个会改变结论的关键假设；回应前不形成最终结论。 |
| 草案修正 | 基于已有草案重写不确定部分；同一轮只处理当前步骤一个会改变结论的事实缺口。 |
| 静默后汇报 | 先验证，再按成功标准报告通过、阻塞、残留风险和下一步。 |

## 用户回应处理

- 回应支撑关键假设时，把推荐理解写入当前步骤 checkpoint，再进入下一步。
- 回应替换当前步骤事实时，重写当前步骤最小决策包并再次验证关键假设。
- 回应替换已闭合上游事实时，回到拥有该事实的步骤重新闭合，再继续后续步骤。
- 回应包含多个事实时，只处理会影响当前步骤结论的事实；其他事实登记为后续步骤候选线索。
- 回应触发目标 Skill 文件、测试、runtime、引用或文档入口改动时，SR-F1 前只登记候选，不执行改动。

## 步骤映射

| 步骤 | 用户侧最小决策包关注点 | 内部写入 |
| --- | --- | --- |
| SR-S2 入口基线 | 真实场景、业务约束、想看到的变化线索、观察到的不适、要保留的能力、候选切入点、承载和待确认事实。 | `current_state.baseline` 与 `co_created_baseline` 字段。 |
| SR-S3 职责与真实流程 | 专业职责域、非目标、真实办事流程和可验证成功边界。 | 职责/流程 checkpoint。 |
| SR-R1~SR-R10 环节沉淀 | 本环节目标形态、保留能力、问题证据、候选策略、验证线索，以及是否需要用户裁决。 | 环节蓝图、来源、适用性、候选操作和证据。 |
| SR-F1 整体策略冻结 | 最终操作、执行范围、排除操作、风险和冻结前未裁决冲突。 | `operation_card`、最终操作和冻结依据。 |
| SR-V1 验收与交付 | 成功标准、fresh proving command、通过/阻塞、残留风险和下一轮候选。 | `skill-refiner-result.json` 与验证证据。 |

## 回退触发

- SR-S2 出现根因、最终成功标准、最终操作或环节策略时，回到入口事实表达。
- SR-S3 职责只能用文件结构、runtime 术语或工具动作解释时，重写为专业职责和真实流程。
- SR-R 环节无法说明消费者、质量维度、证据或验证方式时，只登记候选缺口，不进入 SR-F1。
- 用户事实改变已闭合入口基线、职责边界或不可丢能力时，记录 supersedes 候选并停下裁决。
- SR-F1 未收到明确 `整体策略确认` 时，不得进入执行。
