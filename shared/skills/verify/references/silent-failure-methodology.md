# 静默失败检测方法论

## 5 步系统检查

### Step 1: 识别错误处理代码

扫描变更文件中的所有错误处理结构：
- `try/catch` 块
- `.catch()` Promise 处理
- `if (error)` 条件分支
- 错误回调函数
- `on('error')` 事件监听

输出：错误处理点清单（file:line + 类型）

### Step 2: 审查每个处理器

对每个错误处理点逐一检查：

| 检查项 | PASS 标准 |
|--------|---------|
| 错误是否被消费 | 至少：重新抛出 / 返回错误结果 / 记录并通知 |
| catch 粒度 | 仅捕获预期的错误类型，不捕获所有 |
| 错误信息保留 | 原始错误信息/堆栈是否被保留（不丢弃） |
| 降级行为是否合理 | 降级返回值是否对调用方安全 |
| 日志级别 | error 用 error 级别，warning 用 warn 级别 |

### Step 3: 检查错误消息质量

| 检查项 | PASS 标准 |
|--------|---------|
| 可操作性 | 消息是否告诉用户/开发者下一步该做什么 |
| 上下文 | 消息是否包含操作名称 + 输入上下文 |
| 用户友好 | 用户面消息是否避免技术术语 |
| 开发者友好 | 日志是否包含足够排查信息（参数值、状态） |
| 唯一性 | 相同消息是否出现在多处（导致排查困难） |

### Step 4: 检查隐藏失败模式

| 模式 | 表现 | 危害 |
|------|------|------|
| 空 catch | `catch(e) {}` | 错误完全消失 |
| 仅 log 继续 | `catch(e) { log(e); }` 然后正常返回 | 调用方不知道失败 |
| 返回默认值无 log | `catch(e) { return []; }` | 错误无痕迹 |
| 可选链静默跳过 | `data?.items?.map(...)` 中 data 为 null | 整个操作被跳过 |
| 重试耗尽无通知 | 重试 3 次后静默返回 null | 用户无感知等待 |
| Promise 未 catch | `async` 函数调用未 await/catch | unhandled rejection |
| 事件监听无 error handler | EventEmitter 无 'error' 监听 | 进程崩溃 |
| 条件赋值隐藏错误 | `const val = riskyCall() || defaultVal` | 错误被默认值掩盖 |

### Step 5: 验证项目标准

| 检查项 | 标准 |
|--------|------|
| 一致性 | 新代码的错误处理模式与项目既有模式一致 |
| 框架规范 | 是否使用框架提供的错误处理机制 |
| 全局兜底 | 是否有 uncaughtException/unhandledRejection 处理 |

## 严重度评级

| 级别 | 标准 | 示例 |
|------|------|------|
| Critical | 数据丢失/损坏/安全漏洞 | 空 catch 吞掉写入错误 |
| Major | 功能静默失败，用户无反馈 | API 调用失败但返回空数据 |
| Minor | 信息丢失但功能不受影响 | 非关键日志缺失 |
