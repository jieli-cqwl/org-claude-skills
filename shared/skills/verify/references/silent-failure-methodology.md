# 静默失败审查口径

## 目标

Phase2B 用本文件判断失败是否会被吞掉、隐藏或伪装成成功。

## 裁决顺序

1. 列出变更文件中的失败入口：外部调用、文件 IO、网络、数据库、异步任务、事件监听和解析逻辑。
2. 读取每个失败入口的处理路径：抛出、返回错误、用户提示、日志和清理动作。
3. 反证调用方能否感知失败：失败后是否还能继续返回成功状态。
4. 给出 `file:line`、失败影响和 owner。

## ISSUE 信号

| 信号 | 为什么是问题 |
| --- | --- |
| 空 catch / 裸 except | 错误完全消失，调用方无法处理。 |
| catch 中只 log 后继续成功返回 | 日志不是错误传播，用户仍看到成功。 |
| 失败后返回空数组、默认对象或 null 且无错误状态 | 数据缺失被伪装成合法结果。 |
| Promise 未 await / 未 catch | 异步失败脱离当前流程。 |
| 重试耗尽无通知 | 系统已失败，但用户和上游无法感知。 |
| 可选链或 `|| default` 跳过关键数据缺失 | 输入异常被当成正常空值。 |
| 外部调用无超时 | 验收无法证明失败路径可控。 |

## PASS 要求

- 预期失败有明确错误状态、异常、返回值或用户可理解提示。
- 原始错误信息被保留给排查链路，但用户面不暴露敏感内部细节。
- 清理、回滚、重试耗尽和超时都有可观察结果。
- 结论直接引用代码位置和对应风险。
