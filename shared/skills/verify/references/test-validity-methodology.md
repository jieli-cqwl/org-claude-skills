# 测试有效性判定口径

## 目标

Phase2C 用本文件判断测试是否证明 AC 行为，而不是只证明代码被执行过。

## 裁决顺序

1. 从 AC 和 test_ref 提取应证明的行为、边界、错误路径和副作用。
2. 读取测试断言，确认断言对象是外部可观察结果。
3. 读取实现，反证测试是否只是复制内部逻辑或固定样本。
4. 标出未覆盖行为和脆弱断言。

## PASS 标准

- 每条 AC 至少有一个行为断言。
- 边界值、错误路径或排除项有对应测试，或有明确不适用理由。
- 重构内部实现但保持行为不变时，测试应继续通过。
- 测试失败能指向具体行为缺口，而不是泛化失败。

## ISSUE 信号

| 信号 | 为什么是问题 |
| --- | --- |
| 只检查行覆盖、快照或命令退出码 | 不能证明业务行为正确。 |
| 断言函数调用次数、内部状态或私有方法 | 锁死实现，不能保护用户行为。 |
| `expect(true).toBe(true)`、无断言或只断言非空 | 无行为证明。 |
| 只测 happy path | 错误路径和边界仍可能失败。 |
| 测试 expected 与实现硬编码一致 | 可能是镜像测试或伪通过。 |

## 验收输出

每个缺口写明 AC / test_ref、缺失行为、现有测试位置和需要补的证明方式。
