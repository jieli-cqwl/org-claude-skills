# 对话指南

## 深度路由

| 深度 | 触发信号 | 行为 |
|------|---------|------|
| 快速收敛 | 边界清晰、功能点 <= 2、用户已充分分析 | 1-2 轮确认后输出 |
| 标准探索 | 一般业务需求、有待确认项 | 逐项确认追问 |
| 深度探索 | 跨模块、隐含假设多、描述方案而非问题 | 挑战假设，方案探索 |

动态升级：追问中发现复杂度升级时提升深度。用户催促时简化非关键问题，但不跳过影响验收正确性的追问。

## 对话节奏

- 每条消息只问一个问题，先复述理解再追问
- 多选题优先，开放提问仅用于选项无法覆盖时
- 用自然对话，不用编号+粗体标签列表

## 沟通风格

先说已知再问未知，用自然语言而非结构化模板。

## 深入信号

| 信号 | 追问方向 |
|------|---------|
| "竞品有这个功能" | 我们的用户也遇到同样问题吗？ |
| "老板/客户说要做" | 遇到了什么具体问题？ |
| 描述方案而非问题 | 希望解决什么问题？ |
| "应该很简单" | 预期的具体行为是什么？ |
| "顺便加个 X" | 去掉 X 核心问题还能解决吗？ |

## 问题框架启发（极度模糊时）

当用户无法明确问题时（如"XX 需要改善"），提出 2-3 个不同的问题框架供选择：
- 不是解决方案，而是看问题的不同视角
- 每个框架用一句话描述痛点 + 一个具体场景

示例：
用户："权限系统需要改善"
→ "权限改善可以从几个角度理解：
   A. 管理员配置权限太复杂（如：每次加新角色要改 5 个配置）
   B. 用户被错误拒绝或错误放行（如：应有权限的用户被 403）
   C. 审计追踪不够（如：出问题后无法追溯谁改了什么权限）
   哪个最接近你的痛点？"

触发条件：用户描述极度模糊（无具体痛点、无具体场景、无具体期望），且第一性原理第 1 步（剥离方案回到问题）无法获得有效信息时使用。

## 追问策略（第一性原理 4 步）

1. 剥离方案回到问题 — 解决什么问题？现在怎么处理？
2. 定位根本问题 — 背后原因？不做最坏结果？
3. 最简方案 — 最少需要做什么？
4. 复杂度验证 — 额外复杂度的价值？

## UNIT 拆分校验问句

- 这是同一个闭环功能，还是两个功能被写在一起？
- 去掉这个功能后，根问题是否仍能成立？
- 这个规则是当前 UNIT 的边界，还是另一个 UNIT 的职责？

## UNIT 拆分正反例

### 反例 1：多功能混合

差：UNIT-001: 用户管理（含注册、登录、修改密码、注销）
好：拆为 4 个 UNIT——注册、登录、修改密码、注销。每个有独立的输入→行为→结果闭环。
原因：混合 UNIT 导致验收标准膨胀、优先级无法独立判断、下游 Task 粒度失控。

### 反例 2：主题式 UNIT

差：UNIT-002: 权限体系梳理
好：UNIT-002: 角色权限校验（请求接口时校验当前用户角色是否有权限 → 有权放行/无权返回 403）
原因："梳理"是分析活动不是功能。UNIT 标题必须是可实现的功能名。

### 反例 3：过细拆分

差：UNIT-003: 显示用户名；UNIT-004: 显示用户邮箱；UNIT-005: 显示用户头像
好：UNIT-003: 用户信息展示（个人中心页加载用户信息 → 展示姓名/邮箱/头像）
原因：三个 UNIT 共享同一数据源和触发条件，不构成独立闭环。拆得过细增加管理开销且下游无法独立交付。

## 共创模式

每个步骤按标注的模式执行，禁止跳过暂停点。

### 全共创（S2, S3, G1, S12）

1. 呈现当前步骤的发现/分析
2. 提出一个问题（优先选择题，2-3 选项 + 推荐标注）
3. 暂停，等待用户回应
4. 复述用户回应，确认理解一致
5. 记录到共创摘要（关键提问 + 用户回应 + 对产品的影响）
6. 进入下一步

### 草案修正（S4, S5, S8, S6, S7）

1. 输出该步骤的草案
2. 用 `[?]` 标注待确认项（每项附简短说明为什么需要确认）
3. 暂停，等待用户修正
4. 接受用户修正，复述变更点
5. 记录到共创摘要（关键待确认项 + 用户修正 + 对产品的影响）

`[?]` 标注格式：`[?] 术语"活跃用户"的定义是否为"7 日内有登录行为"？`

### 条件共创（S9, S10）

1. 自主执行该步骤
2. 无问题 → 直接继续，不暂停
3. 发现问题/不确定项 → 暂停追问用户
4. 追问触发条件：
   - 发现 PRD 内部矛盾
   - 发现遗漏的异常路径或边界条件
   - 待设计决策的业务约束不明确

## 中途插问处理

1. 用户在当前步骤中途插问时，先判断该问题属于当前问题澄清、临时岔题、流程改道，还是结束请求。
2. 属于当前问题澄清时，直接回答，当前步骤保持不变；回答末尾必须明确“当前仍停留在本步骤，下面继续当前问题”。
3. 属于临时岔题时，先用最小必要信息回答，不推进主流程；回答后回到当前步骤继续收口。
4. 属于流程改道或结束请求时，停止当前流程推进，明确说明冲突点，等待用户裁决后再继续或终止。
5. 未经用户显式确认，禁止因为中途插问自动进入交付、完成或下一阶段。
