# Phase 拆分指南

> 一句话原则：Phase 是交付节奏的载体，基于范围和交付价值切分，而非 UNIT 计数。

## 切分原则

Phase 切分发生在 S8（交付节奏决策），此时尚无 UNIT。决策依据是 S5 收口的范围产出：

1. **价值独立性**：每个 Phase 必须交付用户/业务可感知的独立价值
2. **范围自包含**：每个 Phase 的范围边界清晰，不依赖后续 Phase 才能交付价值
3. **渐进交付**：先交付核心价值（MVP 闭环），再交付增强和扩展
4. **默认单 Phase**：除非存在明确的切分信号，否则使用单 Phase（phase-1/）

## 信号识别

以下信号提示应考虑多 Phase 切分：

| 信号 | 说明 | 示例 |
|------|------|------|
| 独立价值层次 | 范围中存在"核心 + 增强"或"基础 + 高级"层次 | 基础搜索 vs 高级筛选 |
| 用户反馈依赖 | 部分功能需要先上线收集反馈再决定后续方向 | 先 A/B 测试核心流程 |
| 外部依赖时序 | 部分范围依赖外部系统/团队的交付时间线 | 先做不依赖第三方的部分 |
| 风险隔离 | 高风险部分应与稳定部分分离，降低交付风险 | 新技术探索 vs 稳定迁移 |

**无信号时** → 单 Phase，不做多余切分。

## 校验规则（S6 后生效）

S6 完成 UNIT 拆解后，用以下规则校验 Phase 边界合理性：

| 校验项 | 规则 | 触发动作 |
|--------|------|----------|
| 空 Phase | Phase 内无 UNIT | 提示用户调整 Phase 边界 |
| UNIT 超限 | 单 Phase 超过 5 个 UNIT | 建议回到 S8 拆分该 Phase |
| 跨 Phase 硬依赖 | Phase N+1 的 UNIT 强依赖 Phase N 的未完成 UNIT | 调整分组，确保依赖在同 Phase 内闭合或上游先行 |

注：UNIT 计数是 S6 后的事后校验指标，不是 S8 的决策输入。

## 默认行为

- 单功能需求 → 单 Phase（phase-1/）
- 范围明确无分层 → 单 Phase
- 所有项目至少有一个 Phase（phase-1/）

## 目录创建

S8 完成时必须创建：
- 所有 `phase-{N}/` 物理目录
- 每个 `phase-{N}/prd.md` 骨架（含阶段目标、入口出口条件、UNIT 索引占位）

Brief 交付计划中必须明确列出所有 `phase-{N}/unit-{N}/` 工作区路径和 `phase-{N}/units/UNIT-{N}.md` 定义文件路径。

产物层级规则：
- `phase-{N}/` — Phase 级产物（design.md、plan.md、ADR）
- `phase-{N}/unit-{N}/` — UNIT 级执行产物（test-cases.md、dev-report.md）
- `phase-{N}/units/UNIT-{N}.md` — UNIT 定义文件

## 反模式

- 不要基于 UNIT 数量在 S8 做切分决策——S8 时还没有 UNIT
- 不要为了拆分而引入跨 Phase 硬依赖——如果拆分后 Phase 2 的范围强依赖 Phase 1 的未完成交付，说明分组不当
- 不要按"均匀分配"拆分——Phase 大小可以不均等，以价值边界为准
- 不要为没有独立交付价值的范围创建独立 Phase——合并到能交付价值的 Phase 中
