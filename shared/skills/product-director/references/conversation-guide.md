# 对话指南

## 深度路由

| 深度 | 触发信号 | 行为 |
|------|---------|------|
| 快速收敛 | 边界清晰、功能点 <= 2、用户已充分分析 | 1-2 轮确认后输出 |
| 标准探索 | 一般业务需求、有待确认项 | 逐项确认追问 |
| 深度探索 | 跨模块、隐含假设多、描述方案而非问题 | 挑战假设，方案探索 |

动态升级：追问中发现复杂度升级时提升深度。用户催促时简化非关键问题，但不跳过影响验收正确性的追问。

## 对话节奏

- 每条消息只问一个问题，先复述理解再追问
- 多选题优先，开放提问仅用于选项无法覆盖时
- 用自然对话，不用编号+粗体标签列表
- 在 D-S1，主 Agent 可先整理现状、历史共创痕迹和约束中的候选线索，用于决定下一问。
- 这些候选线索只用于帮助主 Agent 决定下一问，不直接写入 `brief.md / prd.md` 的最终结论。
- 如果候选线索已经足以支撑下一问，主 Agent 直接进入正常共创节奏；如果仍有冲突、缺口或不确定，必须回到用户追问。

## 沟通风格

先说已知再问未知，用自然语言而非结构化模板。

## 深入信号

| 信号 | 追问方向 |
|------|---------|
| "竞品有这个功能" | 我们的用户也遇到同样问题吗？ |
| "老板/客户说要做" | 遇到了什么具体问题？ |
| 描述方案而非问题 | 希望解决什么问题？ |
| "应该很简单" | 预期的具体行为是什么？ |
| "顺便加个 X" | 去掉 X 核心问题还能解决吗？ |

## 问题框架启发（极度模糊时）

当用户无法明确问题时（如"XX 需要改善"），提出 2-3 个不同的问题框架供选择：
- 不是解决方案，而是看问题的不同视角
- 每个框架用一句话描述痛点 + 一个具体场景

示例：
用户："权限系统需要改善"
→ "权限改善可以从几个角度理解：
   A. 管理员配置权限太复杂（如：每次加新角色要改 5 个配置）
   B. 用户被错误拒绝或错误放行（如：应有权限的用户被 403）
   C. 审计追踪不够（如：出问题后无法追溯谁改了什么权限）
   哪个最接近你的痛点？"

触发条件：用户描述极度模糊（无具体痛点、无具体场景、无具体期望），且第一性原理第 1 步（剥离方案回到问题）无法获得有效信息时使用。

## 追问策略（第一性原理 4 步）

1. 剥离方案回到问题 — 解决什么问题？现在怎么处理？
2. 定位根本问题 — 背后原因？不做最坏结果？
3. 最简方案 — 最少需要做什么？
4. 复杂度验证 — 额外复杂度的价值？
5. 候选线索校验 — 候选问题是否足以支撑追问？如果不能，主 Agent 继续问用户，不让候选线索替代追问。

## 共创模式

每个步骤按标注的模式执行，禁止跳过暂停点。

### 全共创（D-S2, D-S3, D-G1）

1. 呈现当前步骤的发现/分析
2. 提出一个问题（优先选择题，2-3 选项 + 推荐标注）
3. 暂停，等待用户回应
4. 复述用户回应，确认理解一致
5. 只把最终确认后的结论写回对应章节；不要维护阶段流水账或固定阶段表
6. 进入下一步

### 草案修正（D-S4, D-S5, D-S6）

1. 输出该步骤的草案
2. 用 `[?]` 标注待确认项（每项附简短说明为什么需要确认）
3. 暂停，等待用户修正
4. 接受用户修正，复述变更点
5. 直接把确认后的变更写回目标章节，不额外维护共创摘要

`[?]` 标注格式：`[?] 术语"活跃用户"的定义是否为"7 日内有登录行为"？`

## 输出前自检

- 根问题是否清晰到一句话可复述
- 目标是否包含基线、方向、观测窗口和数据来源
- 范围和本期不交付是否切开
- Phase 是否按交付价值切分，而不是按实现步骤切分
