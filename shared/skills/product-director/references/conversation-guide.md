# 关键假设验证协议

## 共创回合协议

- 回复前读取当前步骤 reference、已闭合 checkpoint 和静默扫描候选线索。
- 第一段用一句话复述当前步骤的已闭合事实和本轮目标。
- 第二段给一个推荐结论草案；草案包含推荐结论、推荐理由和会改变结论的未闭合业务假设。
- 只有业务事实会改变根问题、成功标准、范围、风险或 Phase 拆法时，才列出 2-3 个业务场景分支；每个分支包含触发条件和默认推荐。
- 最后一段只暴露一个会改变写入结果的假设：默认写入 X，依赖事实 Y；若 Y 不成立，只接收替换事实，不要求用户选择方法。
- 发出关键假设验证后暂停；业务事实回应前不写最终 `brief.json / phase-prd.json` 结论。

## 业务事实回应处理

- 回应中的业务事实支撑关键假设时，将推荐结论作为当前步骤结论写入 checkpoint，再进入下一步。
- 回应包含当前步骤替换事实时，重写当前步骤草案并再次按共创回合协议验证关键假设。
- 回应包含已闭合上游事实的替换事实时，回到该事实的拥有步骤重新闭合，再继续后续步骤。
- 回应接受默认路径时，继续使用默认推荐；只有会改变最终 JSON 正确性的关键假设仍未闭合时，按共创回合协议验证该假设。
- 回应包含多个事实时，只处理会影响当前步骤结论的事实；其余事实登记为后续步骤候选线索。
- 候选线索与回应事实冲突时，指出冲突来源，只暴露一个会改变结论的冲突事实。

## 模式差异

| 模式 | 行为 |
| --- | --- |
| 静默 | 收集候选线索、来源和冲突点；不输出对外问题；不形成最终结论。 |
| 全共创 | 从已闭合事实生成推荐结论草案，验证一个会改变结论的具体业务假设。 |
| 草案修正 | 基于已有草案重写不确定部分；用 `[?]` 标出未闭合事实；只处理当前步骤的一处关键事实缺口。 |
| 确认门 | 汇总已闭合字段、gate 命令和写入边界；只接受明确 gate 状态，不引入新业务事实。 |

## 深度路由

| 深度 | 触发条件 | 行为 |
| --- | --- | --- |
| 快速收敛 | 当前步骤必需事实已齐全，且没有来源冲突。 | 输出推荐结论草案；关键假设闭合后写 checkpoint。 |
| 标准探索 | 当前步骤存在 1-2 个未闭合业务事实。 | 每轮只验证一个会影响结论的事实。 |
| 深度探索 | 用户给的是方案、跨模块影响大、隐含假设多或来源冲突多。 | 先把方案改写为待验证问题，再确认根问题、成功标准、范围、风险或 Phase 影响。 |

要求加速时，保留会影响最终 JSON 正确性的关键假设验证，删掉不会改变结论的解释。

## 方案输入处理

- 用户先给方案时，先确认该方案要解决的业务问题和当前绕行方式。
- 用户要求增加能力时，先判断去掉该能力后核心问题是否仍能闭环。
- 用户要求按实现步骤拆分时，先改写为交付价值分支，再判断 Phase 边界。
- 用户使用模糊验收词时，改写为可观察结果；AC 细化交给 `/product-manager`。
- 静默扫描只能决定下一条关键假设；关键假设闭合前不作为最终业务事实。

## 确认门自检

- 根问题能用一句话复述。
- 用户画像包含角色、场景和当前绕行方式。
- 目标包含基线、方向、观测窗口和数据来源。
- Appetite 能限制下游方案复杂度。
- 范围和 Non-goals 已切开。
- 可行性约束、风险与未知项、决策理由已记录。
- Phase 按交付价值切分，且每个 Phase 有入口条件和出口条件。
