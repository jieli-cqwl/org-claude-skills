# 对话节奏

## 适用边界

- 本文件只规定每轮回应节奏和冻结前检查。
- 具体业务判断读取对应 reference；本文件只管节奏。
- 每轮只推进一个会改变结论的判断点。

## 每轮回应信息

每轮按需要覆盖以下信息；首次回应、步骤切换或事实复杂时按此顺序组织，简单确认可以压缩成短句。

1. **本轮对象**：首次回应或步骤切换时，一句话确认操作对象、边界和预期产物。
2. **线索状态**：仅在进入问题澄清且根问题、直接原因或用户画像未闭合时，说明静默信息收集只形成候选线索，不冻结根问题或用户画像。
3. **闭合事实**：一句话复述已确认事实，只写本轮结论依赖的信息。
4. **推荐草案**：给出默认结论草案，用可替换文本呈现。
5. **推荐理由**：说明草案为何由已闭合事实推出，只写决策依据。
6. **关键验证**：只验证一个会改变草案的业务事实，给出默认判断和替换口径。
7. **暂停等待**：发出验证后停止，不展开下一步。

回复前读取当前步骤 reference、已闭合检查点和静默扫描候选线索。用户只需确认、补充或替换关键事实。

本轮对象说明操作对象、边界和预期产物即可。

首次问题澄清时，`操作对象` 写待判断的问题域或受影响角色与场景，不直接复述未验证方案名。

未闭合问题澄清时，说明静默信息收集只记录线索与缺口，不冻结根问题或用户画像。

用户已明确闭合根问题、直接原因或用户画像时，不输出线索状态；把这些事实写入闭合事实。

待确认草案阶段不得写“冻结候选判断”或“冻结草案”；只能写“形成候选判断”。

推荐理由必须显式出现；不得只把理由隐含在范围、约束或草案字段中。

关键验证必须是单一可替换业务事实句。若有多个缺口，选择最会改变基线的一项，其余只列入门禁状态；不得把观测窗口、数据来源、timebox、总监确认或多个字段打包。

关键验证不得要求确认整份草案、总监冻结或多个字段打包；产品总监确认只在所有关键事实闭合后出现。

暂停等待必须明确只等待当前业务事实确认，不进入 PRD / UNIT / AC / 最终 JSON。

非 Director Finalization 阶段，写入门禁压缩为一句；不得展开 ledger、schema、hook 或 digest 细节。

## 用户回应处理

- 用户确认关键事实：纳入闭合事实，进入下一轮。
- 用户替换上游事实：回到该事实首次影响的步骤，重写闭合事实、推荐草案、推荐理由和关键验证。
- 用户一次给多条事实：先处理最会改变结论的一条，其余作为候选线索暂存。
- 用户给方案、能力清单或实现动作：改写成可确认事实或可观察结果，再进入每轮回应结构。

## 冻结前检查

- 基线闭合且收到明确 `产品总监确认` 后，才进入最终 JSON 写入。
- 冻结确认只核对闭合事实、写入边界和确认语句；写入前仍必须进入 `final-artifacts` gate。
- 基线事实被替换或产品总监未确认时，回到对应步骤继续对话。

## 输出约束

- 中文短句，句句服务执行判断。
- 正向推荐优先；每条限制必须对应当前门槛或失败条件。
- 每句提供判断、动作或门槛。
- 使用普通中文条目；提到协作角色时写“产品经理同事”。
