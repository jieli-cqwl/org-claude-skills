# 对话策略

## 核心原则

- 你主导方法推荐和结论草案，用户聚焦业务事实和业务判断。
- 每轮只推进一个决策点：一个关键假设、一个方案选择或一处事实缺口。
- 先给推荐再验证，用户只需确认或补充业务事实。

## 每轮对话节奏

每轮回复按三个意图组织：

1. **定位**：一句话复述当前步骤已闭合事实和本轮目标。
2. **推进**：根据当前步骤的回应方式选择行动——
   - 关键假设确认：给推荐结论草案（推荐结论 + 推荐理由 + 未闭合假设）
   - 方案探索：先给推荐方案和理由，再给 1-2 个备选方案及权衡
   - 业务草案确认：基于已有草案重写不确定部分，用 `[?]` 标出未闭合事实
   - 业务事实存在真实分叉且会改变根问题、成功标准、范围、风险或 Phase 拆法时，列出 2-3 个业务场景分支（触发条件 + 默认推荐）
3. **验证**：指出一个会改变结论的关键假设，说明默认判断和依据；用户只需确认或给出替换事实。

回复前读取当前步骤 reference、已闭合 checkpoint 和静默扫描候选线索。发出假设验证后暂停，等待用户回应。

## 回应方式

| 回应方式 | 行为 |
| --- | --- |
| 静默扫描 | 收集候选线索、来源和冲突点；不输出对外问题；不形成最终结论。 |
| 关键假设确认 | 从已闭合事实生成推荐结论草案，验证一个会改变结论的具体业务假设。 |
| 业务草案确认 | 基于已有草案重写不确定部分；用 `[?]` 标出未闭合事实；只处理当前步骤的一处关键事实缺口。 |
| 冻结确认 | 汇总已闭合字段、gate 命令和写入边界；只接受明确 gate 状态，不引入新业务事实。 |
| 方案探索 | 当前步骤有多个可行产品/业务路径且选择会改变范围、Phase 或成功标准时激活；先给推荐方案和理由，再给 1-2 个备选方案及权衡；用户选定方向后回到关键假设确认继续推进。 |

## 方案探索

### 触发条件

当前步骤存在 2 个以上可行的产品/业务路径，且路径选择会实质影响范围、Phase 拆法或成功标准时，从关键假设确认切换为方案探索。

### 输出结构

1. 一句话复述当前步骤已闭合事实和本轮目标
2. 推荐方案：方案内容 + 推荐理由
3. 1-2 个备选方案：每个包含优势、代价和适用条件
4. 一句话邀请用户基于业务判断选择或补充

### 用户回应处理

- 用户选定方案：将选定方案作为当前步骤方向，回到关键假设确认验证具体事实
- 用户提出新方案或组合：把新信息纳入后重写方案探索
- 用户要求加速：保留推荐方案，跳过备选方案展示，直接进入关键假设确认

## 用户输入处理

- 用户先给方案时，先确认该方案要解决的业务问题和现有处理方式。
- 用户要求增加能力时，先判断去掉该能力后核心问题是否仍能闭环。
- 用户要求按实现步骤拆分时，先改写为交付价值分支，再判断 Phase 边界。
- 用户使用模糊验收词时，改写为可观察结果；AC 细化交给 `/product-manager`。
- 用户给的是方案、跨模块影响大或隐含假设多时，先把方案改写为待验证的业务问题，再逐个确认根问题、成功标准、范围、风险或 Phase 影响。

## 业务事实回应处理

- 业务事实支撑关键假设时，将推荐结论写入 checkpoint，进入下一步。
- 回应包含当前步骤替换事实时，重写草案并再次验证关键假设。
- 回应包含已闭合上游事实的替换事实时，回到闭合该事实的步骤重新验证。
- 回应接受默认路径时，继续使用默认推荐；仍有影响结论正确性的假设未闭合时，继续验证。
- 回应包含多个事实时，只处理会影响当前步骤结论的事实；其余登记为后续步骤候选线索。
- 候选线索与回应事实冲突时，指出冲突来源，只提出一个会改变结论的冲突事实。
- 要求加速时，保留影响结论正确性的假设验证，删掉不会改变结论的解释。
