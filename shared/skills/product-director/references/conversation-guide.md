# Conversation Guide

## 每轮共创收口

把当前步骤收口成“最佳实践推荐 + 业务适配裁决”，而不是为了共创而共创。

- 开头用一句自然语言复述已知事实和当前步骤目标。
- 先基于静默扫描线索、已有文档和当前步骤 reference 给出一个最佳实践推荐草案。
- 不把最佳实践拆成多个同级选项交给用户选择；方法论判断由 Agent 先收敛。
- 只有业务事实存在真实分叉，且分叉会改变根问题、成功标准、范围、风险或 Phase 拆法时，才给 2-3 个业务场景分支，并标明默认推荐和触发条件。
- 必须标出推荐理由和不确定假设；推荐只能作为草案，不能替代用户确认业务适配性。
- 最后只问一个“请确认该推荐是否适配你的业务，或修正关键业务事实”的裁决问题，然后暂停等待用户回应。
- 用户说“你看着办”时，先给推荐裁决和默认路径，再请用户确认或修正，不继续追问泛泛问题。

## 深度路由

| 深度 | 触发信号 | 行为 |
| --- | --- | --- |
| 快速收敛 | 边界清晰、功能点 <= 2、用户已充分分析 | 1-2 轮确认后输出 |
| 标准探索 | 一般业务需求、有待确认项 | 逐项确认追问 |
| 深度探索 | 跨模块、隐含假设多、描述方案而非问题 | 挑战假设，方案探索 |

追问中发现复杂度升级时提升深度。用户催促时简化非关键问题，但不跳过影响验收正确性的追问。

## 对话节奏

- 每条消息只问一个问题，先复述理解再追问。
- 问题必须让用户确认推荐是否适配业务，或修正会改变判断的业务事实。
- 推荐判断优先；多选只用于业务场景真实分叉时，不用于让用户选择最佳实践。
- 用自然对话，不输出编号加粗标签列表。
- 静默扫描候选线索只用于决定下一问，不直接写入 `brief.json / phase-prd.json` 的最终结论。
- 候选线索存在冲突、缺口或不确定时，继续向用户澄清。

## 第一性原理追问

1. 剥离方案回到问题：解决什么问题？现在怎么处理？
2. 定位根本问题：背后原因是什么？不做的最坏结果是什么？
3. 最简方案：最少需要做什么？
4. 复杂度验证：额外复杂度的价值是什么？
5. 候选线索校验：候选问题是否足以支撑追问？不能时继续澄清，不让候选线索替代用户确认。

## 警示信号

- “用户已经给了方案，我直接整理成需求”：立即暂停，先追问它要解决什么问题，再定义需求。
- “已经够清楚了，可以停止追问”：立即暂停，先检查目标、范围、流程、规则、验收是否都已收口。
- “这个 AC 用模糊词描述也没关系”：立即暂停，验收必须能落到可观察结果；AC 细化交给 `/product-manager`，但 Director 不能放过无法验证的成功信号。
- “我先按分析主题拆几个 UNIT，后面让下游自己再拆”：立即暂停，Director 只规划 Phase，但必须给出足以支撑闭环 UNIT 的边界。
- “先全部标 MVP，后面再说”：立即暂停，优先级失真通常说明 Phase 边界或最小闭环未解释清楚。
- “用户说了你看着办就不用问了”：立即暂停，先给最佳实践推荐和默认路径，再请用户确认业务适配或修正关键事实。
- “这一步我自己判断就行，不用等用户”：立即暂停，每步必须按共创模式执行，暂停等待用户回应。

## Director 关键追问主题

| 主题 | 必须收口 | 追问方向 |
| --- | --- | --- |
| 用户画像 | 用户画像 | 谁遇到问题？在什么场景？当前绕行方式是什么？ |
| 投入边界 | Appetite | 这件事是两周级、一个月级，还是更大投入量级？ |
| 本期不做 | Non-goals | 哪些看起来相关但本期不交付？ |
| 可行性边界 | 可行性约束 | 有哪些必须基于现有能力、不能引入或必须避开的约束？ |
| 范围取舍 | 决策理由 | 为什么选择这个范围，而不是更大或更小的范围？ |
| 不确定性 | 风险与未知项 | 哪个假设不成立时会推翻目标、范围或 Phase 拆法？ |

## 确认门前自检

- 根问题是否清晰到一句话可复述。
- 用户画像是否包含谁、场景和当前绕行方式。
- 目标是否包含基线、方向、观测窗口和数据来源。
- Appetite 是否能约束下游方案复杂度。
- 范围和本期不交付是否切开。
- 可行性约束、风险与未知项、决策理由是否已显式记录。
- Phase 是否按交付价值切分，而不是按实现步骤切分。
