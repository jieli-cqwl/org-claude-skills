# 问题澄清

- 把用户输入的方案、诉求或模糊问题，收口为可验证的根问题、直接原因和用户画像。
- 你负责提出推荐判断，用户负责确认或替换业务事实。先给推荐根问题，再请用户确认一个会改变判断的关键事实。
- 只有受影响角色、触发场景、当前处理方式、现实代价和直接原因明确后，才进入目标、成功标准或范围判断。
- 静默信息收集候选线索只用于形成推荐判断和待验证事实；不得把候选线索、推测或冲突信息写成已闭合结论。
- 方案词、技术词较重或候选根问题冲突时，召集 agent teams 分别从受影响角色、触发场景、当前处理方式、现实代价、直接原因维度交叉取证；子 Agent 只返回证据与缺口，不写根问题结论。取证返回后，主 Agent 直接进入正常共创节奏：给出推荐判断、推荐理由和一个待验证事实。

## 先还原真实问题

- 受影响角色：承担成本、风险或结果的人。
- 触发场景：触发事件、发生时机和频率线索。
- 当前处理方式：系统处理、人工处理、沟通、表格、脚本、绕过、延迟或暂不处理。
- 现实代价：可观察的时间、错误、等待、风险、返工、机会损失或协作成本。
- 直接原因：当前处理方式为什么导致现实代价。

根问题使用这个结构：

`谁在什么场景下，因为当前什么处理机制，承受了什么现实代价。`

## 方案先行第一轮输出

当用户先给方案、竞品功能或实现形态，例如配置中心、角色树、批量授权、自动化、dashboard、平台化时，第一轮不要裸问“谁来配置”或展开功能设计。先把方案当作线索，给出可被用户纠偏的推荐投影，再只问一个会改变根问题判断的事实。

- 方案线索：列出用户给出的方案词，并说明它们只是线索。
- 推荐根问题：用 `谁在什么场景下，因为当前什么处理机制，承受了什么现实代价。` 给出当前推荐判断。
- 事实状态表：覆盖 `受影响角色 / 触发场景 / 当前处理方式 / 现实代价 / 直接原因`，状态只能是 `用户已确认 / 推测 / 冲突 / 缺失`。
- 推荐理由：说明为什么先验证根问题，而不是顺着方案进入功能、权限模型或实现细节。
- 只问一个会改变根问题判断的事实：优先追问具体用户、触发场景、当前处理方式、损失或风险；不要只问配置对象、角色树层级或由谁操作。

## 没闭合就留在问题澄清

- 缺少受影响角色、触发场景、当前处理方式或现实代价时，停在问题澄清。
- 停下时每轮只请求用户确认一个事实。这个事实必须能改变根问题、直接原因或用户画像。
- 候选线索存在冲突时，必须验证冲突事实；冲突闭合后再继续推荐判断。
- 输入过于模糊，且现有材料无法还原具体角色、场景或代价时，给 2-3 个可能业务痛点方向用于校准；每个方向只写一句痛点、一个具体场景和默认判断。
- 以下输入通常只是线索，不直接写成根问题：想做自动化、竞品有这个功能、老板要求、体验不好、效率低、技术上应该重构、需要一个 dashboard。遇到这些线索时，回到受影响角色、触发场景、当前处理方式和现实代价。

## 技术诉求先还原业务影响

- 遇到重构、升级、性能、稳定性、平台化或研发效率诉求时，先把 HOW 表述改写成 WHY 层判断：
`因为当前处理机制或技术约束，导致业务影响、交付约束、风险或效率代价。`

- 本步骤只闭合业务影响/现实代价、当前处理机制和直接原因；成功标准、投入边界和本期范围在后续步骤分别闭合。任一前置事实缺失时，只给待验证判断并请求用户确认。
- 本步骤只请求用户确认 WHY 层问题定性、业务/交付约束、风险和 Phase 影响；不得确认架构、接口、模块拆分、代码组织或实现计划。
