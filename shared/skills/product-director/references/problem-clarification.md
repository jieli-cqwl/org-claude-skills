# Problem Clarification

## 主导共创

问题澄清的目标是把静默信息收集候选线索转成用户确认的根问题、直接原因和用户画像。先给问题框架或 2-3 个选项，标出推荐和理由，再只问一个“请确认/选择/修正”的问题。

静默信息收集候选线索只用于决定下一问，不直接写入 `brief.json / phase-prd.json` 的最终结论。候选线索足以支撑下一问时，主 Agent 直接进入正常共创节奏；候选线索存在冲突、缺口或不确定时，必须回到用户追问。

## 用户画像与当前绕行方式

根问题必须落到具体人群和真实场景：

- 谁遇到这个问题：角色、权限或业务责任。
- 在什么场景发生：触发时机、业务流程和频率。
- 当前绕行方式是什么：手工补救、额外沟通、线下表格或临时脚本。
- 绕行方式的代价是什么：时间、错误率、风险或客户体验。

核心问句：谁现在用什么绕行方式撑着这个问题？

## 问题框架启发

当用户描述极度模糊，且无法从现有材料得到具体痛点、场景或期望时，给 2-3 个问题框架供选择。每个框架只写一句痛点和一个具体场景。

示例：权限系统需要改善时，可给出管理员配置复杂、用户被错误拒绝或放行、审计追踪不足三个框架，让用户选择最接近的痛点。

## 深入信号

| 信号 | 追问方向 |
| --- | --- |
| 竞品有这个功能 | 我们的用户是否遇到同样问题 |
| 老板或客户说要做 | 对方遇到了什么具体问题 |
| 用户描述方案而非问题 | 这个方案要解决什么问题 |
| 应该很简单 | 预期的具体行为是什么 |
| 顺便加一个能力 | 去掉它后核心问题是否还能解决 |

## 输出边界

用户确认后，只形成根问题、直接原因和用户画像 checkpoint。不得把候选线索、问题框架或未确认假设写成最终结论。
