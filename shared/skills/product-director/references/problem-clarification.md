# Problem Clarification

## 问题澄清共创形态

问题澄清的目标是把静默信息收集候选线索转成已闭合的根问题、直接原因和用户画像。先给一个推荐问题框架，标出推荐理由和会改变根问题判断的未闭合假设；只验证一个具体假设，例如：`我将把根问题写成 X，除非真实用户不是 Y；若 Y 不成立，给出替换事实。`

静默信息收集候选线索只用于决定下一条关键假设，不直接写入 `brief.json / phase-prd.json` 的最终结论。候选线索足以支撑关键假设验证时，主 Agent 直接进入正常共创节奏；候选线索存在冲突、缺口或不确定时，必须验证冲突事实。

## 用户画像与当前绕行方式

根问题必须落到具体人群和真实场景：

- 谁遇到这个问题：角色、权限或业务责任。
- 在什么场景发生：触发时机、业务流程和频率。
- 当前绕行方式是什么：手工补救、额外沟通、线下表格或临时脚本。
- 绕行方式的代价是什么：时间、错误率、风险或客户体验。

核心问句：谁现在用什么绕行方式撑着这个问题？

## 问题框架启发

当用户描述极度模糊，且无法从现有材料得到具体痛点、场景或期望时，给 2-3 个业务场景分支供用户校准。每个分支只写一句痛点、一个具体场景、默认推荐和触发条件。

示例：权限系统需要改善时，可给出管理员配置复杂、用户被错误拒绝或放行、审计追踪不足三个框架；只验证最可能框架中的一个关键假设，或要求补充真实业务场景。

## 深入信号

| 信号 | 验证方向 |
| --- | --- |
| 竞品有这个功能 | 我们的用户是否遇到同样问题 |
| 老板或客户说要做 | 对方遇到了什么具体问题 |
| 用户描述方案而非问题 | 这个方案要解决什么问题 |
| 应该很简单 | 预期的具体行为是什么 |
| 顺便加一个能力 | 去掉它后核心问题是否还能解决 |

## 输出边界

根问题、直接原因和用户画像的关键假设闭合后，只形成对应 checkpoint。不得把候选线索、问题框架或未闭合假设写成最终结论。
