# 业务语义收口

把已闭合的根问题、用户画像、成功标准和投入边界，转成后续范围、风险和 Phase 规划必须沿用的业务语言。

你负责提出推荐术语、业务对象和流程草案，用户负责确认或替换业务事实。

业务语义收口只对齐语言和事实，不设计页面、字段、权限、状态机或验收项。

只收口会影响范围、风险、Phase 拆分或产品经理同事后续细化的语义；不要定义每一个普通名词。

## 判断对象

- 关键术语：影响后续判断的业务名词、指标、对象状态或分组。
- 业务对象：对象边界、生命周期、归属关系和关键差异。
- 业务判定条件：会影响范围或 Phase 的业务判定条件。
- 当前流程：触发事件、参与角色、当前处理顺序，以及它如何承接根问题中的现实代价。
- 目标流程：目标状态下的业务顺序、可观察结果，以及它如何支撑成功标准。

术语、对象或流程存在多种解释时，先推荐默认口径，再验证一个最会改变范围、风险或 Phase 的事实。

## 检查点

- 关键术语：
  - 推荐定义：
  - 使用边界：
  - 不包含：
- 业务对象：
  - 推荐定义：
  - 对象边界：
  - 关键状态或关系：
- 业务判定条件：
  - 条件：
  - 影响范围或 Phase 的原因：
- 当前流程：
  - 触发事件：
  - 参与角色：
  - 当前处理顺序：
  - 现实代价承接：
- 目标流程：
  - 目标处理顺序：
  - 可观察结果：
  - 成功标准承接：
- `[?]` 未闭合事实：
- 推荐理由：

`[?]` 只标会改变范围、风险、Phase 拆分或产品经理同事后续细化口径的事实。每轮最多验证一个 `[?]`；存在多个未闭合事实时，优先验证最可能改变后续范围或 Phase 拆分的一项。

## 最终 JSON 边界

业务语义闭合后，影响 WHY、范围、风险或 Phase 的结论必须体现在最终锁定字段的自然语言中；检查点只保留推理证据。

需要业务流、用户路径或规则映射时，不在 Director 最终 JSON 中创建、冻结或填充这些字段；由产品经理同事在自己的产物中细化。

不得把推测、冲突事实、未闭合 `[?]` 或产品经理同事拥有的业务流字段写成最终结论。

## 停止条件

术语定义、业务对象含义、对象边界、影响范围或 Phase 的业务判定条件、当前流程和目标流程存在会改变后续判断的缺口时，停在业务语义收口。

语义差异会推翻根问题、用户画像或成功标准时，回到对应上游步骤重新验证，不在业务语义收口里硬改上游结论。

缺口只涉及字段名、页面交互、权限矩阵、接口、状态机细节或验收项，且不改变 WHY 层判断时，不阻塞 Director；标记为产品经理同事后续细化事项。
