# Phase 拆分指南

> 一句话原则：Phase 是交付节奏的载体，基于范围和交付价值切分，而非 UNIT 计数。

## 切分原则

Phase 切分发生在 D-S6，此时尚无 UNIT。决策依据是 D-S5 收口的范围产出：

1. **价值独立性**：每个 Phase 必须交付用户/业务可感知的独立价值
2. **范围自包含**：每个 Phase 的范围边界清晰，不依赖后续 Phase 才能交付价值
3. **渐进交付**：先交付核心价值（MVP 闭环），再交付增强和扩展
4. **默认单 Phase**：除非存在明确的切分信号，否则使用单 Phase（phase-1/）

## 信号识别

以下信号提示应考虑多 Phase 切分：

| 信号 | 说明 | 示例 |
|------|------|------|
| 独立价值层次 | 范围中存在"核心 + 增强"或"基础 + 高级"层次 | 基础搜索 vs 高级筛选 |
| 用户反馈依赖 | 部分功能需要先上线收集反馈再决定后续方向 | 先 A/B 测试核心流程 |
| 外部依赖时序 | 部分范围依赖外部系统/团队的交付时间线 | 先做不依赖第三方的部分 |
| 风险隔离 | 高风险部分应与稳定部分分离，降低交付风险 | 新技术探索 vs 稳定迁移 |

**无信号时** → 单 Phase，不做多余切分。

## 校验规则（进入 Manager 前）

| 校验项 | 规则 | 触发动作 |
|--------|------|----------|
| 空 Phase | Phase 内没有可承载的目标范围 | 调整 Phase 边界 |
| 预期 UNIT 超限 | 预期 UNIT 数量明显超过 7 | 建议拆出新 Phase |
| 跨 Phase 硬依赖 | 后续 Phase 强依赖前一 Phase 未完成部分 | 调整分组，确保依赖先闭合 |

## 默认行为

- 单功能需求 → 单 Phase（phase-1/）
- 范围明确无分层 → 单 Phase
- 所有项目至少有一个 Phase（phase-1/）

## Director 产物

D-S6 完成时必须创建：
- 所有 `phase-{N}/` 物理目录
- 每个 standard-chain `phase-{N}/phase-prd.json` 骨架（含阶段目标、入口出口条件、UNIT 索引占位）

Brief 交付计划只写 Phase 级目标、顺序、入口/出口条件和预期 UNIT 数量范围。UNIT 定义、UNIT 工作区路径和 AC 由 `/product-manager` 负责。

产物层级规则：
- `phase-{N}/phase-prd.json` — Director 写入阶段目标、入口条件、出口条件和空 `unit_index`。
- `phase-{N}/` 下游 canonical 产物由后续角色生成。
- `phase-{N}/units/UNIT-{M}.json` 与 `phase-{N}/unit-{M}/` 执行工作区由 `/product-manager` 之后生成。

## 反模式

- 不要因为预期 UNIT 数量好看而硬切 Phase
- 不要为了拆分而引入跨 Phase 硬依赖
- 不要按"均匀分配"拆分，Phase 大小可以不均等
- 不要为没有独立交付价值的范围创建独立 Phase
