# 风险与未知项

## 目标

把已闭合的根问题、目标、投入边界、范围、本期不做范围和可行性约束中的不确定性，收口为进入 Phase 规划前必须处理的风险判断。

风险与未知项只处理会影响 WHY 层基线的事项：根问题、目标、范围、本期不做范围、可行性约束和 Phase 拆法。

## 工作原则

你负责判断风险对 Director 基线的影响，用户负责确认或替换风险事实。

风险不是担忧清单；风险必须说明如果事实不成立，会改变哪个 Director 判断。

未知项必须写成可验证的业务事实句，不能写成“需求不清”“待确认”。

只影响后续细化顺序、验收取样或执行排期的事项，是下游执行风险；记录移交影响，不反向扩大 Director 范围。

没有识别到风险时，必须明确记录“无已识别风险”，不得留空。

## 风险分层

| 类型 | 判断标准 | 处理动作 |
| --- | --- | --- |
| 基线推翻风险 | 事实一旦不成立，会推翻根问题、目标、范围、本期不做范围或可行性约束 | 进入 Phase 规划前暂停，验证该事实 |
| Phase 拆法风险 | 事实一旦不成立，会改变 Phase 顺序、边界、timebox 或是否拆分 | 先验证或重切 Phase，再继续 |
| 下游执行风险 | 事实不影响 WHY 层基线，只影响产品经理同事后续细化和交付安排 | 写入风险项并标明移交动作，不改变 Director 范围 |
| 非风险 | 只涉及页面、业务字段、状态流转、接口、实现路径或偏好，且不改变 WHY 层基线 | 不写入 Director 风险 |

## 执行步骤

1. 读取已闭合的根问题、用户画像、目标、投入边界、范围、本期不做范围、可行性约束和决策理由。
2. 逐项追问：如果这个事实不成立，哪一个 Director 判断必须改变？
3. 能改变根问题、目标、范围、本期不做范围、可行性约束或 Phase 拆法的，列为基线风险或 Phase 拆法风险。
4. 只影响产品经理同事后续细化、验收取样或执行排期的，列为下游执行风险。
5. 无法说清影响对象的，改写为可验证事实；仍无法改写时不写入风险。
6. 每项风险写清 `item / impact / mitigation / status`。
7. 没有风险时，写一条“无已识别风险”记录。
8. 存在基线推翻风险或 Phase 拆法风险时，先验证一个会改变判断的关键事实，再进入 Phase 规划。

## 检查点

- 风险判断口径：
- 基线推翻风险：

  - 影响的 Director 判断：
  - 待验证事实：
  - 处理动作：
  - 状态：
- Phase 拆法风险：
  - 风险项：
  - 影响的 Phase 判断：
  - 待验证事实：
  - 处理动作：
  - 状态：

  - 风险项：
  - 下游影响：
  - 移交动作：
  - 状态：

- 进入 Phase 规划判断：

## 最终 JSON 映射

`brief.json.risks_and_unknowns[]` 每项必须包含：

- `item`：风险或未知项，用业务事实句表达。
- `impact`：写明会影响目标、范围、本期不做范围、可行性约束、Phase 拆法，或仅影响下游执行。
- `mitigation`：写下一步验证、收口、移交或接受动作。
- `status`：使用 `OPEN`、`ACCEPTED` 或 `RESOLVED`。

基线推翻风险和 Phase 拆法风险在未验证前使用 `OPEN`。

已确认接受且不改变 Director 基线的下游执行风险使用 `ACCEPTED`。

已验证关闭的风险或“无已识别风险”使用 `RESOLVED`。

没有识别到风险时，`risks_and_unknowns` 写入一条记录：

```json
{
  "item": "无已识别风险",
  "impact": "当前已闭合事实未发现会推翻根问题、目标、范围、本期不做范围、可行性约束或 Phase 拆法的风险",
  "mitigation": "进入 Phase 规划；若新增事实触及 Director 基线，回到风险与未知项重新判断",
  "status": "RESOLVED"
}
```

风险项不得新增 Director 模板外结构；证据、来源和对话过程只留在台账检查点。

## 停止条件

存在会推翻根问题、目标、范围、本期不做范围、可行性约束或 Phase 拆法的未知项时，停在风险事实验证。

风险影响对象说不清时，先改写风险，不进入 Phase 规划。

`mitigation` 实际替用户做了业务决策时，停下验证该决策事实。

下游执行风险被用来扩大范围、补回本期不做范围或拆新 Phase 时，回到范围收口或 Phase 规划重新判断。

风险列表为空时，补写“无已识别风险”记录后再继续。

## 反模式

- 把所有不确定性都写成“需求不清”。
- 只写风险名称，不写会改变哪个 Director 判断。
- 把业务字段、状态流转、页面、接口或实现方案写成 Director 风险。
- 用 `mitigation` 预设未确认业务事实。
- 把下游执行风险升级成 Director 范围。
- 没有风险时把 `risks_and_unknowns` 留空。

## 输出边界

风险与未知项及其 Phase 影响闭合后，形成对应检查点。

风险判断只冻结 WHY 层影响、处理动作和状态；不输出 UNIT、AC、业务字段、状态流转、设计或实现方案。
