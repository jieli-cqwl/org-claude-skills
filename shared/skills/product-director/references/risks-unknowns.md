# 风险与未知项

把已闭合的根问题、目标、投入边界、范围、本期不做范围和可行性约束中的不确定性，收口为进入 Phase 规划前必须处理的风险判断。

你负责判断风险对 Director 基线的影响，用户负责确认或替换风险事实。

风险不是担忧清单；风险必须说明如果事实不成立，会改变哪个 Director 判断。未知项必须写成可验证的业务事实句，不能写成“需求不清”“待确认”。

风险与未知项只处理会影响 WHY 层基线的事项：根问题、目标、范围、本期不做范围、可行性约束和 Phase 拆法。

没有识别到风险时，必须明确记录“无已识别风险”，不得留空。

风险来源跨业务、技术、流程或合规时，召集 agent teams 分别从基线推翻风险、Phase 拆法风险、移交备注维度交叉识别影响对象；只返回风险证据、影响判断和待验证事实。

## 风险分层

| 类型 | 判断标准 | 处理 |
| --- | --- | --- |
| 基线推翻风险 | 事实一旦不成立，会推翻根问题、目标、范围、本期不做范围或可行性约束 | 进入 Phase 规划前暂停，验证该事实 |
| Phase 拆法风险 | 事实一旦不成立，会改变 Phase 数量、顺序、入口条件或出口条件 | 进入 Phase 规划前暂停，验证该事实 |
| 移交备注 | 事实不影响 WHY 层基线，只影响后续细化、验收取样或执行排期 | 留在台账检查点或移交提示，不写入最终 `risks_and_unknowns` |
| 非风险 | 只涉及页面、业务字段、状态流转、接口、实现路径或偏好，且不改变 WHY 层基线 | 不写入 Director 风险 |

## 最终 JSON 映射

`brief.json.risks_and_unknowns[]` 每项必须包含：

- `risk`：写不确定事实或风险事件。
- `impact`：写明会影响目标、范围、本期不做范围、可行性约束或 Phase 拆法。
- `status`：`open / accepted / mitigated / none_identified`。
- `mitigation`：写当前处理动作；需要验证时写待验证事实。

没有识别到基线风险时写一条：

```json
{
  "risk": "无已识别风险",
  "impact": "当前已闭合事实未发现会推翻根问题、目标、范围、本期不做范围、可行性约束或 Phase 拆法的风险",
  "status": "none_identified",
  "mitigation": "进入 Phase 规划；若新增事实触及 Director 基线，回到风险与未知项重新判断"
}
```

移交备注不得写入最终 `risks_and_unknowns`。

风险项不得新增 Director 模板外结构；证据、来源和对话过程只留在台账检查点。

## 停止条件

存在会推翻根问题、目标、范围、本期不做范围、可行性约束或 Phase 拆法的未知项时，停在风险事实验证。

风险只写“可能有风险”“待确认”但没有说明会改变哪个 Director 判断时，继续收口。

`mitigation` 实际替用户做了业务决策时，停下验证该决策事实。

风险判断只冻结 WHY 层影响、处理动作和状态；不输出 UNIT、AC、业务字段、状态流转、设计或实现方案。
