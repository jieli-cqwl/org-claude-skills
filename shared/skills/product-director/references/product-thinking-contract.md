# Product-Thinking Contract v1

## 价值假设验证

每个关键范围判断背后都有一个赌注。在定义需求前先回答：

- 假设是什么？（"我们相信 X 会导致 Y"）
- 怎么验证？（上线后看什么数据/行为变化？）
- 当前基线是什么？（现在的数字、状态或行为是什么）
- 目标值或方向是什么？（要提升/降低到哪里，或至少朝哪个方向变化）
- 观测窗口是什么？（多长时间后判断）
- 数据来源是什么？（日志、报表、埋点、人工回访或指定证据面）
- 失败长什么样？（如果指标没动，说明什么？）

核心问句："如果这个功能上线，你怎么知道它成功了？" 答不出来就别往下走。

## 用户画像与当前绕行方式

问题必须落到具体人群和真实场景：

- 谁遇到这个问题？（角色、权限、业务责任）
- 在什么场景发生？（触发时机、业务流程、频率）
- 当前绕行方式是什么？（手工补救、额外沟通、线下表格、临时脚本）
- 绕行方式的代价是什么？（时间、错误率、风险、客户体验）

核心问句："谁现在用什么绕行方式撑着这个问题？" 答不出来就继续澄清。

## Appetite

Appetite 定义投入边界，不定义实现方案：

- 这是两周级、一个月级，还是更大投入量级？
- 如果投入超出 Appetite，优先缩小哪些范围？
- 哪些复杂度不值得为了本期目标承担？
- Appetite 是否与成功标准的业务价值匹配？

核心问句："这件事值得多少投入？" 答不出来时，不要让下游用过度方案填空。

## MVP 范围界定

用三分法逼出真正的最小闭环：

- **核心**（必须有）：没有它，问题就没解决
- **增强**（锦上添花）：有它更好，但核心已经能独立交付价值
- **未来**（明确延后）：写下来是为了现在不做它

核心问句："如果只能做一件事，是哪件？" 答不出来说明切片还不够。

## Non-goals、可行性约束与决策理由

范围判断必须同时写清楚做什么、不做什么、为什么这样切：

- Non-goals：本期明确不交付的相关能力或场景。
- 可行性约束：必须沿用的系统、数据、流程、合规、上线窗口或资源限制。
- 决策理由：选择当前范围的原因，以及排除相邻范围的原因。

核心问句："为什么是这个范围，而不是更大或更小？" 答不出来说明边界还没收口。

## Rabbit Holes / 风险与未知项

在 Phase 规划前识别可能推翻判断的风险：

- 哪个假设不成立会推翻目标、范围或 Phase 拆法？
- 哪个依赖如果不可用，会让本期无法闭环？
- 哪个未知项需要在下游优先验证？
- 是否可以显式声明"无已识别风险"？

核心问句："什么事情一旦错了，后面全要重来？" 答不出来就不要进入 Phase 规划。

## 警示信号

If you catch yourself thinking:

- "用户已经给了方案，我直接整理成需求" → 立即暂停。先追问它要解决什么问题，再定义需求。
- "已经够清楚了，可以停止追问" → 立即暂停。先检查目标、范围、流程、规则、验收是否都已收口。
- "这个 AC 用模糊词描述也没关系" → 立即暂停。验收必须能落到可观察结果；AC 细化交给 `/product-manager`，但 Director 不能放过无法验证的成功信号。
- "我先按分析主题拆几个 UNIT，后面让下游自己再拆" → 立即暂停。Director 只规划 Phase，但必须给出足以支撑闭环 UNIT 的边界。
- "先全部标 MVP，后面再说" → 立即暂停。优先级失真通常说明 Phase 边界或最小闭环未解释清楚。
- "用户说了'你看着办'就不用问了" → 立即暂停。共创需要双方投入，引导用户参与而非放弃提问。
- "这一步我自己判断就行，不用等用户" → 立即暂停。每步必须按共创模式执行，暂停等待用户回应。
