# 规划判断模型

## 目标

规划完成后，你的输出必须通过四个测试：

1. **目标保真** — Tasks 合起来 = Phase 目标，不多不少
2. **风险前置** — 最大不确定性先验证，每个 batch 边界有验证点
3. **集成先行** — 拆分方案包含集成收口点和资源冲突处理
4. **消费者可执行** — 每个 Task 合同信息完整：goal、scope 来源、实施级 AC、证据路径

## 基础定义

一个拆分正确的 Task 必须同时满足：

- **独立交付**: 完成后能落到明确文件和边界，不依赖实现者二次猜测
- **独立验收**: AC 可单独验证，verify 能给出明确证据
- **独立回滚**: 失败时可单独撤回，不污染其他 Task 的主路径
- **边界稳定**: 拆分后不会制造临时接口、重复验收目标或不稳定依赖

不满足任一条的拆分必须调整，不能靠注释或口头约定补救。

## 复杂度校准

先判断 Phase 复杂度，决定分析深度：

| 信号 | 简单（快通道） | 复杂（完整分析） |
| --- | --- | --- |
| Task 数量预估 | <= 3 | > 5 |
| 不确定性 | 技术栈已知，依赖已验证 | 新技术、外部依赖未验证、性能未知 |
| 依赖深度 | Task 间基本独立 | 多级串行、共享文件或共享状态 |
| 集成面 | 单模块或单层 | 跨模块、跨层或前后端 |

简单场景：直接用拆分启发式，快速确认 4 个目标即可。
复杂场景：每个目标逐项深度分析。

## 判断目标

### 1. 目标保真

分解后的 Tasks 合起来必须 = Phase 目标。不多（scope creep），不少（遗漏）。

**做法：**
- 列出 Phase 目标的所有交付结果和 AC。
- 逐条检查每个 AC 至少被一个 Task 的 `scope_item_refs` 覆盖。
- 检查是否有 Task 引入了 Phase 目标之外的范围。

**信号：** 每个 brief/design AC 都有 Task 承接，且没有无源 Task。
**反面：** Task 的 `scope_item_refs` 追踪不回上游 AC，或存在 Task 的目标在 brief 里找不到来源。

### 2. 风险前置

最大不确定性先验证。每个 batch 边界创造验证点。

**做法：**
- 识别 Phase 中的不确定性类型：技术可行性、外部依赖、性能、数据质量、集成复杂度。
- 按不确定性排序，第一个 batch 覆盖最大不确定性。
- 不确定到无法拆时，建 readiness/spike Task 证明假设，不硬拆。
- 每个 batch 结束后能判定：该 batch 的不确定性是通过还是失败，后续 batch 是否按原计划继续。

**信号：** batch 1 完成后能验证最关键的假设；高不确定性 Task 在关键路径上靠前。
**反面：** 最确定的 Task 排第一批，最不确定的排最后（回避风险）。所有 Task 全并行最后集成（消灭中间验证点）。

**排序优先级：**

| 不确定性 | 关键路径 | 排序 |
| --- | --- | --- |
| 高 | 是 | 最先执行 |
| 高 | 否 | 尽早但不阻塞关键路径 |
| 低 | 是 | 按依赖顺序 |
| 低 | 否 | 可并行或推迟 |

排序冲突时：高风险前置 > 数据层优先 > 共享基础设施先行 > 独立功能先做。

### 3. 集成先行

拆分时同时定义集成方案——怎么拆决定了怎么合。

**做法：**
- 拆分时定义集成收口点：哪个 Task 或 batch 负责集成验证？
- 识别资源竞争：文件/模块、测试环境/端口、共享配置/状态。
- 评估回滚代价：只影响自己、影响下游输入、还是影响全局状态？
- worktree 隔离时在计划中写明合并顺序。

**信号：** 计划中有明确的集成收口 Task 或 batch；资源冲突有处理方案；高回滚代价 Task 有额外验证门禁。
**反面：** 每个 Task 独立绿灯但合起来没人负责验证；`shared_files` 过多但无隔离策略。

**资源竞争处理：**

| 竞争类型 | 策略 |
| --- | --- |
| 同文件/模块 | 串行化或 worktree 隔离，计划中写明合并顺序 |
| 同测试环境/端口 | 隔离环境或串行测试阶段 |
| 同配置/共享状态 | 串行化写入方，或隔离配置实例 |

**回滚代价评估：**

| 影响范围 | 策略 |
| --- | --- |
| 只影响自己 | 可与其他 Task 并行 |
| 影响下游输入 | 先验证成功再释放下游 |
| 影响全局状态 | 独立执行，确认回滚方案后再开始 |

### 4. 消费者可执行

每个 Task 合同写入完整的 goal、scope 来源、实施级 AC 和证据路径。

**做法：**
- developer 视角：goal + `scope_item_refs` + `acceptance_targets` 是否足够开始影响范围分析？
- verify 视角：AC 是否可 assert、可复验、可举证？（精度标准见 `ac-precision-guide.md`）
- delivery-owner 视角：关键路径、重/险/慢 Task、返工概率是否可见？
- QA 视角：组合测试义务和验收标准是否明确？

**信号：** Task 的 goal 指向具体交付结果；scope_item_refs 追踪到上游 AC；AC 可直接转 assert；证据路径可复验。
**反面：** AC 只是 brief AC 的复述，没有实施层面具体化；Task 缺少投入/风险标注。

## 拆分启发式

### 何时拆分一个 MOD 为多个 Task

| 场景 | 差的拆法 | 好的拆法 | 原因 |
| --- | --- | --- | --- |
| MOD 含数据库迁移+业务逻辑 | 全放一个 Task | Task-A: schema 迁移 + 数据兼容; Task-B: 业务逻辑 | 迁移失败可独立回滚，不污染业务代码 |
| MOD 含接口定义+多个消费方 | 全放一个 Task | Task-A: 接口定义+类型; Task-B/C: 各消费方实现 | 接口先稳定，消费方可并行开发 |
| MOD 含共享基础设施+业务 | 混在业务 Task 里 | Task-A: 共享基础设施; Task-B+: 业务功能 | 基础设施是依赖根，前置后下游可并行 |
| MOD 含前端+后端 | 前后端混合一个 Task | Task-A: 后端 API; Task-B: 前端页面 | 关注点分离，review 更聚焦 |

### 何时不拆

| 场景 | 原因 |
| --- | --- |
| 改动 <= 3 文件且逻辑内聚 | 拆了反而增加依赖管理开销 |
| 数据模型和唯一使用方强耦合 | 分开会导致 Task 间接口不稳定 |
| 配置文件+使用该配置的唯一模块 | 天然原子操作，拆开无意义 |

### 过度拆分信号

| 信号 | 说明 | 建议 |
| --- | --- | --- |
| `shared_files` 过多 | 多个 Task 反复改同一核心文件 | 重看边界，必要时合并或重切 |
| 验收目标重复 | 多个 Task 指向同一可观察结果 | 合并重复 Task 或重写 AC 归属 |
| 依赖链过长 | 同一子功能被切成过多串行 Task | 按稳定边界回收为更完整的 Task |
| 单 Task 无法独立成立 | 单独完成后不可运行、不可验收或不可回滚 | 应合并或改切口 |

Task 数量多不等于拆错。大需求出现 10+ Task 很常见，只要每个满足基础定义中的四个条件。只在确认出现上述信号时才考虑合并。

### 全栈功能强制拆分

全栈功能 MUST 按以下模式拆分：

| 拆分 | 职责 | 依赖 |
| --- | --- | --- |
| Task-A: 后端 API | 接口定义、入参校验、业务逻辑、出参格式、错误码 | 无 |
| Task-B: 前端页面 | 调用 Task-A API，实现交互和展示 | depends_on: Task-A |

例外：改动仅涉及 1 文件且前后端逻辑完全内聚（如 SSR 页面修改）。

### 并行判断

| 维度 | 可并行 | 建议串行 |
| --- | --- | --- |
| 文件交集 | 0 个 shared_files | >= 3 个 shared_files |
| 数据依赖 | 读写不同表/不同字段 | 写同一张表的同一字段 |
| 接口依赖 | 各自独立接口 | Task-B 调用 Task-A 新建的接口 |
| 测试隔离 | 测试数据独立 | 共享测试 fixtures 且会修改 |

shared_files 1-2 个时可并行，但 merge 时需确认冲突点。

## 自检

对照上述四个判断目标确认后，执行结构检查：

1. 原子性：每个 Task 可独立实现、验收、回滚？
2. 粒度：默认 <= 5 文件；超过时说明不可再拆原因。
3. 依赖完整性：`depends_on` 反映真实执行顺序，无遗漏、无环。
4. 草稿收口：所有 Task 回收到同一冻结版本后才写入最终 `plan.json / tasks.json`。

## 常见场景

| 场景 | 诊断 | 处理 |
| --- | --- | --- |
| Phase 混合探索性和确定性工作 | 探索部分不确定性高，不能和确定部分同批 | 先 spike/readiness Task 验证假设，再拆确定性 Task |
| 多个候选拆分方案都说得通 | 结构都合理，无法从原子性判断优劣 | 用风险前置原则选——哪个方案让最大风险最早暴露 |
| 依赖图有环 | 计划有结构性错误 | 停止拆解，报告环依赖并重新设计 Task 边界 |
| 所有 Task 都标高风险 | 不可能全部最先执行 | 按关键路径优先级排序；非关键路径的高风险 Task 并行探测 |
| Phase 目标超出单 Phase 合理规模 | Task 数量 > 15 且依赖复杂 | 建议回流 product-manager 拆分 Phase |
