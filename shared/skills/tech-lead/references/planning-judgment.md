# 规划判断模型

## 目标

把 Phase 目标拆成 Task 计划，使每个 Task 可独立交付、验收和回滚。

## 分解流程

### 1. 理解交付目标

从上游产物提取计划输入：

| 上游产物 | 提取什么 | 用于 |
|---------|---------|------|
| phase-prd | Phase 目标、范围边界 | 确定交付终点 |
| UNIT | 产品 AC（示例输入、预期结果、边界、失败模式） | 绑定 scope_item_refs |
| design | 架构决策、模块划分、接口定义、planning_constraints | 绑定 design_refs，识别切割线 |
| test-cases | 测试断言、覆盖矩阵 | 绑定 test_refs |

逐条检查 Phase 目标的所有 AC 是否有上游产物覆盖。有 AC 无法追踪到上游 → 缺口检测。

### 2. 识别工作包边界

按自然切割线把交付目标分成 work package：

| 切割线 | 示例 | 拆分原因 |
|--------|------|---------|
| 数据层 vs 逻辑层 | schema 迁移 和 业务逻辑 | 迁移失败可独立回滚 |
| 后端 vs 前端 | API 和 页面 | 关注点分离，可并行 |
| 共享基础设施 vs 业务 | 公共模块 和 业务功能 | 基础设施是依赖根，前置后下游可并行 |
| 接口定义 vs 消费方 | 类型/契约 和 各消费方实现 | 接口先稳定，消费方可并行 |

先判断复杂度决定分析深度：

| 信号 | 简单（快通道） | 复杂（完整分析） |
|------|--------------|----------------|
| Task 数量预估 | <= 3 | > 5 |
| 不确定性 | 技术栈已知，依赖已验证 | 新技术、外部依赖未验证 |
| 依赖深度 | Task 间基本独立 | 多级串行、共享文件或状态 |
| 集成面 | 单模块或单层 | 跨模块、跨层或前后端 |

### 3. 分解为 Task

每个 work package 分解为满足**基础定义**的 Task。

一个拆分正确的 Task 必须同时满足：

- **独立交付**: 完成后能落到明确文件和边界，不依赖实现者二次猜测
- **独立验收**: 验收可单独执行，verifier 能给出明确证据
- **独立回滚**: 失败时可单独撤回，不污染其他 Task 的主路径
- **边界稳定**: 拆分后不会制造临时接口、重复验收目标或不稳定依赖

不满足任一条的拆分必须调整，不能靠注释或口头约定补救。

#### 何时拆分一个 MOD 为多个 Task

| 场景 | 差的拆法 | 好的拆法 | 原因 |
|------|---------|---------|------|
| MOD 含数据库迁移+业务逻辑 | 全放一个 Task | Task-A: schema 迁移; Task-B: 业务逻辑 | 迁移失败可独立回滚 |
| MOD 含接口定义+多个消费方 | 全放一个 Task | Task-A: 接口定义; Task-B/C: 消费方实现 | 接口先稳定，消费方并行 |
| MOD 含共享基础设施+业务 | 混在业务 Task 里 | Task-A: 基础设施; Task-B+: 业务功能 | 依赖根前置 |
| MOD 含前端+后端 | 混合一个 Task | Task-A: 后端 API; Task-B: 前端页面 | 关注点分离 |

全栈功能 MUST 按后端→前端拆分（例外：改动仅涉及 1 文件且逻辑完全内聚）。

#### 何时不拆

| 场景 | 原因 |
|------|------|
| 改动 <= 3 文件且逻辑内聚 | 拆了反而增加依赖管理开销 |
| 数据模型和唯一使用方强耦合 | 分开会导致 Task 间接口不稳定 |
| 配置文件+使用该配置的唯一模块 | 天然原子操作 |

#### 过度拆分信号

| 信号 | 建议 |
|------|------|
| `shared_files` 过多（多 Task 改同一文件） | 重看边界，合并或重切 |
| 验收目标重复（多 Task 指向同一结果） | 合并重复 Task |
| 依赖链过长（同一子功能切太多串行 Task） | 按稳定边界回收 |
| 单 Task 无法独立成立 | 合并或改切口 |

Task 数量多不等于拆错。大需求出现 10+ Task 很常见，只要每个满足基础定义。

### 4. 绑定 Task 合同

每个 Task 的合同字段从上游产物绑定，不自造内容：

| Task 字段 | 绑定来源 | 判断问题 |
|-----------|---------|---------|
| unit_refs | UNIT 定义 | 这个 Task 实现哪些 UNIT？ |
| scope_item_refs | UNIT AC / design scope | 这个 Task 为什么在范围内？ |
| design_refs | design 决策 | 按什么架构做？ |
| test_refs | test-cases | 怎么验证？ |
| acceptance_targets | 从 test_refs 提取 | 做完后什么为真？ |
| proving_command | 从 test_refs / design 推导 | 怎么复现验证？ |
| evidence_target | 验证产物路径 | 证据放哪？ |
| depends_on | 依赖分析 | 先做什么才能做这个？ |
| shared_files | 文件冲突分析 | 和谁冲突？ |
| real_dependency_note | 真实依赖描述 | 实际运行需要什么？ |
| mock_boundary_note | Mock 边界说明 | 哪些可 Mock、哪些必须真实？ |

以下字段在后续步骤分配：`batch`、`critical_path_role` 在 step 5 排序后确定；`wbs_ref` 对应 step 2 的工作包编号。

`scope_item_refs` 说明范围来源；实际变更范围由 developer 在执行阶段自主分析确定。

字段无法从上游产物填实时 → 进入缺口检测（见下文）。

### 5. 排序与并行

#### 关键路径识别

关键路径 = 从所有 `depends_on` 链中找出最长的依赖链。这条链上的任何 Task 延迟，整个 Phase 交付就延迟。

识别方法：
1. 从每个无依赖的 Task 出发，沿 `depends_on` 反向追踪所有下游 Task。
2. 找出从起点到终点最长的链 — 这就是关键路径。
3. 关键路径上的 Task 标 `critical_path_role: "critical"`。
4. 非关键路径但阻塞其他 Task 的标 `"supporting"`；完全独立的标 `"independent"`。

关键路径确定后，排序和资源分配优先保障这条链。

#### 风险驱动排序

在关键路径基础上，按不确定性调整执行顺序：

| 不确定性 | 关键路径 | 排序 |
|---------|---------|------|
| 高 | 是 | 最先执行 |
| 高 | 否 | 尽早但不阻塞关键路径 |
| 低 | 是 | 按依赖顺序 |
| 低 | 否 | 可并行或推迟 |

不确定性类型：技术可行性、外部依赖、性能、数据质量、集成复杂度。
不确定到无法拆时 → 建 readiness Task 证明假设，不硬拆。
排序冲突时：高风险前置 > 数据层优先 > 共享基础设施先行 > 独立功能先做。

#### Batch 编排

按依赖层级把 Task 分组为 batch：

1. Batch 1 = 无依赖的 Task（或仅依赖 readiness Task 的）。
2. Batch N+1 = 所有依赖项都在 Batch 1~N 中的 Task。
3. 同一 Batch 内的 Task 可并行执行（需通过并行判断确认）。
4. 每个 Batch 结束就是一个验证点：判定假设通过还是失败，后续 Batch 是否按原计划继续。

#### 并行判断

同一 Batch 内多个 Task 时，逐维度确认能否并行：

| 维度 | 可并行 | 建议串行 |
|------|-------|---------|
| 文件交集 | 0 个 shared_files | >= 3 个 shared_files |
| 数据依赖 | 读写不同表/字段 | 写同一张表同一字段 |
| 接口依赖 | 各自独立接口 | B 调用 A 新建的接口 |
| 测试隔离 | 测试数据独立 | 共享 fixtures 且会修改 |

shared_files 1-2 个时可并行，但 merge 时需确认冲突点。

#### 集成收口

- 拆分时同时定义：哪个 Task 或 batch 负责集成验证？
- 并行 batch 包含多个 Task 时，写明隔离策略（worktree / 独立环境）、合并顺序和集成检查点，供 delivery-owner 确定分配方案。

| 竞争类型 | 策略 |
|---------|------|
| 同文件/模块 | 串行化或 worktree 隔离，写明合并顺序 |
| 同测试环境/端口 | 隔离环境或串行测试阶段 |
| 同配置/共享状态 | 串行化写入方，或隔离配置实例 |

| 回滚影响范围 | 策略 |
|------------|------|
| 只影响自己 | 可与其他 Task 并行 |
| 影响下游输入 | 先验证成功再释放下游 |
| 影响全局状态 | 独立执行，确认回滚方案后再开始 |

#### 投入/风险标注

每个 Task 标注投入和风险信号，供 delivery-owner 决定监控频率、回退方案和资源优先级：

| 信号 | 判断依据 | delivery-owner 关注 |
|------|---------|-------------------|
| 投入高（重） | 涉及文件多、逻辑复杂、跨模块 | 预留更多时间，避免与其他重 Task 并行 |
| 风险高（险） | 技术方案未验证、外部依赖不稳定、并发/状态管理 | 准备回退方案，提前识别替代路径 |
| 进度慢（慢） | 需要多轮集成验证、依赖链长、阻塞其他 Task | 优先启动，密切跟踪进度 |
| 易返工 | 上游输入模糊、需求有多种解读、架构边界不稳定 | 先确认理解一致，关键节点提前验收 |

一个 Task 可以同时有多个信号。无显著信号的 Task 不需要标注。

## 缺口检测与阻断

| 无法填实的字段 | 缺口类型 | owner | tech-lead 行为 |
|--------------|---------|-------|---------------|
| scope_item_refs | 产品定义不足 | product-manager | 阻断 → 用户决策包 |
| design_refs | 架构未闭合 | designer | 阻断 → 用户决策包 |
| test_refs | 测试义务不明 | test-designer | 阻断 → 用户决策包 |
| 执行前提（环境/权限/SDK） | 执行前提未验证 | tech-lead | 建 readiness Task |

前三类缺口必须阻断并回流用户决策包；只有第四类由 tech-lead 自行建 readiness Task 处理。

### Readiness Task

当执行前提无法在计划阶段验证时（环境、权限、SDK、命令可用性），建 readiness Task：

- **goal**: 证明某个执行前提可用
- **success_signal**: 前提满足时的可观察证据（如 "SDK auth 返回 200"）
- **failure_signal**: 前提不满足时的判定标准（如 "连续 3 次超时 → 阻断后续"）
- **evidence_target**: 证据落点路径
- 后续 Task 通过 `depends_on` 等待 readiness 结论

readiness Task 不得改变产品范围、架构决策或测试义务。

## 自检

分解完成后逐项确认：

1. 目标对齐：每个 Phase AC 都有 Task 承接？没有无源 Task？
2. 原子性：每个 Task 满足基础定义的四个条件？
3. 粒度：默认 <= 5 文件；超过时说明不可再拆原因。
4. 合同完整：每个字段都从上游产物填实？缺口已处理？
5. 依赖完整性：`depends_on` 反映真实执行顺序，无遗漏、无环。
6. 排序合理：高风险前置？batch 边界有验证点？集成有收口？
7. 草稿收口：所有 Task 回收到同一冻结版本后才写入 `tasks.json`。

## 常见场景

| 场景 | 诊断 | 处理 |
|------|------|------|
| Phase 混合探索性和确定性工作 | 探索部分不确定性高 | 先 readiness Task 验证假设，再拆确定性 Task |
| 多个候选拆分方案都说得通 | 结构都合理 | 用风险前置原则选——哪个方案让最大风险最早暴露 |
| 依赖图有环 | 结构性错误 | 停止拆解，报告环依赖并重新设计 Task 边界 |
| 所有 Task 都标高风险 | 不可能全部最先执行 | 按关键路径优先级排序；非关键路径高风险并行探测 |
| Phase 目标超出单 Phase 合理规模 | Task 数量 > 15 且依赖复杂 | 建议回流 product-manager 拆分 Phase |
