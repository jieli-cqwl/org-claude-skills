## 顶层评审模型

评审固定使用 5 个 Gate：

1. 需求语义一致性 Gate
2. 决策充分性 Gate
3. 边界与契约完整性 Gate
4. 演进可实施性 Gate
5. 计划交接就绪 Gate

只有 5 个 Gate 全部 PASS，才可输出 `REVIEW: DESIGN_OK`。

## 四层结构（必须分层）

1. 阶段 Gate：判断是否可进入下一阶段
2. 证据检查：证明 Gate 通过的具体证据
3. 横切原则：简单 / 合适 / 演化
4. 场景方法论：系统拆分、旧系统重构、质量属性、风险评估等专项检查

`覆盖` 必须拆成两类证据：
- `需求语义覆盖`：Design 是否正确承接 PRD，归 Gate 1
- `执行追踪覆盖`：AC 是否能追踪到 Task 拆分，归 Gate 5

## 三原则统一口径（全 Gate）

- 简单：削减无证据的 Accidental Complexity
- 合适：保留问题域要求的 Essential Complexity
- 演化：按需增长复杂度 + 可逆性优先 + 延迟不可逆决策（LRM）

说明：各 Gate 中出现的“可验证/可停机/可回退”等表述，是演化原则在实施层的证据投影，不是完整定义。
原则冲突统一按 L1-L4 裁决（L1 非协商约束 > L2 质量属性优先级 > L3 可逆性优先 > L4 默认选简单）。

## Gate 1：需求语义一致性

判断目标：
- 证明 Design 对 PRD 的根问题、目标、范围、业务规则、待设计决策承接正确，无语义偏差。

必备证据：
- `design.json.input_analysis` 与 `PRD 技术理解校正` 明确列出根问题与目标承接关系
- `需求语义覆盖` 证据：PRD AC 可映射到 Design 的模块/接口/数据边界
- PRD 的范围/本期不交付、业务规则、排除项在 Design 中有显式响应
- `待设计决策` 有承接结果或保留为明确开放项

阻断条件：
- 根问题或目标被错误理解
- 出现 PRD AC 无法映射到 Design 的核心能力（语义级缺口）
- PRD 范围/规则被静默改写或遗漏

常见失败模式：
- 只做“文档章节对齐”，没有语义对齐
- 只覆盖功能 AC，忽略全局约束/排除项
- 直接将 PRD 的开放问题当作已决事项

三原则裁决：
- 简单：不为未出现的需求扩展复杂语义
- 合适：对真实复杂规则（状态、权限、一致性）不做过度简化
- 演化：语义承接必须可支持从现状到目标的渐进落地

复杂场景附加检查：
- 系统拆分：跨域语义在各服务边界是否保持一致
- 旧系统重构：旧行为兼容边界是否在语义层明确

## Gate 2：决策充分性

判断目标：
- 证明关键设计决策已被识别、比较并确认，不是拍脑袋定稿。

必备证据：
- `关键决策记录` 覆盖所有关键决策点，每个决策有对应的独立 ADR 文件（`design/adr/ADR-NNN.md`）
- `共创摘要` 记录了关键提问和用户回应，且每个关键决策有用户参与的选择记录
- 每个关键决策至少 2 个本质不同方案（记录在对应 ADR 文件中）
- 每个推荐方案都有取舍理由（复杂度/性能/维护/风险）
- 有用户确认结论或显式未决项

阻断条件：
- 关键决策缺失或未比较替代方案
- `共创摘要` 缺失或无实质内容
- 共创记录未通过可信度检查（用户回应缺乏领域特异性、阶段间逻辑不连贯、或与 ADR 用户确认矛盾）
- 关键决策无用户参与记录
- 推荐结论无理由，或理由无法追溯到目标/约束
- 未确认即直接进入细节拍板

常见失败模式：
- 先给唯一答案，再补“伪对比”
- 只比较技术偏好，不比较业务约束
- 追求“最先进”而非“最适配”

三原则裁决：
- 简单：默认选择更小复杂度方案，除非证据证明不足
- 合适：当复杂性是业务必需时，允许并要求显式说明
- 演化：优先可渐进迁移的方案，降低一次性切换风险

复杂场景附加检查：
- 系统拆分：同步/异步、数据一致性、边界拆分策略必须有对比依据
- 旧系统重构：改造策略（绞杀/抽象分支/并行运行）必须有选择理由

## Gate 3：边界与契约完整性

判断目标：
- 证明服务/模块/数据/接口边界清晰，契约可执行，异常路径完整。

必备证据：
- `架构边界`、`接口边界`、`数据边界` 章节完整
- 接口至少定义：输入、输出、关键错误码/错误场景、依赖约束
- 边界责任清晰：谁负责、谁调用、谁持有数据
- 与外部依赖/跨服务交互的契约约束明确

阻断条件：
- 边界定义缺失或职责重叠
- 接口只有 happy path，无错误路径
- 数据边界与服务边界冲突，导致实现无法收敛

常见失败模式：
- “模块职责描述”替代“可执行契约定义”
- 接口只写字段，不写错误条件和约束
- 共享数据库但无边界约束说明

三原则裁决：
- 简单：边界最小必要，不引入无证据的层次
- 合适：关键复杂边界（权限、状态机、一致性）必须精确定义
- 演化：边界变化要可迁移，避免一次性断裂

复杂场景附加检查：
- 系统拆分：跨服务契约版本与兼容策略
- 高风险外部依赖：超时、重试、幂等、降级约束

---

## Gate 4：演进可实施性

判断目标：
- 证明设计不仅“看起来对”，而且“能实施、能验证、能回滚”。

必备证据：
- `迁移策略` 明确阶段切分、前置条件与切换方式
- `验证与可观测性` 明确验证指标/方法/观测信号
- `回滚方案` 明确触发条件、回滚路径、数据处理策略
- `风险与缓解` 覆盖高风险项并可验证

阻断条件：
- 无迁移路径或仅一句“逐步迁移”
- 无可观测性与验证策略
- 无回滚闭环或回滚不可执行

常见失败模式：
- 把“上线后观察”当验证方案
- 只写“支持回滚”但无触发条件和步骤
- 风险识别完整但无缓解动作

三原则裁决：
- 简单：迁移路径避免不必要多阶段和额外组件
- 合适：涉及高风险数据/交易时，必须保留必要防护复杂度
- 演化：按需增长复杂度并优先可逆方案；实施上要求每个阶段可验证、可停机、可回退

复杂场景附加检查：
- 旧系统重构：新旧并行阶段的数据一致性与差异校验
- 系统拆分：跨边界事务与一致性补偿策略

---

## Gate 5：计划交接就绪

判断目标：
- 证明 Design 已提供足够约束与追踪信息，Plan 可以稳定拆分执行。

必备证据：
- `待计划约束` 结构化完整，字段齐全
- `覆盖表` 可支持 `AC -> Design -> Plan` 追踪
- `执行追踪覆盖` 证据：不存在不可落地的 AC
- 不可并行项、关键依赖、前置验证事项清晰

阻断条件：
- 缺失 `待计划约束` 或内容无法指导任务拆分
- 覆盖表无法支持追踪链路
- 存在明显“Design 能描述但 Plan 无法拆分”的黑箱点

常见失败模式：
- 只给架构图，不给可拆分约束
- 覆盖表有名无实，无法追踪到可执行任务
- 把关键依赖留给实现阶段临场决策

三原则裁决：
- 简单：交接信息只保留能直接影响拆分与顺序的内容
- 合适：关键依赖与高风险前置验证必须显式，不可省略
- 演化：交接结构必须支撑分阶段实施和验证反馈

复杂场景附加检查：
- 系统拆分：不可并行边界、灰度顺序、回切依赖是否显式
- 多团队协作：跨团队接口交接与时序依赖是否明确

---

## 评审结论规则

- 全部 Gate PASS：`REVIEW: DESIGN_OK`
- 任一 Gate FAIL：`REVIEW: DESIGN_ISSUE`

输出要求：
- 逐 Gate 给出 PASS/FAIL 与证据摘要
- 对 FAIL Gate 给出可执行修正点，不写空泛建议
