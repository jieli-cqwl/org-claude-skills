# Task 拆分实践模式

> 引用者：tech-lead SKILL.md Step 4

## 一、正确拆分定义

Task 拆分的目标不是压缩数量，而是形成可被下游稳定执行的最小可交付单元。一个拆分正确的 Task 应同时满足：

- 独立交付：完成后能落到明确文件和边界，不依赖实现者二次猜测
- 独立验收：AC 可单独验证，`verify` 能给出明确 `file:line` 证据
- 独立回滚：失败时可单独撤回，尽量不污染其他 Task 的主路径
- 边界稳定：拆分后不会制造临时接口、重复验收目标或不稳定依赖

裁决优先级：

1. 原子性
2. 边界清晰
3. 依赖清晰
4. 并行性
5. 默认粒度
6. 复杂度预警

结论：`Task` 数量多不等于拆错。大需求出现 `10+` Task 很常见，只要每个 Task 仍满足最小可交付单元定义，并且计划能按 `workstream / phase / batch` 清晰组织。

## 二、拆分启发式

### 何时拆分一个 MOD 为多个 Task

| 场景 | 差的拆法 | 好的拆法 | 原因 |
|------|---------|---------|------|
| MOD 含数据库迁移+业务逻辑 | 全放一个 Task | Task-A: schema 迁移 + 数据兼容; Task-B: 业务逻辑 | 迁移失败可独立回滚，不污染业务代码 |
| MOD 含接口定义+多个消费方 | 全放一个 Task | Task-A: 接口定义+类型; Task-B/C: 各消费方实现 | 接口先稳定，消费方可并行开发 |
| MOD 含共享基础设施(fixtures/helpers)+业务 | 混在业务 Task 里 | Task-A: 共享基础设施; Task-B+: 业务功能 | 基础设施是依赖根，前置后下游可并行 |
| MOD 含前端+后端 | 前后端混合一个 Task | Task-A: 后端 API; Task-B: 前端页面 | 关注点分离，review 更聚焦 |

### 不应拆分的场景

| 场景 | 为什么不拆 |
|------|-----------|
| 改动 <= 3 文件且逻辑内聚 | 拆了反而增加依赖管理开销 |
| 数据模型和唯一使用方强耦合 | 分开会导致 Task 间接口不稳定 |
| 配置文件+使用该配置的唯一模块 | 天然原子操作，拆开无意义 |

## 三、过度拆分信号

| 信号 | 说明 | 建议动作 |
|------|------|---------|
| `shared_files` 过多 | 多个 Task 反复改同一核心文件，说明边界可能切错 | 优先重看边界，必要时合并或重切 |
| 验收目标重复 | 多个 Task 指向同一可观察结果，说明拆分没有形成独立闭环 | 合并重复 Task 或重写 AC 归属 |
| 依赖链过长 | 同一子功能被切成过多串行 Task，导致执行和 review 被拉长 | 按稳定边界回收为更完整的 Task |
| 单 Task 无法独立成立 | 单独完成后系统不可运行、不可验收或不可回滚 | 说明拆分错误，应合并或改切口 |

只有确认出现上述信号时，才考虑合并。不得仅因 Task 数量较多而强制合并。

## 四、执行排序经验规则

| 规则 | 适用条件 | 示例 |
|------|---------|------|
| 高风险前置 | 有技术不确定性（新技术/外部依赖/性能瓶颈） | 先做"第三方支付对接"验证联通性，再做业务流程 |
| 数据层 > 业务层 > 展示层 | 全栈功能，跨 3 层 | Task-1: 建表+迁移 > Task-2: Service 层 > Task-3: API/页面 |
| 共享基础设施先行 | 多 Task 共用 fixtures/helpers/types | Task-1: 测试 fixtures + 共享类型 > Task-2+: 各业务 Task |
| 独立功能优先 | 有 Task 无前置依赖 | 独立 Task 先做，为并行创造条件 |

排序冲突时的优先级：高风险前置 > 数据层优先 > 共享基础设施 > 独立功能

## 五、并行判断启发式

| 判断维度 | 可并行 | 建议串行 |
|---------|--------|---------|
| 文件交集 | 0 个 shared_files | >= 3 个 shared_files |
| 数据依赖 | 读写不同表/不同字段 | 写同一张表的同一字段 |
| 接口依赖 | 各自独立接口 | Task-B 调用 Task-A 新建的接口 |
| 测试隔离 | 测试数据独立 | 共享测试 fixtures 且会修改 |

shared_files 1-2 个时：可并行，但 merge 时需人工确认冲突点。

## 七、全栈功能强制拆分规则

全栈功能（同时涉及前后端）MUST 按以下模式拆分：

| 拆分 | 职责 | 依赖 |
|------|------|------|
| Task-A: 后端 API | 实现接口定义（入参校验、业务逻辑、出参格式、错误码） | 无 |
| Task-B: 前端页面/组件 | 调用 Task-A 的 API，实现交互和展示 | depends_on: Task-A |

约束：
- Task-A 的 AC 必须包含接口契约验证（入参校验、出参格式、错误码覆盖）
- Task-B 的 AC 必须包含联调验证（前端调用后端 API 的端到端验证）
- Task-A 和 Task-B 的 api_ref 必须指向同一接口定义
- 禁止将前后端混合在一个 Task 中（除非改动 <= 1 文件且逻辑完全内聚）

例外条件：
- 改动仅涉及 1 个文件且前后端逻辑完全内聚（如 SSR 页面修改），可合并但需注明 `split_reason: "前后端内聚于单文件，拆分无意义"`

## 八、自检流程

对 Plan 中的 Task 清单逐项执行：

1. 原子性检查：每个 Task 是否可独立实现、验收、回滚？不能则拆分有误
2. 边界检查：拆分是否沿子功能、接口、风险、共享基础设施边界展开？若只是为压文件数而切开，应重做
3. 粒度检查：是否满足默认粒度 `<= 5` 文件？超过时是否已说明不可再拆原因？
4. 复杂度检查：若 Task 总数较多，是否存在过度拆分信号？若无，则保留，不因数量多而强制合并
5. 排序检查：高风险 Task 是否排在前面？数据层是否先于业务层？
6. 并行检查：标注并行的 Task 是否满足"可并行"条件？`shared_files` 是否都已声明？
7. 依赖完整性：`depends_on` 是否反映了真实的执行顺序？有无遗漏？

## 九、草稿收口边界

收口时遵守以下约束：
- 任何 Task 草稿都必须回收到同一冻结版本后，才允许进入最终 `plan.json / tasks.json`
- `shared_files`、`depends_on`、`batch` 只能在主 Agent 冻结后作为真源
- 发现多个候选拆分版本并存时，先收敛再继续，不得把并行草稿当成最终计划
