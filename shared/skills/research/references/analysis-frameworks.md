# 调研分析框架

Trigger: `/research` Step 2 需要判定 `research_mode` 与候选收敛方式时读取。
Read: `references/analysis-frameworks.md`。
Expect: 获得 `selection / analysis / discovery` 的判定规则、输出结构和证据要求。
Consume: `/research` 主流程 Step 2、Step 4 与最终 `research-report.md`。
Evidence: 报告显式写出 `调研模式`，并使用对应模式正文模板。
Sync: 模式定义变化时同步 `SKILL.md`、相关模板和 `tests/test-research-skill-contract.sh`。

`/research` 统一先判断两组独立维度：
- `research_mode`：`selection`、`analysis`、`discovery`
- `presentation_profile`：`decision`、`understanding`、`audit`

## 呈现模式（presentation_profile）

| profile | 目标 | 首屏应该先回答什么 | 典型触发 |
|---------|------|------------------|---------|
| `decision` | 帮用户做决定 | 要回答什么问题、当前判断、决定性理由、最大风险、建议动作 | 技术选型、是否采纳、是否值得投入 |
| `understanding` | 帮用户建立认知 | 这是什么、为什么值得关注、核心机制、适用边界 | 概念拆解、框架辨析、陌生对象理解 |
| `audit` | 帮用户审计证据链 | 当前判断、挑战表、覆盖证明、剩余盲区 | 反方质询、对象定位定案、留档复核 |

默认映射：
- `selection` → 默认 `decision`
- `analysis` → 若目标是“是否采纳/如何行动”则默认 `decision`；若目标是“先看懂再判断”则默认 `understanding`
- `discovery` → 若目标是“先搞清对象是什么”则默认 `understanding`；若目标是“证明为什么它就是/不是它”则默认 `audit`

警告：
- `audit` 不是更高级版本；只有在读者真的要看证据链时才前置覆盖证明
- `decision` 不是删掉证据；只是把证据放到后层
- `understanding` 不等于泛泛科普；仍要写清边界和误解点

## 通用证据分级

| 等级 | 含义 | 典型来源 |
|------|------|---------|
| A | 一手且可复核 | 官方文档、源码、基准测试、生产案例、内部代码扫描 |
| B | 二手但可交叉验证 | 社区统计、公开复盘、第三方测评、行业报告 |
| C | 经验性观点 | 个人文章、论坛评论、播客、演讲摘录 |

规则：
- 关键结论优先使用 A 级证据。
- 只有 B/C 级证据时，必须标注局限性与结论翻转条件。
- 权威来源只提升检索优先级，不直接提升结论等级。

## Selection 框架

适用：技术选型、产品路线、方案比较、工具取舍。

### 评估维度

| 维度 | 权重 | 评估要点 |
|------|------|---------|
| 目标匹配度 | H | 是否直接解决当前问题，关键缺口是否可接受 |
| 证据稳健性 | H | 是否有高质量实证，支持与反方证据谁更强 |
| 成熟度与稳定性 | H | 版本历史、breaking changes、维护节奏、LTS 政策 |
| 集成与迁移成本 | H | 与现有技术栈兼容性、改造范围、试点成本 |
| 长期维护成本 | M | 升级难度、依赖链、许可风险、团队维护负担 |
| 性能与规模边界 | M | 基准数据、资源消耗、扩展上限、极限场景表现 |
| 学习与协作成本 | M | 文档质量、概念复杂度、团队已有经验 |

权重说明：H = 决策关键因素，M = 有影响但非决定性。权重可以调整，但必须说明原因。

## Analysis 框架

适用：拆解别人分享的方案、文章、知识、项目方法、单个技术点。

### 分析维度

| 维度 | 分析要点 |
|------|---------|
| 原始论点 | 它到底在主张什么，是否被过度包装 |
| 核心机制 | 这个说法靠什么成立，不是功能列表而是因果链 |
| 支持证据 | 哪些事实支持它，证据等级和时间是什么 |
| 反方挑战 | 最强反对意见是什么，是否存在反例或失败案例 |
| 适用边界 | 在什么条件下成立，什么条件下失效 |
| 项目适配度 | 对我们当前项目到底值不值得吸收 |

### 论点挑战表模板

| 论点 | 最强支持证据 | 最强反方挑战 | 当前判定 | 结论稳健性 |
|------|-------------|-------------|---------|-----------|
| 论点 1 | ... | ... | 成立/部分成立/不成立/待验证 | 高/中/低 |
| 论点 2 | ... | ... | ... | ... |

### 吸收决策模板

- 可以直接吸收：证据强、适配度高、风险可控
- 改写后吸收：方向对，但要补条件、降假设、换实现
- 不采纳：证据弱、反方更强、或不适配当前上下文

## Discovery 框架

适用：定位 community 里的 skill、MCP、plugin、package、仓库或榜单对象。

### 解析维度

| 维度 | 分析要点 |
|------|---------|
| 原始词条 | 用户原话、截图文案、榜单标题、命令、slug |
| 名称归一化 | 空格/连字符/连写/大小写/owner/别名/命令名 |
| 对象类型覆盖 | repo / skill / MCP / plugin / package / 目录页是否都查过 |
| 上游来源 | 仓库、官方文档、包管理页、目录镜像之间谁是上游 |
| 排除证据 | 为什么某个候选不是目标，缺了什么硬证据 |
| 剩余盲区 | 还有哪些入口没查、哪些条件变化会翻案 |

### 实体解析表模板

| 候选 | 类型 | 上游来源 | 主要证据 | 反证/疑点 | 当前状态 |
|------|------|---------|---------|-----------|---------|
| A | repo/skill/... | ... | ... | ... | 命中/部分命中/排除/待验证 |
| B | ... | ... | ... | ... | ... |

### 判断规则

- `命中`：名称解析、对象类型、上游来源、安装入口/结构等至少两项硬证据一致
- `部分命中`：方向接近，但 owner、类型、安装入口或上游来源仍有冲突
- `排除`：已有反证足以说明它不是目标对象
- `待验证`：候选存在，但缺少能够定案的硬证据
