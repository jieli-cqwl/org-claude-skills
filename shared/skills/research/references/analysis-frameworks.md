# 调研分析框架

本文件只负责 `/research` 的 Source Targeting 辅助、Step 2 候选收敛、Evidence Qualification 和 Step 4 结构化评估。它不是流程入口，不负责范围确认、深度分析、报告自检或用户确认。任何候选收敛或结构化评估，都必须先证明资料/对象找对了。

## 使用边界

- 读取时机：`research_mode`、`presentation_profile`、对象、资料入口和关键维度已经确认或可安全推断之后。
- 允许动作：补齐 Source Targeting 检查、选择研究模式、定义候选/论点/实体的收敛口径、完成 Evidence Qualification、生成结构化评估表和 Decision Package 输入。
- 禁止动作：不得进入深度分析，不得替代 `deep-analysis-template.md`，不得替代 Report Self-Review。
- 停止条件：候选边界、论点边界、对象类型或上游来源仍不清楚时，回到主流程补 Source Targeting；不要用本文件硬凑判断。

## 输出合同

Step 2 必须输出可进入 Step 3 的收敛对象和最小 Source Targeting Package；Step 4 必须输出可进入 challenger 的 Evidence Qualification、结构化评估和 Decision Package 输入。

| research_mode | Step 2 输出 | Step 4 输出 | 失败状态 |
| --- | --- | --- | --- |
| `selection` | TOP 3 候选、淘汰项、评估维度、候选上游来源 | 对比矩阵、证据等级、推荐/次选/不推荐、翻案条件 | 候选多于 3 且无淘汰理由，或只凭弱证据推荐 |
| `analysis` | 1-3 个核心论点、挑战焦点、原始出处 | 论点挑战表、证据等级、当前判定、稳健性 | 论点只是复述原文，没有机制、反方或来源定位 |
| `discovery` | 名称归一化、对象类型覆盖、候选表、排除项 | 实体解析表、证据等级、排除证明、剩余盲区 | 未覆盖别名、对象类型或上游来源就下结论 |

## 模式与呈现

`/research` 统一先判断两组独立维度：

- `research_mode`：`selection`、`analysis`、`discovery`
- `presentation_profile`：`decision`、`understanding`、`audit`

| profile | 目标 | 首屏回答 | 典型触发 |
| --- | --- | --- | --- |
| `decision` | 帮用户做决定 | 当前判断、决定性理由、最大风险、下一步 | 技术选型、是否采纳、是否投入 |
| `understanding` | 帮用户建立认知 | 这是什么、核心机制、适用边界 | 概念拆解、框架辨析、陌生对象理解 |
| `audit` | 帮用户审计证据链 | 当前判断、挑战表、覆盖证明、剩余盲区 | 反方质询、对象定位定案、留档复核 |

默认映射：

- `selection` -> 默认 `decision`
- `analysis` -> 采纳/行动问题默认 `decision`；理解/启发问题默认 `understanding`
- `discovery` -> 定位对象默认 `understanding`；要求证明命中/排除时默认 `audit`

警告：

- `audit` 不是更高级版本；只有读者真的要看证据链时才前置覆盖证明。
- `decision` 不是删掉证据；只是把证据放到后层。
- `understanding` 不等于泛泛科普；仍要写清边界和误解点。

## 证据分级

Evidence Qualification 必须在推荐、排除、采纳或不采纳之前完成。A/B/C 是本参考文件的细分写法，对应主流程里的 strong/medium/weak；弱证据只能生成待验证项，不能单独支撑采纳判断。

| 等级 | 含义 | 典型来源 |
| --- | --- | --- |
| A | 一手且可复核 | 官方文档、源码、基准测试、生产案例、内部代码扫描 |
| B | 二手但可交叉验证 | 社区统计、公开复盘、第三方测评、行业报告 |
| C | 经验性观点 | 个人文章、论坛评论、播客、演讲摘录 |

规则：

- 关键结论优先使用 A 级证据。
- 只有 B/C 级证据时，必须标注局限性与结论翻转条件。
- 权威来源只提升检索优先级，不直接提升结论等级。

## Selection 框架

适用：技术选型、产品路线、方案比较、工具取舍。

| 维度 | 权重 | 评估要点 |
| --- | --- | --- |
| 目标匹配度 | H | 是否直接解决当前问题，关键缺口是否可接受 |
| 证据稳健性 | H | 是否有高质量实证，支持与反方证据谁更强 |
| 成熟度与稳定性 | H | 版本历史、breaking changes、维护节奏、LTS 政策 |
| 集成与迁移成本 | H | 与现有技术栈兼容性、改造范围、试点成本 |
| 长期维护成本 | M | 升级难度、依赖链、许可风险、团队维护负担 |
| 性能与规模边界 | M | 基准数据、资源消耗、扩展上限、极限场景表现 |
| 学习与协作成本 | M | 文档质量、概念复杂度、团队已有经验 |

对比矩阵必须在每个候选格里同时写评分和证据编号。综合判断必须包含推荐、次选、不推荐和各自翻案条件。

## Analysis 框架

适用：拆解别人分享的方案、文章、知识、项目方法、单个技术点。

| 维度 | 分析要点 |
| --- | --- |
| 原始论点 | 它到底在主张什么，是否被过度包装 |
| 核心机制 | 这个说法靠什么成立，不是功能列表而是因果链 |
| 支持证据 | 哪些事实支持它，证据等级和时间是什么 |
| 反方挑战 | 最强反对意见是什么，是否存在反例或失败案例 |
| 适用边界 | 在什么条件下成立，什么条件下失效 |
| 项目适配度 | 对当前项目是推荐、可吸收、待验证还是不采纳 |

论点挑战表必须给出：论点、最强支持证据、最强反方挑战、当前判定、稳健性、失效条件。

## Discovery 框架

适用：定位 community 里的 skill、MCP、plugin、package、仓库或榜单对象。

| 维度 | 分析要点 |
| --- | --- |
| 原始词条 | 用户原话、截图文案、榜单标题、命令、slug |
| 名称归一化 | 空格、连字符、连写、大小写、owner、别名、命令名 |
| 对象类型覆盖 | repo、skill、MCP、plugin、package、目录页是否都查过 |
| 上游来源 | 仓库、官方文档、包管理页、目录镜像之间谁是上游 |
| 排除证据 | 为什么某个候选不是目标，缺了什么硬证据 |
| 剩余盲区 | 还有哪些入口没查，哪些条件变化会翻案 |

判断规则：

- `命中`：名称解析、对象类型、上游来源、安装入口/结构等至少两项硬证据一致。
- `部分命中`：方向接近，但 owner、类型、安装入口或上游来源仍有冲突。
- `排除`：已有反证足以说明它不是目标对象。
- `待验证`：候选存在，但缺少能够定案的硬证据。
