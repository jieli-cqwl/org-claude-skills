# 深度分析模板

Trigger: `/research` Step 3 对候选对象或核心论点做并行深挖时读取。
Read: `references/deep-analysis-template.md`。
Expect: 获得单个候选/论点的核心机制、证据、反方挑战和失效边界结构。
Consume: TeamCreate 深度分析成员与主 Agent 的证据汇总。
Evidence: 最终报告的证据层包含每个候选/论点的机制、证据源、反方挑战和待验证项。
Sync: 深挖结构变化时同步 `SKILL.md` Step 3、报告模板和研究合同测试。

单个分析目标的深度分析结构。每个目标必须按此结构完成，不可省略任何必填节。
它属于报告的证据层/审计层展开，不应该抢占 `decision` 或 `understanding` 首屏。

## 模板

```markdown
## {分析目标名称}

### 核心机制（必填，每段有证据）
- 解决什么问题：[一句话 + 证据源]
- 怎么解决：[核心技术原理/设计思路，不是功能列表]
- 适用边界：[在什么条件下有效/失效]

### 证据分层（必填）
- A 级证据：[官方文档/源码/基准/生产案例]
- B 级证据：[社区统计/第三方测评/行业报告]
- 证据冲突：[哪些来源互相冲突，当前如何处理]

### 正反论证（必填）
- 最强支持证据：[最能支撑当前论点的事实]
- 最强反方挑战：[最强的反对意见或替代解释]
- 反例/失败案例：[在哪些场景下失败，为什么失败]

### 深层分析（必填，每段有证据）
- 设计哲学：[核心设计理念]
- 关键取舍：[为了什么放弃了什么]
- 演进方向：[roadmap / RFC 中的变化]

### 项目适配评估（必填）
- 最匹配的点：[为什么适合当前项目]
- 最不匹配的点：[为什么不适合当前项目]
- 采纳成本：[工作量 + 风险]
- 退出成本：[切换代价]

### 当前判断（必填）
- 判定：[成立 / 部分成立 / 不成立 / 待验证]
- 结论稳健性：[高 / 中 / 低 + 理由]
- 失效边界：[什么条件变化会让当前判断失效]
- 待验证项：[必须补的实验、数据或代码验证]
```

## 证据标准

### 有效证据

| 类型 | 说明 | 示例 |
|------|------|------|
| 官方文档 | 项目官方文档、API 参考、设计文档 | "据 React 官方文档 Concurrent Mode 章节..." |
| 基准测试 | 有明确条件和环境的性能测试数据 | "TechEmpower Round 22 中，框架 X 在 JSON 序列化场景下..." |
| 源码分析 | 直接阅读源码得出的结论 | "从 src/core/scheduler.ts 第 42 行可见..." |
| 社区数据 | GitHub stars/issues/PR 频率、NPM 下载量 | "过去 12 个月 GitHub issues 关闭率 85%..." |
| 生产案例 | 公开的生产环境使用案例和效果数据 | "Shopify 在 2024 年将 X 迁移至 Y，处理量从..." |
| RFC/ADR | 项目的技术决策记录和提案 | "据 RFC-0042，该特性被拒绝的原因是..." |

### 无效证据

| 类型 | 问题 | 处理方式 |
|------|------|---------|
| 个人博客主观评价 | 无法验证，可能有偏见 | 仅作参考，不作为论据 |
| 过时信息（>2 年） | 技术生态变化快 | 标注时间，补充当前状态 |
| 无出处的数据 | 无法追溯验证 | 标注"无实证"，列出验证方式 |
| "大家都在用" | 流行度 ≠ 适合度 | 替换为具体采用数据 + 适配分析 |
| 营销材料 | 立场偏颇 | 交叉验证，以实测/社区反馈为准 |

### 判定规则

- `成立`：支持证据强于反方挑战，且项目适配度明确
- `部分成立`：方向成立，但依赖额外条件或仅适用于局部场景
- `不成立`：反方挑战更强，或关键证据缺失/被反例击穿
- `待验证`：当前证据不足以下结论，但已明确验证路径
