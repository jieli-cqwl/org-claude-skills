# 设计共创模板

> 引用者：design SKILL.md Step 3/4/5/7
> 设计模式：Wizard-Style Workflow（Anthropic 官方 Skill 模式）
> 核心参考：skills/product/references/conversation-guide.md（对话节奏）、Superpowers brainstorming（共创流程）

## 共创对话原则

- 一次一个问题，问完 STOP 等用户回应
- 优先选择题（2-3 个选项 + 推荐），开放题用于选项无法覆盖时
- 先呈现事实发现，再提问——给用户判断的上下文
- 用业务语言，不用技术术语轰炸
- 用户回应后先复述理解，再进入下一个问题

## 深度路由

| 深度 | 触发信号 | 共创行为 |
|------|---------|---------|
| 快速收敛 | 决策点 <= 2、约束清晰、用户已充分分析 | 1-2 轮确认后进入边界定义 |
| 标准探索 | 一般架构设计、有待确认项 | 逐项决策点提问确认 |
| 深度探索 | 跨模块/服务、隐含假设多、用户描述方案而非问题 | 挑战假设，多轮问题拆解 |

动态升级：共创中发现复杂度升级时提升深度。用户催促时简化非关键问题，但不跳过影响架构正确性的追问。

## 问题拆解提问指南（Step 3）

### 引出业务约束
- "PRD 提到了 [X]，这个约束的根源是什么？是技术限制、合规要求还是业务规则？"
- "这个场景的并发量级大概是？高峰期和日常差多少？"
- "如果 [X] 做不到 100% 实时，业务上能接受多少延迟？"

### 区分刻意选择 vs 历史遗留
- "现有系统用了 [Y 模式]，这是当时刻意的设计选择还是历史原因？"
- "如果从零开始，你还会选这个方案吗？"

### 质量属性优先级（驱动架构决策的核心）
- "性能、可靠性、安全、可维护性——这次最重要的是哪个？有没有明确的量化目标？"
- "一致性和可用性如果不能兼得，你优先哪个？"
- "[方案 A] 更简单但扩展性差，[方案 B] 更灵活但复杂度高，你倾向哪边？"

### 领域建模
- "这个功能涉及的核心业务概念有哪些？它们之间的关系是什么？"
- "哪些概念是同一个限界上下文的？哪些应该分开管理？"

## 决策点清单呈现模板（Step 4）

```
基于问题拆解，我识别了以下需要决定的事：
1. [决策点] — [为什么需要决定，用业务语言]
2. ...
你看还有遗漏的吗？哪个你认为不需要深入对比？
```

## 方案探索呈现模板（Step 5）

```
[决策点名称]
背景：[为什么需要做这个决定]
方案 A：[一句话] — 好处：[...] / 代价：[...]
方案 B：[一句话] — 好处：[...] / 代价：[...]
我推荐 [方案 X]，因为 [核心理由]。但如果 [某条件成立]，方案 Y 会更合适。
你倾向哪个？或者有别的想法？
```

## 方案对比必评维度

| 维度 | 评估要点 |
|------|---------|
| 实现复杂度 | 代码量、新概念引入数、团队学习成本 |
| 运行时性能 | 延迟、吞吐、资源消耗（仅性能敏感场景） |
| 可维护性 | 改动传播范围、调试难度、新人理解成本 |
| 迁移成本 | 数据迁移、接口兼容、灰度切换、回滚复杂度 |
| 演进弹性 | 对已知 roadmap 中下一步需求的适应能力 |
| Constitution 合规 | 方案是否与项目架构原则一致 |

维度冲突时的裁决顺序：L1 非协商约束 > L2 质量属性优先级（须用户确认）> L3 可逆性优先 > L4 默认选简单。详见 `reference/设计原则.md` 裁决规则。

## 实施策略确认模板（Step 7）

```
迁移方式：{一句话描述} → 风险：{关键风险} → 回滚：{回滚能力概述}
这里有个复杂度取舍想跟你确认：[复杂度项] 去掉的话是否仍满足目标？
你对这个实施策略有没有顾虑？
```
