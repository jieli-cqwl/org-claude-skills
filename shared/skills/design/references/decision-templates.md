# 设计共创模板

> 引用者：design SKILL.md Step 3/4/5/7
> 设计模式：Wizard-Style Workflow（Anthropic 官方 Skill 模式）
> 核心参考：`../../product-manager/references/conversation-guide.md`（对话节奏）

## 阶段补充字段

本文件只保留 design 阶段决策收敛真正需要的最小草稿字段。

| 字段 | 含义 | 约束 |
|------|------|------|
| `decision_id` | 决策编号 | 与 `design.json.key_decisions[*].decision_id` 一致 |
| `decision_state` | 决策状态 | 只允许 `候选` / `待裁决` / `已冻结`；最终 design 只能保留 `已冻结` |
| `fact_anchor` | 现状依据锚点 | 指向 `runtime-fact-capture` 的维度或采证命令 |
| `option_id` | 候选方案编号 | `A/B/C...`，只用于草稿对比 |
| `tradeoff` | 方案代价与收益 | 必须写清对比点 |
| `user_confirmation` | 用户确认记录 | 必须可回溯到共创轮次 |
| `adr_ref` | ADR 引用 | 冻结后才可填写 |

## 共创对话原则

- 一次只推进一个决策点
- 先给事实，再给选项
- 优先选择题，必要时再开放题
- 用户回应后先复述，再进入下一步

## 深度路由

| 深度 | 触发信号 | 共创行为 |
|------|---------|---------|
| 快速收敛 | 决策点 <= 2、约束已冻结、无跨模块依赖 | 1-2 轮确认后进入边界定义 |
| 标准探索 | 存在未冻结决策点，但无跨模块/跨服务依赖 | 逐项决策点提问确认 |
| 深度探索 | 跨模块/跨服务、外部依赖、多隐含假设、用户描述方案而非问题 | 挑战假设，多轮问题拆解 |

动态升级：共创中发现依赖范围扩大、未冻结决策增加或外部约束出现时提升深度。用户催促时可压缩非关键问题，但不跳过影响正确性的追问。

## 问题拆解提问指南（Step 3）

### 引出业务约束
- "PRD 提到了 [X]，这个约束的根源是什么？是技术限制、合规要求还是业务规则？"
- "这个场景的并发量级大概是？高峰期和日常差多少？"
- "如果 [X] 做不到 100% 实时，业务上能接受多少延迟？"

### 区分刻意选择 vs 历史遗留
- "现有系统用了 [Y 模式]，这是当时刻意的设计选择还是历史原因？"
- "如果从零开始，你还会选这个方案吗？"

### 质量属性优先级（驱动架构决策的核心）
- "性能、可靠性、安全、可维护性——这次最重要的是哪个？有没有明确的量化目标？"
- "一致性和可用性如果不能兼得，你优先哪个？"
- "[方案 A] 更简单但扩展性差，[方案 B] 更灵活但复杂度高，你倾向哪边？"

### 领域建模
- "这个功能涉及的核心业务概念有哪些？它们之间的关系是什么？"
- "哪些概念是同一个限界上下文的？哪些应该分开管理？"

## 决策点清单呈现模板（Step 4）

```
基于问题拆解，我识别了以下需要决定的事：
1. [决策点] — [为什么需要决定，用业务语言]
2. ...
你看还有遗漏的吗？哪个你认为不需要深入对比？
```

## 方案探索呈现模板（Step 5）

```
[决策点名称]
背景：[为什么需要做这个决定]
方案 A：[一句话] — 好处：[...] / 代价：[...]
方案 B：[一句话] — 好处：[...] / 代价：[...]
我推荐 [方案 X]，因为 [核心理由]。但如果 [某条件成立]，方案 Y 会更合适。
你倾向哪个？或者有别的想法？
```

## Option Draft Agent 落盘要求

- 每个候选至少写：`decision_id`、`decision_state ∈ {候选, 待裁决}`、`fact_anchor`、`option_id`、`tradeoff`
- 如仍有待确认点，显式写 `unresolved_item`、owner 和下一步
- 输出边界：只给候选对比，不给最终冻结结论；最终写回 `design.json.key_decisions` 时必须由主 Agent 转成 `decision_state=已冻结`

## 冻结回填模板

```
decision_id: D-xxx
decision_state: 已冻结
fact_anchor: [现状事实维度 / 采证命令]
user_confirmation: [用户原话或轮次]
adr_ref: ADR-xxx
```

> ADR Draft Agent 若被启用，只能先产出结构草稿；`ADR-NNN.md` 的最终正文必须由主 Agent 在冻结后转写，不能把 draft 直接落为最终工件。

## 方案对比必评维度

| 维度 | 评估要点 |
|------|---------|
| 实现复杂度 | 代码量、新概念引入数、团队学习成本 |
| 运行时性能 | 延迟、吞吐、资源消耗（仅性能敏感场景） |
| 可维护性 | 改动传播范围、调试难度、新人理解成本 |
| 迁移成本 | 数据迁移、接口兼容、灰度切换、回滚复杂度 |
| 演进弹性 | 对已知 roadmap 中下一步需求的适应能力 |
| Constitution 合规 | 方案是否与项目架构原则一致 |

维度冲突时的裁决顺序：L1 非协商约束 > L2 质量属性优先级（须用户确认）> L3 可逆性优先 > L4 默认选简单。详见 `{{RUNTIME_HOME}}/reference/设计原则.md` 裁决规则。

## 实施策略确认模板（Step 7）

```
迁移方式：{一句话描述} → 风险：{关键风险} → 回滚：{回滚能力概述}
这里有个复杂度取舍想跟你确认：[复杂度项] 去掉的话是否仍满足目标？
你对这个实施策略有没有顾虑？
```
