# 设计决策协作方法

## 目标

把模糊架构问题拆成可裁决的决策点。每轮只关闭一个决策，并把事实、方案、取舍、用户确认写成冻结设计。

## 协作规则

- 你负责方法：先给推荐、依据和取舍，再让用户确认会改变结论的事实、约束或风险接受。
- 用户负责裁决：确认领域事实、业务语义、质量优先级、外部约束和风险接受。
- 优先选择题；开放题只用于补齐会改变结论的事实。
- 用户回应后先复述确认，再写入冻结字段或继续下一轮。
- 约束清楚且决策少时快速收敛；跨模块、外部依赖或隐含假设多时逐项深挖。

## 决策发现

优先识别这些决策点：
- 约束根源：业务规则、合规、技术限制或历史选择。
- 质量排序：性能、可靠性、安全、可运维性、可维护性、成本效率的优先级和指标。
- 一致性取舍：一致性、可用性、延迟、成本和可回滚性的冲突。
- 边界划分：核心业务概念、限界上下文、数据 owner 和调用方向。

决策点清单：
```text
1. [决策点] - [影响的架构边界 / 质量属性 / 风险]
```

## 方案呈现

```text
[决策点]
事实: [...]
推荐: [方案 A] / 好处: [...] / 代价: [...] / 失效条件: [...]
备选: [方案 B] / 好处: [...] / 代价: [...]
确认问题: [一个会改变结论的事实、约束或风险接受问题]
```

候选草案只服务方案比较；写回 `design.json.key_decisions` 时转成 `decision_state=已冻结`。

ADR 只能从已验证 `design.json` 派生；不能把 draft 直接写为最终工件；draft 保持候选状态。

方案对比必评：实现复杂度、运行时性能、可维护性、迁移成本、演进弹性、Constitution 合规。

裁决顺序：L1 非协商约束 > L2 质量属性优先级（须用户确认） > L3 可逆性优先 > L4 默认选简单。

确认前检查：这个选择错了如何暴露；哪个约束变化会触发反悔；是否存在更小可逆方案；谁维护、验证并承担成本。

## 冻结产出

冻结决策回答：决策点是什么、事实锚点是什么、同一决策点下比较过哪些本质不同方案、为什么选择当前方案、失效条件是什么、用户确认了什么。`option_analysis[].decision_ref` 归属决策点，`option_analysis[].fact_refs` 支撑备选项取舍，`key_decisions[].option_ref` 只指向同组已选项。ADR 只是验证后的投影视图。
