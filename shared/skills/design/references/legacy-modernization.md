# 旧系统重构方法（场景方法论）

> 引用者：`design/SKILL.md`。仅在"设计场景判断 = 旧系统重构"时强参考。
> 目标：不中断业务前提下演进到目标架构，固定回答 5 个问题。

## Resource Contract

| 字段 | 内容 |
| --- | --- |
| Trigger | S4 判断设计场景为旧系统重构，或存在新旧兼容、数据迁移、灰度切换、回滚补偿问题 |
| Read | `references/legacy-modernization.md` |
| Expect | 获得现状建模、关键决策点、演进路径、验证方式和回滚方式的重构场景框架 |
| Consume | 写入 `design.json.input_analysis`、`design.json.migration_plan`、`design.json.rollback_plan`、`design.json.risks` |
| Evidence | 迁移阶段有发布策略、成功标准、验证方式、回滚触发和数据补偿说明 |
| Sync | 变更时同步 `design/SKILL.md`、design template/schema、semantic validator、review prompts 和 fixtures |

| 阶段 | 必须回答 | 最小输出 |
|------|---------|---------|
| 1) 现状建模 | 痛点（性能/稳定性/交付效率/合规/安全）、不可破坏约束（业务规则/数据一致性/外部契约）、历史包袱（耦合点/数据质量/高风险模块） | 表：现状域 / 主要问题 / 业务影响 / 证据 |
| 2) 关键决策点 | 改造策略（绞杀/抽象分支/并行运行/保留分层）、新旧接口兼容策略、数据迁移策略（全量/增量/双写/回放）、切换策略（路由/开关/版本） | 每决策给出备选方案 + 选择依据 |
| 3) 演进路径 | 禁止"最终重写后一次切换"；每阶段必须可独立发布、独立验证、独立回退 | 表：阶段 / 改造范围 / 发布策略 / 成功标准 |
| 4) 验证方式 | 功能一致性（新旧结果一致）、契约兼容（调用方无需大改）、数据一致性（账实一致可对账）、运行稳定性（错误率/延迟/资源在阈值内） | 每阶段逐项定义 |
| 5) 回滚方式 | 回滚触发阈值（错误率/核心流程失败率/数据偏差）、回滚路径（流量切回/版本回退/开关回退）、数据回滚与补偿（双写回放/对账修复）、RTO 与 RPO | 每阶段明确 |

三原则裁决（与 `{{RUNTIME_HOME}}/reference/设计原则.md` 对齐）：
- 简单：最小侵入 + 最短反馈链，优先削减 Accidental Complexity
- 合适：高风险链路保留必要复杂度，不为“整洁”引入额外机制
- 演化：按需增长复杂度 + 可逆性优先 + 延迟不可逆决策（LRM）
本场景中的演化证据：每阶段可独立发布、独立验证、独立回退。
原则冲突按 L1-L4 裁决（L1 非协商约束 > L2 质量属性优先级 > L3 可逆性优先 > L4 默认选简单）。
自检：「去掉这个，业务需求是否仍满足？」能 -> Accidental，应削减。
