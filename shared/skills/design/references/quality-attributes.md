# 质量属性方法

## 目标

把性能、可靠性、安全、可运维性、可维护性、成本效率等目标写成可取舍、可验证的设计约束。每个质量属性都要落成场景、优先级、目标指标、设计策略和验证引用。

## 执行规则

- 质量目标优先从 PRD 非功能需求提取；缺失时先协作确认，未确认前不写入 `quality_attributes`。
- 每个质量属性必须写成质量场景：触发条件、运行环境、期望响应、可度量指标。
- 写入 `quality_attributes` 的每个质量属性必须给出设计策略、取舍理由和 `verification_refs`。
- 有冲突时先让用户确认优先级，再进入方案取舍。
- 性能优化先给瓶颈证据、容量假设或用户确认的目标指标，再讨论缓存、异步或批处理。
- 缓存决策写明失效、回滚、观测和数据一致性影响，并取得用户确认。
- 降级、熔断或重试策略改变用户体验、业务语义、告警责任或恢复流程时，先取得用户确认。

## 质量场景

| 要素 | 问题 |
|------|------|
| 触发条件 | 谁在什么情况下触发质量要求？ |
| 运行环境 | 正常流量、峰值、故障、迁移期还是降级态？ |
| 期望响应 | 系统应该如何响应、恢复、拒绝或告警？ |
| 可度量指标 | 用什么阈值证明达标？ |

## 常见属性

| 属性 | 指标 | 策略 | 验证 |
|------|--------------|-------------|---------|
| 性能 | 延迟、吞吐、资源占用 | 缓存、异步、批处理、索引优化 | 压测/基准对比 |
| 可靠性 | 可用性、故障恢复时间 | 重试、熔断、降级、幂等 | 故障注入/恢复演练 |
| 安全 | 认证授权、数据保护 | 权限模型、输入校验、加密、审计 | 安全测试/渗透验证 |
| 可运维性 | 可观测性、告警质量、发布恢复 | 日志追踪、健康检查、灰度、回滚 | 冒烟、告警演练、发布演练 |
| 可维护性 | 变更成本、认知负荷、边界稳定 | 清晰边界、单一职责、少量稳定抽象 | 代码审查、变更影响分析 |
| 成本效率 | 资源成本、人工维护成本 | 复用现有能力、按实际容量扩展、避免过度冗余 | 成本估算、容量基线 |
| 资源效率 | 能耗、资源利用率、闲置比例 | 合理容量、区域/资源选择、减少无效计算 | 容量与利用率观测 |

## 取舍检查

- 可靠性提升增加的成本或操作复杂度是否被用户接受。
- 安全控制改变的用户路径、运营流程或故障恢复方式是否被产品确认。
- 性能优化牺牲的可维护性、数据一致性或回滚能力是否有验证和补偿。
- 成本压缩降低的峰值容量、可观测性或恢复能力是否进入风险回应。
- 新抽象解决真实变化点，而不是提高当前实现的认知负担。

## 有效质量属性

- 质量属性必须能解释某个设计选择；不能只作为形容词存在。
- 目标指标必须可测量；无法量化时写成可观察信号和判定阈值。
- 策略必须能映射到验证引用；没有验证引用的质量目标只能作为待确认项。
- 质量属性冲突必须有用户确认的优先级，不能由设计者隐式排序。

## 产出

每个质量属性写清场景、优先级、目标指标、设计策略、取舍说明和 `verification_refs`。`verification_refs` 必须能解析到 `verification_mapping[].evidence_ref`；没有指标或验证引用的质量目标只能作为待确认项，不能支撑关键决策。
