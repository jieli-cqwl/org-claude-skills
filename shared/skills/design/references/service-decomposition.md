# 系统拆分方法

## 目标

把拆分方案落到可实施设计。新边界必须降低真实协作、部署、扩展或质量属性压力。

## 执行顺序

| 阶段 | 必须回答 | 最小输出 |
|------|---------|---------|
| 1) 现状建模 | 模块边界/调用链/共享数据点、事务一致性热点/并发热点/故障热点、外部依赖与跨团队协作边界 | 表：现状域（调用关系/数据关系/一致性关系） / 事实 / 证据 |
| 2) 关键决策点 | 服务边界怎么切、数据边界怎么切、同步/异步通信选择、一致性策略（强一致/最终一致/补偿）、迁移阶段切分点 | 每决策给出 2 个本质不同方案 + 取舍理由 |
| 3) 演进路径 | 每阶段可单独发布、有观测信号、可独立回滚 | 表：阶段 / 目标 / 入口变更 / 数据变更 / 退出标准 |
| 4) 验证方式 | 功能验证（关键 AC 新旧路径可验证）、契约验证（接口输入/输出/错误码兼容）、一致性验证（异常场景不破坏业务规则）、性能验证（时延/吞吐不低于基线） | 每阶段逐项定义 |
| 5) 回滚方式 | 触发条件（何时判定回滚）、回滚路径（路由/开关/版本切回）、数据策略（双写停用/补偿/对账修复）、时效要求（多久内完成回滚恢复服务） | 每阶段明确 |

## 有效拆分标准

- 新边界必须减少真实协作、部署、扩展或质量属性压力；不能只为了代码整洁。
- 数据所有权必须清楚；共享数据、双写、补偿和对账没有策略时不得拆分。
- 跨边界调用必须说明同步/异步选择、失败语义和可观测信号。
- 每个迁移阶段必须可发布、可停止、可回退，并有退出标准。

## 产出

写入模块边界、数据所有权、接口边界、迁移阶段和待计划约束。每个拆分边界必须有事实证据、消费者、验证方式和回滚策略。
