# 系统拆分方法（场景方法论）

> 引用者：`design/SKILL.md`。仅在"设计场景判断 = 系统拆分"时强参考。
> 目标：把拆分方案落到可实施设计，固定回答 5 个问题。

## Resource Contract

| 字段 | 内容 |
| --- | --- |
| Trigger | S4 判断设计场景为系统拆分，或出现跨模块、跨服务、共享数据、一致性边界问题 |
| Read | `shared/skills/design/references/service-decomposition.md` |
| Expect | 获得边界切分、数据所有权、通信方式、一致性策略、迁移阶段的判断材料 |
| Consume | 写入 `design.json.modules`、`design.json.data_architecture`、`design.json.interface_boundary`、`design.json.planning_constraints` |
| Evidence | 模块边界、数据边界、验证方式和回滚路径能追溯到事实或用户确认 |
| Sync | 变更时同步 `design/SKILL.md`、design template/schema、semantic validator、tech-lead 消费规则和 fixtures |

| 阶段 | 必须回答 | 最小输出 |
|------|---------|---------|
| 1) 现状建模 | 模块边界/调用链/共享数据点、事务一致性热点/并发热点/故障热点、外部依赖与跨团队协作边界 | 表：现状域（调用关系/数据关系/一致性关系） / 事实 / 证据 |
| 2) 关键决策点 | 服务边界怎么切、数据边界怎么切、同步/异步通信选择、一致性策略（强一致/最终一致/补偿）、迁移阶段切分点 | 每决策给出 2 个本质不同方案 + 取舍理由 |
| 3) 演进路径 | 禁止"一步到位重构"；每阶段可单独发布、有观测信号、可独立回滚 | 表：阶段 / 目标 / 入口变更 / 数据变更 / 退出标准 |
| 4) 验证方式 | 功能验证（关键 AC 新旧路径可验证）、契约验证（接口输入/输出/错误码兼容）、一致性验证（异常场景不破坏业务规则）、性能验证（时延/吞吐不低于基线） | 每阶段逐项定义 |
| 5) 回滚方式 | 触发条件（何时判定回滚）、回滚路径（路由/开关/版本切回）、数据策略（双写停用/补偿/对账修复）、时效要求（多久内完成回滚恢复服务） | 每阶段明确 |

三原则裁决（与 `{{RUNTIME_HOME}}/reference/设计原则.md` 对齐）：
- 简单：最少边界变更 + 最小迁移面，优先削减 Accidental Complexity
- 合适：真实复杂一致性场景保留必要机制，不做无证据复杂化
- 演化：按需增长复杂度 + 可逆性优先 + 延迟不可逆决策（LRM）
本场景中的演化证据：阶段性可验证、可停机、可回退。
原则冲突按 L1-L4 裁决（L1 非协商约束 > L2 质量属性优先级 > L3 可逆性优先 > L4 默认选简单）。
自检：「去掉这个，业务需求是否仍满足？」能 -> Accidental，应削减。
