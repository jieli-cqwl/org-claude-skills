# 风险评估方法

## 目标

识别会阻断实施或放大业务损失的风险，并给出可执行缓解动作。

## 风险分类

| 维度 | 常见信号 |
|------|------|
| 技术风险 | 性能瓶颈、迁移失败、外部依赖不稳定 |
| 交付风险 | 单点知识、跨团队阻塞、关键资源冲突 |
| 业务风险 | 合规缺口、核心流程失败、数据偏差 |

## 评估矩阵

按概率(P) x 影响(I)评估优先级：

| P\I | 高影响 | 中影响 | 低影响 |
|-----|--------|--------|--------|
| 高概率 | P0 | P1 | P2 |
| 中概率 | P1 | P2 | P3 |
| 低概率 | P2 | P3 | P3 |

## 裁决标准

- P0：必须有可执行缓解动作、验证方式和回滚触发；缺任一项则不能完成设计。
- P1：必须有缓解动作、负责人或下游承接路径。
- 任意风险：只写“关注/监控”但没有动作、证据或触发条件，视为无效风险项。
- 风险缓解不能引入无证据复杂度；复杂防护必须对应高影响风险。
- 风险回应必须能被下游消费：高影响风险需要写入 `risk_response`、`verification_mapping`、`rollback_plan` 或 `planning_constraints` 中至少一个可执行承接点；无法映射到验证、回滚、计划或用户裁决的风险，不得作为已闭合风险。

## 有效风险回应

- 缓解动作必须能改变风险概率、影响或发现时间；只写“关注/监控”无效。
- 高影响风险必须有触发阈值、负责人、验证方式和回滚或升级路径。
- 复杂防护必须绑定具体风险；没有高影响场景支撑时不进入设计。

## 产出

每条风险写清维度、概率、影响、优先级、缓解动作、验证方式、回滚触发或升级路径。无法设计缓解动作的高优风险必须升级给用户裁决。
