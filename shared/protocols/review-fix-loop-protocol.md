# 外层修复循环协议

> 类型：skill-specific 协议（非通用按需知识）。
> 职责: 定义"审完 -> 修 -> 重审"的外层修复循环控制参数，适用于所有带评审步骤的 skill。
> 边界: 本协议只控制修复循环的次数、收敛判定和熔断机制，不干预单次审查的内部深度（由内层审查递增协议控制）。
> 引用者: /product S11、/design S9、/tech-lead Step 7、/project-manager P3
> 内层协议: `reference/review-iteration-protocol.md`（R1->R2->R3 审查递增）

## 核心参数

```
max_rounds: 10
convergence: delta_findings = 0 -> 正常收敛
non_convergence: 连续 2 轮问题数不减少 -> AskUserQuestion 暂停
circuit_breaker: 同一问题连续 3 轮未关闭 -> BLOCKED
shallow_pass_guard: R1 无问题时强制 R2 确认
```

| 参数 | 值 | 语义 |
|------|-----|------|
| max_rounds | 10 | 外层修复循环的硬上限轮数；达到后强制终止 |
| convergence | delta_findings = 0 | 本轮重审新增问题数为零，判定为正常收敛，循环结束 |
| non_convergence | 连续 2 轮问题数不减少 | 问题数停滞或上升，表明当前修复方向可能有误，暂停等用户介入 |
| circuit_breaker | 同一问题连续 3 轮未关闭 | 该问题被标记为 BLOCKED，停止尝试自动修复，报告给用户 |
| shallow_pass_guard | R1 无问题时强制 R2 确认 | 防止浅层审查遗漏：即使首轮零问题，也必须执行第二轮确认 |

## 收敛判定逻辑

每轮重审结束后，统计本轮新增的 FAIL 项数量（delta_findings）：

1. delta_findings = 0: 正常收敛。输出最终审查报告，循环结束。
2. delta_findings > 0: 尚有新问题。进入修复阶段，修复后触发下一轮重审。
3. 每轮均记录 FAIL 项数量，用于趋势分析（不收敛检测和达上限终止报告均依赖此数据）。

## 不收敛判定与暂停机制

触发条件: 连续 2 轮问题数不减少（含持平和上升两种情况）。

处理流程:
1. 暂停修复循环
2. AskUserQuestion，展示趋势数据：各轮 FAIL 数、问题类别分布、修复尝试摘要
3. 等待用户指示：调整修复方向 / 跳过特定问题 / 终止循环
4. 收到指示后恢复循环或按用户要求终止

non_convergence 暂停时的 AskUserQuestion 模板:
```
修复循环未收敛（连续 {N} 轮问题数未减少）。

趋势：
| 轮次 | FAIL 数 | 新增 | 已关闭 |
|------|---------|------|--------|
| ...  | ...     | ...  | ...    |

残留问题：[问题列表]

请选择：
1. 调整修复方向（请说明）
2. 跳过特定问题继续
3. 终止循环
```

## 熔断机制（circuit_breaker）

触发条件: 同一问题（按 Issue ID 追踪）连续 3 轮未关闭。

处理流程:
1. 将该问题标记为 BLOCKED
2. 停止对该问题的自动修复尝试
3. 在审查报告中明确标注 BLOCKED 状态和历史修复尝试记录
4. 其他未熔断的问题继续正常的修复-重审循环

设计意图: 避免在单一顽固问题上无限消耗轮次。BLOCKED 不等于放弃——而是将问题升级为需要用户干预或设计层面解决。

## 浅通过防护（shallow_pass_guard）

触发条件: 外层循环首轮（R1）审查结果为零问题。

处理流程:
1. 不直接判定为收敛
2. 强制执行第二轮（R2）审查确认
3. 如果 R2 同样零问题，则判定为正常收敛
4. 如果 R2 发现新问题，则进入正常的修复-重审循环

设计意图: 同一 LLM 自审存在视角盲区，首轮零问题可能是审查不充分而非真正无问题。强制 R2 确认提供第二次检验机会。

## 修复模式声明表

各 skill 在自身 SKILL.md 中声明 fix_mode，本协议定义可选模式：

| skill | fix_mode | 修复主体 | 确认方式 | 说明 |
|-------|----------|---------|---------|------|
| /product S11 | fix_mode=user_directed | 主代理修改文档 | AskUserQuestion | 每轮修复后询问用户确认 |
| /design S9 | fix_mode=user_directed | 主代理修改文档 | AskUserQuestion | 每轮修复后询问用户确认 |
| /tech-lead Step 7 | fix_mode=user_directed | 主代理修改计划 | AskUserQuestion | 每轮修复后询问用户确认 |
| /project-manager P3 | fix_mode=auto | fixer agent | 自动 | fixer agent 自动修复并触发重审 |
| /review | fix_mode=none | 不修复（纯审查） | N/A | 不进入外层修复循环 |

fix_mode 语义:
- user_directed: 主代理执行修复，每轮修复后 AskUserQuestion 确认修复方向
- auto: fixer agent 自动执行修复并触发重审，无需用户逐轮确认
- none: 该 skill 不执行修复，不进入外层修复循环。仅引用内层审查递增协议（如有）

## 用户确认节点

外层修复循环中有 4 个用户确认节点，确保关键决策由用户做出：

### 节点 1: 不收敛暂停

- 触发: 连续 2 轮问题数不减少
- 行为: AskUserQuestion 展示趋势（各轮 FAIL 数、问题分布、修复尝试）
- 用户选项: 调整方向 / 跳过问题 / 终止

### 节点 2: 修复方向存疑

- 触发: fix_mode=user_directed 时，每轮修复完成后
- 行为: AskUserQuestion 展示本轮修复内容和理由
- 用户选项: 确认 / 调整 / 回退

### 节点 3: 达上限强制终止

- 触发: 循环达到 max_rounds（10 轮）仍未收敛
- 行为: 输出终止报告（详见下一章节），不再继续循环
- 输出内容: 未收敛原因 + 风险边界 + 残留问题清单

### 节点 4: DECEPTION 检测

- 触发: 审查中检测到 DECEPTION（欺骗性内容）
- 行为: DECEPTION 检测结果原样展示（不过滤/不汇总/不降级），AskUserQuestion
- 用户选项: 用户选择修复方式（人工修复 / 指定修复策略 / 标记接受）

## 达上限终止输出要求

当循环达到 max_rounds 仍未收敛时，必须输出以下三部分：

### 1. 未收敛原因

分析为什么 10 轮修复后仍有未关闭的问题。可能的原因类别：
- 问题本身超出当前修复能力（需要设计层面变更）
- 修复引入新问题（修复-回归循环）
- 问题定义模糊，无法判定关闭条件

### 2. 风险边界

评估残留问题的潜在影响：
- 对当前交付物的影响范围
- 对下游依赖的风险传导
- 建议的后续处理优先级

### 3. 残留问题清单

列出所有未关闭的 FAIL 项：

```
| Issue ID | 描述 | 首次发现轮次 | 最近修复尝试 | 状态 | 建议处理方式 |
|----------|------|-------------|-------------|------|-------------|
| ...      | ...  | ...         | ...         | OPEN/BLOCKED | ... |
```

## 与内层协议的正交关系

本协议（外层修复循环）与 `reference/review-iteration-protocol.md`（内层审查递增协议）正交：

| 维度 | 外层（本协议） | 内层（review-iteration-protocol） |
|------|--------------|----------------------------------|
| 控制对象 | "审完 -> 修 -> 重审"循环次数 | 单次审查的深度（R1 广度 -> R2 深度 -> R3 对抗） |
| 上限 | max 10 轮 | max 3 轮/次（R1 必执行，R2/R3 按条件触发） |
| 触发场景 | 审查发现 FAIL 后的修复-重审 | 每次"审查"内部的递增检查 |
| 计数方式 | 外层计数独立于内层，内层多轮不影响外层计数 | 内层每轮产出的 findings 汇总后作为外层的输入 |

协作方式:
- 外层每轮"重审"时，如果该 skill 同时引用内层协议，重审按内层的 R1->R2->(R3) 递增执行
- 内层产出的合并 findings 作为外层本轮的审查结果，用于外层的收敛判定
- 两层组合的理论上限：外层 10 轮 x 内层 3 轮/次 = 30 次审查执行。实际因收敛机制远低于此

各 skill 引用关系:
- /product、/design: 同时引用外层 + 内层
- /tech-lead: 引用外层（内层视 SKILL.md 定义）
- /project-manager P3: 引用外层（fixer agent 模式）
- /review: 仅引用内层（fix_mode=none，不进入外层循环）
