# 代码复用

复用判断的是同一业务规则是否该由同一个地方维护。

## 复用判断

同时满足以下条件时，优先复用或在现有实现上重构：

- 语义一致：表达的是同一业务意图，而不是写法相似。
- 变化节奏一致：它们会随同一业务规则一起变化。
- 依赖方向健康：复用不会破坏分层、制造循环依赖或跨边界耦合。
- 抽象后更清晰：职责、命名、边界比原来更容易理解。
- 扩展点稳定：新增变化能落到语义拥有方内扩展，而不是让调用方到处同步改动。

成立信号：同一规则多处出现，历史上发生过同步修改；单点改动能覆盖同一业务意图。

## 保留具体实现的场景

- 当前只有一个实现，还没有稳定重复模式。
- 两段代码外形相似，但业务语义不同。
- 未来变化方向明显不同，只是当前碰巧相似。
- 抽象后需要模糊命名、过多参数或额外中间层。
- 复用会破坏模块边界，或把不相关场景绑在一起。

默认节奏：第一次写清楚，第二次观察模式，重复模式稳定后再抽象。

## 边界清晰的重复

- 测试中的叙事性重复：优先可读性和意图表达。
- 语义尚未稳定的早期实现：先保留具体逻辑，避免过早抽象。
- 未来明确会分叉的场景：宁可暂时重复，也不要制造错误耦合。
- 为隔离边界保留的小范围重复：优先边界稳定，而不是全局共享。

## 判断方式

先确认它们是不是同一份知识，不要把相似命名或流程外观当成语义一致。LSP 可用时，用定义跳转和引用追踪确认真实定义和使用方式；响应慢或偶发超时不构成跳过语义确认的理由。

## 新建举证

选择不复用而新建时，在代码注释、设计文档或 PR 描述中说明：看过哪些候选实现、为什么不能复用、为什么新建比改造更合适。
