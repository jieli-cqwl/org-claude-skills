# 代码复用

复用要减少的是同一知识的重复维护，而不是单纯减少代码行数。行数变少可以是好复用的结果，但不能作为复用是否成立的理由；真正的判断是同一业务语义是否应该由一个清晰拥有方维护。好的复用会让行为更一致、变更更集中、边界更稳定。

## 复用判断

同时满足以下条件时，优先复用或在现有实现上重构：

- 语义一致：表达的是同一业务意图，而不是写法相似。
- 变化节奏一致：它们会随同一业务规则一起变化。
- 依赖方向健康：复用不会破坏分层、制造循环依赖或跨边界耦合。
- 抽象后更清晰：职责、命名、边界比原来更容易理解。

常见信号：同一规则多处出现，历史上发生过同步修改；新需求到来时，单点改动能覆盖同一业务意图。

## 不急着复用的场景

- 当前只有一个实现，还没有稳定重复模式。
- 两段代码外形相似，但业务语义不同。
- 未来变化方向明显不同，只是当前碰巧相似。
- 抽象后需要模糊命名、过多参数或额外中间层。
- 复用会破坏模块边界，或把不相关场景绑在一起。

默认节奏：第一次写清楚，第二次观察模式，重复模式稳定后再抽象。

## 好的复用效果

- 修改更集中：同一知识变化时，改动位置更少。
- 命名更清晰：抽象名称能准确表达业务含义。
- 行为更一致：同一规则不会在不同实现中逐步分叉。
- 调用更简单：调用方认知负担降低。
- 边界更稳定：抽象职责单一，变化原因一致。

如果抽象只能叫 `utils`、`common`、`helper`，参数越来越多，或调用方为了适配抽象写出更多分支，通常说明复用方向错了。

## 允许的战略性重复

- 测试中的叙事性重复：优先可读性和意图表达。
- 语义尚未稳定的早期实现：先保留具体逻辑，避免过早抽象。
- 未来明确会分叉的场景：宁可暂时重复，也不要制造错误耦合。
- 为隔离边界保留的小范围重复：优先边界稳定，而不是全局共享。

## 判断方式

先确认它们是不是同一份知识，不要把相似命名、相似流程外观当成语义一致。

如项目 LSP 可用，可结合定义跳转、引用追踪等方式确认真实定义和使用方式；重点是排除“名字像，但语义并不一样”的误判。只有项目没有对应语言的 LSP server，或调用明确返回 `server not initialized`，才算 LSP 不可用；响应慢、偶发超时不构成跳过语义确认的理由。

## 新建时的最小举证责任

如果最终选择不复用而新建实现，应在代码注释、设计文档或 PR 描述中说明：

- 看过哪些候选实现。
- 为什么这些候选不能直接复用。
- 为什么新建比改造现有实现更合适。
- 本次新建不会制造未来重复维护问题的依据。
