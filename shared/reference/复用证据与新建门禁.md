# 复用证据与新建门禁

> 触发条件：准备新增实现且需要收集复用证据时读取。
> 本文件定义 How：在准备新增实现时，如何为”是否已有可复用代码”收集证据，并为”不复用”留下说明。
> 复用原则、适用时机和效果标准见 `{{RUNTIME_HOME}}/reference/代码复用.md`。

## 适用范围

适用于以下场景：

- 新增功能前，判断是否已有现成实现
- 重构前，判断应扩展现有能力还是新建分支
- 代码审查时，追问“为什么这里没有复用”

## 证据收集的基本顺序

### 1. 文本召回

先用功能词、领域对象、关键动词组合搜索代码库，找候选实现。

建议优先搜索这些目录：

- Java: `service/` `util/` `common/` `helper/`
- Python: `services/` `utils/` `core/` `helpers/`
- TS: `services/` `utils/` `hooks/` `lib/` `components/`

文本搜索的目的不是直接下结论，而是尽量召回候选项。

### 2. 语义确认

文本召回后，如项目 LSP 可用，应继续做语义确认：

- `workspaceSymbol`：定位候选符号
- `goToDefinition`：确认真实定义
- `findReferences`：查看现有调用方和使用方式

这一步的目的，是排除“名字像，但语义并不一样”的误判。

### 3. 影响评估

如果候选实现理论上可复用，再评估：

- 复用是否会破坏边界或引入循环依赖
- 改现有实现是否会影响大量既有调用方
- 候选实现的语义是否足够稳定，还是当前只是碰巧相似
- 在现有实现上重构，是否比新建更清晰、更低风险

## 允许新建实现的典型情况

满足以下任一情况时，新建通常是合理的：

- 没有找到语义一致的候选实现
- 候选实现的业务语义与当前需求本质不同
- 在现有实现上扩展会引入错误耦合或循环依赖
- 现有调用方很多，且改造成本明显高于独立实现
- 为了复用必须引入模糊抽象，反而让职责更不清晰

这里的判断是启发式的，不是机械计数题。重点不是“是否超过某个数字阈值”，而是“复用后是否真的更好”。

## 新建时的最小举证责任

如果最终选择不复用而新建实现，应在代码注释、设计文档或 PR 描述中说明：

- 找过哪些候选实现
- 为什么这些候选项不能直接复用
- 为什么新建比改造现有实现更合适

对 LLM 协作场景，至少应回答下面两个问题：

1. 为什么它不是同一份知识？
2. 为什么这次新建不会制造未来的重复维护问题？

## LSP 不可用的判定

只有以下情况才算 LSP 不可用：

- 项目没有对应语言的 LSP server
- LSP 调用明确返回 `server not initialized`

网络延迟、响应慢、偶发超时，不构成跳过语义确认的理由。LSP 不可用时，可退化为文本搜索和静态引用分析，但应说明证据不足之处。
