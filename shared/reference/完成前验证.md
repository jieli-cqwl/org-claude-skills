# 完成前验证

完成不是“感觉做完”，而是成功标准被当前证据证明。

铁律：亲眼看到验证命令成功之后，才声明完成。

完成前先回到本次变更对应的成功标准；若轻量任务此前未显式写出，则先把“做成什么样算完成”显式化，再确认每条标准都有对应的验证证据与 fresh proving command。

## 验证思路

1. 对齐成功标准：本次目标、完成边界和不可破坏的既有行为是什么。
2. 映射验证证据：每条标准对应测试、构建、运行结果、复现步骤或文档证据。
3. 运行 fresh proving command：使用当前工作区重新执行，不复用历史结论。
4. 检查变更范围：`git diff` 应只覆盖本次目标，并与成功标准和已知约束一致。
5. 汇报验证结果：按标准逐项说明通过、阻塞或不适用原因。

## 代码变更后

- 运行与变更直接相关的测试；共享、核心或高风险路径再扩大回归面。
- 运行构建、类型检查或 linter；没有对应命令时说明不适用原因和替代验证。
- 涉及接口、配置、行为或文档事实变化时，同步对应文档、契约或调用方。
- 基于影响范围确认调用方、用户路径和业务不变量没有被破坏。

## 错误修复后

- 之前失败的命令现在成功。
- 重新执行原复现步骤或回归测试，记录预期结果出现且原错误不再出现；日志仅作为辅助证据。
- 基于影响范围运行对应回归；列出已覆盖对象、未覆盖风险、阻塞项或风险接受依据。

## 验证命令速查

- Python: `pytest tests/ -v` / `ruff check .` / `mypy .`
- TS: `npm test` / `npm run lint` / `npx tsc --noEmit` / `npm run build`
- Java: `mvn test` / `mvn compile` / `curl localhost:8080/actuator/health`

完成汇报前，列出本次适用的验证项；每项记录命令与通过证据，或记录不适用原因和替代验证。
