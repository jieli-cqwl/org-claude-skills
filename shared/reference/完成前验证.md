# 完成前验证

声称完成前，先回到本次成功标准。每条标准必须有对应证据；有验证命令时，用当前工作区重新执行；没有自动化命令时，留下可复验记录。

## 验证步骤

1. 回到成功标准，确认每条都是可判定结果；只描述执行动作时，先按目标重述为可观察结果；重述会改变验收口径时，先取得用户裁决。
2. 从影响范围定义验证面：目标行为、边界路径、失败路径、调用方和业务不变量。
3. 每条标准对应测试、构建、运行结果或可复验记录。
4. 用当前工作区重新执行验证；历史结果和缓存结论只作参考。
5. `git diff` 确认变更只覆盖本次目标。

## 证据标准

- 只采纳能直接证明目标行为或质量约束的命令或记录。
- 没有自动化命令时，形成可复验记录：输入、步骤、预期结果、实际结果和环境。
- 命令失败时先定位根因；如需变更成功标准、调整证据口径或接受未覆盖风险，先报告覆盖缺口与风险并取得用户裁决；裁决前不把弱证据作为通过结论。

## 代码变更后

- 运行与变更直接相关的测试；影响范围包含共享模块、公共契约或用户路径时，扩大回归面。
- 运行项目已有的构建、类型检查或 linter；没有对应命令时说明原因。
- 涉及接口、配置或行为变化时，同步文档、契约或调用方。

## 错误修复后

- 之前失败的命令现在成功。
- 重新执行原复现步骤，确认预期结果出现且原错误不再出现。
- 基于影响范围运行对应回归。

## 命令选择

优先使用项目已有脚本、Makefile、CI 命令或 README 指定的验证入口；命令应能直接证明目标行为或质量约束。
