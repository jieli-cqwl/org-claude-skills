# 完成前验证

完成前验证用于裁决能否声明完成、上线或交付。完成声明必须由本次成功标准、影响范围、当前工作区重新执行的验证命令或可复查记录共同支撑。证据闭合的项才能汇报为已通过；证据缺口归入阻塞、缺陷处理、风险接受或待裁决。

完成前先回到本次变更对应的成功标准；若轻量任务此前未显式写出，则先把“做成什么样算完成”显式化，再确认每条标准都有对应的验证证据与 fresh proving command。

## 裁决顺序

- 回到成功标准：确认每条标准都是目标达成后的可判定结果；只有执行动作或工具命令时，先补成可判定结果。
- 定义验证面：从影响范围确认需要证明的目标行为、边界路径、失败路径、调用方、用户路径、业务不变量和同步项。
- 选择证明方式：每条成功标准应对应测试、构建、运行结果、复现步骤、覆盖率报告、文档证据或可复验记录。
- 重新执行验证：fresh proving command 使用当前工作区的新执行结果；历史结果、缓存结论和上一轮输出只作为参考。
- 核对变更范围：`git diff` 应只覆盖本次目标，并与成功标准、影响范围和已知约束一致。
- 输出裁决结论：验证结果按成功标准逐项汇报为已通过、阻塞或不适用原因。

## 证据标准

- 完成声明只采纳能直接证明目标行为、影响范围或质量约束的命令或记录。
- 没有自动化命令时，形成可复验记录：输入、步骤、预期结果、实际结果、环境和仍未自动化的风险。
- 需要人工判断时，记录判断依据、观察结果、环境和证据位置；截图、录屏和日志应附着在行为验证或复验步骤上。
- 命令失败时先定位根因；调整成功标准、跳过验证或改用更弱证据前，应取得用户裁决。

## 代码变更后

- 运行与变更直接相关的测试；影响范围包含共享模块、公共契约、配置/数据流、用户路径或业务不变量时，扩大到对应回归面。
- 运行项目已有的构建、类型检查或 linter；没有对应命令时说明不适用原因和替代验证。
- 涉及接口、配置、行为或文档事实变化时，同步对应文档、契约或调用方。
- 基于影响范围确认调用方、用户路径和业务不变量没有被破坏。

## 错误修复后

- 之前失败的命令现在成功。
- 重新执行原复现步骤或回归测试，记录预期结果出现且原错误不再出现；日志仅作为辅助证据。
- 基于影响范围运行对应回归；列出已覆盖对象、未覆盖风险、阻塞项或风险接受依据。

## 命令选择

- 优先使用项目已有脚本、package scripts、Makefile、CI 命令、README、AGENTS 或 skill 指定的验证入口。
- 命令应能直接证明目标行为、影响范围或质量约束；语言通用命令只作为候选，项目事实决定最终入口。
- 多个命令都可证明同一标准时，选择最贴近成功标准、影响范围和项目既有验证入口的命令；必要时补充专项命令覆盖风险。

## 完成汇报

完成汇报前，列出本次适用的验证项；每项记录命令与通过证据，或记录不适用原因和替代验证。

完成汇报应逐项说明成功标准、达成状态、验证证据、未覆盖风险和下一步。完成结论按证据范围命名：全部闭合时汇报完成；部分闭合时汇报已通过项、未闭合项和下一步；风险接受时写明接受范围、原因和后续处理方式。
