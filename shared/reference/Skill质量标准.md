# Skill 质量标准

## Why

好的 Skill 让 AI 按真实职责流程办成事：触发正确、关键输入可校验、流程可执行、资源按需、产物被消费、证据可复验。

## 核心原则

1. 真实职责优先：Skill 对应软件工程、项目管理、研究、设计、测试等专业工作中的真实办事流程，围绕办事路径组织内容。
2. 单一职责：`SKILL.md` 写主操作手册；`references/` 承载按需方法论；`scripts/` 承载确定性执行与校验；`schemas/` 和 `templates/` 定义机器或人工产物形状；`evals/` 和 `tests/` 证明能力与回归。
3. 渐进式披露：默认只加载当前步骤需要的信息；长方法论、样例和细则按需读取。
4. 工程化分工：确定性、可枚举、可复验的事项交给脚本、schema、hook、gate 或测试；LLM 聚焦理解意图、专业判断、实现取舍和异常处理。
5. 无消费者即噪音：任何字段、段落、模板、脚本、引用或说明，如果没有明确消费方、使用时机或验证价值，就会干扰模型理解。
6. 正向操作优先：Skill 告诉 AI 如何把事办成；负面边界只保留会改变行为或防止误伤的部分。
7. 证据闭环：完成声明必须能回到成功标准，并由当前运行结果、可复查产物或明确复验命令支撑。
8. 旧资料只是证据：历史设计、旧测试和交接文档可作为输入参考；新目标形态由当前职责、成功标准和消费者决定。
9. 正文执行价值：`SKILL.md` 每句话必须属于执行动作、判断条件、阻断规则、产物要求、引用路由、失败处理或不可绕过 Why。分析维度、消费者解释、历史说明、工具边界说明、写作约束和测试意图不得直接进入正文。

## 确定性校验

可枚举、可复验的判断必须落到脚本、schema、hook、gate 或测试。看四项：触发者、执行入口、执行时机、失败结果。

| 触发者 | 适用场景 | 判断标准 |
| --- | --- | --- |
| Skill 主流程 | 进入关键步骤前的输入、范围或依赖校验 | `SKILL.md` 写清命令、参数和执行点。 |
| hooks 运行面 | 写入产物或会话收口后的自动 gate | `shared/hooks/registry.json` 能定位 event、handler、payload 和失败状态。 |
| 测试/CI | 回归与质量守护 | 命令直接证明成功标准。 |

示例：

- developer preflight 由主流程在实现前触发：`bash shared/skills/developer/scripts/preflight_check.sh --phase-dir "$PHASE_DIR" --task-id "$TASK_ID"`。
- developer completion gate 由 hooks 在 `Stop` 收口触发：`shared/hooks/registry.json` 的 developer entry 调用 `shared/skills/developer/scripts/completion_check.sh`。

## 分层模型

质量分为准入门禁、运行质量和效果信号三层。前两层判断 Skill 是否正确运行；效果信号判断能否宣称更高价值。

### 准入门禁

| 门禁 | 名称 | 判断标准 |
| --- | --- | --- |
| G0 | Skill 本体存在 | 目录、`SKILL.md` 和必要 frontmatter 可被定位和解析。 |
| G1 | 运行入口可达 | 目标 runtime、catalog、adapter 或显式调用方式能找到该 Skill，启用状态不冲突。 |
| G2 | 关键材料可读 | 主流程依赖的 reference、script、schema、template、eval 或测试存在且路径正确。 |

门禁失败时，先处理缺失项。

### 运行质量维度

| 维度 | 名称 | 判断标准 |
| --- | --- | --- |
| S1 | Discovery & Trigger | description 能说明何时使用、何时不使用，并能与相邻 Skill 分流。 |
| S2 | Task Contract | 目标、输入、输出、范围、完成标准和阻塞条件清楚，且不会把上游职责转嫁给本 Skill。 |
| S3 | Professional Workflow | 流程贴近对应专业工作的真实办事顺序，步骤之间有因果关系，能从理解问题推进到交付结果。 |
| S4 | Resource Architecture | 主体、reference、script、schema、template、eval、test 各守职责，按需加载，不互相复制内容。 |
| S5 | Runtime Fit & Safety | 所需工具、权限、运行时入口和外部影响与任务匹配；危险动作有明确执行入口、范围和确认方式。 |
| S6 | Artifact Contract | 产物的路径、格式、字段和消费者清楚；机器消费的形状由 schema 或模板承载，正文不重复定义大段合同。 |
| S7 | Verification Loop | 前置校验、目标测试和完成验证都有可执行入口；验证能直接证明成功标准，失败只能指向根因修复、明确阻塞，或在用户裁决后回退；不得调整成功标准或继续交付。 |
| S8 | Evolution & Integration | Skill 改动能同步到真实消费者、eval、tests、adapter、catalog 或文档入口；不存在 active 漂移引用。 |

### 效果信号

G0-G2 和 S1-S8 闭合后，E1-E5 才能支撑更高价值。

| 信号 | 名称 | 判断标准 |
| --- | --- | --- |
| E1 | Baseline 对比 | 能与裸模型、普通提示、旧 Skill 或相邻 Skill 对比。 |
| E2 | 任务成功率 | 代表性场景能证明任务成功标准的达成质量。 |
| E3 | 成本收益 | token、时间、复杂度和维护成本与收益匹配。 |
| E4 | 稳定性 | 不同输入、任务规模、模型或 runtime 下仍能保持核心行为。 |
| E5 | 反证样本 | 能说明哪些场景无收益、会误触发或应交给其他能力。 |

E1-E5 的采样、度量和保留/优化/退役信号见 `Skill能力有效性标准.md`。

## 常见质量问题

以下情况是常见质量问题：

- 专业职责不清：Skill 只描述“整理文件”“遵守流程”，但看不出对应的真实工作职责和办事路径。
- 流程错位：先写产物再理解需求，先给结论再收集证据，或把应由上游确认的事项放到当前 Skill 内解决。
- 职责混写：`SKILL.md` 塞入长方法论、脚本逻辑、schema 字段全集、历史说明或测试细节。
- 资源失去消费方：reference、template、script、字段或段落存在，但没有被流程、脚本、测试或下游产物使用。
- 确定性检查靠文字约束：本可由脚本、schema、hook 或测试校验的内容，只写文字要求，没有可执行入口、触发者或执行时机。
- 输出字段不必要：模板或 JSON 字段没有消费者，或消费方不会读取该字段。
- 正向操作不足：大量边界说明压过了操作步骤，导致模型知道风险，却不知道怎么完成任务。
- 分析层泄漏：分析维度、消费者解释、工具边界说明、写作约束或测试意图直接进入 `SKILL.md`，未落到流程动作、资源路由、脚本/schema/test 或删除项。
- 渐进披露失败：默认要求读取长参考、旧设计或大段方法论，而当前步骤只需要其中一小部分。
- 证据不可复验：完成声明只给命令字符串、历史结论或主观判断，没有当前输出、可复查产物或可重复复验入口。
- 同步不完整：改了 Skill 主体但未同步 schema、template、eval、test、catalog、adapter 或说明入口。

## 质量等级

| 等级 | 含义 |
| --- | --- |
| L0 | 不可审计：本体、入口或关键材料缺失。 |
| L1 | 可触发：能被发现并进入任务，但流程或资源尚未稳定。 |
| L2 | 可执行：能按职责完成主要任务，并有可执行的最小验证闭环。 |
| L3 | 可维护：资源分层、消费者、测试和同步关系清楚，噪音低。 |
| L4 | 可证明有效：在 L3 基础上，有效果信号支持长期保留或最佳实践声明。 |

缺少效果信号时，质量等级停在 L2/L3。
