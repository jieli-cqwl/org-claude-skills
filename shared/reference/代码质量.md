# 代码质量

代码质量的核心是降低理解成本、变更成本和失败定位成本。数字阈值只是提醒，真正目标是让代码边界清楚、行为可测、失败可见。

## SHOULD 级指南

- 函数长度 <= 50 行；超过时优先评估是否职责混杂。
- 认知复杂度（CogC）<= 15；分阶段治理，先观测再强制。
- 一个函数只做一件清晰的事，主流程尽量线性。
- 优先早返回，减少深层嵌套和状态交织。
- 命名体现业务语义，避免缩写和上下文依赖。
- 同类问题保持同类写法，减少项目内风格漂移。

## 复杂度治理

- 循环复杂度（CC）阈值 `<= 10` 为 MUST，定义于代码规范。
- CogC `<= 15` 为 SHOULD；未接入稳定工具前，不直接设置为 MUST 门禁。
- Rollout 节奏：`warn` 观测 2-4 周，再按增量范围进入 `enforce`。
- 门禁变量：`COMPLEXITY_CHECK_MODE=warn|enforce`、`COMPLEXITY_SCOPE=changed|all`、`COMPLEXITY_ALLOW_MISSING_TOOLS=0|1`。

常见重构方向：

- 用早返回替代深层嵌套。
- 拆出表达业务概念的纯函数。
- 用策略表或映射分发替代重复条件链。
- 将参数组合分支前移为校验层，主流程保持线性。

## 注释与错误处理

有效注释解释业务意图、边界、约束或失败条件；无效注释只复述代码或保留过期事实。

用户可见错误提示应说明哪个操作失败、用户下一步该做什么，并隐藏堆栈、SQL、内部服务名等技术细节。

外部服务调用应有配置化超时、错误分类和可观测上下文；错误路径要能定位上游依赖、请求 ID 和重试状态。

## 可测试性与安全

- 纯逻辑优先写成可直接测试的函数。
- 时间、随机数和外部依赖通过边界注入或项目既有机制控制。
- 验收仍必须基于真实依赖或真实集成路径，不能用可替换依赖伪造完成。
- 输入验证、参数化查询、上下文输出编码和最小权限是基础安全编码底线。

## 常用检查命令

- Python：`ruff check --select E,F,I,C901 .` / `mypy app/` / `vulture app/`
- TS：`npm run lint` / `npx tsc --noEmit --strict`
- Java：`mvn pmd:check` / `mvn spotbugs:check`

## 完成标准

- 新增或修改代码属于当前模块职责边界。
- 没有引入不必要耦合、循环依赖或难以验证的隐藏状态。
- 接口变更与相邻模块契约兼容。
- 注释解释意图和边界，不复述实现。
- 死代码、未使用导入、无效变量和过期注释已清理。
