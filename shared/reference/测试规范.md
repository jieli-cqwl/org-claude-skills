# 测试执行规范

接到代码变更后，按顺序执行：明确测试依据，生成测试义务，选择测试层级，将每条义务绑定到完成前重新执行的命令（fresh command）、测试结果、覆盖率报告或验证记录。任一环节无法闭合时，完成结论进入阻塞、缺陷处理或用户明确风险接受。

每条测试义务都应写清依据来源、测试层级、命令或人工步骤、环境依赖、通过标准和证据位置。无法追溯到目标行为、影响范围或风险的测试只用于探索；探索发现的风险应转成可追溯的测试义务后再作为交付条件；无法绑定完成证据的测试义务不支撑完成、上线或客户交付。

## 测试依据

测试依据来自本次成功标准、验收标准（AC）、影响范围分析、代码变更点、接口契约、业务不变量、历史缺陷和专项风险。专项风险包括性能、安全、兼容性、可访问性、第三方依赖和数据迁移风险。

每个依据都应转成可观察目标：输入或操作、前置状态、预期结果、边界条件、失败路径、真实依赖和影响对象。

测试依据不清时：

- 先把“做成什么样算通过”补成可观察行为、边界条件、失败路径和真实依赖。
- 仍无法确认时，记录待裁决问题。
- 待裁决问题未关闭前，不给出完成结论。

## 测试义务

任何代码变更都应验证本次成功标准对应的目标行为、被修改逻辑的正常路径、边界路径、失败路径，以及影响范围中需要回归的调用方、用户路径和业务不变量。

新增或变更可观察行为时，先形成会因目标缺失而失败的自动化测试。仅当验证依赖一次性人工判断、外部环境不可控、缺少可调用入口或当前工具无法稳定复现时，才使用可复验的验收用例，并记录不自动化原因、输入、步骤、预期结果和验证方式。

写测试或实现新行为时，应先看到目标测试因行为缺失失败，再写最小实现使其通过。重构只在测试绿色后进行，并保持行为不变。

修复缺陷时，用原复现步骤或对应回归用例证明原错误结果不再出现；只看到新结果正确，不足以证明缺陷已修复。

## 何时追加专项验证

先完成测试义务；当变更命中以下条件时，追加对应专项验证。未命中的专项验证不作为交付条件，未命中原因应能从影响范围分析中说明。

- 成功标准依赖数据库落库、文件读写、HTTP 调用、缓存读写、消息投递、鉴权结果、模块协作或前后端接口契约时，完成证据应包含真实依赖、测试环境、本地容器或已验证集成路径。
- 接口契约变更时，应验证请求方法、路径、参数、鉴权、幂等、分页、响应字段、状态码、错误结构和副作用结果。
- 成功标准跨越用户入口、服务处理、持久化或外部依赖中的两个及以上环节时，应使用最短真实流程验证从入口到最终可观察结果。
- 变更影响高频请求、批处理、数据库查询、缓存策略、并发控制、队列消费、启动耗时或资源占用时，应记录变更前后指标或明确目标阈值。
- 变更涉及鉴权、权限、输入处理、文件上传、外部 URL、密钥、敏感数据、SQL/命令执行或跨租户数据时，应验证授权路径、拒绝路径、非法输入和敏感输出处理。
- 变更影响浏览器、设备、运行时、依赖版本、数据格式或 API 版本时，应验证声明支持范围内的行为一致性。
- 变更涉及页面、表单、控件、导航、提示、颜色或动态内容时，应验证键盘可操作、焦点可见、语义可识别、对比度合格和错误提示可感知。
- 对无测试环境的第三方外部 API，录制回放应来自首次真实响应，并记录重录周期、最近一次重录时间和格式校验结果。

最短真实流程指用户或调用方从真实入口完成本次成功标准的最少必要步骤。指标退化时，应说明原因、影响范围和用户明确的处理决定。

## 测试层级裁决

- 单元测试：证明纯业务规则、分支判断、边界计算、数据转换和错误处理。单元测试应可独立运行并稳定复现，失败信息应定位到具体规则、分支或错误结果；内部调用次数、私有方法路径等实现细节只作为辅助定位信息。
- 功能测试：证明用户可见功能、API 行为、CLI 行为或业务流程。功能测试证据应包含输入、操作、预期结果和实际结果；页面、接口或命令行输出应能直接证明验收条件成立。
- 集成路径、测试环境或真实依赖：证明依赖真实协作的成功标准、跨模块协作结果和真实外部依赖影响。Mock、Stub、Fake 用于单元测试中的依赖隔离和异常路径构造；它们证明替身条件下的本地行为，不替代真实依赖验收。
- E2E：证明跨入口、服务、持久化或外部依赖的发布关键路径、本次交付主路径，以及功能测试或集成测试无法直接证明的高风险失败路径。主路径是目标用户或调用方完成核心成功标准的最短正常流程。

## 覆盖率裁决

先用覆盖率发现未执行代码，再用行为断言、边界结果、失败路径和真实依赖证据证明测试有效性。

新增或变更的业务逻辑、分支判断和错误处理路径，行覆盖率与分支覆盖率目标为 90% 以上。项目已有覆盖率基线时，本次变更影响范围的覆盖率应保持或提升；未达成时，完成结论应说明未覆盖项、业务风险和补充验证证据。

覆盖率报告无法生成时，完成结论应说明工具缺口、已覆盖的测试义务和仍未量化的风险。

## 缺陷裁决

先定严重程度，再定优先级；不得用优先级替代严重程度。

严重程度衡量问题本身的影响：

- `S0 阻断`：核心流程不可用，数据丢失，权限/安全/资金/合规风险，线上高影响且无可接受绕行。
- `S1 严重`：主要功能不可用，关键用户路径无法完成，影响大量用户或关键业务，有绕行但代价高。
- `S2 一般`：局部功能异常、边界结果错误或体验明显受损，影响范围有限且有可接受绕行。
- `S3 轻微`：文案、样式、低频边界或轻微体验问题，不影响核心目标和交付结果。

优先级衡量本次交付中应多快处理：

- `P0 立即处理`：阻断验收、上线或客户交付，或线上高影响且无绕行。
- `P1 本轮处理`：影响本次成功标准、关键用户路径或承诺范围。
- `P2 排期处理`：影响真实用户但有明确绕行，不阻断本次交付。
- `P3 后续优化`：低频、轻微或可延后的改善项。

缺陷记录应说明触发条件、实际结果、预期结果、影响范围、严重程度、优先级和复验方式。

## 测试代码质量

测试所需数据应在测试内创建或由 fixture 声明，并在执行后清理或隔离；测试不得依赖本地已有数据。测试之间不共享可变状态，数据库测试使用事务回滚、独立测试库、清理策略或 schema 隔离。

测试结构使用 AAA：Arrange 准备环境，Act 执行行为，Assert 验证结果。每个测试保留一个主要 Act，不在 Assert 中执行副作用。测试名应描述行为、条件和结果；helper 只提取稳定重复的 setup，不隐藏关键输入、目标行为和断言。

完成证据使用保留并稳定通过的测试结果；skip、xfail、flaky 结果、注释或删除的测试、无意义断言和复制实现逻辑的测试只作为风险信号，不作为通过证据。

## 交付裁决

只有以下条件全部成立，才能汇报完成、上线或客户交付：

- 本次成功标准对应的目标行为、边界路径和失败路径已验证。
- 影响范围中需要回归的对象已验证，未覆盖项有风险说明、责任人和用户明确的处理决定。
- 触发的真实依赖、集成路径、E2E、性能、安全、兼容性或可访问性义务已闭合。
- 新增或变更业务逻辑、分支判断和错误处理路径覆盖率达成目标，或未达成项已说明风险和补充证据。
- 已知缺陷完成严重程度和优先级裁决；`S0`、阻断交付的 `S1`、`P0` 和本次范围内的 `P1` 已修复或取得用户明确风险接受。
- 完成前逐项绑定完成前重新执行的命令（fresh command）、测试结果、覆盖率报告或验证记录。
- 证据未闭合的项目进入阻塞、风险或用户明确的处理决定。
- 风险接受应记录接受人、接受范围、原因和后续处理方式。
