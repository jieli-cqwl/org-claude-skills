# 测试规范

测试的目标是建立对可观察行为和关键设计单元的信心。单元测试可以直接覆盖函数，尤其是纯逻辑、业务规则、边界计算和错误处理函数；但不要机械要求每个函数都有一条对应测试。覆盖率是发现遗漏的信号，不能替代对用户目标、业务规则、边界条件和失败路径的判断。

## Red-Green-Refactor

1. RED：先写一个因功能缺失而失败的测试，失败原因必须指向目标行为缺失，不是语法或环境错误。
2. GREEN：写最小实现让测试通过，不添加额外行为。
3. REFACTOR：只在 GREEN 后清理结构，保持测试绿色，不改变行为。

## 分层判断

- 单元测试：以函数、类或模块为粒度，验证纯逻辑、数据转换、业务规则计算和边界条件，追求快速反馈。
- 集成测试：验证数据库、文件、HTTP、消息队列、外部适配和模块协作，使用真实依赖或真实测试环境。
- E2E 测试：验证少量关键用户旅程，证明系统从入口到结果真实可用。

不确定时，先拆不确定来源：纯逻辑留在单元测试；涉及真实依赖、跨模块协作、高失败代价或验收信心时升级到集成或 E2E。

## 测试替身边界

Mock、Stub、Fake 属于测试替身。测试替身可以在单元测试中隔离外部依赖、构造异常路径并获得秒级反馈；使用时要清楚替代了什么真实依赖，以及哪一层测试会覆盖真实路径。测试替身不能替代集成测试、验收测试或真实完成证据。

对无测试环境的第三方外部 API，录制回放是最后手段，必须满足：

1. 首次录制使用真实 API 响应。
2. 定期重新录制，验证响应格式未变。
3. 仅限第三方外部 API；内部服务、数据库、缓存、队列禁止使用录制回放伪造验收。

## 测试数据与隔离

- 测试必须自给自足，不依赖数据库预存数据。
- 测试之间不共享可变状态；数据库测试使用事务回滚、独立测试库、清理策略或 schema 隔离。
- 构造复杂对象时使用 factory 或 fixture；固定数据版本化，随机数据只用于验证随机性处理。
- 并行测试必须有独立数据标识或隔离空间。

## 测试代码质量

- 使用 AAA：Arrange 准备环境，Act 执行行为，Assert 验证结果。
- 每个测试只保留一个主要 Act，不在 Assert 中执行副作用。
- 测试名描述行为、条件和结果，不描述实现。
- 测试优先可读性，允许叙事性重复；完全相同且稳定的 setup 再提取 helper。
- 断言外部可观察行为，不断言无意义真值、实现细节或复制实现逻辑。

## 完成前检查

- 每个新增可观察行为都有先失败的测试；关键纯逻辑或业务函数应由单元测试直接覆盖；内部辅助函数可以由所属行为、边界或错误路径间接覆盖。覆盖关系不明显时，说明其对应的可观察行为或设计单元。
- 边界、错误路径和关键回归已覆盖。
- 所有相关测试通过，输出干净。
- 验收结论使用真实依赖、真实测试环境或已验证的集成路径支撑。
