# 测试规范

测试规范定义“测什么、测到什么程度、用什么证据证明可以交付”。测试要证明行为正确、变更风险受控、真实路径可信；覆盖率用于发现遗漏和守住基线，不能替代有效断言、边界覆盖和真实依赖证明。

## 规范作用

- 牵引力：用先失败的测试或可复验验收用例牵引实现，让代码围绕可观察行为、业务规则和失败路径收敛。
- 裁决力：用风险、依赖真实性、失败代价和反馈速度裁决测试层级、覆盖率目标和验证范围。
- 验收力：用覆盖维度、覆盖率口径、真实依赖证明和完成前检查判断是否可以声明完成。

## 覆盖维度

| 维度 | 覆盖对象 | 达标口径 |
|------|----------|----------|
| 行为与验收 | 新增或变更的可观察行为、业务规则、输入输出、状态变化 | 每个新增或变更行为至少有一个会先失败的测试或可复验验收用例；断言直接对应成功标准，不复制实现逻辑 |
| 关键设计单元 | 纯逻辑、业务计算、边界判断、错误处理函数 | 关键纯逻辑或业务函数由单元测试直接覆盖；内部辅助函数可由所属行为、边界或错误路径间接覆盖 |
| 边界与失败路径 | 空值、非法输入、权限不足、超时、重复提交、并发冲突、外部依赖失败 | 关键边界和失败路径有显式断言；错误结果可观察、可定位、符合用户或调用方预期 |
| 集成与契约 | 数据库、文件、HTTP、缓存、消息队列、鉴权、前后端接口、外部适配器 | 涉及真实依赖或跨模块协作时，用真实依赖、测试环境或已验证的集成路径证明；不能只用测试替身证明完成 |
| 回归与影响范围 | 受影响调用方、配置/数据流、用户路径、业务不变量 | 根据影响范围运行相关回归；未覆盖项必须说明风险、原因和下一步验证方式 |
| E2E 与验收 | 少量关键用户旅程、发布阻断路径、跨系统主链路 | 从真实入口到真实结果完成验证；E2E 保持少而稳定，不替代单元和集成测试 |
| 质量属性 | 性能、安全、可靠性、兼容性、可访问性等被本次变更触发的属性 | 触发时定义目标或基线，并用基准、扫描、故障注入、兼容性检查或人工验收补证；未触发时说明不适用即可 |
| 测试自身质量 | 独立性、确定性、可读性、速度、失败可诊断性 | 测试自给自足、不共享可变状态、不依赖预存数据；失败能定位目标行为，不能长期保留 flaky 测试 |

## 覆盖率口径

- 新增或变更的业务代码：行覆盖率和分支覆盖率目标为 90% 以上；低于目标时，必须说明未覆盖行或分支为什么可接受，并用集成测试、E2E、人工验收或风险记录补足证据。
- 金额、权限、数据写入、安全、迁移、批处理等高风险逻辑：不能只看百分比，业务分支、边界条件和错误路径必须逐项覆盖。
- 全仓覆盖率：作为健康趋势和回归信号，不直接等同完成标准；有既有基线时不得无理由下降，没有基线时先记录当前值，再按项目风险逐步提高。
- 覆盖率排除：生成代码、声明文件、纯配置、迁移样板或不可达防御分支可排除，但必须能说明其没有独立业务逻辑，或已由更高层测试覆盖。
- 禁止为了提高覆盖率添加无意义断言、镜像实现逻辑或只执行不验证的测试。

## Red-Green-Refactor

1. RED：先写一个因功能缺失而失败的测试，失败原因必须指向目标行为缺失，不是语法、环境或测试写错。
2. GREEN：写最小实现让测试通过，不添加额外行为。
3. REFACTOR：只在 GREEN 后清理结构，保持测试绿色，不改变行为。

## 分层选择

- 单元测试：验证函数、类或模块内的纯逻辑、数据转换、业务规则计算、边界条件和错误处理，追求快速、确定、定位清楚。
- 集成测试：验证数据库、文件、HTTP、缓存、队列、外部适配和模块协作，使用真实依赖、测试环境或本地容器。
- E2E 测试：验证少量关键用户旅程，证明系统从入口到结果真实可用。

不确定时，先拆不确定来源：纯逻辑留在单元测试；真实依赖、跨模块协作、高失败代价或验收信心不足时升级到集成或 E2E。

## 运行节奏

- 开发中优先运行目标单元测试和相关快速测试，先用快反馈确认行为方向。
- 完成前根据影响范围补跑相关集成测试、回归测试或少量 E2E，让真实依赖和关键用户路径参与证明。
- 发布、迁移、权限、支付、数据修复、批处理和跨系统主链路变更，验证力度优先于速度；无法覆盖真实路径时，必须记录阻塞、风险和用户可裁决的下一步。

## 测试替身边界

Mock、Stub、Fake 属于测试替身。测试替身可以在单元测试中隔离外部依赖、构造异常路径并获得秒级反馈；使用时要清楚替代了什么真实依赖，以及哪一层测试会覆盖真实路径。测试替身不能替代集成测试、验收测试或真实完成证据。

对无测试环境的第三方外部 API，录制回放是最后手段，必须满足：

1. 首次录制使用真实 API 响应。
2. 定期重新录制，验证响应格式未变。
3. 仅限第三方外部 API；内部服务、数据库、缓存、队列禁止使用录制回放伪造验收。

## 测试数据与隔离

- 测试必须自给自足，不依赖数据库预存数据。
- 测试之间不共享可变状态；数据库测试使用事务回滚、独立测试库、清理策略或 schema 隔离。
- 构造复杂对象时使用 factory 或 fixture；固定数据版本化，随机数据只用于验证随机性处理。
- 并行测试必须有独立数据标识或隔离空间。

## 测试代码质量

- 使用 AAA：Arrange 准备环境，Act 执行行为，Assert 验证结果。
- 每个测试只保留一个主要 Act，不在 Assert 中执行副作用。
- 测试名描述行为、条件和结果，不描述实现。
- 测试优先可读性，允许叙事性重复；完全相同且稳定的 setup 再提取 helper。
- 断言外部可观察行为，不断言无意义真值、实现细节或复制实现逻辑。

## 完成前检查

- 覆盖维度已逐项判断，触发项都有测试或验收证据，不适用项有明确原因。
- 新增或变更业务代码的覆盖率达成目标；未达成时有可接受理由和补充证据。
- 边界、错误路径和关键回归已覆盖。
- 所有相关测试通过，输出干净；flaky、skip、xfail、注释或删除测试不能作为通过依据。
- 验收结论使用真实依赖、真实测试环境或已验证的集成路径支撑。
