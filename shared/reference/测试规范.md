# 测试执行规范

本规范用于指导 AI Coding Agent 在代码变更过程中选择测试能力、形成验证标准，并在完成前用可复验证据支撑结论。执行时先判断本次变更触发哪些测试义务，再用对应测试结果、覆盖率、真实路径记录证明目标行为已达成；证据不足时应记录阻塞、风险或用户裁决结果。

## 基本口径

- 新增或变更的可观察行为，应先形成会因目标缺失而失败的自动化测试；暂不适合自动化时，应说明原因，形成可复验的验收用例，并记录输入、步骤、预期结果和验证方式。
- 写测试或实现新行为时，应先看到目标测试因行为缺失失败，再写最小实现使其通过；重构只在测试绿色后进行，并保持行为不变。
- 完成证据应逐项对应本次成功标准；测试命令通过只有在覆盖对应成功标准时，才支撑完成结论。
- 覆盖率用于发现遗漏和守住基线；行为断言、边界结果、失败路径和真实依赖证据共同决定测试是否有效。
- 项目已有覆盖率基线时，本次变更影响范围的覆盖率应保持或提升；覆盖率下降时，应说明下降位置、原因、业务风险和补充验证证据。

## 单元测试

- 新增或变更的业务规则、分支判断、边界计算、数据转换和错误处理，应由单元测试直接证明。
- 新增或变更的业务逻辑、分支判断和错误处理路径，行覆盖率与分支覆盖率目标为 90% 以上；未达成时，应说明未覆盖项、业务风险和补充验证证据。
- 单元测试应可独立运行并稳定复现，失败信息应定位到具体规则、分支或错误结果；内部调用次数、私有方法路径等实现细节只作为辅助定位信息。

## 集成测试

- 成功标准依赖数据库落库、文件读写、HTTP 调用、缓存读写、消息投递、鉴权结果、模块协作或前后端接口契约时，完成证据应包含真实依赖、测试环境或本地容器下的集成验证结果。
- 接口契约变更应验证请求方法、路径、参数、鉴权、幂等、分页、响应字段、状态码、错误结构和副作用结果。
- Mock、Stub、Fake 用于单元测试中的依赖隔离和异常路径构造；依赖真实协作的成功标准，应由真实依赖、测试环境或已验证集成路径支撑。
- 对无测试环境的第三方外部 API，录制回放应来自首次真实响应，并记录重录周期、最近一次重录时间和格式校验结果。

## 功能测试

- 新增或变更用户可见功能、API 行为、CLI 行为或业务流程时，功能测试应覆盖成功标准对应的正常结果、边界结果和失败反馈。
- 功能测试证据应包含输入、操作、预期结果和实际结果；页面、接口或命令行输出应能直接证明验收条件成立。

## E2E 测试

- 当成功标准跨越用户入口、服务处理、持久化或外部依赖中的两个及以上环节时，完成证据应包含从真实入口触发到最终可观察结果出现的验证记录。
- E2E 测试应围绕本次成功标准的最短真实流程设计；单个页面、接口或模块内可证明的行为优先由功能测试或集成测试承载。

## 回归测试

- 变更影响共享模块、公共契约、配置/数据流、历史缺陷场景、用户路径或业务不变量时，应运行受影响范围的回归测试。
- 修复缺陷时，完成证据应包含原复现步骤或对应回归用例通过，并证明原错误结果不再出现。
- 回归范围应来自影响范围分析，覆盖直接变更点、依赖链和影响面中标记需回归的对象；未覆盖的受影响对象应说明原因、风险和下一步验证方式。

## 性能测试

- 变更影响高频请求、批处理、数据库查询、缓存策略、并发控制、队列消费、启动耗时或资源占用时，应记录变更前后指标或明确目标阈值。
- 性能证据应使用同一场景对比响应时间、吞吐、资源占用、查询计划或任务耗时；指标退化时，应说明原因、影响范围和用户裁决结果。

## 安全测试

- 变更涉及鉴权、权限、输入处理、文件上传、外部 URL、密钥、敏感数据、SQL/命令执行或跨租户数据时，应验证授权路径、拒绝路径、非法输入和敏感输出处理。
- 安全证据可来自安全用例、集成验证、扫描结果或人工审查记录；证据应能对应到具体安全边界。

## 兼容性测试

- 变更影响浏览器、设备、运行时、依赖版本、数据格式或 API 版本时，应验证声明支持范围内的行为一致性。
- 兼容性证据应包含目标环境、版本范围、验证结果；不兼容变化应说明迁移方式、影响范围和用户裁决结果。

## 可访问性测试

- 变更涉及页面、表单、控件、导航、提示、颜色或动态内容时，应验证键盘可操作、焦点可见、语义可识别、对比度合格和错误提示可感知。
- 可访问性证据可来自自动化检查、键盘走查、语义检查、截图或录屏；证据应覆盖本次变更影响的交互点。

## 测试代码质量

- 测试应自给自足，不依赖预存数据；测试之间不共享可变状态，数据库测试使用事务回滚、独立测试库、清理策略或 schema 隔离。
- 测试结构使用 AAA：Arrange 准备环境，Act 执行行为，Assert 验证结果；每个测试保留一个主要 Act，不在 Assert 中执行副作用。
- 测试名应描述行为、条件和结果；测试优先可读性，稳定重复的 setup 再提取 helper。
- 完成证据使用保留并稳定通过的测试结果；skip、xfail、flaky 结果、注释或删除的测试、无意义断言和复制实现逻辑的测试只作为风险信号，不作为通过证据。

## 完成前检查

- 列出本次变更触发的测试能力，并为每项对应 fresh command、测试结果、覆盖率报告或验证记录；无法证明的项目应记录阻塞、风险或用户裁决结果。
- 新增或变更的业务逻辑、分支判断和错误处理路径覆盖率达成目标；未达成时，完成结论应包含未覆盖项、风险判断和补充验证证据。
- 覆盖率报告无法生成时，完成结论应说明工具缺口、已覆盖的测试义务和仍未量化的风险。
- 涉及真实依赖、跨模块协作或用户入口到结果的链路时，完成证据应包含真实依赖、测试环境、集成路径或 E2E 记录。
