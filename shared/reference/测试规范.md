# 测试规范

测试的目标是发现真实问题：验证目标行为、暴露边界缺陷、证明失败路径和真实依赖的正确性。无法追溯到目标行为或风险的测试只用于探索，不作为完成证据。

## 测试依据

测试点来自本次成功标准、验收标准（AC）、影响范围分析、代码变更点、接口契约、业务不变量、历史缺陷和专项风险。专项风险包括性能、安全、兼容性、可访问性、第三方依赖和数据迁移风险。

测试依据不清时：

- 先把“做成什么样算通过”补成可观察行为、边界条件、失败路径和真实依赖。
- 仍无法确认时，记录待裁决问题。
- 待裁决问题未关闭前，不给出完成结论。

## 测试义务

任何代码变更都应验证本次成功标准对应的目标行为、被修改逻辑的正常路径、边界路径、失败路径，以及影响范围中需要回归的调用方、用户路径和业务不变量。

- **新增或变更行为**：先形成会因目标缺失而失败的自动化测试。仅当验证依赖一次性人工判断、外部环境不可控、缺少可调用入口或当前工具无法稳定复现时，才使用可复验的验收用例，并记录不自动化原因、输入、步骤、预期结果和验证方式。
- **RED → GREEN → REFACTOR**：先看到目标测试因行为缺失失败，再写最小实现使其通过。重构只在测试绿色后进行，并保持行为不变。
- **修复缺陷**：用原复现步骤或对应回归用例证明原错误结果不再出现；只看到新结果正确，不足以证明缺陷已修复。

## 何时追加专项验证

基础测试只能证明局部行为；当变更触达更高风险面时，要追加能证明真实结果的专项验证。未触达的专项验证不作为交付条件，未触达原因应能从影响范围分析中说明。

- 涉及 DB 落库、缓存、文件、消息、外部调用或模块协作，就要用真实依赖、测试环境、本地容器或集成路径证明结果。
- 涉及接口契约，就要验证请求、响应、状态码、错误结构和关键副作用。
- 涉及鉴权、权限、敏感数据或跨租户数据，就要验证授权路径、拒绝路径、非法输入和敏感输出。
- 涉及高频查询、批处理、缓存策略、并发或资源占用，就要看性能指标或目标阈值。
- 涉及页面交互，就要验证键盘操作、焦点、语义、对比度和错误提示。
- 涉及第三方外部 API 且无稳定测试环境，就要用首次真实响应、录制回放、重录周期和格式校验证明可复验。
- 涉及数据迁移、数据格式、运行时或 API 版本，就要验证迁移结果、兼容范围和回滚准备。

最短真实流程指用户或调用方从真实入口完成本次成功标准的最少必要步骤。指标退化时，应说明原因、影响范围和用户明确的处理决定。

## 测试层级裁决

| 层级 | 证明什么 | 证据要求 |
| --- | --- | --- |
| 单元测试 | 纯业务规则、分支判断、边界计算、数据转换和错误处理 | 可独立运行并稳定复现；失败信息定位到具体规则、分支或错误结果；内部调用次数等实现细节只作辅助定位 |
| 功能测试 | 用户可见功能、API 行为、CLI 行为或业务流程 | 包含输入、操作、预期结果和实际结果；页面、接口或命令行输出直接证明验收条件成立 |
| 集成测试 | 跨模块协作结果和真实外部依赖影响 | 使用真实依赖、测试环境或集成路径；Mock/Stub/Fake 用于单元测试依赖隔离和异常路径构造，不替代真实依赖验收 |
| E2E | 发布关键路径、本次交付主路径、功能或集成测试无法证明的高风险失败路径 | 主路径是目标用户完成核心成功标准的最短正常流程 |

## 覆盖率裁决

先用覆盖率发现未执行代码，再用行为断言、边界结果、失败路径和真实依赖证据证明测试有效性。

新增或变更的业务逻辑、分支判断和错误处理路径，行覆盖率与分支覆盖率目标为 90% 以上。项目已有覆盖率基线时，本次变更影响范围的覆盖率应保持或提升；未达成时，完成结论应说明未覆盖项、业务风险和补充验证证据。

覆盖率报告无法生成时，完成结论应说明工具缺口、已覆盖的测试义务和仍未量化的风险。

## 测试代码质量

- **数据隔离**：测试数据在测试内创建或由 fixture 声明，执行后清理或隔离；不依赖本地已有数据。测试之间不共享可变状态，数据库测试使用事务回滚、独立测试库、清理策略或 schema 隔离。
- **测试结构**：使用 AAA（Arrange → Act → Assert）。每个测试保留一个主要 Act，不在 Assert 中执行副作用。测试名描述行为、条件和结果；helper 只提取稳定重复的 setup，不隐藏关键输入、目标行为和断言。
- **完成证据**：使用保留并稳定通过的测试结果；skip、xfail、flaky 结果、注释或删除的测试、无意义断言和复制实现逻辑的测试只作为风险信号，不作为通过证据。

## 交付裁决

测试义务、专项验证和覆盖率全部闭合后，方可汇报完成。风险接受应记录接受人、接受范围、原因和后续处理方式。
