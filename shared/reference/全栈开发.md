# 全栈开发

全栈任务先确定接口契约，再推进前后端实现。完成边界是用户从入口触发，到后端处理、必要副作用和前端反馈闭合。

## 接口先行

先写清接口契约，作为前后端实现和联调标准：

- 写明请求方法、路径、参数、鉴权、幂等和分页规则。
- 写明响应字段、状态码、错误结构、空态和边界场景。
- 前端据此实现调用、状态展示和错误反馈；后端据此实现接口能力和校验。
- 契约未确定时，写明待决策项和阻塞范围，不把临时假设当成完成依据。
- 前端临时计算、后端补字段、字段兼容、权限或旧数据判断，同时读 `{{RUNTIME_HOME}}/rules/code-changes.md` 和 `{{RUNTIME_HOME}}/reference/impact-analysis.md`；是否能发必须以影响范围和同链路回归为依据。

## 推进顺序

- 进入联调前，后端提供契约匹配的真实接口、校验规则和错误结构，让前端接入真实依赖。
- 前端接入接口时同步处理 loading、empty、error、permission 和 retry 等用户可见状态。
- 任一侧修改接口契约时，同步另一侧调用、错误处理、测试和契约引用。
- 按用户路径组织阶段性交付，让每个阶段都能用真实调用和可见结果证明进展。

## 联调验收

全栈完成边界是前后端实现闭合，并通过同一条真实用户路径联调。

联调证据应来自真实运行结果：

- 前端从真实页面、组件或客户端入口发起请求。
- 后端按契约返回成功结果、错误结构、状态码和必要副作用。
- 用户可见的成功、空态、错误、权限和重试反馈匹配契约。
- 测试或记录能证明前端调用、后端处理和用户结果属于同一条链路。

## 同步点

- 契约待定时，只按已确定字段推进；记录待决策项、阻塞范围和临时假设失效条件。
- 后端暂未可用时，前端可先按契约完成界面状态和调用代码；完成结论仍等待真实接口联调。
- 发现前后端实现不一致时，先回到接口契约裁决，再同步调用方、服务端、测试和文档。
- 任务拆分应围绕可联调的用户路径收口，避免长期只完成单侧能力。
- 用户等级、价格、权益、风控等前端临时计算或后端兜底，必须先明确规则 owner、集中变更责任、权限口径、旧数据语义、接口契约、触发条件、失效边界、回滚路径和同链路回归证据。
- 用户等级前端自算的短答若给最低放行条件，先删解释，不删这些槽位：规则 owner、集中变更入口、前后端契约、权限口径、旧数据语义、删除或回滚条件、同链路回归；缺任一项就不能放行。
- 字段兼容或灰度开关只有在源头归属、兼容对象、移除条件和前后端同链路验证明确后才能接受。
