# 系统调试

调试的目标是确认根因，不是尽快改出一个看似有效的症状修复。

HARD-GATE: 完成 Phase 1 之前禁止改代码。

Phase 1-3 属于铁律允许的受控诊断范围，只用于定位根因、收集证据和验证假设；不得借调试名义继续实现、静默切换方案或宣称任务完成。

Phase 4 仅在根因已确认、修复不改变原目标与验收标准时进入；若修复需要扩大范围、切换方案或调整标准，必须先向用户报告并等待裁决。

## 四阶段

| 阶段 | 目标 | 产出 |
| --- | --- | --- |
| 1. Observe | 复现问题，记录错误信息、环境、输入、时间线和最小触发条件 | 问题事实卡片 |
| 2. Hypothesize | 基于事实提出可证伪假设；简单确定性问题可记录唯一证据链 | 假设清单 + 证伪条件 |
| 3. Test | 从证据支持度最高的假设开始，一次只变一个变量 | 实验记录 |
| 4. Fix | 根因确认后写回归测试、最小修复、重新复现并按影响范围验证 | 修复 diff + 测试结果 |

## 判断准绳

- 观察不足时，不改代码。
- 假设必须能被证伪，不能为凑数量编造。
- 实验一次只改变一个变量，避免把多个变化混成“修好了”。
- 修复必须指向根因；消除日志、吞掉异常、绕过失败路径不算修复。
- 修复后重新执行原复现步骤和回归测试；核心、共享或高风险变更再扩大验证面。
