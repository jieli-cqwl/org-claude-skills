# 设计原则

> 触发条件：面临设计决策（是否抽象/分层/引入模式）时读取。
> 引用者：design, refactor

## 统领：Essential vs Accidental Complexity

好的设计不是最少结构，也不是最完整结构，而是在当前证据下，用最小必要结构承载真实约束，并允许后续增删回退。

- Essential：承载业务成功标准、非协商约束、已确认质量属性、领域不变量、外部契约、风险边界或真实变更痛点
- Accidental：来自未证实未来、工具/模式偏好、目录对称、主观整洁、纯透传、形状重复或过期兼容

删除自检：去掉该结构后，正常行为、异常/并发/回滚/恢复、安全/审计/合规/数据不变量仍可被验证证据证明 -> 优先削减；否则保留。

证据包括：当前需求、用户场景、测试/监控/压测数据、事故复盘、法规要求、威胁模型、领域事故史、真实变更痛点。`将来可能变化`、`长期可维护`、`架构一致性` 不能单独作为证据。

## 简单原则（最小必要复杂度）

在不削弱成功标准、风险控制和可验证性的前提下，选择理解、修改、测试、运行成本最低的结构。

- `万一将来需要` -> 不设计（YAGNI）
- 单实现接口，若不承载外部契约、信任边界、依赖隔离、已确认变化轴或测试替换需求 -> 删除
- 透传层，若不承载权限、审计、事务、观测、错误映射或反腐职责 -> 合并
- 只为目录对称、模式完整、主观整洁，且无独立职责/变化原因/验证方式 -> 合并
- 代码形状相似但业务语义不同 -> 不抽象；模块数量过多只作为检查信号，不按数字裁决

简单不等于省略完整度：错误处理、失败场景、安全校验、审计留痕、幂等、事务、恢复能力不能因简单原则被削减。

## 合适原则（用必要结构承载真实约束）

复杂度必须能说清：承载什么约束、证据是什么、替代方案为何不够、何时可删除。

- 有业务不变量、状态转换、规则组合、冲突语义或高错误代价 -> 用领域模型/状态机承载
- 有多实现、外部契约、信任/权限/事务边界、依赖隔离或反腐需求 -> 保留接口/适配层
- 有安全、合规、审计、资金、数据完整性风险 -> 保留防御和追溯能力
- 有真实性能/可靠性瓶颈 -> 可评估队列、限流、熔断、超时、重试退避；缓存仍需用户明确同意

业务不直接决定 `分几层` 或 `用什么模式`；业务通过能力、语言、不变量、状态、错误代价、质量属性、安全合规和变化拓扑约束技术设计。业务名词本身不是建模理由。

## 演化原则（随证据校准复杂度）

演化不是增长复杂度，而是随证据增加、删除、合并、替换或延迟不可逆决策。

- 重复 3 次只触发抽象评估；只有共同语义稳定、变化方向一致、差异不会变成参数/条件分支时才抽象
- 性能优化必须有监控、压测或生产数据；高风险约束可用法规、威胁模型、事故史作为前置证据
- 耦合痛点可拆分，但拆分后必须降低变更传播、测试范围或协作冲突
- 功能开关、兼容层、迁移逻辑、临时适配失去约束价值 -> 删除或收敛
- 信息不足时保持直接实现；不可逆决策推迟到 Last Responsible Moment

可逆性优先：功能开关 > 全量发布；渐进改造 > 大爆炸重写；可回滚变更 > 不可逆迁移。

## 裁决规则（原则冲突时）

| 层级 | 规则 | 说明 |
|------|------|------|
| L1 | 非协商约束 | 安全 / 正确性 / 合规 / 数据完整性 / 审计追溯优先 |
| L2 | 质量属性排序 | 按用户确认的性能、可靠性、安全、可维护性、成本、交付速度排序裁决 |
| L3 | 证据强度 | 真实需求、数据、事故、法规、威胁模型、变更痛点 > 偏好和猜测 |
| L4 | 可逆性优先 | 能回退的方案优于不能回退的局部最优 |
| L5 | 默认选简单 | 仍无法裁决时，选 Accidental Complexity 更少的方案 |

设计决策至少记录：约束、证据、备选方案、取舍原因、验证方式、删除条件。小改动可写在任务/PR 说明；跨模块或长期架构决策写入设计文档或 ADR。
