# TDD 规范

> 没有先失败的测试，就没有生产代码。

## Red-Green-Refactor

1. RED：写一个测试，验证它因功能缺失而失败（不是语法错误）
2. GREEN：写最简代码让测试通过，不添加额外功能
3. REFACTOR：只在 GREEN 后清理，保持测试绿色，不添加行为

## 反模式

| 禁止 | 正确做法 |
|------|---------|
| 先写实现后补测试 | 先写失败测试再实现 |
| 测试 Mock 行为 | 测试真实组件（见 rules/铁律.md） |
| 复制预期当实际结果 | 独立验证实际输出 |
| 生产代码中加仅测试方法 | 测试工具类处理 |

## 测试分层

> 详细策略见 `reference/测试分层策略.md`。

| 层级 | 范围 | 速度 | 何时写 |
|------|------|------|--------|
| 单元测试 | 单函数/单类的纯逻辑 | 毫秒级 | 每个函数的核心逻辑 |
| 集成测试 | 模块间交互、数据库操作、外部调用 | 秒级 | 涉及 IO/跨模块时 |

### 选择标准

- 纯计算/转换/验证逻辑 → 单元测试
- 涉及数据库读写 → 集成测试（真实数据库，禁止 Mock）
- 涉及外部 API 调用 → 集成测试（真实测试环境）
- 涉及多模块协作 → 集成测试
- 不确定时 → 优先集成测试（更高信心）

## 测试数据管理

| 策略 | 适用场景 | 实践 |
|------|---------|------|
| Factory 模式 | 需要构造复杂对象 | 提供默认值 + 允许覆盖特定字段 |
| Fixture 文件 | 固定测试数据集 | JSON/YAML 文件，版本控制 |
| 事务回滚 | 数据库集成测试 | 每个测试在事务中执行，结束后回滚 |
| 数据隔离 | 并行测试执行 | 每个测试使用独立数据标识，不共享状态 |

### 禁止

- 测试间共享可变状态（测试 A 创建的数据被测试 B 依赖）
- 依赖数据库中预存数据（测试必须自给自足）
- 使用随机数据（除非测试目的就是验证随机性处理）

## 测试代码质量

> 详细标准见 `reference/测试代码质量.md`。

### AAA 模式（强制）

每个测试必须清晰分为三段：
1. Arrange — 准备数据和环境
2. Act — 执行被测行为（通常一行）
3. Assert — 验证结果

### 命名规范

`should_{预期行为}_when_{条件}` 或 `given_{前提}_when_{动作}_then_{结果}`

### DAMP 原则

测试代码优先可读性（Descriptive And Meaningful Phrases），允许适度重复。但完全相同的 setup 应提取为 helper。

## 完成前检查

- 每个新函数都有测试，且先看到失败
- 所有测试通过，输出干净
- 边界和错误情况已覆盖
- 禁止 Mock（见 rules/铁律.md）
