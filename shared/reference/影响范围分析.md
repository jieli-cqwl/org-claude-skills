# 影响范围分析

影响范围分析用于把直接变更转换成可验收的功能影响、技术触点、验证范围、覆盖盲区和待裁决风险。

## 三步识别法

### 1. 列变更点

从需求、Bug、重构或文档变更中提取直接修改对象和变更原因。对象可以是代码符号、配置键、文档/规则条目、契约字段、脚本入口、数据表、API 端点或运行入口。

产出：直接修改对象和变更原因。

### 2. 追依赖链

从变更点出发，找到依赖它或被它依赖的对象。优先使用可用的代码智能能力追踪定义和引用，包括 LSP 支持的定义/引用搜索、IDE 导航、代码索引和类型感知搜索；再用文本搜索补充字符串引用、配置引用、动态调用、生成内容和表字段引用。

产出：受影响但不一定直接修改的候选对象和用户路径。

### 3. 评估影响面

把候选对象归类为功能影响、需同步修改、仅需回归验证、内部实现影响、覆盖盲区或待裁决风险。行为语义不变时，说明依据和需要证明未受影响的验证对象。

产出：功能影响项、需同步修改项、需回归验证项、覆盖盲区和待裁决风险。

## 必查维度

下列维度是最低检查面；再补查项目特有入口、契约、验证入口、样例/夹具和运行消费路径。

| 维度 | 追查方向 |
| --- | --- |
| 功能影响 | 业务能力、用户路径、成功标准、验收要求、既有功能承诺。 |
| 技术触点 | 代码符号、接口、配置、契约、数据、脚本入口、运行时依赖。 |
| 业务规则 | 状态流转、数据一致性、权限、幂等、审计、业务不变量。 |
| 验证范围 | 功能、集成、E2E、真实依赖、发布验证、未覆盖风险。 |
| 覆盖盲区 | 代码智能不可见路径、动态调用、生成内容、历史高风险区、环境差异。 |

每个维度都必须落到功能影响项、需回归验证项、覆盖盲区、待裁决风险或明确不涉及依据；不得只列发现项。

## 功能影响项

功能影响项用业务、测试、开发能对齐的功能术语表达。文件名、函数名、脚本名和搜索命中不是功能影响项；必须转译成业务能力、用户路径、可验收行为或业务不变量。

每项写清：

- 功能点：受影响的业务能力或用户可感知行为。
- 影响原因：为什么受影响，原因要可追溯到变更点或依赖链。
- 技术触点：支撑或影响该功能的代码、接口、配置、契约、数据或运行入口。
- 验证与风险：验证方式、证据状态、覆盖盲区和待裁决风险。

## 并行安全

`shared_files` 为 0 只说明文件范围无交集；确认无顺序依赖、共享契约变更、共享数据写入或同一用户路径后，才可并行。

涉及共享文件、共享契约、共享数据写入或同一用户路径时，先验收共享前置任务；无独立边界则串行执行。并行后必须统一合并验证。

## 影响记录

功能影响项记录业务可验收影响；`impact_files` 记录技术影响证据，不承载搜索流水账，也不替代功能影响结论。

写法口径：

- 需要同步修改：写对象和具体原因。
- 仅需回归验证：写功能点、技术触点和需要验证的行为。
- 内部实现影响：写不改变业务行为的依据，不能当作逃避功能分析的兜底。
- 已被其他工作覆盖：写覆盖来源、边界和剩余验证责任。
- 无额外影响：写 `[]` 前必须记录已检查的维度和未受影响依据；不能只写空列表。
- 存在覆盖盲区、真实依赖或用户路径风险时，在风险或验证说明中记录待裁决项。

## 分析结果

- 每个影响项都有因果原因，不只是搜索结果。
- 技术影响项应能映射到功能影响项；映射不到时，说明内部实现影响和不改变业务行为的依据。
- 回归验证覆盖受影响功能点、技术触点、用户路径和业务不变量。
- 需回归验证项、覆盖盲区和待裁决风险必须进入完成前验证；未关闭项不得写成完成。
