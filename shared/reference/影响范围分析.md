# 影响范围分析

影响范围分析用于确定本次变更边界和验证面：找出会影响哪些代码、配置、数据流、运行时依赖、用户路径和业务不变量。

## 三步识别法

### 1. 列变更点

从需求、Bug 或重构描述中提取将被修改的对象：代码符号、配置键、文档/规则条目、契约字段、脚本入口、数据表或 API 端点。

产出：直接修改文件和变更原因。

### 2. 追依赖链

从变更点出发，找到依赖它的调用方、配置、测试、文档、数据读写方和运行时路径。优先使用 LSP `findReferences` / `goToDefinition`，再用 `rg` 补充字符串引用、配置引用、动态调用和表字段引用。

产出：受影响但不一定直接修改的候选文件和用户路径。

### 3. 评估影响面

判断每个候选影响是需要同步修改，还是只需要回归验证。行为语义不变时，列出调用方验证对象，并用回归结果证明行为未受影响。

产出：需同步修改的文件、需回归验证的功能、无法覆盖的盲区和待裁决风险。

## 必查维度

先覆盖以下维度；再补查项目特有入口、文档/contracts、测试、fixtures、CI 和运行消费路径。

| 维度 | 要看什么 | 追查重点 |
| --- | --- | --- |
| 代码符号 | 函数、类、字段、导入、公开接口 | 区分同名不同义，补查动态分发；接口变更追到相邻模块契约。 |
| 配置/数据流 | 配置键、环境变量、缓存 key、队列、数据库表字段 | 补查字符串拼接和异步消费者；新增状态必须能被测试或日志定位。 |
| 运行时依赖 | 中间件、拦截器、装饰器、定时任务、外部服务 | 补查条件分支内才触发的依赖；新增依赖必须来自本次目标，并检查依赖图是否成环。 |
| 用户路径 | 验收路径、关键流程、错误路径、权限路径 | 覆盖目标路径、边界路径和错误路径。 |
| 业务不变量 | 状态转换、一致性、审计、资金/安全/合规约束 | 追到跨模块规则和长期约束。 |
| 搜索盲区 | LSP 不可见路径、反射、生成代码、历史高风险区 | 用运行验证、生成入口或历史风险区补足搜索结果。 |

## 并行安全

`shared_files` 为 0 仅表示文件范围无交集；确认无顺序依赖、共享契约变更、共享数据写入或同一用户路径后，才可并行。

存在共享文件、共享契约、共享数据写入或同一用户路径时，先拆出共享前置任务；无法拆出时串行执行，并行后必须统一合并验证。

## 影响记录

`impact_files` 记录本次变更影响的文件、路径或回归对象，以及它们被影响的原因。它表达影响判断结果，不承载搜索流水账。

写法口径：

- 需要同步修改：写 `路径: 具体原因`。
- 仅需回归验证：写路径和需要验证的行为。
- 已被其他 Task 覆盖：写 `已由 Task-N 覆盖`。
- 无额外影响：写 `[]`。写 `[]` 前必须已检查代码符号、配置/数据流、运行时依赖、用户路径/业务不变量和搜索盲区。
- 存在无法覆盖的搜索盲区、运行时依赖或用户路径风险时，在任务/计划风险或验证说明中记录盲区和待裁决风险。

## 分析结果

- 每个影响项都有因果原因，不只是搜索结果。
- 回归验证覆盖受影响调用方、用户路径和业务不变量。
