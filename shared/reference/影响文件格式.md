# impact_files 格式定义

> 触发条件：填写 `impact_files`、评审 Scope Freeze / Task 清单中的影响面声明时读取。
> 本文件定义 `plan.md` 中 `impact_files` 字段的共享格式契约，避免引用下游 skill 模板。

## 适用位置

`impact_files` 在 `plan.md` 中有两种承载位置：

| 位置 | 目的 | 表达方式 |
|------|------|---------|
| Scope Freeze 与映射矩阵 | 快速声明该 scope item 的受影响文件集合 | 单元格内写文件列表，逗号分隔 |
| Task 清单 | 说明每个 Task 的直接影响面与原因 | 列表形式，逐项写文件和原因 |

## Scope Freeze 格式

单元格内填写受影响文件列表，按阅读顺序列出：

```text
services/user.ts, api/user.ts, tests/user.test.ts
```

约束：
- 只写文件路径，不写解释性长句。
- 顺序建议为：主实现 → 调用方/适配层 → 测试/文档。
- 无额外影响时写 `[]`，不要留空；写 `[]` 前必须已按影响范围分析检查代码符号、配置/数据流、运行时依赖、用户路径/业务不变量和搜索盲区。

## Task 清单格式

Task block 中使用如下结构：

```md
- impact_files:
  - services/user.ts: 引用了被重命名的接口
  - api/user.ts: 需要同步适配返回字段
  - 已由 Task-2 覆盖
```

约束：
- 每一项都必须说明“为什么受影响”，不能只列搜索结果。
- 如果某文件已经是其他 Task 的直接修改文件，使用 `已由 Task-N 覆盖`，避免重复分派。
- 确认没有额外影响时写 `[]`；`[]` 只表示无额外文件或回归项，不表示跳过影响分析。
- 若存在无法覆盖的搜索盲区、运行时依赖或用户路径风险，在任务/计划风险或验证说明中记录盲区和接受理由。

## 判定口径

| 情况 | 写法 |
|------|------|
| 需要同步修改 | `路径: 具体原因` |
| 仅需回归验证 | 仍可列出 `路径: 需要回归验证的原因` |
| 已被其他 Task 主文件覆盖 | `已由 Task-N 覆盖` |
| 无关联修改或回归项，且已检查影响分析维度 | `[]` |

## 最小示例

```md
- impact_files:
  - apps/web/src/api/user.ts: 引用了新增的 status 字段
  - apps/web/src/pages/user/detail.tsx: 需要回归验证详情页展示
  - 已由 Task-3 覆盖
```
