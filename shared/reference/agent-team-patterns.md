# TeamCreate 协作模式参考

协作的目的不是增加并行度，而是把需要多视角判断、独立评审或模块所有权的工作做得更稳。没有明确收益时，主 Agent 自己完成更好。

当 runtime 提供 `TeamCreate` 时，跨视角评审和多人协作默认使用 `TeamCreate` 作为一等团队工具；普通 `Agent` 只用于单个 helper、sidecar 或草稿采证，不替代团队评审权限。

## 选择协作模式

| 目标 | 模式 | 判断 |
| --- | --- | --- |
| 多视角独立判断 | 竞争假设 | 技术选型、方案评估、问题域调研等需要先独立形成判断，再交叉比对。 |
| 多维质量门禁 | 分层评审 | PRD、设计、测试设计、代码审查等需要不同专业视角独立出具结论。 |
| 并行交付 | 模块化开发 | 不同成员拥有不同模块或组件，写入边界清楚，接口可共享。 |
| 独立审批 | 规划-审批 | 一方生成方案或计划，另一方审查可执行性、风险和遗漏。 |

## 主 Agent 职责

- 节点责任不下放，工序可下放。
- 主 Agent 负责确认、裁决、Gate、回退和签收。
- 关键提问、设计裁决、测试门禁、Task 冻结或风险接受不能交给协作成员最终决定。
- 协作成员输出只作为证据和候选，必须由主 Agent 复核合并。

## 启用前必须说清

- 固定输入：每个成员读什么，不能自行扩大范围。
- 固定输出：每个成员交付什么格式和证据。
- 禁止越权项：哪些决策、写入、回退或确认不能做。
- 回收边界：主 Agent 如何合并、裁决和处理冲突。
- 成本边界：最大协作成员数和是否需要用户确认。

## 高差异模式

当协作模式会显著改变用户体验、token 成本、并行度或裁决方式时，必须在主流程中显式共创选择，不能把模式选择藏在实现细节、补充说明或外部协议里。

最大协作成员数：`product=2`、`design=3`、`test-design=3`、`tech-lead=3`、`delivery-owner=1`。
