# Agent Team 使用模式参考

> 类型：reference（指南，非执行规范）。
> 用途：帮助 skill 设计者选择合适的 agent team 使用模式。

## 四种模式

### 1. 竞争假设（Competing Hypotheses）

多 agent 从不同角度独立研究同一问题，禁止先共享结论，最后统一交叉比对与裁决。适用于技术选型、方案评估、问题域调研等需要多视角独立判断的场景。

### 2. 分层评审（Parallel Review）

多 reviewer agent 从不同专业维度并行审查同一工件，各视角独立出具结论，由主 agent 复核合并。适用于 PRD 审查、设计审查、测试设计审查、代码审查等需要多维度质量门禁的场景。

### 3. 模块化开发（Module Ownership）

不同 agent 负责不同模块/组件的独立实现，通过共享接口定义协作。适用于多 Task 并行开发、worktree 隔离实现等需要并行交付的场景。

### 4. 规划-审批（Plan Approval）

一方生成方案/计划，另一方审查/审批。适用于设计评审、计划评审等需要独立视角检验的场景。

## 选择原则

- 需要多视角独立判断 → 竞争假设
- 需要多维度质量门禁 → 分层评审
- 需要并行交付 → 模块化开发
- 需要独立审批 → 规划-审批

## 高差异模式附加约束

高差异模式必须在主流程中显式共创选择，不能把模式选择藏在实现细节、补充说明或外部协议里。

- 主文档必须写清模式选择触发点、用户共创节点、推荐路径、主代理职责和最大 agent 数。
- 不能只写“用户明确要求时”，必须把“什么时候触发、为什么推荐、主代理怎么汇总”写成可执行说明。
- 当模式差异会显著改变用户体验、token 成本、并行度或裁决方式时，必须在主流程中先完成模式选择，再进入后续步骤。

## 全局合同落地约束

- 节点责任不下放，工序可下放。
- 主 Agent 只负责确认、裁决、Gate、回退和签收，不把关键提问、设计裁决、测试门禁、Task 冻结或风险接受交给 sub agent。
- 推荐最大 sub agent 数：`product=2`、`design=3`、`test-design=3`、`tech-lead=3`、`delivery-owner=1`。
- 任何阶段若引入 sub agent，都必须先写清固定输入、固定输出、禁止越权项和回收边界，再进入执行。
