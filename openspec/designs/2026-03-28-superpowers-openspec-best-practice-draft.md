# superpowers + openspec 最强最佳实践评审与 LLM 编码环境研究设计（Draft）

## 1. 背景

当前仓库刚引入 `community`，核心目标不是再堆一层流程，而是基于 `superpowers + openspec` 的设计思路与实践经验，收敛出一套**轻量但高质量**的产品研发工作方式。

当前问题不在于“是否有更多流程可以加”，而在于以下判断尚未被澄清：
- `superpowers + openspec` 到底解决了哪些真实问题，边界在哪里？
- 什么样的产出才配得上“最强最佳实践”，而不只是更复杂、更正式？
- 怎样结合当前仓库，把这套方法论收敛成适合 LLM 的最佳编码环境？
- 如果引入 `codex query rewrite` 一类预处理，它到底是在增强判断，还是在打断责任链？

近期提交已明显显示当前仓库在向 `community-first` 与 `opsx consistency` 收敛，但这条路径是否已经接近最佳实践，仍需要独立评审，而不是默认接受。

## 2. 目标

本设计要为当前仓库产出一套**可执行、可复核、可反驳**的研究框架，用来回答三类问题：

1. 识别 `superpowers + openspec` 在轻量级产品研发流程中的真正最佳实践标准与评审维度。
2. 定义什么样的内容与约束，才算对日常问题真正有效、且能够提升产出质量与效率的“最强最佳实践”。
3. 结合当前项目，设计一个以 LLM 为中心的最佳编码环境与协作流程。

本研究的默认落地对象是：**当前项目中用户与 Claude/agents 的个人主战场**。

## 3. 非目标

本设计不做以下事情：
- 不直接修改 `community/**`、`openspec/**`、skills、prompt 或 router。
- 不直接把任何评审口径接成自动硬门禁。
- 不先为团队规模化或对外产品化设计统一模板。
- 不默认把 `codex query rewrite` 视为正向增强。
- 不把外部“主流最佳实践”直接当作当前仓库结论。

## 4. 决策优先级

本研究范围内采用以下优先级：

1. **质量第一**：先判断是否真的提升需求清晰度、实现正确性、评审质量与验证闭环。
2. **效率第二**：在质量成立后，再看是否减少返工、沟通成本与上下文切换。
3. **可复制性第三**：先服务个人主战场，再判断哪些做法值得外推到团队层。

这意味着：
- “更完整”不等于“更好”。
- “更严格”不等于“更可靠”。
- “更像权威方法论”不等于“更适合当前项目”。

## 5. 设计原则

### 5.1 Rubric-first，而不是 Refactor-first

这轮工作的首要任务不是继续改 prompt、改 skill 或改 router，而是先统一“怎么判断它是不是最佳实践”的口径。没有统一口径，任何后续优化都容易变成结构漂移或偏好之争。

### 5.2 Repo-native，而不是权威移植

外部方法论、社区经验、Codex 或其他 agent 方案只能作为候选假说。最终结论必须绑定当前仓库、当前流程与当前工作对象，而不是靠权威背书成立。

### 5.3 反方是裁判，不是陪衬

挑战线的作用不是礼貌性补位，而是专门攻击主线结论中的权威幻觉、流程表演、过早收敛与个人最优陷阱。没有真正的反驳压力，这轮研究不能称为最佳实践评审。

### 5.4 先服务个人主战场，再谈外推

当前最真实、最有价值的落地场景，是用户与 Claude/agents 的高强度协作。只有这层跑通，才有资格讨论团队复制、方法论沉淀与产品化表达。

## 6. 方案选择

### 6.1 候选方式

1. **Rubric-first**：先定义评审口径，再并行研究并统一裁决。
2. **Workflow-first**：直接从日常协作链路倒推当前流程的改造方案。
3. **Benchmark-first**：先广泛对标外部方法论，再回评当前仓库。

### 6.2 选择结果

选择 **Rubric-first** 作为主骨架。

原因：
- 用户当前真正缺的不是更多观点，而是一个能区分“最佳实践”与“rigor theater”的稳定评审语言。
- 当前仓库已经存在 `community-first` 与 `opsx consistency` 的收敛趋势，此时继续局部修改，容易把方向正确的结构推成不稳定的强约束。
- `Workflow-first` 仍然重要，但更适合成为其中一条主线，而不是总方法。
- `Benchmark-first` 能提供外部证据，但不能取代当前项目判断。

因此，本研究采用：**Rubric-first + workflow grounded + challenge driven**。

## 7. 研究总架构

本研究采用：**1 个统一评审矩阵 + 3 条主线 + 2 条挑战线 + 1 个汇总裁决层**。

### 7.1 统一评审矩阵

所有研究线都必须围绕同一组问题产出判断：
- 是否真的服务决策，而不是服务报告表演？
- 是否绑定当前仓库，而不是通用百科式论述？
- 是否具备证据与回链，而不是只看起来严谨？
- 是否处理了真正会改变结论的反方？
- 是否控制了执行负载，而不是靠模板堆叠制造仪式感？
- 是否保留了从输入到结论的责任链？

### 7.2 主线 1：方法论真相线

回答：
- `superpowers` 与 `openspec` 各自解决什么问题。
- 二者组合后哪些是互补，哪些是重复，哪些存在结构性张力。
- 当前仓库里哪些约束真正提高质量，哪些更像流程表演。

产出：
- 方法能力地图
- 高价值约束 / 仪式性约束清单
- 关于最佳实践边界的关键判断

### 7.3 主线 2：最强实践定义线

回答：
- 对“质量第一、效率第二、个人主战场优先”的场景，什么才算“最强最佳实践”。
- 哪些标准是必备项，哪些只是加分项，哪些应一票否决。
- 哪些做法容易被误判为最佳实践，但实际上会降低真实质量。

产出：
- 最强实践定义
- 分层 rubric
- 反例与误判清单

### 7.4 主线 3：项目落地线

回答：
- 当前仓库里怎样组织 skill 入口、agent 协作、评审闭环与验证闭环，才能形成 LLM 最佳编码环境。
- 哪些门禁应保留，哪些应降噪，哪些应延后。
- 什么才是“最小高质量闭环”，而不是“最大全流程”。

产出：
- 个人主战场 LLM 编码环境蓝图
- 最小高质量闭环
- 当前仓库的保留 / 调整 / 删除 / 延后建议表

### 7.5 挑战线 A：认知与决策质量挑战

专门攻击以下假设：
- 更复杂的流程天然更严谨。
- 更多模板字段天然提升判断质量。
- 更快形成“一页结论”天然更高效。

其职责是识别：
- 权威幻觉
- `rigor theater`
- 过早收敛
- 证据看似丰富但判断仍然脆弱的结构

### 7.6 挑战线 B：工程与组织扩展性挑战

专门攻击以下假设：
- 个人主战场最优做法天然可复制到团队。
- 高上下文密度与强提示依赖不会形成长期维护成本。
- 多 agent 分工天然优于单 agent 聚焦。

其职责是识别：
- 不可复制性
- 高手依赖
- 门禁疲劳
- 文档漂移与协作失真

### 7.7 汇总裁决层

汇总层不做平均值综合，而是只输出三类高价值结果：
- 哪些结论已经被多条主线和挑战线共同支持。
- 哪些结论仍有强争议，不应提前固化。
- 哪些论点应直接淘汰，不得进入最终方案。

## 8. 证据契约

每条研究线的每个**关键判断**都必须带以下字段：

- **结论**：一句话判断
- **证据**：具体来源，必须是文件、提交或外部材料中的可定位对象
- **证据强度**：高 / 中 / 低
- **最强反证**：当前最能推翻该判断的相反证据或相反解释
- **翻转条件**：什么变化会让当前判断失效

证据使用采用以下偏好顺序：
1. 当前仓库的实际结构与行为
2. 当前仓库的提交演进与已写设计
3. 外部材料与社区经验

外部“最佳实践”只能提供对比与假说，不能直接替代 repo 证据。

## 9. 反驳契约

挑战线对主线的每次攻击，都必须按以下结构表达：

- **攻击对象**：反驳哪条主线结论
- **攻击类型**：权威幻觉 / `rigor theater` / 过早收敛 / 个人最优团队失真 / 不可复核 / 不可复制
- **反驳论点**：为什么该结论可能错误或代价被低估
- **所需证据**：主线需要补什么证据才能顶住这次反驳
- **风险等级**：高 / 中 / 低

这使反方压力测试可审计，而不是停留在抽象质疑。

## 10. 裁决语义

汇总层采用以下四档裁决：

- **共识成立**：至少两条主线独立支持，且挑战线未击穿核心前提。
- **有条件成立**：方向正确，但依赖明确前提、边界或待验证条件。
- **存在争议**：主线与挑战线均有强证据，当前不应强行收敛。
- **直接淘汰**：不能提升质量、不可复核、不可复制，或明显属于流程表演。

其中两条硬规则不可放松：
1. 没有 repo 绑定的“最佳实践”，不得进入最终建议。
2. 没有 evidence 回链与 provenance 的 query rewrite / 路由建议，不得进入正式方案。

## 11. 对 codex query rewrite 的位置定义

`codex query rewrite` 在本研究中只能被视为一个**待验证假说**，而不是默认增强项。

判断它是否成立，必须回答：
- 它是否真的提升研究与评审质量，而不是仅提升表达工整度？
- 它是否改变了问题边界、评价口径或结论倾向？
- 它是否保留了从 `raw query` 到 `rewritten query` 的责任链？

若未来要把 rewrite 引入正式流程，至少需要补齐：
- `raw_query`
- `rewritten_query`
- `rewrite_rationale`
- `equivalence_confirmation`

在 provenance 不完整前，rewrite 不得被当作正式研究链路的默认前置步骤。

## 12. 即时汇报机制

为了满足“并行推进、即时汇报”的要求，本研究不采用一次性最终报告，而采用三次节奏化回报：

1. **初判阶段**：每条线先给一句核心判断，尽快暴露分歧。
2. **证据阶段**：每条线补充证据、反例、风险与翻转条件。
3. **裁决阶段**：汇总层只输出共识、争议与淘汰项。

这样可以在不中断研究的前提下，持续让用户看到方向、分歧与收敛状态。

## 13. 最终交付物

本研究最终应沉淀为四份结果：

1. `superpowers + openspec` 最佳实践判定 rubric
2. 适用于个人主战场的“最强实践”定义与反例集
3. 当前项目的 LLM 最佳编码环境蓝图
4. 挑战结论与保留异议清单

这些产物的目标不是包装一个“看起来更完整”的流程，而是帮助当前项目更稳定地获得高质量判断、更少返工和更可信的协作闭环。

## 14. 设计结论

当前仓库最值得做的，不是继续默认接受 `community-first` 或 `superpowers + openspec` 已经等于最佳实践，也不是直接开始改造 skill / prompt / workflow。

更稳的路径是：
- 先用统一 rubric 定义什么叫“真正更强”；
- 再通过三条主线去建立正向论证；
- 同时通过两条挑战线持续攻击权威幻觉、流程表演与个人最优陷阱；
- 最后只把经得起 repo 证据与反方压力测试的结论收进当前项目的正式建议。

这让本轮工作从“观点竞争”转成“可复核裁决”，也让后续任何实现、调整或验证都有统一依据。
