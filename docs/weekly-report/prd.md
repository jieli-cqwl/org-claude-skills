# PRD: 团队内部技术周报平台

功能名: weekly-report | 产出时间: 2026-04-06

## 业务背景与根问题

团队工程师（10-50 人规模）的技术周报散落在飞书、邮件、文档等多个工具中，导致：
- 找不到：没有统一入口，想看某人的周报要翻多个平台
- 看不全：没有完整的周报列表，容易遗漏
- 没有沉淀：周报内容随时间沉没在聊天记录和邮件流中，无法作为知识资产积累

根问题：缺乏一个集中的技术周报阅读平台。本期解决"集中阅读"问题；"沉淀"问题需待写作功能（CRUD）上线后验证。

## 目标与成功标准

| 目标 | 成功标准 | 度量方式 |
|------|---------|---------|
| 提供集中的周报阅读入口 | 登录后可看到所有已发布周报的列表 | 首页可正常加载并展示周报列表 |
| 提高周报可见性 | 周报按时间倒序排列，支持分页浏览 | 分页功能正常，排序正确 |
| 保障访问安全 | 未登录用户无法访问周报内容 | 路由守卫正确拦截并跳转 |

## 关键假设

| 假设 | 不成立时的后果 | 验证方式 |
|------|--------------|---------|
| A1: 团队规模 10-50 人，不需要高并发 | 需要引入缓存/分布式架构 | 上线后监控 QPS |
| A2: 账号由管理员预置，不需要注册功能 | 需要增加注册流程和邮箱验证 | 用户反馈 |
| A3: 周报数据初期可通过种子数据填充 | 需要先完成发布功能才能验证首页 | 种子数据加载后验证首页展示 |

## 用户角色与核心场景

- 作为工程师（作者），我希望登录后看到团队所有已发布的技术周报列表，这样我能快速了解团队成员的工作进展
- 作为工程师（读者），我希望通过统一入口浏览周报，这样不用在多个工具间切换查找

## 业务术语

| 术语 | 定义 | 备注 |
|------|------|------|
| 作者（Author） | role=author 的用户，可发布/编辑/删除自己的周报 | 本轮 author/reader 行为一致 |
| 读者（Reader） | role=reader 的用户，只能浏览周报 | 本轮 author/reader 行为一致 |
| 周报（Weekly Report） | 一篇技术周报，归属某个作者 | 状态：draft/published |
| 首页 | 登录后的默认页面 | 只展示 status=published 的周报 |

## 业务对象

| 对象 | 说明 | 关键状态/属性 |
|------|------|---------------|
| 用户（User） | 公司内部工程师，管理员预置账号 | id, username, password_hash, display_name, role(author/reader), created_at |
| 周报（Weekly Report） | 一篇技术周报，归属某个作者 | id, title, content, author_id, status(draft/published), created_at, updated_at |

## 当前业务流程

周报写在飞书/邮件/文档 → 各处散落 → 想看某人周报要逐个平台翻找 → 经常遗漏 → 无法沉淀为知识资产

## 目标业务流程

统一登录入口 → 首页看到所有已发布周报（按时间倒序）→ 集中浏览和沉淀

## 范围 / 本期不交付

| 类型 | 内容 |
|------|------|
| 范围 | 登录页（账密登录+JWT签发）、首页（已发布周报列表+分页+倒序）、路由守卫（未登录跳转+已登录跳转+过期处理）、种子数据（3用户+10周报） |
| 本期不交付 | 用户注册、密码找回、周报发布/编辑/删除（CRUD写操作）、周报详情页、评论、标签、搜索、统计、管理员后台 |

## 业务规则

- R1: 密码错误时返回通用错误提示"用户名或密码错误"，不区分用户名不存在和密码错误
- R2: JWT token 有效期 24 小时，过期后需重新登录（本轮不做 refresh token）
- R3: 首页只展示 status=published 的周报，draft 不可见
- R4: 分页每页 10 条，首页默认第 1 页

## 影响范围

经评估，本次变更不影响现有功能。本项目为全新模拟项目。

## 功能需求（UNIT 索引）

| UNIT | 标题 | 闭环目标 | 优先级 | 依赖 |
|------|------|----------|--------|------|
| UNIT-1 | 用户账密登录 | 用户输入凭据 → 验证+签发JWT → 进入首页或看到错误提示 | MVP | 无 |
| UNIT-2 | 首页周报列表展示 | 已登录用户访问首页 → 查询已发布周报 → 展示分页倒序列表 | MVP | UNIT-1 |
| UNIT-3 | 登录态路由守卫 | 用户访问任意页面 → 检查JWT → 按登录态路由到正确页面 | MVP | UNIT-1 |

## MVP 最小闭环说明

- 最小闭环包含哪些 UNIT：UNIT-1, UNIT-2, UNIT-3
- 关键路径（按依赖顺序）：UNIT-1 → UNIT-2 / UNIT-3（UNIT-2 和 UNIT-3 可并行，均依赖 UNIT-1）
- 逐项不可移除论证：
  - 移除 UNIT-1 则：用户无法登录系统，UNIT-2 和 UNIT-3 均无法工作
  - 移除 UNIT-2 则：用户登录后看到空壳页面，"看周报"的核心价值闭环断裂
  - 移除 UNIT-3 则：认证边界形同虚设，未登录用户可直接访问首页，安全模型崩溃

## 非功能需求

| 编号 | 类别 | 验收标准（输入/操作 → 可观察结果） |
|------|------|-----------------------------------|
| GAC-001 | 安全 | 密码存储使用 bcrypt/argon2 哈希，数据库中不存在明文密码 |
| GAC-002 | 性能 | SQLite 含 10 条已发布周报时，`GET /api/reports` 接口响应时间 < 500ms（Chrome DevTools Network 面板测量）；前端从请求发出到列表渲染完成 < 1000ms |
| GAC-003 | 安全 | JWT token 不包含密码等敏感信息，业务自定义 claim 仅含 user_id 和 role（标准 JWT claims 如 exp/iat 不受限制） |

## 已排查并排除的潜在问题

| 编号 | 潜在问题 | 排查过程 | 排除证据 |
|------|---------|---------|---------|
| EP-001 | SQLite 并发写入锁导致登录失败 | 本轮登录只读取用户表验证凭据，不涉及写入 | 登录流程为纯读操作，SQLite 支持并发读 |
