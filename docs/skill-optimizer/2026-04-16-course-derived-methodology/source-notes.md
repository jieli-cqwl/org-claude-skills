# Skills 技能系统课程信息沉淀

## 文档定位

本文件沉淀极客时间「Skills 技能系统」7 讲对 `skill-optimizer` 设计的二次抽象。它不是课程原文、逐字笔记或知识库搬运，而是用于后续设计评审、实施追踪和证据校验的 source map。

课程来源：https://time.geekbang.org/column/article/945937

本文件解决三个问题：

- 让后续 reviewer 知道哪些方法论来自课程，哪些是本仓库延展。
- 让 `design.md` 的关键结论能回到明确来源与证据等级。
- 防止把课程案例归纳、本地规则和主线程推断混成同一类权威。

## 逐讲方法论沉淀

### C09：SKILL.md 结构与触发机制

核心抽象是：`description` 是运行时路由合同，不是给人看的简介。模型先看到 metadata，再决定是否加载 `SKILL.md`。因此 description 需要表达能力、触发场景、边界和相邻 Skill 区分点。

对 `skill-optimizer` 的设计影响：

- 触发审计必须检查 frontmatter、能力声明、使用场景、不适用场景和相邻 Skill 冲突。
- `SKILL.md` 被视为 Skill 入口，不是全部知识的容器。
- Skill 与 Command 的区分基于路由方式、复用方式、副作用和参数稳定性。
- 触发样例和非触发样例进入 eval 设计，防止 description 只靠主观阅读判断。

不可外推边界：

- 课程强调触发机制，不等于所有 Skill 都要写长 description。
- Skill 自包含不等于所有信息都内联到 `SKILL.md`。
- 触发契约是审计对象，不自动成为所有场景的阻塞门禁。

设计锚点：`触发契约`、`加载契约`、`skill-creator 与 skill-optimizer 边界`、`验证设计`。

### C10：任务型 Skills 与 Command 实战

核心抽象是：任务型 Skill 是受控执行入口。质量不只来自命令是否可运行，还来自输入、上下文、权限、失败路径和安全网是否成组设计。

对 `skill-optimizer` 的设计影响：

- 审计任务型 Skill 时要看参数提示、参数解析、缺参、错参、危险参数、依赖缺失和终止行为。
- 有副作用或权限敏感的入口需要最小工具权限和显式确认边界。
- review、audit、explain 类 Skill 默认不应拥有 Edit/write 权限；需要修改文件时由后续明确实施环节接管。
- hooks 适合承载状态流转拦截和门禁，不适合把方法论判断硬塞到脚本里。

不可外推边界：

- 有稳定命令不代表必须封装为 Command；自动触发的 Skill 与手动调用的 Command 是不同交互模型。
- 权限越少越好不是唯一标准；权限要与职责和失败路径匹配。
- hooks 是工程护栏，不替代 Skill 内的流程说明与证据要求。

设计锚点：`任务型 Skill 契约`、`资源目录职责模型`、`质量维度扩展`、`验证设计`。

### C11：渐进式披露架构设计

核心抽象是：Skill 是三层加载系统。metadata 决定是否加载，`SKILL.md` 决定如何执行与读取资源，bundled resources 承载低频细节、模板、脚本和资产。

对 `skill-optimizer` 的设计影响：

- 优化目标是职责归位，不是单纯压缩 `SKILL.md`。
- `references/` 承载长方法论和背景知识；`examples/` 承载正反例与边界例；`scripts/` 承载确定性工程动作；`schemas/` 承载 runtime artifact 合同。
- 契约式引用是渐进式披露的运行时控制方式：模型不只知道“有文件”，还知道何时读、读什么、用于哪个判断、如何证明读过且用过。
- 简单 Skill 只包含 `SKILL.md` 也成立；目录只在承担真实职责时创建。

不可外推边界：

- 拆目录不是质量本身；没有消费者的资源会制造维护成本。
- reference 不需要全部完整六字段；关键 runtime reference 才需要完整契约。
- 低频细节外置后，入口仍要能让模型完成正确路由。

设计锚点：`加载契约`、`资源目录职责模型`、`契约式引用`、`契约式引用详细规范`。

### C12：Skills 与 SubAgent 配合

核心抽象是：Skill 管 HOW，SubAgent 管 WHO/WHAT/WHERE/OUTPUT。Skill 提供方法、规则、判断框架；SubAgent 在独立上下文中执行分析、实现、验证或挑战。

对 `skill-optimizer` 的设计影响：

- 引入 SubAgent 的理由是独立上下文、并行分析、对抗审查、责任隔离或独立验收。
- SubAgent prompt 需要明确输入边界、输出格式、证据要求和冲突裁决方式。
- agent team 的产出不能直接成为权威，需要经过主 Agent 归并、证据等级标注和反方挑战。
- `agents/` 可承载暴露元数据或平台侧入口，但不替代 `SKILL.md` 的方法与合同。

不可外推边界：

- 复杂任务不天然需要 SubAgent；关键是是否存在独立上下文或并行价值。
- SubAgent 数量不等于完整性；完整性来自覆盖矩阵和挑战机制。
- 对抗审查给出的是风险证据，不是自动否决权。

设计锚点：`Skill 与 SubAgent 组合契约`、`调研到实施追踪契约`、`风险与裁决`。

### C13：Skills 架构定位与高级能力

核心抽象是：Skill 是 Agent 系统中的知识层，负责把经验、流程、判断框架和工程能力组织成可调用能力。高级 Skill 不只指导模型写文本，还能选择模式、调用脚本、隔离工具和沉淀组织经验。

对 `skill-optimizer` 的设计影响：

- 审计对象从 Markdown 结构扩展到运行链路：触发、加载、决策、执行、验证、演化。
- 质量模式拆成模板驱动、脚本增强、知识分层和工具隔离。
- 成熟度分为 SOP、专家系统、组织智能，用于诊断 Skill 当前能力层级。
- `rules/`、`references/`、`examples/`、`evals/`、`schemas/`、`scripts/` 和 `hooks/` 是职责分离模型，不是每个 Skill 的固定模板。

不可外推边界：

- 成熟度模型是诊断维度，不替代本仓库 L1/L2/L3 评级。
- “高级能力”不等于堆资源；只有真实消费者和验证路径的资源才进入 Skill 包。
- 脚本增强只适合确定性、重复性强、易出错的工程动作。

设计锚点：`架构定位与模式选择`、`成熟度模型`、`skill-optimizer 运行模型`、`质量维度扩展`。

### C14：从 Claude Code 到行业开放标准

核心抽象是：Skill 的长期价值来自声明式、自包含、可迁移和可组合。平台差异不可避免，但需要隔离在清楚的位置，避免把平台特定字段误当成方法论本身。

对 `skill-optimizer` 的设计影响：

- Push/Pull 治理用于区分全局硬规则、共享技术真源和按需加载知识。
- 平台无关知识进入 `SKILL.md` 或 `references/`；平台特定执行约束要标注适用端。
- `agents/openai.yaml`、Claude Code 字段、hooks、allowed-tools 等都需要明确消费端。
- 兼容设计要承认 `skill-creator`、`skill-optimizer` 和 legacy `new-skills` 的边界。

不可外推边界：

- 可迁移不等于去除本地特化；本地特化需要清楚标注。
- 开放标准不覆盖本仓库硬规则；本仓库 rules 仍是运行时优先级最高的约束。
- 课程给出方向，不直接决定本仓库目录和命名。

设计锚点：`Push/Pull 治理契约`、`平台兼容设计`、`new-skills 迁移形态`。

### C99：专题总结

核心抽象是：Skill 的交付物不是一个孤立 Markdown 文件，而是一套能被触发、使用、验证、迭代的能力包。总结价值体现在可用性、复测性和组织知识沉淀。

对 `skill-optimizer` 的设计影响：

- `evals/` 作为 `skill-optimizer` 的必需目录，用于证明优化收益。
- 5/10/30 分钟模型作为可用性门槛，帮助判断 Skill 是否可上手、可诊断、可产出优化计划。
- 改造收益不能只看 token 和耗时，还要看触发误判、reference 证据、runtime artifact 稳定性、失败路径覆盖和人工复审发现。
- 最终交付需要覆盖表，证明每个设计锚点已进入任务、计划、文件 diff 和 fresh proving command。

不可外推边界：

- 5/10/30 是可用性门槛，不是质量收益的唯一指标。
- eval 是证据通道，不替代真实工程验证。
- 总结课启发完整交付意识，不等于要求所有 Skill 都达到组织智能层级。

设计锚点：`验证设计`、`调研到实施追踪契约`、`设计裁决`。

## 横向方法论

### 契约闭环

7 讲共同指向一个运行时闭环：

```text
触发 → 加载 → 决策 → 执行 → 验证 → 演化
```

`skill-optimizer` 的审计单位不是章节完整性，而是这个闭环是否可观察、可验证、可复盘。任一环节缺失时，优化建议要指向缺失合同，而不是只改文案。

### 契约式引用

契约式引用的核心是“给下游消费者的读取合同”。裸路径只告诉模型文件存在，契约式引用要告诉模型在什么控制点读取、读取后服务哪个判断、输出中如何体现证据。

完整契约包含六个要素：

| 要素 | 运行时问题 |
| --- | --- |
| 触发条件 | 何时读取 |
| 读取对象 | 读取哪个一跳直达路径 |
| 内容预期 | 读完要获得哪类信息 |
| 消费方式 | 信息用于流程、输出、校验、prompt 还是脚本参数 |
| 证据要求 | 输出如何证明内容被使用 |
| 同步义务 | reference 变化后入口合同如何更新 |

常见失败形态：

- 只有路径，没有读取时机。
- 只有文件名，没有内容预期。
- 读取后没有进入决策、输出或校验。
- reference 内容变了，入口描述不变。
- 让模型“读完所有资料”，造成上下文浪费和决策漂移。

适用粒度：

- 关键 runtime reference 使用完整契约。
- 模板、Agent prompt、示例使用轻量契约，至少写清用途和内容预期。
- 普通背景材料只作为来源记录，不强制进入契约。

### 结构化信息与 Harness Engineering

课程提供 Skill 机制与组织方式，Harness Engineering 提供稳定性目标：把不稳定的模型行为放进可观察、可验证、可回放的工程护栏里。由此形成 Runtime Info Contract：

- 参与流程、状态、验证、拦截、统计、回放和下游消费的信息进入 JSON runtime artifact。
- 背景解释、权衡叙述和人类展示进入 Markdown/HTML 派生视图。
- JSON 不是质量来源；schema 合同、语义校验、状态机、验证证据和消费合同才是质量来源。
- Schema 不只是字段格式，而是上下游之间的接口合同。

这部分是 S 类本地综合推断，不是课程直接结论。进入实施时需要通过样例、validator 和 eval 证明价值。

### 权限与职责分离

课程中的任务型 Skill、SubAgent 配合和开放标准共同支持一个工程原则：职责要分层，权限要随职责收敛。

- Skill 聚焦流程、规则、判断和资源路由。
- scripts 聚焦确定性、重复性强、可机械执行的工程动作。
- hooks 聚焦状态流转拦截和门禁。
- SubAgent 聚焦独立上下文中的并行分析、执行、审查或验收。
- review/audit 类入口默认只读；修改文件需要进入实施角色或明确用户授权。

该原则与本仓库执行纪律、权限边界和完成前验证共同形成 E3+E5 设计约束。

## 本地综合结论

下列结论不是课程原意，属于本仓库结合课程、官方工具、Harness Engineering 和现有规则形成的设计决策：

| 结论 | 来源组合 | 设计状态 |
| --- | --- | --- |
| `new-skills` 改造为 `skill-optimizer` | C09/C13/C14 + O + L + S | 本仓库命名与职责收敛决策 |
| `skill-creator` 负责创建与 benchmark，`skill-optimizer` 负责质量治理 | O + L + S | 边界决策 |
| `rules/`、`examples/`、`evals/`、`schemas/` 独立成目录 | C11/C13 + L + S | 资源职责模型 |
| Runtime Info Contract 使用 JSON 作为事实源 | Harness Engineering + L + S | 首轮试点决策 |
| Markdown/HTML 从 JSON 派生 | Harness Engineering + S | 视图生成决策 |
| hooks 用于状态流转拦截 | C10 + L + S | 后续阶段能力，不进首轮接入 |
| `evals/` 对 `skill-optimizer` 必需 | C99 + O + S | 价值验证决策 |
