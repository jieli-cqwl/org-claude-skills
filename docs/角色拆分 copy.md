  1. Phase 到什么程度才是最佳实践？

  Phase
  应该定义**"为什么分这几步走"和"每步走到哪"**，而不是"每步里有什么具体功能"。

  ┌────────────────────────────────────────┬───────────────────────────────┐
  │       Phase 应该定义（到此为止）       │ Phase 不应该涉及（留给 UNIT） │
  ├────────────────────────────────────────┼───────────────────────────────┤
  │ 阶段目标："本阶段后用户能端到端完成 X" │ 具体功能点有哪些              │
  ├────────────────────────────────────────┼───────────────────────────────┤
  │ 范围边界："包含 A/B/C 能力域，不含 D"  │ 每个功能的输入输出            │
  ├────────────────────────────────────────┼───────────────────────────────┤
  │ 进入/退出条件                          │ 验收标准                      │
  ├────────────────────────────────────────┼───────────────────────────────┤
  │ 阶段间依赖关系                         │ 错误处理场景                  │
  ├────────────────────────────────────────┼───────────────────────────────┤
  │ 交付价值（对用户可感知的变化）         │ 技术实现考量                  │
  └────────────────────────────────────────┴───────────────────────────────┘

  判断准则：Phase 的粒度应该是你能用一句话向老板说清楚的 ——
  "第一阶段完成后，用户能自主注册并登录"。如果你需要说*"用户能注册、能用邮箱登录
  、能用手机号登录、能重置密码"*，那就太细了，这些是 UNIT 级别的。

  实践检验：Phase 描述应该在 3-6
  个月后回头看仍然清晰且正确。具体功能可能在开发中调整，但 Phase
  的目标和边界不应该变。

  2. 产品经理（unit-design）的关注点是否是最佳实践？

  当前 UNIT 模板的关注点覆盖了：

  - 闭环定义（输入→行为→结果）
  - AC（正常/异常/边界）
  - 优先级 + 依据
  - 依赖 + 排除项

  这个关注点清单是合理的，但我认为有一个重要的缺失环节：

  缺失：用户场景驱动的边界验证

  人类产品经理在拆解功能时，脑子里始终有一个"用户在做什么"的故事线。TA
  不是在抽象地判断"这是一个功能还是两个"，而是在追踪用户的实际操作路径，在路径中
  找到自然的断点。

  当前 UNIT
  模板直接从"闭环定义"开始，跳过了"这个闭环是从用户的哪个场景中切出来的"。

  建议补充：在 UNIT 边界判断之前，先建立Phase 级用户场景（不是完整的 User
  Story，而是一个粗粒度的操作路径），然后从场景中识别自然的功能断点。

  示例：
  Phase 目标："用户能自主注册并登录"

  用户场景路径：
    用户打开首页 → 点击注册 → 填写信息 → 提交 → 收到验证邮件 → 点击链接 →
  注册成功
                                                                              ↓
    用户打开首页 → 点击登录 → 输入凭据 → 登录成功 → 看到主页
                                ↓
                           忘记密码 → 申请重置 → 收到邮件 → 设置新密码

  自然断点识别：
    → UNIT-001: 用户注册（首页→注册成功）
    → UNIT-002: 邮箱验证（发送验证→激活账号）  ← 独立触发器，独立结果
    → UNIT-003: 用户登录（首页→主页）
    → UNIT-004: 密码重置（忘记密码→新密码生效）  ← 独立闭环

  这样 UNIT 的边界不是 AI 凭模板推理出来的，而是从用户实际操作路径中发现的。

  关键发现：需要一个桥接步骤

  所有框架都指向一个共识：从"阶段范围"到"具体功能"之间，需要一个"用户场景"桥接层
  。

  - User Story Mapping 先走通用户活动路径，再从中识别故事
  - Shape Up 先理解用户问题场景，再定义解决方案边界
  - 需求工程先做 Use Case 分析，再提取功能需求

  这不是额外的"步骤"，而是 UNIT
  拆解的认知前提。人类产品经理脑子里自动有这个场景，AI 没有 — 必须显式建立。

  最终推荐的角色划分

  /product（产品总监）
    输入：原始需求/想法
    核心活动：全共创
      S1: 根问题确认
      S2: 目标与成功标准
      S3: 业务语义闭合
      S4: 范围与规则
      S5: Phase 规划（含进入/退出条件）
      G1: 理解对齐确认
    产出：brief.md + phase-prd.md
    边界准则：Phase 能用一句话对老板说清楚

  /unit-design（产品经理）
    输入：brief.md + phase-prd.md（从工件读取，干净上下文）
    核心活动：全共创
      U1: Phase 级用户场景路径建立 ← 桥接步骤
      U2: 场景中自然断点识别（哪里是一个功能的结束）
      U3: 逐 UNIT 闭环定义共创
      U4: AC 定义（正常/异常/边界）
      U5: UNIT 间依赖与排除项
      U6: 场景化走查验证（每个 UNIT 放回场景中检验）
      U7: 三方交叉评审
      G2: 用户审阅并确认
    产出：UNIT-*.md（完整闭环定义 + AC）
    边界准则：每个 UNIT 满足 INVEST 原则

  INVEST 作为 UNIT 质量的检验标准：
  - 独立（Independent）— 可独立交付和验收
  - 可协商（Negotiable）— 细节可通过共创调整
  - 有价值（Valuable）— 用户能感知到的价值
  - 可估算（Estimable）— tech-lead 能据此估算 Task 复杂度
  - 粒度合适（Small）— 不超过 3-5 个 tech-lead Task
  - 可测试（Testable）— AC 可直接转化为测试用例

  Phase 粒度建议

  推荐：每个 Phase 包含 3-7 个 UNIT

  - 3 个以下：Phase 太碎，增加链路交接开销，意义不大
  - 3-5 个：最佳区间，下游所有环节都能在一个上下文中高质量处理
  - 5-7 个：可接受，但 tech-lead 需要更多注意力管理
  - 7 个以上：必须拆分为子 Phase 或重新审视 Phase 边界

  拆分准则：如果一个 Phase 自然包含 8+ 个 UNIT，检查是否存在以下信号：
  - UNIT 之间存在明显的依赖断层（前 4 个 UNIT 完成后，后 4 个才能开始）→
  拆为两个 Phase
  - UNIT 覆盖多个独立能力域（认证 + 权限 + 审计日志）→ 按能力域拆 Phase
  - UNIT 的优先级明显分层（4 个 MVP + 4 个增强）→ 按优先级拆 Phase

  这个约束应该加在 product skill 的 S5（Phase
  规划）步骤中，作为一个显式检查：Phase 定义完成后，预估每个 Phase 的 UNIT
  数量，超过 7 个则触发拆分讨论。

  整体设计小结

  到目前为止我们确认了以下设计决策：

  1. 拆分 product → product + unit-design — 在天然接缝处分离战略决策和精度决策
  2. unit-design 使用全共创模式 — 从工件出发，场景驱动，逐 UNIT 讨论边界
  3. 增加用户场景路径作为桥接步骤 — UNIT 边界从用户操作路径中"发现"
  4. Phase 粒度约束（3-7 UNIT） — 为下游 AI 执行预留足够的上下文空间
  5. INVEST 作为 UNIT 质量检验标准 — 独立、有价值、可测试、粒度合适
