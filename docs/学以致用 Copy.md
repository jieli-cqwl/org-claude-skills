  维度二：课程转译边界 + 体系一致性

  课程方法论的角色错位

  这是我认为最根本的方向问题：

  课程教的是"如何设计和构建好的 Skill"。skill-optimizer 做的是"审计已有 Skill 
  的质量"。

  课程方法论应该进入 skill-optimizer 的审计维度列表（检查什么），而不是
  skill-optimizer 的系统架构（怎么构建）。

  但 design.md 把课程概念当成了架构模块：
  - "触发契约"变成了 skill-optimizer 自身的一个设计章节
  - "加载契约"变成了一个章节
  - "资源目录职责模型"变成了一个章节
  - "Skill 与 SubAgent 组合契约"变成了一个章节

  正确的做法应该是：这些是 skill-optimizer 在审计目标 Skill 
  时需要检查的维度，而不是 skill-optimizer 自身架构的组成部分。

  举个类比：一个代码 linter 需要知道"什么是好的代码规范"（审计知识），但 linter
  本身的架构不需要按代码规范来组织。

  source-notes 质量

  source-notes.md 本身质量很高：
  - 逐讲覆盖，证据标注清晰
  - "不可外推边界"是好的自我约束
  - 横向矩阵有参考价值

  但 source-notes 的定位有偏差 — 它把自己定位为"design.md 复审、实施追踪、eval
  设计和证据校验的 source map"。这意味着后续所有实施都要回溯到课程证据。对于一个
  本地工程工具来说，这个追踪链路太重了。

  维度三：可交付性 + ROI

  首轮交付评估

  design.md 定义的首轮 vertical
  slice："只读审计链路"。听起来很轻量，但实际依赖：

  1. skill-audit.json schema 设计和实现
  2. Semantic validator 实现
  3. Eval runner 搭建（含 seed dataset 13个样例）
  4. Markdown renderer（从 JSON 派生）
  5. SKILL.md 本身（含完整流程、审计维度、reference 路由）
  6. 多个 reference 文件
  7. 迁移映射和兼容入口

  对比一个更轻的首轮方案：
  - 一个 SKILL.md 定义审计流程和标准
  - 2-3 个 reference 文件承载详细审计维度
  - 输出为结构化 Markdown 审计报告
  - 不需要 JSON、schema、validator、renderer

  ROI 问题

  - 仓库里需要被审计的 Skill 有多少个？使用频率如何？
  - 手动按 D1-D7 review 一个 Skill 大约需要多久？
  - skill-optimizer 的开发成本（按 design.md 的完整设计）vs 手动 review
  的累计成本？

  如果 Skill 数量有限且变更频率不高，投入产出比可能不划算。

  ---
  维度四：内部 Review 的有效性

  观察

  internal-review-report.md 记录了10个 reviewer，结果：
  - 全部 REQUEST_CHANGES，无 BLOCKED — 没有任何 reviewer 质疑根本方向
  - 全部修正都被采纳 — 没有取舍和权衡
  - 完整度 challenger 和过度设计 challenger 同时存在 —
  理论上这两个角色应该有冲突（一个要求加更多，一个要求减少），但都被采纳了

  问题

  这个 review 更像是**"框架内的完善"，而不是"对框架本身的挑战"**。

  类比：如果有人设计了一座过度工程化的桥，10个 reviewer
  分别看了地基、桥墩、护栏、灯光等，每个人都提了改进建议并被采纳。但没有人问："
  这条河需要一座这么大的桥吗？"

  具体表现：
  - 没有 reviewer 质疑"JSON runtime artifact 是否必要"
  - 没有 reviewer 质疑"状态机是否必要"
  - 没有 reviewer 质疑"14个锚点 ID 的维护成本"
  - 没有 reviewer 质疑"E1-E5 证据分级对最终用户的价值"

  这些都是关于**"框架本身是否正确"**的问题，在内部 review 中缺席了。
