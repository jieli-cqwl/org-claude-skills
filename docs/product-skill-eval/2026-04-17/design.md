# Product Skill 双轴评估框架设计

## 背景

product-director 和 product-manager 两个 Skill 从旧的 /product monolith 拆分而来，尚未经过面向团队投产的系统性评估。需要回答两个问题：
1. Skill 本身是否有设计缺陷（不一致、飘逸、工程/LLM 边界不合理）
2. 产出是否符合行业 PRD 最佳实践，能否被下游 AI Agent（/design、/plan 等）直接消费

## 目标

建立一套可复用的双轴评估标准，跑测后给出综合结论（可投产 / 需改进 / 需重大改造），并输出优先级排序的改进路线图。

## 评估对象

- `/product-director`（shared/skills/product-director/）：负责根问题、目标、范围、Phase 规划与 Director 基线冻结
- `/product-manager`（shared/skills/product-manager/）：负责 handoff 后的业务流程细化、UNIT 共创、AC 收口、审查与交付确认

## 轴 1：Skill 内功审计

### 审计维度

| 维度 | 检查内容 | 判定方式 |
|------|---------|---------|
| 契约一致性 | Director 和 Manager 的 HARD-GATE、输出契约、lock 机制是否自洽、无矛盾 | 静态交叉比对 SKILL.md + output-contract + lock schema |
| 工程/LLM 边界 | 该用工程手段保障的（如 lock file 校验、handoff 准入）是否有脚本/契约兜底，还是纯靠 LLM 自觉 | 检查 scripts/ 和 HARD-GATE 覆盖 vs 纯 prompt 约束的条目 |
| 飘逸防护 | 跳步、越权、自动补确认、静默降级等已知风险模式是否有机制拦截 | 用已知风险场景跑测验证 |
| 模板/引用完整性 | references/ 中的文件是否都被正确引用、模板字段是否和产出契约对齐 | 静态扫描引用链 |
| 共创纪律 | 每步的交互模式（全共创/草案修正/条件共创）是否有明确的暂停机制 | 评估 conversation-guide 暂停点的硬度 |
| 下游契约对接 | 产出格式（brief.md + prd.md + UNIT-*.md）是否和 /design 输入契约对齐 | 交叉比对字段 |
| 上下文压力 | Skill 引用的 references 文件总量是否在 LLM 上下文窗口承受范围内 | 估算总 token 量 |

### 已知风险（初步发现）

1. completion_check.sh 只做文件存在性检查，不验证内容正确性
2. 共创模式的暂停点完全靠 prompt 约束，无工程级拦截
3. 三方评审（M-S8）的 reviewer prompt 质量直接决定评审深度
4. iteration-4 benchmark 中 entry-routing 案例 old_monolith 赢了 blind comparison

### 动态审计场景

| 场景 | 目的 |
|------|------|
| 跳步测试 | 在 D-S3 阶段直接给出完整 UNIT 定义，验证 Director 是否拒绝越权 |
| 自动补确认测试 | 给一个没有 `产品总监确认` 的旧 brief，验证 Manager 是否拒绝接入 |
| 篡改 lock 测试 | 在 Manager 阶段要求修改 Director 已锁定的范围，验证是否正确阻断 |

### 评分

每个维度标注 PASS / WARN / FAIL。

## 轴 2：产出 vs 行业最佳实践

### PRD 最佳实践 Checklist

参照 Marty Cagan（Inspired/Empowered）、SVPG、头部科技公司（Shopify/Stripe/Airbnb）公开分享的产品实践共识：

| # | 环节 | 说明 | 是否必须 |
|---|------|------|---------|
| P1 | 问题陈述 | 用户痛点 + 根因分析 + 当前状态 | 必须 |
| P2 | 目标与成功指标 | 可量化目标 + 基线 + 目标值 + 观测窗口 + 数据来源 | 必须 |
| P3 | 用户画像与场景 | 目标用户 + 核心使用场景 + 用户旅程 | 必须 |
| P4 | 范围界定 | MVP / 增强 / 明确不做 | 必须 |
| P5 | 业务流程 | 端到端流程 + 状态变化 + 分支路径 | 必须 |
| P6 | 功能规格 | 输入/行为/输出 + 正常/异常/边界 AC | 必须 |
| P7 | 数据模型 | 业务对象、字段、关系、生命周期 | 视复杂度 |
| P8 | 非功能需求 | 性能/安全/可用性/可观测性的量化标准 | 视复杂度 |
| P9 | 集成与依赖 | 外部系统/API/第三方服务的接口契约 | 视复杂度 |
| P10 | 约束与假设 | 技术约束/业务约束/合规要求 + 关键假设 | 必须 |
| P11 | 风险与缓解 | Pre-mortem + 缓解策略 | 必须 |
| P12 | 术语表 | 领域术语统一定义 | 视复杂度 |
| P13 | 交付计划 | Phase 划分 + 优先级排序 + 依赖关系 | 必须 |

### AI 可消费性补充维度

P1-P13 是行业通用的内容完整性标准。由于下游消费者是 AI Agent，还需额外评估：

| # | 维度 | 说明 |
|---|------|------|
| A1 | 结构一致性 | 产出是否遵循固定模板，字段名/章节顺序是否可预测 |
| A2 | 无歧义引用 | UNIT 之间的依赖引用是否使用统一 ID 格式（如 UNIT-001），而非自然语言描述 |
| A3 | AC 可验证性 | 每条 AC 是否可直接转化为测试用例（有明确的输入/操作和期望输出） |
| A4 | 信息自包含 | 下游 Agent 是否无需回看对话历史，仅靠产出文件就能理解需求全貌 |

### 测试场景

| 场景 | 复杂度 | 具体描述 | 关注点 |
|------|--------|---------|--------|
| 场景 1 | 低 | 为现有后台系统加一个"批量导出 CSV"按钮 | 最小闭环完整性、是否过度设计 |
| 场景 2 | 中 | 用户权限系统从"全局角色"改造为"项目级角色+资源级权限" | Phase 划分、UNIT 拆解质量、依赖识别 |
| 场景 3 | 高 | 从零搭建内部费用审批平台（含多级审批流、预算控制、报表） | 全链路覆盖、数据模型、非功能需求、风险评估 |

### 跑测协议

#### 证据分级

每次跑测必须标注证据等级，不同等级的证据权重不同：

| 等级 | 名称 | 定义 | 可用于判定"可投产"？ |
|------|------|------|------------------|
| E1 | 真实用户跑测 | 用户本人参与共创，回答基于真实业务判断 | 可以 |
| E2 | 基准脚本跑测 | 按预定义的"基准答案大纲"模拟用户回答，大纲已经用户预审批 | 可以 |
| E3 | 自由模拟跑测 | 评估者自由模拟用户回答，无预定义约束 | 不可以——仅作为探索性证据 |

"可投产"结论必须至少有 1 个场景达到 E1 或 E2 等级并通过门槛。纯 E3 证据只能支撑"需改进后投产"或更低结论。

#### 基准答案大纲

每个测试场景预定义一份基准答案大纲，包含：
- 场景背景设定（公司规模、行业、团队结构）
- 每个共创步骤的预期回答要点（不是逐字脚本，而是回答范围和关键信息点）
- 预设的"挑战点"（故意给出模糊/矛盾的回答，测试 Skill 的追问能力）
- 大纲在跑测前必须经用户预审批

#### 跑测记录要求

每次跑测必须捕获并保存以下产物：

| 产物 | 说明 | 保存位置 |
|------|------|---------|
| 对话 transcript | 完整的 Skill 对话记录（含所有共创问答） | `scenario-{N}/transcript.md` |
| 产出工件 | brief.md + prd.md + UNIT-*.md 等全部产出 | `scenario-{N}/artifacts/` |
| 跑测元数据 | 证据等级、评估者身份、时间戳、使用的模型、答案大纲版本 | `scenario-{N}/run-metadata.json` |

#### 可复现性规则

- 同一场景的不同跑测之间，若使用相同证据等级和基准大纲，评分差异超过 1 分（满分 3 分制）的环节需标注为"不稳定"，纳入改进路线图
- 评分矩阵必须标注每个分数对应的证据等级

### 评分标准

| 分数 | 含义 |
|------|------|
| 3 | 环节存在、内容深入、可直接被下游 AI 消费 |
| 2 | 环节存在、内容基本完整、下游可用但需少量补充 |
| 1 | 环节存在但内容浅或模糊，下游无法直接使用 |
| 0 | 环节不存在 |

### 通过门槛

- 必须环节（P1-P6, P10-P11, P13）：平均分 >= 2.0，无单项 0 分
- 视复杂度环节（P7-P9, P12）：中/高复杂度场景平均分 >= 1.5
- AI 可消费性（A1-A4）：无单项 0 分，平均分 >= 2.0

## 综合判定

| 结论 | 条件 |
|------|------|
| 可投产 | 轴 1 无 FAIL + 轴 2 所有场景通过 + 至少 1 个场景为 E1 或 E2 证据等级 |
| 需改进后投产 | 轴 1 无 FAIL + 轴 2 有 1-2 个环节不达标，或全部场景仅有 E3 证据 |
| 需重大改造 | 轴 1 有 FAIL 或轴 2 多个核心环节缺失 |

## 执行顺序

1. 写 D1（评估标准文档）
2. 执行轴 1 静态审计 → D2
3. 执行轴 1 动态审计 → D3
4. 编写基准答案大纲 → D4a（需用户预审批）
5. 执行轴 2 跑测 → D4 + D4b + D4c（按跑测协议执行）
6. 评分 → D5（标注证据等级）
7. 综合判定 → D6

## 约束

- 轴 2 跑测的证据分级、记录要求和可复现性规则见"跑测协议"章节
- 基准答案大纲必须在跑测前由用户预审批；未审批的大纲跑出的结果降级为 E3
- 真实用户跑测（E1）中，用户扮演需求方回答共创问题，预计每场景 20-40 分钟对话
- 评分矩阵中每个分数必须标注对应的证据等级
- 评分由评估者初评，用户终评
- 本次评估不改代码，改进作为后续任务
