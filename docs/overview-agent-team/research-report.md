# overview skill x agent team x 分层理解 调研报告

## 一页判断
- 当前结论：条件成立
- 是否符合当前目标：高
- 一句话判断：`overview` 天然适合和 agent team 结合，但最适合的不是自由协作式“大家一起聊”，而是“主代理监督 + 分层专职子代理 + 统一收口”的层级模式。
- 最大收益：在大项目、多栈项目、文档不完整项目中，更快建立稳定的项目画像，降低单代理遗漏结构、依赖、接口、配置或文档线索的概率。
- 最大风险：把“分层理解”误做成“重复扫描 + 口径漂移 + 汇总幻觉”，导致产出的概览更长但不更准。
- 不适用场景：小型单栈项目、用户只要快速概览、任务强依赖连续澄清、或证据主要依赖统一叙事而不是并行采样。
- 结论翻转条件：如果后续真实任务对比表明多 agent 的调度/汇总成本持续高于遗漏减少收益，或者质量主要取决于主代理整合能力而非分层采集，则应收缩为默认单代理。

## 核心论点拆解

## 论点 1：`overview` 是天然的“异质证据聚合”任务，因此具备多 agent 潜质

### 核心机制
- 解决什么问题：在陌生仓库中快速建立“它解决什么问题、模块怎么协作、从哪里开始深入”的统一画像，而不是只找单个 bug 或完成单个改动
- 怎么解决：先用确定性脚本拿到项目骨架，再对结构、技术栈、依赖、模块、接口、数据、配置、文档这些异质证据面做并行采样，最后由主代理收口成一份项目心智模型
- 适用边界：项目规模足够大、证据面异质、单代理单线程容易遗漏时有效；小项目或结构极清晰时收益会迅速下降

### 证据分层
- A 级证据：
  - `shared/skills/overview/SKILL.md` 已把 `overview` 定义为“项目结构 + 技术栈 + 核心模块 + 文档输出”的综合任务
  - `shared/skills/overview/references/agent-assignments.md` 明确把任务拆为 8 个互补视角
  - `shared/skills/overview/scripts/project-detect.sh` 与 `dir-tree.sh` 已把确定性预扫描从自由推理中分离出来
  - `tests/test-skill-output-and-gate-contract.sh` 已把 `Agent`、8 个上限和主代理汇总写成测试门禁
- B 级证据：
  - `docs/shared-skills-subagent-strategy/research-report.md` 已把 `overview` 定位为“保留默认串行，但把条件式多 agent 做成可执行契约”
- 证据冲突：
  - 冲突不在“能否多 agent”，而在“是否该默认多 agent”；本轮结论采用“能力成立，但默认不开”

### 正反论证
- 最强支持证据：当前 skill 自身已经把任务拆成多个证据面，说明设计者默认承认它不是单一线性阅读任务
- 最强反方挑战：并行采样未必等于更好画像，尤其当项目小、文档好、入口清楚时，单代理足够且更便宜
- 反例/失败案例：在简单仓库里，8 个 agent 很容易扫描出八份相似摘要，反而增加合并噪音

### 深层分析
- 设计哲学：`overview` 的真正产物不是“扫描结果列表”，而是“能带新人入门的压缩心智模型”
- 关键取舍：它牺牲了单次阅读的简洁性，换取更高的覆盖面与更低的遗漏率
- 演进方向：当前已经有预扫描和 agent 分工，下一步不是再加 agent，而是加强触发条件、合并协议和禁用场景

### 项目适配评估
- 最匹配的点：当前仓库已经接受“先脚本化确定性数据，再让 agent 补推理”的模式
- 最不匹配的点：尚无证据表明每次 `overview` 都值得启动 8 个 agent
- 采纳成本：中，主要是补规则而不是重写框架
- 退出成本：低，保留默认串行即可

### 当前判断
- 判定：成立
- 结论稳健性：高，仓库代码、reference、测试门禁、既有研究结论一致
- 失效边界：如果后续实测发现大部分使用场景都是小项目快速概览，这个判断会弱化
- 待验证项：跨项目对比串行 vs 条件并行的真实收益曲线

## 论点 2：`overview` 最适合“监督者 + 专家代理”的层级模式，而不是自由协作 team

### 核心机制
- 解决什么问题：如何在多视角并行采样的同时，保持最终文档口径一致
- 怎么解决：主代理负责派发、约束、去重、裁决与构图；子代理只处理自己负责的视角，并以稳定 schema 返回
- 适用边界：当目标是稳定文档产出、可回放证据链、可重跑失败 scope 时最有效；当目标是开放式探索或创意涌现时不一定最优

### 证据分层
- A 级证据：
  - `shared/reference/agent-team-patterns.md` 明确给出“命中模式时再启用 sub agent；未命中时保持单 agent”
  - `shared/skills/overview/SKILL.md` 已写明“主代理负责合并 8 个 agent 的返回结果”
  - LangGraph supervisor 官方文档把层级系统定义为“中央 supervisor 协调多个 specialized agents，并控制通信与任务委派”
  - Anthropic《Building Effective AI Agents》把 hierarchical/supervisory systems 定义为中央监督者委派专家并综合结果，同时强调上下文管理与协调开销
- B 级证据：
  - AutoGen 论文证明多 agent 会话适合复杂任务，但并未要求必须采用 peer-to-peer 讨论
  - 2025 年 communication-centric survey 指出 LLM multi-agent 的核心挑战之一就是 communication efficiency 与 scalability
- 证据冲突：
  - 外部资料同时承认 collaborative systems 在开放探索上有价值，但其挑战恰好是通信复杂度和涌现不可预测性

### 正反论证
- 最强支持证据：`overview` 的目标是“收口成单一概览文档”，天然偏向中央监督、统一输出
- 最强反方挑战：自由协作式 team 更可能发现监督者没想到的隐藏关系
- 反例/失败案例：如果让多个 agent 自由互聊而没有 schema 和轮次控制，`overview` 容易退化成长对话，而不是高信噪比概览

### 深层分析
- 设计哲学：对 `overview` 来说，“可合并性”比“创造性”更重要
- 关键取舍：牺牲部分涌现能力，换取结果稳定、证据可追踪、失败可局部重跑
- 演进方向：可以保留一类“探索型额外 agent”作为补充，但不应替代监督者主线

### 项目适配评估
- 最匹配的点：仓库本身已经是强 contract、强模板、强 gate 的体系，层级监督模式与整体风格一致
- 最不匹配的点：如果以后把 `overview` 扩展到高互动式共创入口，这个模式会显得偏硬
- 采纳成本：低到中，主要是文档契约强化
- 退出成本：低，保留当前默认串行不受影响

### 当前判断
- 判定：成立
- 结论稳健性：高，内部 contract 与外部一手资料方向一致
- 失效边界：如果未来把 `overview` 目标改成“探索性知识发现”而非“稳定项目画像”，这个判断会弱化
- 待验证项：设计一版固定 schema，观察汇总质量是否显著提升

## 论点 3：你说的“分层模式”应优先按证据层切，而不是按目录层或传统三层架构切

### 核心机制
- 解决什么问题：怎样切分 agent 才能直接服务“理解项目”，而不是只是把代码库均分
- 怎么解决：按认知任务分层，把项目理解拆成结构层、技术栈层、依赖层、模块层、接口层、数据层、配置层、文档层，然后由主代理把这些证据重新组织成产品视角、架构图和入门路径
- 适用边界：在跨语言、跨模块、文档不一致的仓库中最有效；在边界天然按业务域隔离的仓库里，可以再叠加目录层切分

### 证据分层
- A 级证据：
  - `shared/skills/overview/references/agent-assignments.md` 的 8 Agent 正好对应 8 类证据层
  - `shared/skills/overview/references/templates/project-overview-template.md` 的产物不是目录报告，而是产品视角、架构图、模块表、入门路径
  - `shared/skills/overview/scripts/project-detect.sh` 和 `dir-tree.sh` 已把目录结构识别作为底层输入，而非最终目标
- B 级证据：
  - Anthropic 指出层级系统可把专家团队抽象给 supervisor；这更适合按“职责与证据”而不是按物理目录来切
- 证据冲突：
  - 目录层切在某些大仓库中确实有效，但它更适合并行开发或大规模 code review，不一定最适合做 `overview`

### 正反论证
- 最强支持证据：现有分工表已经隐含“项目理解不是只看代码树，而是看多类证据的合成”
- 最强反方挑战：如果仓库极大，单靠证据层切分可能让某个 agent 的工作面过宽
- 反例/失败案例：在超大 monorepo 中，若 API、模型、配置都分散在多个业务域，仍需要先按业务域切一层，再在域内按证据层切

### 深层分析
- 设计哲学：`overview` 的“层”不是软件架构层，而是认知压缩层
- 关键取舍：优先服务“用户最终需要哪种理解”，而不是“代码天然如何存放”
- 演进方向：未来可演化为“两级分层”：
  - 第一级按业务域/子系统分桶
  - 第二级在桶内按证据层分工

### 项目适配评估
- 最匹配的点：当前仓库本身就是文档、规则、技能、测试并存，按证据层切更能体现真实结构
- 最不匹配的点：若用户只想要“某个目录的代码结构概览”，证据层会显得过重
- 采纳成本：中，需要把分层哲学写清，而不是只留 8 Agent 表
- 退出成本：低，可退回为简单目录导向扫描

### 当前判断
- 判定：成立
- 结论稳健性：中高，仓库内证据非常强，但外部直接讨论“overview 按证据层切”的一手资料较少，更多是方法推断
- 失效边界：如果未来验证发现用户主要关心的是“目录/业务域地图”，而不是证据合成，这个判断需要调整
- 待验证项：在 2 个 monorepo 上测试“证据层切分”与“目录层切分”的概览质量差异

## 论点 4：`overview` 应保持默认串行，只在命中条件时启用 agent team

### 核心机制
- 解决什么问题：避免把多 agent 当成默认正确答案
- 怎么解决：先做确定性预扫描与少量关键文件读取；只有当项目规模、异质性、上下文压力或用户需求明显超过单代理阈值时，再切换到分层 agent team
- 适用边界：适用于绝大多数生产场景，因为复杂度与成本都可控

### 证据分层
- A 级证据：
  - `shared/skills/overview/SKILL.md` 明确写着“默认串行执行”
  - `shared/reference/agent-team-patterns.md` 明确写着“不确定时，从最简单的模式开始”
  - Anthropic《Building Effective AI Agents》明确建议先构建满足需求的最简单方案，再考虑多 agent；并指出 multi-agent 需要更强 observability 与上下文管理
- B 级证据：
  - communication-centric survey 把 communication efficiency、benchmarking、scalability 都列为 multi-agent 挑战
- 证据冲突：
  - 并行确实能在复杂项目里提速，但复杂度与调试成本也同步上升

### 正反论证
- 最强支持证据：仓库现有 contract 和外部资料都反对把并行当默认目标
- 最强反方挑战：如果用户每次都在处理巨大仓库，默认串行会显得偏保守
- 反例/失败案例：对于大型 monorepo 或多语言平台，若仍坚持完全串行，主代理上下文污染和遗漏率可能明显增加

### 深层分析
- 设计哲学：并行是工具，不是价值观
- 关键取舍：先保证稳定闭环，再追求吞吐
- 演进方向：把“何时切并行”写成触发矩阵，而不是靠调用者临时判断

### 项目适配评估
- 最匹配的点：符合当前仓库“显式触发、条件启用、可验证”的设计风格
- 最不匹配的点：对高级用户来说，手动要求并行可能显得多一步
- 采纳成本：低
- 退出成本：无

### 当前判断
- 判定：成立
- 结论稳健性：高
- 失效边界：如果后续大部分用户请求都落在超大仓库，默认策略需要重新评估
- 待验证项：补一版触发矩阵并做真实使用频次统计

## 论点挑战总表
| 论点 | 最强支持证据 | 最强反方挑战 | 当前判定 | 对我们的启示 |
|------|-------------|-------------|---------|-------------|
| `overview` 天然适合 agent team | 8 Agent 分工 + 预扫描脚本 + 测试门禁已存在 | 小项目收益不足 | 成立 | 保留能力，但不要默认开启 |
| 最适合的是层级监督模式 | 内部 contract 与外部 supervisor 模式一致 | 开放协作有更强探索性 | 成立 | 强化 supervisor 职责与 schema |
| 分层应按证据层切 | 当前 8 Agent 已按证据层切分 | 超大 monorepo 仍需先按业务域切 | 成立 | 演化为“两级分层”更稳 |
| 默认并行更好 | 复杂仓库确实会受益 | 简单优先、通信成本、调试成本更强 | 不成立 | 默认串行，命中阈值后再 fan-out |

## 吸收建议
### 可以直接吸收
| 论点/做法 | 适用条件 | 如何吸收 |
|-----------|---------|---------|
| `overview` 可做条件式 agent team | 项目复杂、异质证据多、用户需要系统概览 | 保留默认串行，补强并行触发矩阵 |
| 主代理必须负责汇总与裁决 | 启用任何 agent team 时 | 在主文档中写清 supervisor 职责，不只放 reference |
| 证据层分工优先 | 目标是生成统一项目画像 | 把现有 8 Agent 解释为“认知层/证据层”而不是“随意分工” |

### 改写后吸收
| 原始说法 | 改写后的做法 | 改写原因 |
|---------|-------------|---------|
| `overview` 天生就是和 agent team | `overview` 天生适合条件式 agent team，且优先采用层级监督模式 | 去掉“默认必须”，保留“任务本质适配” |
| 一个团队冲不同视角去理解 | 主代理按证据层派发固定视角，子代理独立返回结构化结果，再统一构图 | 补上可执行 contract，避免口号化 |
| 分层模式 | 先确定性预扫描，再证据层分工；大仓库时可加一层业务域分桶 | 把“层”定义清楚，避免和代码分层混淆 |

### 不采纳
| 论点/做法 | 不采纳理由 |
|-----------|-----------|
| `overview` 默认并行化 | 与当前仓库设计、外部最佳实践和成本控制原则都不一致 |
| 让子代理自由协作讨论后再收口 | 对 `overview` 这种稳定产物型任务，通信复杂度和口径漂移风险过高 |
