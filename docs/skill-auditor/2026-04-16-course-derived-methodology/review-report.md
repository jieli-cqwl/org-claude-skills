# skill-auditor 方法论文档四维度 Review 报告

## Review 背景

**被 review 对象：**
- `source-notes.md`（553 行）— 极客时间 Skills 课程 7 讲的二次方法论抽象
- `design.md`（544 行）— skill-auditor Harness Engineering 设计
- `internal-review-report.md` — Codex 10 维度内部 review 记录

**Review 动机：** 用户对 Codex 梳理的 skill-auditor 方法论文档方向不确定，需要系统性 review 把关。经讨论确定四个 review 维度。

**四维度框架：**

| # | 维度 | 核心问题 |
| --- | --- | --- |
| 1 | 问题-方案匹配度 + 复杂度核实 | skill-auditor 要解决什么问题？方案复杂度是否与问题匹配？ |
| 2 | 课程转译边界 + 体系一致性 | 课程方法论和 skill-auditor 架构的关系是什么？与现有 D1-D7 / L1-L3 是否冲突？ |
| 3 | 可交付性 + ROI | 首轮能否闭环？投入产出比是否合理？ |
| 4 | 内部 review 有效性 | Codex 10 个 reviewer 全部 REQUEST_CHANGES + 全部采纳，是否只是框架内的"完善"，而缺少对框架本身的挑战？ |

## Review 团队

### Phase 1 — 结构化 Review（4 reviewer 并行）

| Reviewer | 维度 | 检查项 |
| --- | --- | --- |
| reviewer-d1 | 问题-方案匹配度 + 复杂度核实 | 消费者验证、E5 回退合同、依赖链评估 |
| reviewer-d2 | 课程转译边界 + 体系一致性 | 证据等级准确性、D1-D7 关系、课程归纳质量 |
| reviewer-d3 | 可交付性 + ROI | 首轮形态、工作量估算、迁移可行性 |
| reviewer-d4 | 内部 review 有效性 | 维度遗漏、自相矛盾、核心假设挑战 |

### Phase 2 — 独立挑战（3 challenger 并行）

| Challenger | 挑战方向 | 职责 |
| --- | --- | --- |
| 设计辩护者 | 为 FAIL/WARN 辩护 | 找 reviewer 判断过苛之处 |
| 极简主义者 | 挑战 PASS/WARN | 认为 reviewer 不够严格 |
| 元审计者 | 挑战四维度框架本身 | 找 review 方法论的系统性偏差 |

三个方向互相对抗：辩护者往回拉、极简者往前推、元审计者从上层看。

## Phase 2 交叉裁决

### 设计辩护者

- 对 1.1（消费者明确性）：合理，但文档确实存在"首轮未用但已设计"的前瞻性超载
- 对 2.1（课程转译）：合理，二次归纳与课程原文的边界确实不够清晰
- 对 2.3（新旧维度）：合理，D6 重叠问题真实存在
- 对 3.2（交付路径）：确认 FAIL，但修正了判断依据 — 不只是行数问题，而是复杂度与消费者不匹配
- 对 4.1（维度遗漏）：确认盲区 — 缺用户视角和成本核算
- 对 4.2（矛盾检测）：辩护降级为 WARN — 认为设计层面 vs 实施层面的不一致不构成矛盾
- 对 4.3（挑战有效性）：确认 FAIL — 过度设计 challenger 确实只做了量调整

### 极简主义者

- 将 1.2（E5 回退合同）从 PASS 降为 WARN — 纸上回退缺执行证据
- 将 1.1 从 WARN 升为 FAIL — 4/10 无消费者比例过高
- 将 2.1 从 WARN 升为 FAIL — 二次归纳混入 E1 是证据链硬伤
- 将 3.3（迁移映射）从 WARN 升为 FAIL — 缺验证命令等于不可执行
- 精简目标压至 200-250 行

### 元审计者

核心发现 — review 框架自身存在系统性偏差：

- **维度重叠导致问题数膨胀**：1.1（消费者）与 3.2（交付路径）本质上在问同一个问题；2.1（课程转译）与 4.1（维度遗漏）有交集。12 项检查去重后实际是 5 个独立问题
- **单方向审计偏差**：四维度只检测"过度设计"，未检测"设计不足"。设计的自我保护机制（E5 回退、consumer-first）被当作复杂度，而非控制手段

## 核心发现（去重）

元审计者正确指出维度重叠导致问题数膨胀。去重后为 5 个独立问题 + 1 个元问题：

### F1 — 设计复杂度超出首轮交付能力

- **涉及检查项：** 3.2, 1.1, 1.3, 3.1
- **严重度：** FAIL
- **具体表现：** 首轮 1500-2500 行，是被优化对象（new-skills ~200 行）的 7-11 倍；部分设计元素首轮无消费者；组件间存在循环依赖
- **根因：** Codex 把课程方法论的丰富度直接传导为架构复杂度

### F2 — 内部 review 未挑战核心假设

- **涉及检查项：** 4.3, 4.1
- **严重度：** FAIL
- **具体表现：** JSON artifact、状态机、Harness Engineering 框架的必要性从未被质疑；10 个 reviewer 全在框架内做完善，无人问"这条河需要这么大的桥吗？"
- **根因：** 内部 review 角色设计缺少框架级挑战者

### W1 — 课程方法论角色模糊

- **涉及检查项：** 2.1, 2.2, 2.3
- **严重度：** WARN
- **具体表现：** 部分 E5 推断标为 E1；新增维度与 D1-D7 重叠（如触发样例→D1、契约式引用→D6）；课程知识应主要作为审计维度（检查什么），而非系统架构（怎么构建）
- **类比：** 代码 linter 需要知道代码规范（审计知识），但 linter 本身的架构不需要按代码规范来组织

### W2 — E5 内容名实不符

- **涉及检查项：** 4.2, 1.2
- **严重度：** WARN
- **具体表现：** 文档声称 E5 不写 MUST，但大量使用"必须/至少/不得"；回退合同存在但缺执行证据（纸上回退）

### W3 — 迁移路径不完整

- **涉及检查项：** 3.3
- **严重度：** WARN
- **具体表现：** 迁移映射缺验证命令、退出条件、遗漏条目

### M1 — Review 自身存在系统性偏差（元问题）

- **涉及检查项：** 元审计者
- **严重度：** 元问题
- **具体表现：** 四维度框架只检测"过度设计"，未检测"设计不足"；设计的自我保护机制（E5 回退、consumer-first）被当作复杂度而非控制手段。维度重叠导致问题数膨胀（12 项去重后实际 5 个独立问题）

## 各方共识点

所有 7 个 agent（4 reviewer + 3 challenger）在以下五点达成一致：

1. **skill-auditor 方向成立** — 运行链路 6 环节审计（触发→加载→决策→执行→验证→演化）是 new-skills 缺少的系统性诊断能力
2. **source-notes.md 方法论质量高** — 作为参考材料有价值
3. **design.md 543 行需要瘦身** — 超过 400 行约束，E5 试点内容需剥离
4. **首轮应大幅简化** — JSON/schema/validator/renderer 推迟到有真实消费者时再引入
5. **核心审计价值不依赖基础设施** — Markdown 结构化输出足以支撑首轮

## 分歧与裁决

| 分歧点 | 辩护者 | 极简者 | 裁决 |
| --- | --- | --- | --- |
| 首轮规模 | 设计文档需要前瞻性覆盖 | 200-250 行够了 | 300-400 行（保留审计框架，砍基础设施） |
| 4.2 矛盾判定 | 设计层面 vs 实施层面不同，非矛盾 | — | 采纳辩护者，降为 WARN |
| 成熟度模型 | 作为可选诊断维度有价值 | 与 L1/L2/L3 冲突，删 | 推迟，首轮不引入 |
| skill-auditor 存在性 | 成立 | 成立，但 70-80% 可被 Skill 质量标准吸收 | 成立，核心价值是运行链路闭环审计 |

## 附录：Essential vs Accidental Complexity 分析

### Essential（skill-auditor 本质需要的）

- 读取目标 Skill 结构
- 对照质量标准（D1-D7）诊断问题
- 对每个问题给出具体位置、原因、改造建议
- 验证改造前后的质量变化

### Accidental（被引入但必要性存疑的）

| 设计元素 | 判断 | 理由 |
| --- | --- | --- |
| E1-E5 证据分级 | 过重 | 审计输出需要告诉用户"这里有问题"和"怎么改"，不需要标注每条规则来自课程第几讲 |
| 14 个锚点 ID（SO-*） | 过重 | 只有多个下游系统机械消费审计结果时才需要；首轮没有这些消费者 |
| Schema 四层合同 | 过重 | 审计报告不是 API 接口，不需要形状+语义+流转+消费四层合同 |
| 状态机（6 状态） | 过重 | 一次 Skill 审计是单次分析，不是需要状态流转的长事务 |
| JSON runtime artifact | 存疑 | 如果 Markdown 结构化输出能满足需求，JSON+schema+validator 的额外价值待证明 |
| 字段消费矩阵 | 过重 | 首轮消费者只有"人读报告"，不需要矩阵管理 |
| benchmark protocol | 过早 | 先有一个能用的审计工具，再考虑如何系统化对比 |
| 5/10/30 人工 eval | 合理但过重 | 可用性检验思路对，但不需要 protocol 级别的规范化 |
| 权限 profile（4 种模式） | 合理 | 审计类工具需只读 |
| 触发/加载/reference 审计 | 核心 | 这是 skill-auditor 的本职 |
| 迁移映射 | 合理 | new-skills → skill-auditor 需要迁移计划 |
