# 产品 Skill PRD 产出能力差距分析与修复设计

功能名: product-prd-gap-analysis | 产出时间: 2026-04-17

## 业务背景与根问题

朋友团队分享了一份正式在用的"客户管理 PRD"（765 行，9 章节，覆盖产品概述→用户故事→业务流程→功能清单→页面交互→接口数据→异常规则→验收标准→非功能需求）。以此为标尺，逆向评估我们的 product-director + product-manager skill 是否能产出团队可用的 PRD。

**根问题**：product-manager 的 prd.md 模板过薄（仅含 UNIT 索引表），导致 M-S1/M-S2/M-S3 的共创成果（详细流程、页面结构、权限关系、状态机等）无处沉淀。PRD 内容完整度不足以支撑研发、测试、运营直接消费。

## 目标与成功标准

| 目标 | 成功标准 | 度量类型 | 当前基线 | 目标值/方向 | 观测窗口 | 数据来源 |
|------|---------|---------|---------|------------|---------|---------|
| PRD 内容完整度 | 对照 6 维判定框架，11 项产品决策内容全部有模板承接 | 覆盖率 | 5/25 完全覆盖 | 16/25 完全覆盖（原 5 + 新增 11） | 实施完成后即时验证 | prd-template 章节对照 |
| 下游消费摩擦 | Design/Test-Design/Analyze 的输入提取清单包含新 PRD 章节 | 完整性 | 3 个 skill 未引用新章节 | 3 个 skill 全部更新 | 实施完成后即时验证 | SKILL.md 输入清单 |
| 共创成果落地 | M-S1/M-S2/M-S3 的成果有对应 prd.md 章节写入 | 映射完整性 | 3 个步骤无落地章节 | 3 个步骤全部有落地章节 | 实施完成后即时验证 | prd-template 对照 |

## 评估方法论

### 6 维判定框架

用于判定每个候选内容维度是否应吸收到 PRD 阶段：

| 维度 | 判定问题 | 优方向 |
|------|---------|--------|
| 消费摩擦 | 下游角色拿到 PRD 后需要额外口头确认吗？ | 摩擦越低越好 |
| 歧义度 | 两个合理的研发看完，会做出不同的东西吗？ | 歧义越低越好 |
| 可追溯性 | 上线发现 bug，能追回到 PRD 的某个具体条目确认"是需求没写还是开发写错"吗？ | 可追溯越强越好 |
| 维护成本 | 需求变更时，需要改几个地方？同一信息是否重复出现？ | 改的地方越少越好 |
| YAGNI | 这项内容至少有一个下游消费者需要它吗？没人用就是负担 | 必须有真实消费者 |
| 下游质量杠杆 | 这项信息的详细程度，能否直接提升 Design/开发/测试 的产出质量？ | 杠杆越大越值得吸收 |

### 核心原则

**产品决策类信息拉入 PRD，技术设计类信息留在 Design。**

### 修复 2：更新 brief-template.md 业务对象表

