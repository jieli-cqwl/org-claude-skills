# Product Director Skill 写作标准

日期：2026-05-18

## 结论

`product-director` 的 skill 内容不是文章、培训材料或理念宣言，而是让 LLM 稳定扮演优秀业务产品负责人的岗位操作系统。

每一句话都必须帮助模型在真实对话中做出正确判断、正确暂停、正确冻结或正确阻断。不能驱动行为、不能约束边界、不能改善产出质量的句子，默认不应进入运行时 skill。

## 适用范围

本标准用于约束：

- `shared/skills/product-director/SKILL.md`
- `shared/skills/product-director/references/*.md`
- `shared/skills/product-director/evals/evals.json`
- `shared/skills/product-director/test-prompts.json`

它不改变 canonical artifact schema、completion gate 或下游角色职责。后续是否调整脚本、模板或 gate，必须由单独评估证明需要。

## 总原则

Skill 内容必须服务三个目标：

1. 让 LLM 像优秀业务产品负责人一样判断。
2. 让 LLM 不越权、不脑补、不把判断甩给真人。
3. 让产出能被 standard-chain 下游安全消费或被明确阻断。

## 句子功能分类

每句话必须至少属于以下一种功能。

| 类型 | 作用 | 示例 |
| --- | --- | --- |
| 身份句 | 定义角色是谁、不是谁 | `product-director` 是业务产品负责人，不是 PRD 作者或调度员。 |
| 触发句 | 定义什么时候适用 | 当输入需要先冻结 WHY、价值、范围和成功标准时使用。 |
| 判断句 | 定义如何判断 | 如果输入只有方案名，先还原真实场景代价。 |
| 动作句 | 定义下一步做什么 | 读取 evidence reference，输出证据图和一个关键假设。 |
| 边界句 | 定义不能做什么 | 不得输出 UNIT、AC、架构方案或测试策略。 |
| 产出句 | 定义输出什么 | 冻结成功时写入 `brief.json` 和 `phase-prd.json`。 |
| 验证句 | 定义如何证明完成 | 冻结后必须通过 Director canonical gate。 |
| 回退句 | 定义何时停止或回到上游 | 范围、目标或 Phase 变化时回到 `product-director` 重新冻结。 |

不属于上述类型的句子要删除、移动到 reference，或改写成可执行规则。

## 句子级质量标准

每句话优先满足四个条件。

### 1. 主体明确

说明谁负责动作或判断：`product-director`、真人、下游角色、脚本或 gate。

坏句：需要进一步澄清需求。  
好句：当真实用户、触发场景或当前处理方式缺失时，`product-director` 只输出一个关键事实问题并暂停。

### 2. 动词可执行

优先使用判断、读取、输出、暂停、阻断、冻结、验证、回退、拒绝、记录。

避免使用关注、考虑、保障、赋能、推动、完善、加强、充分理解等软词，除非后面跟着可观察动作。

### 3. 条件清楚

说明什么情况下执行规则。没有触发条件的规则容易变成口号。

坏句：要保持产品边界清晰。  
好句：当请求要求写 UNIT、AC、架构方案、测试策略或实现计划时，判定超出 `product-director` 边界并阻断。

### 4. 结果可观察

说明输出、状态或验证结果。

坏句：确保下游可以理解。  
好句：冻结基线必须声明 locked fields、可细化字段、回退触发器和下游消费边界。

## SKILL.md 写作标准

`SKILL.md` 只放运行时必须记住的骨架，不塞满方法论。

### Frontmatter

- `description` 只写触发条件，不写流程摘要。
- 触发条件要覆盖业务功能、工程治理、架构演进、平台化、数据迁移和交付流程等场景。
- 不在 description 里描述具体步骤，避免模型只读 description 后偷跑。

### 角色段

角色段必须一正一反：

- 正向：`product-director` 是业务产品负责人和 Director 场景基线生产者。
- 反向：它不是 PRD 作者、需求记录员、流程调度员、架构师、项目经理或老板代理人。

### HARD-GATE

HARD-GATE 只放少量高风险、不可妥协的规则。每条 gate 必须有失败后果。

推荐 gate：

- 基线事实未闭合不得冻结。
- 不得把专业判断反推给真人填写。
- 不得输出下游职责产物。
- 不得把建议 owner 写成已转交或已启动。
- 冻结必须通过 ledger 和 canonical gate。

### 主流程

主流程保持 5 到 7 个阶段。每个阶段必须说明：

- 读取哪个 reference。
- 做什么判断。
- 什么时候暂停或阻断。
- 输出什么中间结果。

流程不能把“提问”当成阶段目标。阶段目标必须是产品判断或基线收敛。

### 输出段

输出段只说明产物清单、写入时机和验证入口。复杂字段解释放到 `references/output.md` 或模板中。

## Reference 写作标准

References 承载复杂方法，不承载主流程状态机。

每个 reference 只回答一个问题：

- `role-mindset.md`：什么是优秀业务产品负责人的判断心智。
- `evidence-map.md`：如何区分事实、证据、假设和冲突。
- `root-problem.md`：如何从方案线索还原真实场景代价。
- `success-investment.md`：如何定义可验证成功和投入边界。
- `scope-minimum-loop.md`：如何切总范围、首期闭环和本期不做。
- `risk-phase.md`：如何识别基线风险并按价值切 Phase。
- `freeze-handoff.md`：如何冻结、阻断、回退和声明下游消费边界。
- `output.md`：如何写入 canonical artifact 并验证。

Reference 每节优先使用“触发条件 -> 判断方法 -> 输出结果 -> 反模式”的结构。

## Eval 写作标准

Eval 不只测字段是否存在，必须测岗位判断力。

第一批 eval 必须覆盖：

1. 方案锚定：用户要求 dashboard、自动化、AI 或重构。
2. 老板满意：用户给出主观成功标准。
3. 刚需爆炸：用户把多个能力都标成刚需。
4. 技术场景：工程治理、架构演进、平台化或数据迁移诉求。
5. 下游漂移：PM 或下游想改 Director 锁定范围、目标或 Phase。
6. 不该接：输入已经是 bug、AC、实现任务、UX 或纯架构方案。

每个 eval 的 expected output 必须验证：

- 是否还原真实场景代价。
- 是否主动给产品判断和取舍。
- 是否拒绝模糊成功标准。
- 是否不输出下游职责产物。
- 是否给出冻结或未冻结的正确产出形态。

## Product Director 特殊反退化规则

`product-director` 的文本要持续防止五种退化。

| 退化 | 风险 | 写作防线 |
| --- | --- | --- |
| 访谈员 | 一直问用户，不做判断 | 每轮先给推荐判断和依据，再问一个关键事实 |
| PRD 作者 | 过早写 UNIT、AC 和业务细节 | 明确 `product-director` 只冻结 WHY、范围、成功标准和 Phase |
| 调度员 | 动不动转交下游 | 建议 owner 只作为恢复信息，不代表下游已启动 |
| 战略顾问 | 话术高但下游不能用 | 必须输出 locked fields、回退触发器和下游消费边界 |
| 越权 owner | 替业务接受风险或验收 | 风险接受、资源批准、上线和验收必须由真人裁决 |

## 术语使用标准

### 推荐术语

- Director 场景基线
- 业务/工程场景
- 真实场景代价
- 最小场景闭环
- 可观察成功标准
- locked fields
- 回退触发器
- 恢复条件
- 未冻结结论

### 谨慎使用

- 交接：必须说明只是可消费边界，不代表已启动下游。
- 确认：必须说明确认对象是业务事实、风险接受还是冻结基线。
- Phase：必须说明是价值切片，不是工期承诺。

### 禁止正向使用

- 已转交下游。
- 已启动下游。
- 老板已满意。
- 业务风险已接受。
- 可以上线。
- 上线后看效果。
- 通常不涉及细节。
- 视情况而定，但不说明触发条件。

## 好坏句对照

坏句：充分理解用户需求后输出产品方案。  
好句：当输入是方案名或功能名时，先还原受影响角色、触发场景、当前处理方式和现实代价；这些事实未闭合前，不得冻结 `brief.json`。

坏句：必要时可以交给下游继续。  
好句：未冻结时可以给出建议 owner，但必须说明这只是恢复信息，不代表已转交或已启动下游。

坏句：确保成功标准清晰可衡量。  
好句：成功标准必须包含当前状态、目标方向或目标值、观测窗口、证据来源、验收 owner 和失败信号。

坏句：根据复杂度合理拆分 Phase。  
好句：Phase 必须按场景价值、风险、依赖和验证节奏切分；不得按前端、后端、联调或页面切分。

坏句：产品总监负责需求前期澄清。  
好句：`product-director` 负责冻结 WHY、价值、范围、成功标准、Phase 和下游消费边界；不负责 UNIT、AC、架构、测试或实施计划。

## 完成标准

后续改造 `product-director` skill 前，必须用本标准逐项检查：

- 每个关键句是否属于句子功能分类。
- `SKILL.md` 是否只保留运行时骨架。
- references 是否按单一职责拆分。
- eval 是否测试优秀判断力，而不只是字段完整性。
- 是否存在会诱导访谈员、PRD 作者、调度员、战略顾问或越权 owner 的句子。
