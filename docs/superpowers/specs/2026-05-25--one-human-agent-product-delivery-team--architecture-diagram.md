## 图的定位

这套图用于让产品、研发、测试和交付角色快速建立同一个心智模型：

- 用户拥有最终方向、范围、投入、风险接受、签收和提交授权。
- 核心定义链逐层冻结：产品方向 → 产品需求 → 架构设计 → 测试设计 → 执行计划 → 交付运行。
- 执行智能代理池只由交付负责人调度，负责开发、验证、审查、验收、修复和一致性审计。
- 工程保障脊柱贯穿全链路，保证交接可验证、失败可定位、阻塞可恢复。
- 支撑输入只能作为证据、建议或待办进入主链，不能直接修改基线。

## 读图顺序

1. 先看整体架构图：确认决策边界、定义链、执行池、保障底座和支撑输入是否成立。
2. 再看产物流与冻结门禁：确认每一阶段冻结什么、交给谁消费。
3. 最后看现状差距摘要：讨论哪些目标架构能力尚未工程化。

## 整体架构图设计

主图只回答一个问题：**这个 1 人 + 智能代理团队如何组织、交接、执行、回派和签收？**

主图包含五个结构边界：

| 边界 | 图上位置 | 职责 |
|---|---|---|
| 用户决策塔 | 顶部 | 决定方向、范围、投入、风险接受、最终签收和提交授权 |
| 核心定义链 | 中部主链 | 从产品方向到交付运行逐层冻结定义 |
| 执行智能代理池 | 主链下方 | 按交付负责人派发包执行、验证、审查、验收、修复和审计 |
| 工程保障脊柱 | 底部 | 提供契约、模板、门禁、追踪、证据、恢复状态和风险台账 |
| 支撑输入 | 左侧 | 提供调研、历史知识、能力沉淀、质量评估、反馈和运营输入 |

主图使用四类箭头：

| 箭头 | 含义 |
|---|---|
| 金色实线 | 冻结交接：上游确认后，下游只消费当前版本 |
| 绿色实线 | 调度与证据：交付运行派发执行池，执行结果回流 |
| 红色虚线 | 失败回派：缺口回到拥有该定义的角色或用户 |
| 灰色虚线 | 支撑输入：只能作为证据、建议或待办进入主链 |

## 产物流与冻结门禁

| 阶段 | 冻结内容 | 主要产物 |
|---|---|---|
| 产品方向冻结 | 问题、目标、阶段边界和业务风险 | `brief.json`、`phase-prd.json` |
| 产品需求冻结 | 需求单元、规则、验收标准和排除项 | `UNIT-*.json` |
| 架构方案冻结 | 模块边界、接口、数据归属、风险应对和回滚约束 | `design.json` |
| 测试证据冻结 | 验收证据、测试层级、负向路径和回归义务 | `test-cases.json` |
| 执行计划冻结 | 任务包、依赖拓扑、并行策略和证明命令 | `plan.json`、`tasks.json` |
| 交付事实汇总 | 运行状态、验证结果、风险和待用户签收事实 | `delivery-state.json`、`signoff-package.json` |

门禁规则：

- 冻结规则：下游只消费当前有效引用；过期或归档引用不作为当前事实。
- 冲突规则：冲突回到对应定义负责人；不能由下游自行改口径。
- 回派规则：需求、设计、测试、计划、实现缺口各回对应负责人。
- 签收规则：交付包只表示准备就绪；最终签收、风险接受和提交授权只来自用户。

## 现状差距摘要

| 维度 | 目标要求 | 现状证据 | 差距判定 | 建议下一步 |
|---|---|---|---|---|
| 层级模型 | 主链、执行池、保障脊柱、支撑输入分层清楚 | `standard-chain.yaml` 主要只有 `main / sidecar` | 机器真源缺少 L0-L4 语义 | 为流程契约增加层级、权限和支撑接口元数据 |
| 产品边界 | 产品总监拥有方向和阶段基线；产品经理只产出需求单元和变更建议 | 当前产品经理仍可 refine 上游 `brief.json` 与 `phase-prd.json` | 可执行契约和目标边界不一致 | 把 refine 改成变更请求或派生视图 |
| 执行池定位 | 开发、验证、审查、验收、修复、审计只由交付负责人调度 | 交付负责人 skill 已这样定义，但标准链仍把部分执行角色放在主链 | 行为描述和机器模型漂移 | 把执行角色统一标成执行池或受控 sidecar |
| 运行门禁 | 交付运行应有可验证、可暂停、可恢复的阶段门禁 | skill 文本有分阶段规则，schema 和 chain 还没有完整承载 | 规则可读但不可充分机器验证 | 把交付阶段门禁落入状态契约和校验脚本 |
| 证据来源 | 事实、假设、建议必须分层进入主链 | 现状多为证据引用，缺少统一 provenance 字段 | 证据可信度和 canonical impact 不够硬 | 新增证据来源契约并接入各阶段门禁 |
| 签收边界 | 交付包表示准备就绪，不等于用户签收 | 已有签收状态字段，但 readiness 和 acceptance 语义仍需收紧 | 字段雏形存在，语义边界未完全工程化 | 增强签收包 schema 与完成门禁 |
