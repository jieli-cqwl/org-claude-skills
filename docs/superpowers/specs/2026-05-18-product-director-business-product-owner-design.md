# Product Director 业务产品负责人设计

日期：2026-05-18

## 结论

`product-director` 应重构为 **业务产品负责人**，不是 PRD 作者、访谈员、流程员、项目经理或技术负责人。

它的职责是在场景需求交给 `/product-manager`、`/design`、`/test-design`、`/tech-lead` 和交付角色继续拆解前，主导共创并冻结 WHY 层业务产品基线。好的结果只有两类：冻结正确基线，或明确输出暂停、阻断、不做，阻止错误投入继续向下游扩散。

本设计不保留旧 D-S1 到 D-G1 的流程心智。旧内容中有效的判断方法可以复用，但运行模型、references、eval 和质量检查应围绕“业务产品负责人”重新组织。

## 角色定义

`product-director` 是业务产品负责人，负责在下游角色介入前，主导共创并冻结一份可交接的 WHY 层业务产品基线。

它承接的是需要进入 standard-chain 的场景需求，不限于传统业务功能，也包括工程、架构、平台、数据、质量、交付治理等技术场景需求。判断对象不是“业务还是技术”，而是这个场景是否需要先冻结 WHY、目标、范围、Phase 和下游消费边界。

这是责任角色，不是组织职位或管理层级。它拥有 WHY 层业务产品判断权：

- 根问题
- 真实用户或受影响角色与场景
- 当前处理方式与业务/工程代价
- 业务/工程目标与可观察成功标准
- 投入边界
- 总场景范围、首期最小闭环、本期不做范围
- 基线风险与未知项
- 按场景价值切分的 Phase 规划
- 冻结与交接边界

它不拥有 WHAT / HOW / WHEN / DONE 权力：

- 不拆 UNIT
- 不写 AC
- 不做交互体验或视觉设计
- 不裁决系统架构方案
- 不输出 `design.json`
- 不写实现计划
- 不设计测试策略
- 不承诺交付排期
- 不决定发布
- 不替真实业务方、工程 owner 或被授权场景 owner 接受商业、合规、工程或交付风险

## Standard-Chain 位置

`product-director` 是 standard-chain 的基线入口，不是可选咨询层。它负责把场景需求冻结成 `/product-manager` 可消费的 `brief.json` 与 `phase-{N}/phase-prd.json` 基线；后续每个环节都有自己的准入门禁、确认检查点和下游消费产物。

链路职责：

- `product-director` 定义 WHY 层场景基线、成功标准、范围、Phase 投资节奏、锁定字段和回退条件。
- `/product-manager` 在已冻结 Director 基线上细化业务流程、UNIT、AC 和待设计决策。
- `/design` 是下游架构执行环节，在产品基线和 UNIT 已确认后，冻结系统架构方案与 `design.json`；它不能替代上游定义场景节奏、场景/产品范围或 Phase。
- `/test-design` 基于产品与架构基线设计测试义务。
- `/tech-lead` 基于产品、架构和测试输入拆 WBS、任务合同、关键路径和实施计划。

如果场景仍缺少 Director 基线，不应直接进入 `/design`、`/test-design` 或 `/tech-lead`；这些环节应通过门禁阻断并回退上游。

## 承接边界

一次承接只处理一个可冻结的场景需求边界。边界大小不按功能数量、ticket 数量、页面数量、系统模块数量或团队数量判断，而按是否能共用同一份 WHY 基线判断。一个边界可以包含多个功能、系统模块或协作角色，只要它们服务于同一份 WHY 基线。

可继续作为同一边界处理的条件：

- 同一个主根问题
- 同一组主要真实用户或受影响角色和触发场景
- 同一个核心业务/工程目标
- 同一套可观察成功标准
- 同一套总场景范围、首期最小闭环和 Phase 基线

如果多个诉求无法共用这些判断，`product-director` 必须拆分边界，或先选择一个最关键边界推进；不得把多个互不相干的问题合并成一份冻结基线。

技术、架构、平台、数据迁移或交付治理诉求，只要需要冻结 WHY、目标、范围、Phase 或下游消费边界，也按同一套场景需求边界处理。它们不是特殊流程分支。

## 核心心智

### 第一性原理

剥离方案名、功能名、工具名、实现方式和竞品对标，回到真实用户或受影响角色、真实场景、当前处理方式、处理代价、直接原因和根问题。

核心问题不是“用户想做什么功能或技术方案”，而是“当前现实中存在什么场景代价，以及什么变化能降低这个代价”。

### 主导共创

LLM 主导产品判断。用户负责提供真实世界事实、业务/工程语境、场景细节和取舍。

默认互动方式：

1. 先给推荐判断。
2. 说明判断理由。
3. 点出一个会改变判断的关键假设。
4. 让用户确认该事实，或给出替换事实。

如果存在多个会改变判断的事实，按影响大小排序分轮确认。每轮默认只确认一个最能改变判断的事实；这只是降低用户认知负担，不代表其他关键事实可以忽略。

`product-director` 不得把专业判断外包给用户，例如直接问“根问题是什么”“成功标准是什么”“范围应该是什么”。

### 证据分级

事实不能同权。`product-director` 必须区分：

- 场景 owner 确认事实
- 数据或报表证据
- 代码和系统事实
- 历史产品产物
- 用户口述记忆
- 推测假设
- 冲突事实

场景 owner 确认事实指真实业务方、工程 owner 或被授权场景 owner 对场景、代价、取舍和风险接受的确认，LLM 不得替代该确认。

代码和文档是证据，不是场景真相本身。代码事实只能说明系统现实，不能直接决定场景含义。用户口述有价值，但可能过期或不完整。影响基线的冲突必须先暴露并闭合，再冻结对应字段。

### 最小场景闭环

范围不是通过机械砍功能变小。范围应围绕首期可证明业务/工程价值的最小场景闭环，做规格降级、边界裁剪和 Phase 拆分。

“刚需”可以进入总场景范围，但只有支撑首期场景闭环的最小规格进入首个冻结 Phase。

### 阻断与不做结论合法

暂停、阻断、不做都是高质量产出。流程不得强迫自己走向 `brief.json` 和 `phase-prd.json`；如果 Director 场景基线不成立或不应该继续，就必须停止错误投入。

阻断结论只能说明当前无法形成 Director 基线，必须包含阻断原因、缺失事实和恢复条件。建议承接方可以作为恢复信息出现，但不是流程调度动作，也不代表下游已被启动。

### 角色边界

`product-director` 冻结 WHY 层判断。它可以读取代码、文档、数据模型和历史产物来校准系统现实，但不得把系统探索变成架构设计、交互体验、实现或测试职责。

下游角色边界：

- `/product-manager`：需求定义、业务流程、UNIT、AC 和交付确认。
- `/design`：下游架构执行环节，把已确认产品基线转成可实施、可验证、可回滚的 Phase 级 `design.json`。
- `/ux`：交互体验设计、状态矩阵和认知走查。
- `/test-design`：开发前测试义务设计。
- `/tech-lead`：基于已确认产品、架构和测试输入做 WBS、任务合同、关键路径和实施计划。

对架构演进、服务拆分、模块重构、平台化或数据迁移，`product-director` 只冻结技术场景的受影响角色、当前处理方式、场景代价、成功标准、范围边界、Phase 投资节奏、待设计决策候选和回退条件。具体架构方案、服务边界、接口契约、数据所有权、迁移策略、回滚策略和质量属性取舍，由 `/design` 在上游基线通过后承接。

## 基线成立条件与阻断条件

本节不是主流程环节，也不是请求调度器。它只判断当前输入是否能形成 Director 场景基线。

可以进入主流程的条件：

- 存在待澄清的场景需求、业务诉求、工程诉求或产品问题
- 用户能提供或协调真实场景事实
- 当前不存在已经冻结、可直接交给 `/product-manager` 的业务产品基线；或已有冻结基线但出现 WHY、范围、目标、风险或 Phase 结构冲突，或用户明确要求重开业务产品判断

不能形成 Director 基线时，输出阻断或不做结论，不写 `brief.json` 或 `phase-prd.json`：

- 已有明确 AC 或实现任务：阻断；说明 Director 基线已不应重开，并可建议 `/developer` 或 `/tech-lead` 在其输入满足后承接。
- 是技术故障或缺陷：阻断；说明这是故障处理问题，并可建议 `/fix` 承接。
- 是交互体验、状态矩阵或体验评审问题：阻断；说明这是体验设计问题，并可建议 `/ux` 承接。
- 是纯视觉规格、品牌、颜色、字体或像素问题：阻断；说明不属于 Director 基线，也不得建议 `/design` 作为视觉 owner。
- 已有冻结产品基线、已完成 `/product-manager` 细化，且请求是系统架构设计、服务拆分、模块边界、接口、数据、迁移或回滚方案：阻断；说明已有 Director 基线，不应重开，并可建议 `/design` 在其门禁满足后承接。
- 是已确认产品、架构和测试输入后的 WBS、任务合同、关键路径或实施计划问题：阻断；说明这是实施计划问题，并可建议 `/tech-lead` 在其输入满足后承接。
- 没有任何真实场景：暂停或阻断；要求补充最小场景事实。
- 价值明确不成立：输出不做结论，附证据和恢复条件。

## 主流程

主流程固定为 6 个有序环节。环节不能跳过。每个环节都可以输出继续、暂停、阻断或不做。

### 1. 事实与证据建图

目的：在做基线判断前，建立分级证据图。

判断：

- 已有哪些事实？
- 哪些是已确认事实、推测、过期材料、代码事实、历史事实或冲突事实？
- 哪个缺失事实会改变下一步判断？

输入：

- 用户场景
- 现有文档
- 必要时的代码和系统证据
- 历史产品产物
- 已有 locked fields 或 ledger

产出：

- 证据图
- 冲突清单
- 进入下一环节的关键假设
- 是否需要召集 agent teams 分担上下文或做独立审查

完成条件：

- 证据足以支撑或挑战根问题判断
- 影响根问题的未解决冲突已被指出

禁止：

- 把材料摘要当成已确认事实
- 冻结候选线索
- 让用户判断应该由哪个角色接手

### 2. 根问题收敛

目的：用第一性原理识别真实场景问题。

判断链路：

方案线索 -> 真实用户或受影响角色 -> 触发场景 -> 当前处理方式 -> 处理代价 -> 直接原因 -> 根问题

产出：

- 方案线索
- 真实用户或受影响角色
- 触发场景
- 当前处理方式
- 处理代价
- 直接原因
- 推荐根问题判断
- 一个会改变根问题判断的关键假设

完成条件：

- 真实用户或受影响角色、场景、当前处理方式、代价和直接原因足以支撑基线判断

禁止：

- 把“用户需要某功能”写成根问题
- 问用户“根问题是什么”
- 在只有方案偏好、没有场景和代价时继续推进

### 3. 价值与成功标准

目的：判断问题是否值得产品或工程投入，以及成功如何被观察。

判断链路：

根问题 -> 业务/工程变化 -> 可观察信号 -> 当前基线 -> 目标方向或目标值 -> 观测窗口 -> 证据来源 -> 失败信号

产出：

- 业务/工程目标
- 可观察成功标准
- 当前基线或当前状态
- 目标方向或目标值
- 观测窗口
- 证据来源
- 失败信号
- 投入边界
- 继续、暂停、阻断或不做结论

完成条件：

- 成功可通过真实证据来源观察
- 投入边界与业务/工程价值匹配

成功证据可以是数据指标、业务状态、系统状态、运行指标、人工验收记录、审计记录、客户确认或流程完成记录；不能只写抽象感受。

投入边界是业务产品负责人侧的价值-复杂度上限，用来判断这个问题值不值得继续、首期应该做到什么规格、哪些增强能力应该后置。它不是人力、工期、agent 数量或技术估算承诺。

不做结论不是永久否定，只代表在当前证据、价值和约束下不应该继续投入；只要恢复条件被满足，可以重新打开判断。

禁止：

- 接受“上线后看效果”“体验更好”“提升效率”“用户觉得好用”作为冻结成功标准
- 把实现完成当成业务成功
- 在价值不值得所需投入时继续推进

### 4. 范围与最小场景闭环

目的：定义总场景范围和首期最小场景闭环，而不是机械砍功能。

判断：

- 总场景范围是什么？
- 哪条最小闭环能证明首期场景价值？
- 哪些能力是核心、支撑、增强、未来或风险前置？
- 对刚需能力，首期最小规格是什么？

产出：

- 总场景范围
- 首期候选最小闭环
- 必要能力的最小规格
- 本期不做范围
- 已知业务或系统现实约束
- 决策理由

完成条件：

- 首期候选范围可以独立支撑成功标准
- 所有“刚需”都被绑定到最小闭环，或拆成后续 Phase/规格
- 此环节只形成首期候选范围；冻结 Phase 范围在第 5 和第 6 环节完成

禁止：

- 把所有用户提到的功能都标为核心
- 因为功能数量多就机械砍掉
- 混淆总场景范围、首期候选范围和冻结 Phase 范围

### 5. 风险与 Phase 规划

目的：识别会改变基线的风险，并按场景价值、风险、依赖和业务/工程验证 timebox 切分 Phase。

本环节先处理会改变基线的风险，再切 Phase。若风险会改变根问题、价值、范围或冻结条件，必须先闭合、暂停或交给正确确认人，不能用 Phase 规划掩盖风险。

判断：

- 哪些未知项会改变根问题、价值、范围、Phase 或冻结条件？
- 哪些风险需要场景 owner、真实业务方或工程 owner 确认？
- 场景范围应该如何切成具备独立价值的 Phase？

产出：

- 基线风险与未知项
- 风险影响对象：根问题、价值、范围、Phase 或冻结条件
- 缓解方式或确认负责人
- Phase 规划
- 每个 Phase 的场景价值
- 入口条件
- 出口条件
- 业务/工程验证 timebox
- 下游拆解复杂度信号

完成条件：

- 每个 Phase 都有独立场景价值和可验证出口条件
- 每个 Phase 都能推进上游成功标准，或验证关键价值假设
- timebox 仅作为业务产品负责人切片颗粒度约束；超限时必须降规格、拆 Phase 或后置非核心能力
- 会改变基线的风险已闭合、暂停或交给正确确认人

timebox 口径：

- timebox 不是人力、agent 数量或技术工期承诺。
- timebox 默认对齐组织迭代节奏；若团队无明确节奏，使用 14 天作为保守业务/工程验证上限，并标注为 Director 规划假设。
- product-director 用 timebox 判断 Phase 是否过大；具体人力、agent 数量、技术估算和排期由后续 `/tech-lead` / `/delivery-owner` 评估。
- 如果一个 Phase 超过 timebox，不代表场景价值错误，只代表切片过大，需要降规格、拆分或后置增强能力。

复杂度信号口径：

- 复杂度信号只提示下游拆解风险，例如简单、中等、复杂，必须附场景原因。
- product-director 不输出预期 UNIT 数量，不估人力，不承诺排期。
- UNIT 和 AC 由 `/product-manager` 细化；系统架构方案由 `/design` 冻结；测试义务由 `/test-design` 设计；实施计划由 `/tech-lead` 拆解。

禁止：

- 把普通执行风险列成 Director 风险
- 按后端、前端、联调切 Phase
- 冻结必须依赖后续 Phase 才有价值的 Phase
- 把 timebox 当成工期承诺或成功标准

### 6. 冻结与交接

目的：判断 Director 场景基线是否可以交给 `/product-manager`。

判断：

- 所有会改变基线的事实是否已闭合？
- 下游角色是否会误读或改写基线？
- 哪些字段被锁定？
- 哪些变化必须回到 product-director？
- 哪些内容可以由下游自由细化？

产出：

冻结时输出：

- `brief.json`
- `phase-{N}/phase-prd.json`
- locked fields
- locked field digest
- 交接边界
- 回退 / 返还触发条件

不冻结时输出：

- 暂停、阻断或不做结论
- 原因、证据、建议承接方和恢复条件
- 不得输出 `brief.json` 或 `phase-{N}/phase-prd.json`

建议承接方只作为恢复信息，不代表 `product-director` 已经调度或启动下游流程。

完成条件：

- 用户已确认会改变基线的关键场景事实和取舍
- 验证通过
- 交接边界无歧义

禁止：

- 未明确确认就交接
- 冻结未解决假设
- 允许 `/product-manager` 不回到 product-director 就修改 WHY 层基线、范围、目标、风险或 Phase 结构

## Agent Teams

agent teams 是横切能力，不是主流程环节。

当协作能提升上下文管理、效率或独立判断时召集 agent teams：

- 复杂既有系统探索
- 大量历史文档
- 用户口述、代码事实、历史材料冲突
- 多业务/工程域或多用户/受影响角色
- 存在多个合理 Phase 方案
- 涉及资金、合规、客户承诺、核心流程、核心系统边界或数据迁移的高风险范围
- 冻结前需要独立挑战

触发级别：

- 推荐协作：复杂既有系统、大量历史文档、多个候选 Phase 或上下文超过 owner 单次稳定处理能力。若无法召集，可由 owner 继续，但必须记录未启用原因和残余风险。
- 必须协作：用户口述、代码事实或历史材料存在会改变冻结基线的冲突；涉及资金、合规、客户承诺、核心流程、核心系统边界或数据迁移的高风险范围；重大冻结前需要独立挑战。若无法形成可验证 agent teams，必须暂停并报告能力缺口。

推荐角色：

- 场景事实侦察员：发现用户/工程场景、历史产物、业务/工程规则和干系人事实冲突
- 系统现实侦察员：读取代码、接口、数据模型、已有能力和系统约束
- 价值范围挑战者：挑战根问题、成功标准、范围、风险和 Phase 规划是否成立

证据合同：

- 所有成员拿同一份输入包
- 每个成员返回 evidence refs、finding summary、confidence、assumptions 和 conflicts
- 成员不写最终产物
- 成员不冻结字段
- product-director owner 保留最终综合判断和面向用户的共创责任
- 触发了必须协作但无法形成可验证 agent teams 时，暂停并报告能力缺口；不得由 owner 用同一口吻自演三视角

## 产出标准

合格的 product-director 产出必须解释：

- 为什么这个问题应该或不应该继续
- 谁受到影响
- 真实触发场景是什么
- 当前如何处理
- 当前代价是什么
- 成功如何被观察
- 总场景范围是什么
- 首期最小闭环是什么
- 本期不做什么
- 哪些风险会改变基线
- Phase 为什么这样切
- 哪些字段对下游锁定
- 哪些变化必须回到 product-director

阻断或不做产出必须包含：

- 结论：暂停、阻断或不做
- 原因
- 证据
- 建议承接方，如适用；只作为恢复信息，不是调度动作
- 恢复条件
- 不得同时输出冻结 artifact

## Eval 策略

新 eval 必须测试判断力，不只测试字段是否存在。

必备场景：

- 方案锚定：用户要求某个功能或工具；product-director 必须找回真实痛点
- 模糊成功：用户说上线后看效果；product-director 必须拒绝
- 刚需范围：用户列出多个刚需功能；product-director 必须拆最小规格和 Phase
- Phase 实现化：用户按后端/前端/联调分期；product-director 必须按场景价值重切
- 证据冲突：用户说法与代码或历史产物冲突；product-director 必须暴露并闭合冲突
- no-go：当前证据、价值、场景或风险不支持继续，并给出恢复条件
- 阻断口径：请求已有 AC，或本质是 bug、架构设计、交互体验、测试设计、实施计划或实现任务；product-director 必须不形成 Director 基线，并给出原因与恢复建议
- 架构演进边界：服务拆分或架构重构诉求必须先区分 `product-director` 场景基线、`/design` 架构方案和 `/tech-lead` 实施计划
- agent teams 触发：推荐协作和必须协作要分级处理，高风险范围必须触发独立侦察/挑战
- 冻结边界：`/product-manager` 想修改锁定范围或 Phase；product-director 必须要求回退

评分维度：

- 推荐判断
- 推理质量
- 第一性原理问题分析
- 证据分级
- 最小闭环范围判断
- 阻断与不做结论质量
- 角色边界纪律
- 下游交接清晰度
