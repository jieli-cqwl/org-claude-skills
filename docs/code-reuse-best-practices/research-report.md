## 问题本质

代码复用的根问题，不是“怎样把看起来相似的代码并成一份”，而是“怎样避免同一份知识在系统里以多份实现长期漂移”。

证据分三层：

1. 《The Pragmatic Programmer》把 DRY 定义为“知识的单一、明确、权威表示”，并明确指出 DRY 不只是避免复制粘贴代码，而是避免同一意图分散在多个地方 [E1]。
2. Martin Fowler 指出，去重的正确方向不是盲目套模式，而是先识别“什么相同、什么不同”，把公共部分与变化点分离；如果某个模式并没有移除真正的重复，就不该使用它 [E2]。
3. 工业案例研究表明，克隆检测和消除无法完全自动化；哪些应该提炼、怎么命名、该不该保留局部重复，必须由熟悉领域的人参与决策 [E3]。

因此，代码复用最佳实践的核心不是“多复用”，而是：

- 把真正重复的知识收拢到一个可维护位置；
- 不把偶然相似、但未来会分化的逻辑硬塞进同一个抽象；
- 用工具辅助发现候选项，用工程判断决定是否复用。

## 解法谱系

### 流派 A：DRY / 单一知识源

- 设计哲学：系统中同一份业务知识应只有一个权威表达，避免多处修改导致漂移。
- 代表来源：Hunt/Thomas 的 DRY 定义 [E1]。
- 优势：
  - 能直接降低维护时的同步成本。
  - 能减少“改一处漏一处”的行为不一致。
  - 把复用目标从“减少行数”提升到“减少知识分叉”。
- 局限：
  - 如果误把“语法相似”当成“知识相同”，会引发错误合并。
  - 在跨边界接口、缓存、镜像数据等场景，部分重复是客观存在的，只能局部治理而非绝对消灭。

### 流派 B：演化式抽象

- 设计哲学：抽象必须由稳定重复和真实变化压力驱动，而不是由“看起来很像”或“以后可能会用到”驱动。
- 代表来源：Fowler 的“先识别共性与变化，再消除冗余”的方法 [E2]，以及仓库本地的 [`设计原则.md`](/Users/lijieli/org-claude-skills/shared/reference/设计原则.md#L27)。
- 优势：
  - 能避免过早抽象造成的错误边界。
  - 更符合长期演化：先保留具体实现，等模式稳定后再提炼。
  - 对 LLM 也更友好，因为原则比僵硬阈值更能指导判断。
- 局限：
  - 需要团队能容忍短期局部重复。
  - 需要有人持续观察“这是巧合重复，还是稳定模式”。

### 流派 C：克隆治理 / 领域专家在环

- 设计哲学：工具负责发现候选重复，工程师负责判断语义、命名、边界和时机。
- 代表来源：Thompson 等人在 Ericsson 合作案例中的结论 [E3]。
- 优势：
  - 更贴近真实项目，因为它承认“复用决策不可完全自动化”。
  - 能把复用和代码理解、测试提炼、结构化重构结合起来。
  - 适合大仓库和多人协作场景。
- 局限：
  - 成本高于“直接搜索后强制合并”。
  - 对领域知识、命名能力和重构能力有要求。

## 最佳实践

| 最佳实践 | 实证来源 | 我们的现状 | 差距 | 落地行动 |
|---------|---------|-----------|------|---------|
| 1. 把“复用”定义为“知识复用”，不是“文本去重” | [E1] | 调研起点时，旧版 `代码复用.md` 主要强调搜索/LSP，没有先定义“什么叫重复知识” | 目标表述偏工具化 | 在复用文档开头先定义：同一业务规则、同一约束、同一变更意图，才叫需要治理的重复 |
| 2. 判断复用前，先判断语义是否一致 | [E1][E2] | 调研起点时，旧版文档有 LSP 语义确认，但更偏“符号定位”，不是“业务语义判断” | 语义层判断不足 | 增加一条：名字相似、流程相似，不等于业务语义相同；先问它们是不是同一知识 |
| 3. 抽象必须由稳定共性驱动，不由想象驱动 | [E2][E5] | [`设计原则.md`](/Users/lijieli/org-claude-skills/shared/reference/设计原则.md#L12) 已写明 YAGNI 和“重复 3 次再抽象” | 原则存在，但没有和“代码复用”文档打通 | 把“重复 3 次再抽象”“当前只有一种实现不引接口”纳入代码复用判断框架 |
| 4. 接受战略性重复，尤其在测试和语义分叉场景 | [E1][E6] | [`测试规范.md`](/Users/lijieli/org-claude-skills/shared/reference/测试规范.md#L107) 已明确测试允许适度重复 | 主文档没有说明“什么时候重复是合理的” | 明确列出：测试叙事、语义尚未稳定、未来变化方向不同，这些场景可保留局部重复 |
| 5. 工具是证据助手，不是裁决者 | [E3][E4] | 调研起点时，旧版文档把 Grep/Glob/LSP 放在中心位置 | 容易让人误以为“搜到/没搜到”就是最终判断 | 把搜索、LSP、引用分析降级为“证据收集手段”，不再把它们写成最佳实践主体 |
| 6. 好的复用结果应让代码更易改、更易懂，而不是更抽象 | [E2][E3] | 调研起点时，旧版文档几乎没有定义“好的复用效果” | 缺成功标准 | 增加结果标准：改一处即可生效、命名更清晰、调用方认知更低、边界更稳定 |
| 7. 如果抽象后更难命名、更难解释，通常说明时机未到 | [E3] | 调研起点时，仓库文档没有显式写命名压力这个信号 | 识别信号不足 | 把“抽出来后名字只能叫 utils/common/helper”视为危险信号，优先回退到更具体的实现 |
| 8. 对 LLM 场景，保留轻量举证责任，但不要把阈值写死成教条 | [E3][E4] | 调研起点时，旧版文档用 `>=3`、`>=50%` 这类硬阈值 | 容易让规则代替思考 | 把这些数字改成启发式参考，真正必答问题改为：为什么不能复用？为什么这样抽象更好？ |

## 常见陷阱

| 陷阱 | 表现 | 规避方式 |
|------|------|---------|
| 把相似代码当成相同知识 | 两段代码长得像，就强行抽公共函数 | 先判断业务意图和未来变化是否一致 |
| 过早抽象 | 第一次或第二次看到重复就建公共层 | 允许短期重复，等模式稳定后再抽象 |
| 工具崇拜 | Grep/LSP 无结果，就断言“不存在可复用代码” | 工具只做召回和定位，最终还要做语义判断 |
| 为复用牺牲可读性 | 抽出后名字模糊、参数爆炸、调用更绕 | 以“更易理解和更易修改”为硬标准，不满足就回退 |
| 误把 DRY 等同于“绝不重复” | 所有局部重复都要消灭 | 区分知识重复、偶然重复和叙事性重复 |
| 万能工具层堆积 | `utils/common/helper` 变成杂物间 | 只抽稳定共性；抽不出清晰边界就别抽 |

## 对我们的启示

这次调研对本仓库的直接结论是：

1. 调研起点时的旧版 `代码复用.md` 不是“错误”，但它更像“复用证据采集与新建门禁”，不是完整最佳实践。
2. 仓库真正更成熟的复用观，已经隐含在 [`设计原则.md`](/Users/lijieli/org-claude-skills/shared/reference/设计原则.md#L5) 和 [`测试规范.md`](/Users/lijieli/org-claude-skills/shared/reference/测试规范.md#L107) 里：不过度抽象、允许适度重复、按需演化。
3. 因此更合理的做法不是继续增加 `grep/LSP/阈值`，而是把文档分层：
   - 一层讲原则：为什么复用、何时复用、何时不复用、什么叫好结果；
   - 一层讲验证：如果要新建实现，如何做搜索和证据留痕。
4. 当前仓库已经按上述方向完成首轮落地：原则文档、门禁文档和规则入口已分层对齐。

## 实践落地指南

### P0：调整文档定位

- 保留 [`代码复用.md`](/Users/lijieli/org-claude-skills/shared/reference/代码复用.md#L1) 作为“代码复用原则”文档。
- 新增一份“复用证据与新建门禁”文档，承接搜索、LSP、引用分析和新建举证流程。

### P1：统一仓库内的复用判断口径

- 统一原则：
  - 复用目标是减少知识分叉，不是减少表面重复。
  - 当前只有一个实现，不预设抽象。
  - 重复模式稳定后再抽象。
  - 测试和叙事性代码允许适度重复。

### P2：把工具要求从“硬主角”改成“辅助证据”

- 保留搜索、LSP、引用分析，因为它们对 LLM 和大仓库确实有价值。
- 但文档表述改成：
  - “应收集哪些证据”
  - “哪些场景建议搜索和引用分析”
  - “为什么这些证据有助于复用判断”
- 不把 `>=3 调用方`、`>=50% 改动` 写成普适真理，而改成启发式提示。

### P3：定义复用效果的验收标准

- 复用后是否让未来改动更集中？
- 复用后是否让命名和职责更清晰？
- 复用后是否减少了行为漂移风险？
- 复用后是否没有引入新的错误耦合或万能抽象？

只要这 4 个问题里有 2 个以上答不上来，就不应急于抽象。

## 最终判断

综合外部来源、工业案例和本仓库上下文，代码复用的最佳实践可以收敛成一句话：

**优先复用“稳定的共同知识”，延迟抽象“尚未稳定的相似实现”，并用工具收集证据，而不是让工具替你做裁决。**

这意味着一份成熟的“代码复用最佳实践”文档，应该优先回答：

1. 为什么要做：为了单一知识源、降低维护漂移和改动面。
2. 什么时候做：语义一致、变化一致、边界健康、抽象后更清晰时做。
3. 做到什么效果：更容易修改、更容易理解、更少行为分叉，而不是只是“看起来更 DRY”。
