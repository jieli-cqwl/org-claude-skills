# 测试规范最佳实践调研

调研模式：analysis
呈现模式：decision

## 结论

`测试规范.md` 应从“写测试原则”升级为“测试决策规范”：面向 AI Coding Agent 的代码变更过程、缺陷裁决与完成前验证，按测试依据、测试义务、何时追加专项验证、测试深度、缺陷分级和交付证据组织内容。

有效性判断使用 7 类代表性变更场景验收，见 `scenario-validation.md`。

## 关键判断

- 覆盖率应进入规范，但不能作为唯一质量标准。Google Testing Blog 的经验是覆盖率能发现未测代码，但高覆盖率不等于测试有效；90% 可作为增量或高质量目标，项目整体超过 90% 往往需要结合收益判断。
- 单元、集成、E2E 是不同证据层，不是互相替代。Martin Fowler 的 Test Pyramid 和 Google 对 E2E 的反思都强调：E2E 要少而关键，真实信心需要测试层级组合。
- 测试替身只能证明替身行为。它适合单元隔离和异常路径构造，但最终验收必须回到真实依赖、测试环境或已验证集成路径。
- 非功能测试不应全量强制，但应按触发条件进入规范：性能、安全、可靠性、兼容性、可访问性等被变更影响时，必须有目标、基线或外部标准。
- flaky 测试会破坏 CI 信任，不能靠反复重跑或忽略维持通过结论；测试自身的确定性、隔离性和失败可诊断性应作为规范维度。

## 调研维度

| 维度 | 为什么要纳入 | 规范化方式 |
|------|--------------|------------|
| 行为与验收覆盖 | 防止只测实现细节，不证明用户目标 | 每个新增或变更行为必须有先失败测试或可复验验收用例 |
| 关键设计单元覆盖 | 回应单元测试应直接覆盖关键函数的合理性 | 纯逻辑、业务计算、错误处理函数直接单测；内部 helper 可间接覆盖 |
| 覆盖率 | 需要客观发现遗漏，但避免数字崇拜 | 变更业务代码 90% 目标；全仓看趋势和基线；高风险看分支和错误路径 |
| 集成与契约 | 防止 Mock-only 完成 | 真实依赖、测试环境或已验证集成路径作为完成证据 |
| E2E/验收 | 证明真实用户路径可用 | 少量关键旅程，稳定且能从入口到结果闭环 |
| 非功能质量 | 变更可能影响性能、安全、可靠性等交付质量 | 触发时补目标/基线/扫描/基准/人工验收，不触发则说明不适用 |
| 测试代码质量 | 低质量测试会制造假信心 | AAA、独立数据、确定性、可读性、禁止无意义断言 |
| 完成门禁 | 让规范能真正影响交付判断 | 覆盖维度逐项判断，失败或未覆盖项进入风险/阻塞说明 |

## 反方挑战

- 反方：写 90% 会诱导 LLM 为覆盖率写无意义测试。
  - 处理：只把 90% 放在新增或变更业务代码目标上，并明确覆盖率不能替代行为断言、高风险分支和真实路径证明。
- 反方：测试维度过多会增加上下文负担。
  - 处理：正文按触发条件、达标口径和证据出口组织，每项只保留能指导执行和交付裁决的信息。
- 反方：不同项目无法共享同一个覆盖率标准。
  - 处理：增量目标统一，全仓基线按项目现状治理；无基线时先记录，再逐步提高。

## 证据来源

- [Google Testing Blog, Code Coverage Best Practices, 2020-08](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html)：覆盖率是发现未测代码的有效工具，但不能单独证明测试质量；覆盖率目标需要结合项目上下文。
- [Google Testing Blog, Just Say No to More End-to-End Tests, 2015-04](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)：E2E 测试提供真实路径信心，但维护成本和不稳定性高，应保持少量关键路径。
- [Martin Fowler, Test Pyramid](https://martinfowler.com/bliki/TestPyramid.html)：测试组合应以大量快速底层测试支撑，少量高层测试证明端到端信心。
- [Microsoft Learn, Unit testing best practices](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-best-practices)：单元测试应快速、可靠、隔离，并避免过度依赖实现细节。
- [ISTQB Glossary](https://istqb-glossary.page/)：测试层级可按 component、integration、system、acceptance 区分；测试类型包括功能与非功能测试。
- [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)：安全验证适合按要求项和风险等级定义验收，而不是只依赖通用测试覆盖率。

## 失效条件

- 项目已有更严格覆盖率、合规或发布门禁时，应以项目规则为准。
- 缺少覆盖率工具时，不应临时伪造指标；先用用例清单、影响范围和真实验证命令证明，再补工具建设。
- 高风险路径即使覆盖率达标，也不能省略真实依赖或集成路径验证。
