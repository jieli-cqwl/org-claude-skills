# Product Skill 取证清单与 Eval 样本设计

日期：2026-04-12

## 目标

这份文档只解决两个问题：
- 先把 `/product` 的待证实判断变成可取证对象，而不是继续凭感觉争论。
- 为 `/product` 设计 3 个最小但有效的 execution eval 样本，验证“内容质量、共创负担、Phase 切片”到底哪里是真问题。

## 已知结论

- 已证实：`/product` 当前是“需求共创 + 上游基线编排”skill，不只是 PRD 写作器。
- 已证实：现有 gate 偏结构/合同校验，偏弱语义结果证据。
- 待证实：内容漂移、错误、歧义是否已经是当前头号问题。
- 待证实：共创是否在真实运行中已经“太重”。
- 待证实：`S6 Phase 切片` 是否在真实 feature 上有效降低返工。

## 取证清单

### 1. 真实执行样本

最小样本量：
- 3 个场景
- 每个场景至少 3 次独立运行
- 保留完整 transcript、最终工件、review 结果

每次运行必须保留：
- 用户首句
- 每轮共创问答
- 最终 `brief.md`
- 最终 `phase-{N}/prd.md`
- 最终 `phase-{N}/units/UNIT-*.md`
- 三视角 reviewer 输出
- 运行轮次统计

### 2. 语义质量检查项

每个样本都检查以下问题是否真实出现：
- 根问题是否被解决，而不是沿着用户方案直接展开
- `目标/范围/规则/AC` 是否前后一致
- AC 是否存在模糊词、主观词、不可观察结果
- 异常/边界/排除项是否被遗漏
- `待设计决策` 是否既不过早给技术答案，也没有漏项

### 3. 共创负担检查项

每个样本都记录：
- 总轮次数
- 真正新增信息的轮次数
- 重复确认轮次数
- 因流程暂停产生但没有新增价值的轮次数
- 中途插问后是否能正确回到当前步骤

判定信号：
- 若高轮次但持续新增关键约束：偏“必要共创”
- 若高轮次但重复确认和格式回写占比高：偏“流程负担”

### 4. Phase 切片检查项

只针对存在多个闭环功能的样本检查：
- Phase 是否按“用户/业务可感知价值”切片
- 是否把执行顺序、并行策略、里程碑过早塞进 `/product`
- 是否出现“因为切错 Phase 导致下游路径和工作区连锁错误”
- 单 Phase / 多 Phase 的选择是否能自洽说明

### 5. 下游可验证性检查项

用下游视角反证 `/product` 是否足够好：
- `/design` 是否还要回头追问根问题或范围
- `/test-design` 是否能直接把 AC 转成用例
- reviewer 是否稳定抓到真实问题，而不是只审结构

### 6. 失败标签

建议统一用这组标签收集失败台账：
- `PROBLEM_DRIFT`：沿方案走，没回到真实问题
- `SCOPE_DRIFT`：范围/不交付边界前后漂移
- `AC_AMBIGUITY`：AC 模糊或不可观察
- `MISSING_EDGE_CASE`：异常/边界遗漏
- `FAKE_CO_CREATION`：共创摘要有记录，但用户信息不真实或无增量
- `OVER_QUESTIONING`：追问过多但新增信息低
- `OVER_PHASING`：Phase 切得过细或过早
- `UNDER_PHASING`：多个独立价值闭环被粗暴压成一个 Phase
- `PREMATURE_DESIGN`：在 `/product` 提前做了设计阶段决策

## Eval 样本设计

### Eval-1: 清晰需求轻量收口

- 场景 ID：`p1-clear-single-phase`
- 目标：
  - 验证 `/product` 能不能在需求边界清晰时保持轻量，而不是机械走重流程
  - 验证是否会过度追问、过度 Phase 化
- 用户首句：
  - “给内部周报系统加一个已发布周报列表页，登录后可分页查看已发布周报，先不做搜索和编辑。”
- 场景特征：
  - 问题清晰
  - 业务对象少
  - 预期单 Phase
- 重点观察：
  - 是否快速确认根问题和成功标准
  - 是否只切出 `phase-1`
  - 是否避免把简单需求拆成过多 UNIT
- 通过信号：
  - 1 到 2 轮关键共创后能稳定收口
  - 无多余 Phase
  - AC 可直接转测试
- 失败信号：
  - 大量重复确认
  - 出现无业务价值的多 Phase
  - UNIT 过细拆分
- 建议 grader：
  - `hard-gate`
  - `product-thinking`
  - 新增 `co-creation-cost`

### Eval-2: 方案先行型模糊需求

- 场景 ID：`p2-solution-anchoring`
- 目标：
  - 验证 `/product` 是否会被用户给出的方案锚定
  - 验证能否先回到问题，再定义需求
- 用户首句：
  - “我想做一个权限矩阵配置中心，最好像竞品那样有角色树和批量授权。”
- 场景特征：
  - 用户描述的是方案，不是问题
  - 隐含约束多
  - 最容易出现“顺着方案写 PRD”
- 重点观察：
  - 是否先追问真实痛点和失败场景
  - 是否识别不同问题框架
  - 是否把技术/设计问题留到 `待设计决策`
- 通过信号：
  - 能产出明确根问题
  - 不直接把“角色树/批量授权”写死成需求
  - reviewer 能在无问题时 PASS，在越界时抓到问题
- 失败信号：
  - 直接沿方案展开
  - AC 与真实业务目标脱节
  - 提前做架构裁决
- 建议 grader：
  - `hard-gate`
  - `product-thinking`
  - 新增 `problem-discovery`

### Eval-3: 多闭环功能的 Phase 切片

- 场景 ID：`p3-multi-phase-value-slicing`
- 目标：
  - 验证 `/product` 的 `S6 Phase 切片` 是否真按业务价值切，而不是按功能均分
  - 验证它是否只做“价值切片”，不越界到执行节奏 owner
- 用户首句：
  - “我们要做一个内部审批系统，本期至少要能提交申请、审批通过/驳回、查看审批记录；后面还想接企业微信通知和统计报表。”
- 场景特征：
  - 多个闭环功能
  - 明显存在“核心 + 增强”
  - 适合检验单 Phase / 多 Phase 决策
- 重点观察：
  - 是否把“申请 + 审批 + 记录”收成最小价值闭环
  - 是否把“企业微信通知 / 统计报表”推到后续 Phase
  - 是否只定义 Phase 价值边界，不提前写计划里程碑和并行策略
- 通过信号：
  - Phase 切片有业务价值解释
  - UNIT 依赖关系清晰
  - 下游可以直接消费工作区路径而不返工
- 失败信号：
  - 只按功能平均分组
  - 把执行节奏、任务批次、并行策略写进 `/product`
  - 切片导致跨 Phase 硬依赖混乱
- 建议 grader：
  - `hard-gate`
  - `product-thinking`
  - 新增 `phase-slicing-quality`

## 推荐落地顺序

1. 先把以上 3 个样本写成 `tools/eval/scenarios/` 场景文档。
2. 将 `product-thinking-grader` 接入 `run_skill_eval.sh`。
3. 只新增两个最小 grader：
   - `co-creation-cost-grader`
   - `phase-slicing-quality-grader`
4. 每个场景至少跑 3 次，再决定“内容质量 / 共创负担 / Phase 切片”哪个才是头号问题。

## 先看什么结果

优先级建议：
- 先看 `Eval-2`
  - 最容易暴露“问题发现能力”是否真实存在
- 再看 `Eval-3`
  - 最容易暴露 `Phase` 到底是价值切片还是越界编排
- 最后看 `Eval-1`
  - 用来判断流程是否在简单需求上过重
