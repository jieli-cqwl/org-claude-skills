# 一人 + Agents 产品研发交付操作系统：目标与成功标准

日期：2026-05-14

## 背景

公司希望建立一种新的产品研发交付方式：由一名产研负责人牵引，配合 Codex、Claude Code 和专门 agents，完成从客户需求接收、需求澄清、方案设计、开发实现、验证测试到上线交付的完整闭环。

这件事的目标不是为了向老板证明“我们有 agents”，也不是为了搭一套看起来完整的组织架构。真正目标是让复杂、模糊、有风险的真实需求，能够被一个人带着 agents 稳定拆清楚、做出来、验通过、上线，并且每次交付后都能沉淀为下一次更快、更稳的团队能力。

当前仓库已经有一些前任留下的资产，包括 skills、rules、agents、standard-chain 和若干样例交付文档。这些资产不能直接当成答案。它们需要通过真实项目验证：哪些能复用，哪些太重，哪些缺关键能力，哪些应该被改造或淘汰。

## 核心目标

建设一套“一人 + agents”的产品研发交付操作系统。

这套系统要让产研负责人可以用自然语言接收真实需求，然后通过清晰的流程和专门 agent 角色，把需求一步步转成可执行、可验证、可上线的交付结果。

它至少要覆盖：

- 客户或业务方提出模糊需求后，能澄清根问题、用户、目标、范围、非目标、约束和风险。
- 需求能被拆成清晰的阶段和交付单元，而不是靠聊天上下文硬撑。
- 产品、架构、测试、计划、开发、审查、验收、交付等角色有明确职责、输入、输出和停止边界。
- 人类负责人只负责关键裁决、范围取舍、风险接受和最终签收，不陷入每一步手工搬砖。
- agents 能在明确边界内执行任务，并用真实证据证明结果，而不是用报告或日志假装完成。
- 交付完成后能复盘出可复制经验，持续优化团队流程、agent 分工和验证标准。

## 第一条真实样板

第一条样板项目选择 `/Users/lijieli/project/qft-pai`。

选择它不是因为它容易，而是因为它足够真实：它有历史债务、复杂业务链路、多个外部依赖、真实线上风险，也有 Codex 和 Claude Code 在旧结构里继续维护困难的问题。

样板项目的候选方向是重建 `qft-pai` 中从外部触发进入到 Agent 响应产出的核心运行流程。这个方向后来被抽象为“Agent 运行时编排系统”，但当前阶段不能直接跳到技术方案、语言选型或架构实现。

在总目标下，`qft-pai` 的定位是试金石：

- 用真实复杂项目验证“一人 + agents”交付链路是否成立。
- 用真实代码和真实业务风险检验 agents 是否能在复杂上下文中可靠协作。
- 用一次可灰度、可回滚、可观测的真实交付，证明流程不是文档表演。
- 用交付过程反向筛选和改造仓库里已有的 skills、agents、rules 和 standard-chain 资产。

## 成功标准

### 1. 需求输入可控

给定一个模糊、复杂、夹杂历史包袱的真实需求，系统能把它收口成稳定的需求基线。

成功时应该能清楚回答：

- 根问题是什么。
- 谁被影响。
- 当前怎么处理。
- 当前处理方式的代价是什么。
- 本次要达成什么目标。
- 本期做什么，不做什么。
- 有哪些前置约束、风险和未知项。

### 2. 人类职责清楚

一名产研负责人不应该变成“所有细节的手工执行者”。

成功时，人类主要负责：

- 判断目标是否正确。
- 裁决范围和优先级。
- 接受或拒绝关键风险。
- 确认关键方案取舍。
- 审查最终证据并签收交付。

如果人类仍然需要长期手动串联每个步骤、反复解释上下文、逐文件指挥 agents，那这套系统没有成功。

### 3. Agents 职责清楚

每个 agent 或 skill 必须有明确职责，而不是“谁都能做一点”。

成功时，至少应该能区分：

- 产品方向谁负责。
- 需求细化谁负责。
- 架构设计谁负责。
- 测试义务谁负责。
- 实施计划谁负责。
- 开发实现谁负责。
- 代码审查谁负责。
- AC 验收谁负责。
- QA 和交付签收谁负责。

每个角色都要有明确输入、输出、消费者、失败时的停止边界和验证证据。

### 4. 交付链路闭环

成功不是“写了一堆文档”，而是需求真的从输入走到可用结果。

完整链路至少包括：

- 需求接收与澄清。
- 目标和成功标准冻结。
- 范围与非目标确认。
- 阶段和交付单元拆分。
- 架构与关键方案设计。
- 测试义务设计。
- AI 可执行实施计划。
- agents 开发实现。
- 代码审查与 AC 验收。
- QA 或真实路径验证。
- 灰度、上线、回滚或交付说明。
- 复盘和资产沉淀。

每一步都必须有产物和证据，且能被下一步消费。

### 5. 真实上线或真实可用

第一条样板不能停在方案、设计稿、demo 或内部报告。

成功结果必须落到 `qft-pai` 的真实可运行能力上。允许第一期只灰度一个渠道、一个 bot 或一条主链路，但必须能证明：

- 真实输入可以进入新链路。
- 新链路能产生正确动作或可验证结果。
- 失败能定位原因。
- 风险可回退。
- 交付结果对后续真实使用有价值。

### 6. 可观测、可复检、可回放

复杂系统不能只靠“日志里大概能找”来维护。

成功时，关键链路要能解释：

- 收到什么输入。
- 装配了什么上下文。
- 命中了什么策略。
- 为什么调用某个 Agent 或工具。
- 为什么跳过或转人工。
- 生成了什么动作。
- 动作是否执行成功。
- 失败发生在哪一层。

这些信息要能支撑调试、验收、复盘和后续优化。

### 7. 可复制为团队能力

第一条样板完成后，不能只是一次英雄式交付。

成功时应该沉淀出：

- 哪些流程必须保留。
- 哪些流程太重需要裁剪。
- 哪些 agent 角色有效。
- 哪些 agent 角色职责重叠或缺失。
- 哪些规则要进入长期规范。
- 下一次真实需求如何更快启动。
- 新人或新窗口如何接手当前上下文。

## 非目标

本需求当前阶段不直接承诺：

- 一次性搭完整组织架构。
- 一次性重写整个 `qft-pai`。
- 一次性替代所有旧 Java 主流程。
- 一次性决定最终编程语言。
- 一次性做成通用平台后台。
- 用模拟需求证明成功。
- 用文档、报告或主观判断替代真实交付证据。

## 当前未冻结事项

以下事项需要在下一阶段继续澄清，不能在当前文档里直接当成结论：

- `qft-pai` 第一条样板的确切 Phase 1 边界。
- 是否正式命名为“Agent 运行时编排系统”。
- 第一阶段是否引入新语言，以及候选语言如何评估。
- 新系统与旧 `qft-pai` 的集成、灰度和回滚方式。
- 当前仓库已有 standard-chain 是否完整适配这类真实交付，还是需要裁剪。
