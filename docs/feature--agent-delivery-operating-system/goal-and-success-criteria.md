# Standard Chain 端到端交付能力验证：目标与成功标准

日期：2026-05-14

## 背景

公司希望建立一种新的产品研发交付方式：由一名产研负责人牵引，配合 Codex、Claude Code 和专门 agents，完成从客户需求接收、需求澄清、方案设计、开发实现、验证测试到上线交付的完整闭环。

当前仓库已经沉淀了 `standard-chain`，它定义了一条从 `product-director` 到 `delivery-owner` 的交付链路。现在真正要验证的不是“我们有没有 agents”，也不是“文档链路是否看起来完整”，而是这条链路能否支撑真实复杂需求的端到端交付。

本阶段的目标要回到一个更硬的问题：

> 一名负责人带着 agents，能不能像带一支高水平产研团队一样，持续交付真实业务结果？

因此，本阶段聚焦 `standard-chain` 本身：

- 它是否能把模糊客户需求收口成稳定基线。
- 它是否能让每个角色明确消费上游、产出下游。
- 它是否能让一名负责人带着 agents 完成交付，而不是被流程拖死。
- 它是否能在真实项目里交付可运行、可验证、可回滚的结果。
- 它是否能沉淀出可复制的团队能力，而不是一次性文档表演。

## 核心目标

验证并打磨一套以 `standard-chain` 为主线的“一人 + agents”产品研发交付操作系统。

这套系统的核心不是先发明新组织架构，也不是先重写某个技术系统，而是证明以下链路成立：

```text
product-director
  -> product-manager
  -> design
  -> test-design
  -> tech-lead
  -> developer
  -> review
  -> verify
  -> qa
  -> consistency-auditor / fix
  -> delivery-owner
```

这条链路必须能处理真实需求，而不是只能处理结构化良好的样例。它要让产研负责人通过自然语言接收复杂需求，然后依靠 `standard-chain` 中的角色和产物，把需求逐步推进到可执行、可验证、可上线的交付结果。

推进上分两阶段：先用内部训练式 eval 验收和打磨团队能力，再进入 `qft-pai` 真实样板交付。第一阶段证明队伍具备上场条件，第二阶段证明队伍能打真实业务战。

## 核心定义

本阶段讨论的不是一个单纯的“消息处理系统”，也不是一个狭义的“Agent 管理后台”。

`qft-pai` 样板里确实会触及从三方消息回调、前置消息处理、上下文处理、agent 调度到响应处理的主流程，但这只是第一条真实样板的业务载体。总目标仍然是验证 `standard-chain` 能否驱动真实需求从输入到上线交付。

更准确的定义是：

> 一套以真实业务需求为入口、以角色协作为过程、以证据闭环为验收方式的 Agent 产品研发交付操作系统。

如果后续在 `qft-pai` 内部重写消息回调到 Agent 响应的运行时闭环，它可以被命名为“Agent 运行时编排系统”或类似名称。但这只是样板项目里的技术子系统，不应替代本阶段的总目标。

## 人机协作权责模型

“一人 + agents”不是让人变成 prompt 操作员，也不是让 agents 变成只会生成文档的表格工具。它要像一支真实团队一样分工，但分工依据不是人类职级，而是谁对哪类问题拥有更可靠的信息和能力。

核心原则是：

> 人主导现实世界事实、业务目标、组织约束和最终裁决；每个 agent 主导其对应角色的专业领域，并对专业判断、产物质量、风险暴露和证据自证负责。

### 人的职责边界

人是现实世界事实与业务裁决 owner。

人负责输入和把关这些内容：

- 真实客户、真实业务场景和真实组织背景。
- 公司当前目标、资源边界、优先级和不可碰约束。
- 外部团队、客户、老板和业务方的真实反馈。
- 范围取舍、风险接受、上线时机和最终验收裁决。
- 判断 agent 产物是否符合业务语境，而不只是逻辑上自洽。

人不应该替每个 agent 完成专业产物，也不应该被迫逐字段微操。否则“一人 + agents”会退化成“一人写需求，agents 帮忙润色”。

### Agent 的职责边界

每个 agent 是对应岗位专业领域 owner。

这意味着 agent 的职责不只是提炼、追问、建模和形成产物。它还必须像同事一样主动承担专业判断：

- 主导本角色领域内的问题识别、方法选择和产物质量。
- 基于用户输入的业务事实，形成专业判断和下游可消费产物。
- 输入不足时主动追问，或显式提出假设、风险和待裁决项。
- 发现上游输入不满足准入条件时，停止脑补并回到对应 owner。
- 输出必须能被下游使用、被验证、被追踪，而不是只让当前对话看起来顺滑。

“同事关系”在这里不是过度拟人化，而是岗位责任关系：每个角色都要对自己的专业边界负责，不能把所有判断重新推回给用户。

### 确定性工具的职责边界

凡是可枚举、可复验、可自动检查的判断，不应交给模型自由发挥。

例如：

- schema 校验负责结构完整性。
- tests 负责行为和回归验证。
- scripts / hooks 负责格式、契约和门禁。
- artifact registry 负责产物追踪和恢复。
- delivery state 负责阶段、阻塞和 signoff 状态。

模型可以参与语义判断、意图澄清、方案取舍和代码生成，但不能替代确定性控制流。

## Standard Chain 协作分层

`standard-chain` 不是所有环节都用同一种协作方式。不同环节对人的依赖强度不同，不能一刀切。

### 1. 强共创输入层

角色：`product-director`、`product-manager`、`design`。

这一层决定方向是否正确。人的作用是输入真实业务场景、组织约束、历史背景和取舍偏好；agent 的作用是主导对应专业领域，把混沌输入收口为专业基线。

这里的 `design` 指链路中的方案/系统设计角色，不默认等同 UI 设计。它仍需要人提供真实系统约束、历史债务、组织边界和上线风险。

这一层失败时，后续执行越快，浪费越大。

### 2. 半共创规划层

角色：`test-design`、`tech-lead`。

这一层由 agent 主导专业规划，人主要负责确认投入边界、风险偏好、交付节奏和不可接受的失败成本。

如果测试义务、任务拆解或技术计划发现上游输入缺口，必须回到对应上游 owner，而不是自行脑补。

### 3. 执行交付层

角色：`developer`、`fix`。

这一层更偏执行。agent 应主导实现、修复、自测和证据输出。人的作用是纠偏、验收和裁决超出任务边界的取舍。

执行层不应该重新定义产品目标，也不应该用实现方便性倒推需求范围。

### 4. 独立质量层

角色：`review`、`verify`、`qa`、`consistency-auditor`。

这一层必须保持独立性，不能为了让链路显得顺滑而降低标准。

- `review` 站在代码风险和行为回归视角。
- `verify` 站在 AC 覆盖和证据有效性视角。
- `qa` 站在用户路径和真实运行体验视角。
- `consistency-auditor` 站在跨工件一致性和追踪闭环视角。

质量层的价值不是“帮忙通过”，而是及时暴露不能交付的事实。

### 5. 交付调度层

角色：`delivery-owner`。

`delivery-owner` 是整条链路的交付调度者。它负责判断当前阶段、阻塞项、下一步 owner、修复循环和 signoff 证据。

但它不能替用户接受业务风险，也不能把缺证据的交付包装成已完成。

## 评估对象

本阶段评估对象是 `standard-chain` 的完整链路，而不是单个 agent、单个 skill 或单个技术实现。

需要重点评估：

- `product-director` 是否能冻结 WHY 层基线：根问题、用户画像、目标、范围、非目标、约束、风险和 Phase 规划。
- `product-manager` 是否能把 Director 基线细化成业务流程、用户路径、规则映射、UNIT 和可执行验收标准。
- `design` 是否能把产品输入转成可实现、可验证、可回滚的系统设计，而不是泛泛方案。
- `test-design` 是否能在开发前定义测试义务，覆盖正向路径、边界路径、失败路径和 QA 交接关注点。
- `tech-lead` 是否能把产品、设计和测试输入拆成 AI 可执行的计划、任务、依赖、批次和证据路径。
- `developer` 是否能在清晰 task 合同下完成最小实现，并输出真实自测证据。
- `review` 是否能发现实现风险，而不是只做表面审查。
- `verify` 是否能独立核对 AC 覆盖、代码真实性和证据有效性。
- `qa` 是否能从用户路径和真实运行视角给出质量裁决。
- `consistency-auditor` 是否能发现跨工件漂移、遗漏、矛盾和追踪断链。
- `fix` 是否能基于失败证据做根因修复，而不是盲目补丁。
- `delivery-owner` 是否能调度整条链路、管理阻塞、组织修复循环、沉淀 signoff 证据，并把交付推到可验收状态。

## 角色与 Skill 能力成长治理模型

只证明链路能跑通还不够。对业务和老板来说，目标是“一人 + agents”能交付；对团队负责人来说，目标是打造一支最强实践团队。因此，每个 standard-chain 角色既要考核岗位能力，也要考核承载该岗位能力的 skill 是否健康。

好 skill 不是“同事全部大脑内容”，而是让同事在正确边界内稳定发挥的岗位操作系统。它必须防止大杂烩化：

- LLM 负责专业判断：理解语义、追问缺口、建模、权衡、风险发现和专业产物生成。
- 工程化负责确定性控制：schema、状态机、脚本、hook、测试、格式校验、产物注册和上下文恢复。
- Skill 负责岗位边界与办事方法：何时触发、消费什么输入、按什么方法判断、输出给谁、失败时停在哪里。
- Reference 负责知识沉淀：复杂方法论、案例、模板和标准，不把长知识全部塞进 `SKILL.md`。
- Script/Test 负责可复验动作：固定规则、结构转换、门禁判断和回归验证不能让 LLM 临场自由发挥。

每个角色都应形成同一套能力卡：

- 角色使命、准入输入、主导专业领域、办事方法论、默认产物和下游消费者。
- 质量证据、失败停止点、协作边界、反模式和 `qft-pai` 样板验证方式。
- LLM 与工程化边界：哪些判断交给模型，哪些必须外置为 schema、script、hook、test 或状态机。
- 考核结论：`retain`、`optimize`、`redesign` 或 `retire`。

考核不是为了打分淘汰，而是为了帮助“这位同事”成长。每个 skill 还应形成成长卡：

- 当前强项：哪些专业判断和产物已经可靠。
- 退化风险：是否正在变成万能提示词、流程大杂烩、文档生成器或隐性人工搬运。
- 外置建议：哪些内容应从 prompt 挪到 reference、script、schema、hook 或 test。
- 回收建议：哪些过度工程化的判断应还给 LLM 做语义取舍。
- 下一轮方向：`clarify`、`simplify`、`externalize`、`automate` 或 `specialize`。

逐角色考核重点：

- `product-director`：主导 WHY 层，追问根问题、影响对象、现状代价、目标约束、范围边界和 Phase 价值切分。
- `product-manager`：主导 WHAT 层，把 Director 基线转成业务流程、用户路径、规则映射、UNIT、AC 和下游输入。
- `design`：主导 HOW 的系统方案，形成边界清晰、依赖明确、可验证、可灰度、可回滚的技术设计。
- `test-design`：主导开发前质量覆盖设计，定义正向路径、边界路径、失败路径、回归面和 QA 交接重点。
- `tech-lead`：主导实施组织，把产品、设计和测试输入拆成 AI 可执行任务、依赖顺序、批次和证据路径。
- `developer`：在 task 合同下完成最小正确实现，遵守复用、边界、测试和验证要求，并输出可审查证据。
- `review`：主导代码审查，发现行为风险、边界遗漏、回归隐患、测试不足和可维护性问题。
- `verify`：主导验收核对，逐条检查 AC、实现、测试和证据是否对应。
- `qa`：主导用户视角质量裁决，从真实路径、关键场景、异常行为和上线风险判断能否交付。
- `consistency-auditor`：主导跨工件一致性审计，发现目标、范围、AC、设计、测试、任务、实现和交付证据之间的漂移。
- `fix`：主导失败根因修复，基于失败证据定位原因、最小修复、补充验证，并把结果重新交回质量层。
- `delivery-owner`：主导交付调度，维护阶段状态、阻塞、owner、修复循环、artifact registry 和 signoff package。

## 两阶段推进路线

### Stage 1：内部训练式 Eval 验收

第一阶段是训练场，不是业务交付。目标是用可重复 eval 摸清并打磨 `standard-chain`、角色 skill、人机边界和工程化门禁的真实能力。

这一阶段必须回答：

- 每个角色能否完成本岗位专业判断，上游产物能否被下游无脑补消费。
- skill 是否边界清晰，是否存在大杂烩、过度工程化或过度依赖 LLM。
- 哪些判断应留给模型，哪些必须外置为 schema、script、hook、test 或状态机；每个角色和 skill 的结论是 `retain`、`optimize`、`redesign` 还是 `retire`。

Stage 1 的证据是 eval 结果、baseline 对比、失败案例、能力卡、成长卡和改造建议。它不能证明业务已经交付，只能证明队伍具备进入真实样板的最低条件。

阶段门：`product-director`、`product-manager`、`design`、`test-design`、`tech-lead`、`delivery-owner` 未通过最小 eval 前，不进入 `qft-pai` 真实需求交付。

### Stage 2：`qft-pai` 真实样板交付

第二阶段才进入 `/Users/lijieli/project/qft-pai`。选择它不是因为它容易，而是因为它足够真实：它有历史债务、复杂业务链路、多个外部依赖、真实线上风险，也有 Codex 和 Claude Code 在旧结构里继续维护困难的问题。`qft-pai` 的定位是 `standard-chain` 的实战试金石，用于证明一名负责人和 agents 能否完成一次可运行、可验证、可回滚的端到端交付。

样板候选方向是 `qft-pai` 中从外部触发进入到 Agent 响应产出的核心运行流程。这个方向要在 Stage 2 开始时进一步冻结为 Phase 1。

## 成功标准

### 横向前置标准：权责和能力可考核

进入具体交付前，必须能证明以下横向标准成立：

- 人、agent、确定性工具三类 owner 的职责边界清晰。
- 每个 agent 都明确自己主导的专业领域，而不是等待用户逐项指挥。
- 关键输入层知道哪些内容必须与用户共创。
- 执行和质量层知道哪些事项可以自行推进，哪些必须升级裁决。
- Stage 1 eval 与 Stage 2 真实交付的目标、证据和通过条件不能混用。
- 每个 standard-chain 角色都有能力卡，可以被逐项考核。
- 每个 skill 都能说明 LLM 判断、工程化控制、reference 知识和 script/test 验证的边界。
- 每个 skill 都有成长卡，能指出强项、退化风险、外置建议、回收建议和下一轮优化方向。
- 考核结论能落到 `retain`、`optimize`、`redesign` 或 `retire`，而不是泛泛说“还可以”。

### 1. Director 基线可冻结

给定一个模糊、复杂、夹杂历史包袱的真实需求，`product-director` 能把需求收口成稳定的 WHY 层基线。

成功时应该能清楚回答：

- 根问题是什么。
- 谁被影响。
- 当前怎么处理。
- 当前处理方式的代价是什么。
- 本次要达成什么业务目标。
- 本期做什么，不做什么。
- 有哪些前置约束、风险和未知项。
- Phase 如何按价值切分，而不是按实现步骤切分。

### 2. Product Manager 能生成下游可消费输入

`product-manager` 不能只是把需求写得更长，而要把 Director 基线变成下游能消费的产品事实。

成功时应该有：

- 清晰业务流程。
- 清晰用户路径。
- 清晰规则映射。
- 独立闭合的 UNIT。
- 每个 UNIT 的验收标准、验证计划、依赖和排除项。
- 对设计、测试、计划和交付有用的输入，而不是只给人看的 PRD。

### 3. 设计、测试和计划能连续消费上游

`design`、`test-design`、`tech-lead` 三段必须形成连续转换，而不是各写各的。

成功时应该证明：

- 设计决策能追溯到产品目标、约束和 UNIT。
- 测试义务能追溯到 AC、业务路径、边界路径和失败路径。
- 实施计划能追溯到产品目标、设计约束和测试义务。
- 下游发现输入缺口时能明确回到上游 owner，而不是自行脑补。

### 4. 开发、审查、验收和 QA 以证据闭环

`developer`、`review`、`verify`、`qa` 必须围绕真实证据工作。

成功时应该证明：

- developer 的实现有 task 边界、自测证据和可审查锚点。
- review 的问题有文件、行号、行为风险或验证证据。
- verify 能逐条核对 AC 是否被真实实现和测试覆盖。
- qa 能用用户路径、真实运行或可复验环境给出质量裁决。
- 任一失败都能进入 fix 循环，而不是靠解释绕过。

### 5. Delivery Owner 能真正调度交付

`delivery-owner` 不能只是最后写总结，它必须能管理整条链路。

成功时应该证明：

- 能接手 plan、tasks、design、test-cases、developer-report、review、verify、qa 等产物。
- 能判断当前阶段、阻塞项、下一步动作和 owner。
- 能调度 developer、review、verify、qa、fix、consistency-auditor。
- 能区分可自行推进事项和必须升级给用户裁决的事项。
- 能形成 delivery-state、artifact-registry、signoff-package 等交付证据。

### 6. Cross-Artifact 一致性可控

`standard-chain` 的价值不在单个文档，而在跨角色产物能互相追踪。

成功时应该证明：

- 目标、范围、AC、设计决策、测试义务、任务、实现证据、QA 结论之间能追踪。
- 上游变更不会静默污染下游。
- 产物之间的矛盾、遗漏和断链能被 consistency-auditor 或门禁发现。
- 新窗口或新人可以从 canonical artifact 恢复上下文，而不是依赖聊天记忆。

### 7. Stage 2 真实交付结果可用

第二阶段真实样板不能停在方案、设计稿、demo 或内部报告。

成功结果必须落到 `qft-pai` 的真实可运行能力上。允许第一期只灰度一个渠道、一个 bot 或一条主链路，但必须能证明：

- 真实输入可以进入目标链路。
- 目标链路能产生正确动作或可验证结果。
- 失败能定位原因。
- 风险可回退。
- 交付结果对后续真实使用有价值。

### 8. 链路轻重能被复盘和裁剪

本次验证不是为了证明 `standard-chain` 永远正确，而是为了找出它对真实交付的真实适配度。

成功时应该沉淀：

- 哪些角色必须保留。
- 哪些角色职责重叠。
- 哪些产物字段有价值。
- 哪些产物字段只是流程噪音。
- 哪些门禁太重或太晚。
- 哪些步骤需要压缩、合并或自动化。
- Stage 1 eval 发现的问题如何反哺 Stage 2，Stage 2 暴露的问题如何反哺 eval。
- 下一次真实需求如何更快启动。

## 非目标

本阶段不直接承诺：

- 一次性搭完整组织架构。
- 一次性重写整个 `qft-pai`。
- 一次性替代所有旧 Java 主流程。
- 一次性决定最终编程语言。
- 一次性做成通用平台后台。
- 把 `qft-pai` 的消息主流程重写当成本阶段唯一目标。
- 把人降级为 prompt 操作员。
- 把 agent 降级为文档生成器或提炼工具。
- 把 skill 写成无边界、不可验证、不可成长的大杂烩提示词。
- 用 Stage 1 eval 结果冒充真实业务交付成功。
- 用模拟需求证明成功。
- 用文档、报告或主观判断替代真实交付证据。
- 绕过 `standard-chain` 另起一套平行流程。

## 当前未冻结事项

以下事项需要在下一阶段继续澄清，不能在当前文档里直接当成结论：

- Stage 1 的 eval 集、baseline、断言、通过阈值、失败分级和最小必测角色范围。
- 每个角色达到 `retain`、`optimize`、`redesign` 或 `retire` 的判定阈值。
- 每个 skill 的 LLM/工程化边界、reference 拆分、script/test 外置和成长卡如何落地。
- Stage 2 中 `qft-pai` Phase 1 的确切边界、灰度、回滚和旧系统集成方式。
- 是否正式命名为“Agent 运行时编排系统”，以及它是否只作为 `qft-pai` 样板内的技术子系统命名。

## 下一步建议

新窗口应先启动 Stage 1 内部训练式 eval 验收，而不是直接进入 `qft-pai`、语言选型、架构设计或实现。

建议下一步先冻结：

1. Stage 1 的 eval 目标、角色范围、样例任务、客观断言和通过阈值。

3. 每个 eval 的 expected output、人工评审点、失败分级和 Stage 2 入口条件。
4. Stage 2 再冻结 `qft-pai` Phase 1 根问题、用户画像、现状代价、范围、非目标和成功证据。

完成 Stage 1 复检并修正关键 skill 后，再进入真实需求、语言选型调研、架构设计和实施计划。
