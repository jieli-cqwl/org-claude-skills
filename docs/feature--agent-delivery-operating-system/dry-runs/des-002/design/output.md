**结论**

推荐以**方案 A：阶段门控闭环**作为 DES-002 dry-run 的默认设计方向，因为它最贴合“两周、单渠道、单 bot、单真实场景样板”的约束，验证路径短，最不容易滑向平台化。但这不是替用户裁决：若 human 明确把“可审计、可重放、未来扩展弹性”排在交付速度前面，则应切换到方案 B 或重新共创。

本输出只基于 PM-002 synthetic 产物，不代表真实 qft-pai 证据，不生成 `design.json`，不声称 Stage 1 通过，也不进入语言、框架、数据库、云产品或实现技术选择。

**1. 输入边界声明**

操作对象：PM synthetic 输出中的单业务线 / 单渠道 / 单 bot / 单真实场景闭环。

已知输入：UNIT-01 到 UNIT-06，覆盖消息接收、前置处理、上下文取用、单 bot 调度、响应生成、可观察记录；每个 UNIT 有 AC、依赖和排除项。

硬边界：不做全渠道平台、通用 bot 管理、完整上下文平台、完整调度平台、观测平台、灰度平台、权限平台、计费平台、配置平台；不做重写方案。

缺口：没有真实代码、接口、部署、运行时、数据源、qft-pai 采证。所有“事实”只能引用 synthetic PM 输入，不能当真实系统约束。

**2. 架构关注点**

核心复杂度不在技术选型，而在闭环边界是否可控：

- 边界控制：只允许目标渠道、目标 bot、目标场景进入闭环。
- 状态语义：范围外、前置阻断、上下文不足、未调度、生成受阻、成功生成必须区分。
- 上下文可信度：上下文不足时不得生成无依据响应。
- 单 bot 调度约束：不得隐式扩展为多 bot 编排。
- 可观察性：每阶段必须有阶段、结果、原因、未继续执行的后续阶段。
- 回滚边界：生成前可停止；生成后是否对外可见，必须由 human 裁决。
- 测试可消费性：方案必须让 test-design 推导正向、边界、失败路径和证据期望。

**3. 方案 A：阶段门控闭环**

核心结构：按 UNIT 顺序形成单一路径门控链路：接收边界 → 前置处理 → 上下文取用 → 单 bot 调度 → 响应生成 → 可观察记录。每一阶段只有三类结果：继续、业务停止、系统失败；停止后不进入后续阶段。

适用场景：两周样板优先、范围必须收紧、验收者需要看清一次消息从进入到响应生成的完整链路。

取舍：优点是简单、可验收、AC 映射直接、失败位置清晰；代价是阶段耦合较强，未来扩展多渠道或多 bot 时需要重新评估边界。

风险：如果阶段职责不清，会把“范围外”和“失败”混在一起；如果可观察记录弱，成功链路无法作为样板证据；如果 human 未裁决响应是否对外发送，回滚语义不完整。

**4. 方案 B：状态证据驱动闭环**

核心结构：把每个 UNIT 看作一次状态转移，所有阶段都围绕“当前状态、触发条件、输出状态、停止原因、证据记录”运转。后续动作只消费明确的合格状态，而不是默认顺序向下执行。

适用场景：更重视审计、问题定位、重复消息保护、未来演进；或者目标场景中会出现乱序、重复、部分失败，需要更强状态证据。

取舍：优点是失败语义和追溯能力更强，test-design 可直接围绕状态转移推用例；代价是建模复杂度更高，容易把样板做成“观测平台”或“通用状态平台”。

风险：如果没有 human 确认质量优先级，可能过度设计；如果状态定义不冻结，下游测试会被状态枚举拖死；如果一致性口径不清，可能出现“记录已成功但响应未可信生成”的业务假象。

**5. 关键取舍矩阵**

| 维度 | 方案 A 阶段门控 | 方案 B 状态证据驱动 |
|---|---|---|
| 两周样板达成 | 更优，路径短 | 较重，需先冻结状态模型 |
| AC 追溯 | 直接按 UNIT 顺序映射 | 按状态转移映射，更细 |
| 失败定位 | 阶段级清晰 | 状态级更强 |
| 演进弹性 | 中等，未来再拆 | 更好，但当前成本高 |
| 过度设计风险 | 低 | 中高 |
| test-design 成本 | 低到中 | 中到高 |

**6. 推荐方案与失效条件**

推荐：采用方案 A，并强制吸收方案 B 的“状态/原因可观察”底线。也就是流程控制保持阶段门控，证据记录必须能表达每个 UNIT 的状态、原因和后续未执行边界。

推荐理由：DES-002 的输入是单渠道、单 bot、单场景；当前目标是样板闭环，不是平台能力。方案 A 更符合简单、合适、演化原则。

失效条件：

- human 要求样板必须支持重复、乱序、重放式审计或强审计证据。
- 单场景实际存在多个并行状态或异步等待，顺序门控无法表达。
- 未来扩展已被确认是本 Phase 成功标准，而非后续演进。
- 响应一旦生成即产生高业务风险，需要更强状态审计和人工裁决点。

**7. 风险、观测、失败语义、回滚边界**

风险：最大 P0 是“生成无依据响应”被当成成功。缓解：上下文不足必须停止，不得进入调度或生成。

观测：每次链路至少记录链路标识、当前阶段、输入摘要、输出摘要、阶段结果、停止原因、后续阶段是否执行、验收可见状态。

失败语义：

- `excluded`：范围外，不是失败。
- `blocked`：业务条件不足，如上下文不足。
- `failed`：系统或依赖异常。
- `generated`：响应已生成，但不等于已对外发送。
- `recorded`：链路证据完整，可供验收查看。

回滚边界：响应生成前可停止或重新生成；响应若已对外可见，只能做补偿记录、标记无效或人工处置。是否自动对外发送必须 human 裁决，design 不能替代。

**8. 待裁决点与 resume condition**

待裁决点：

1. 样板场景的精确定义：触发语、必要上下文、排除样例。
2. 质量优先级：两周交付、审计可追溯、未来扩展，三者排序。
3. 响应策略：只生成供验收查看，还是自动对外返回。
4. 上下文不足的判定阈值：哪些字段缺失必须阻断。
5. 系统失败处理：允许同阶段有界重试，还是立即停止并记录。
6. 采用方案 A 还是方案 B，或采用 A 加状态证据底线。

Resume condition：human 明确上述裁决，尤其是质量优先级、响应是否对外可见、上下文不足阈值和方案选择后，design 才能继续冻结接口边界、状态语义、风险回应和下游验证映射。

**9. 给 test-design 的消费提示**

test-design 可据此推导：

- 正向链路：UNIT-01 到 UNIT-06 全部继续，最终可追溯完整阶段记录。
- 范围外路径：非目标渠道、非目标 bot、非目标场景必须停止，且不执行后续 UNIT。
- 阻断路径：空消息、场景不明、关键上下文缺失、无法确认 bot、无法可靠生成响应。
- 失败路径：系统异常与业务排除分开断言，不能只写“失败”。
- 证据义务：每个 AC 都要断言阶段、结果、原因、后续未执行边界。
- 回滚义务：响应生成前、生成后未发送、生成后已发送三种边界需要不同验证。
- 方案差异测试：若选 A，重点测阶段门控和停止后不继续；若选 B，重点测状态转移、重复输入、乱序输入和证据一致性。
