**结论**
PM-002 dry-run 结果如下：仅做 PM 的 WHAT 层细化，不改写 Director baseline，不进入真实项目，不输出技术方案/架构方案/语言选型/任务拆解，不声明 Stage 1 通过。

**锁定 Baseline**
- WHY/root_problem：当前 agent 交付能力需要证明“一人 + agents 可以端到端完成真实交付闭环”，但全量平台化目标过大，必须先用单场景样板验证方法和交付链路。
- user_profile：产研负责人，负责搭建一人 + agents 的 Agent 产品研发团队，并向老板证明该模式能在真实业务场景中形成可验收交付。
- phase_goal：两周内完成一个单业务线 / 单渠道 / 单 bot / 单真实场景的端到端样板验证。
- scope：只覆盖一个三方消息回调进入后的单场景闭环：接收消息、前置处理、上下文取用、agent 调度、响应生成、可观察结果记录。
- non_goals：不做全渠道平台、通用 bot 管理、完整上下文平台、完整调度平台、观测平台、灰度平台、权限平台、计费平台、配置平台；不做语言选型或重写方案。

**业务流程**
1. 单渠道三方消息回调进入单 bot 样板入口。
2. 判断消息是否属于本期单真实场景；不属于则记录排除结果，不进入后续闭环。
3. 对范围内消息做前置处理：确认来源、目标 bot、消息内容和场景触发条件足以继续。
4. 取用当前单场景所需上下文；不足时形成“上下文不足”的可观察结果。
5. 仅调度 Director 确认的单 bot agent。
6. 基于原消息和可用上下文生成单次响应结果。
7. 记录本次链路各阶段结果：接收、前置处理、上下文取用、agent 调度、响应生成、异常或排除原因。

对象状态：`未进入 -> 已接收/已排除 -> 前置通过/前置阻断 -> 上下文可用/上下文不足 -> 已调度/未调度 -> 响应已生成/生成受阻 -> 已记录`。

**用户路径**
- UP-1 消息发送方：在已选三方渠道发送符合样板场景的消息；可观察结果是该消息对应的响应结果已生成，或明确未生成原因。
- UP-2 产研负责人/验收者：用样板消息查看从接收至响应生成的链路记录；可判断“一人 + agents”样板链路是否可验收。
- UP-3 业务运营/排查者：查看范围外、前置阻断、上下文不足、未调度、生成受阻等记录；可判断阻断发生在哪个业务阶段。

**规则映射**
| 规则 | 业务约束 | 追溯来源 |
|---|---|---|
| R1 单样板边界 | 只允许一个业务线、一个渠道、一个 bot、一个真实场景进入本期闭环 | phase_goal / scope |
| R2 消息入口 | 只有已选渠道进入的三方消息回调可进入样板链路 | scope |
| R3 场景资格 | 消息必须命中本期单真实场景；否则只记录排除，不取上下文、不调度、不生成响应 | scope / non_goals |
| R4 上下文边界 | 只取当前场景必要上下文；不建设完整上下文平台 | scope / non_goals |
| R5 agent 调度边界 | 只调度已确认的单 bot；不做通用 bot 管理或完整调度平台 | scope / non_goals |
| R6 响应约束 | 响应必须能追溯到原消息和已取用上下文；上下文不足时不得生成无依据响应 | success_direction / scope |
| R7 可观察记录 | 每个继续或停止结果都要记录阶段、结果和原因；不扩展为观测平台 | scope / non_goals |

**闭环 UNIT**
| UNIT | 闭环定义 | 依赖 | 排除项 |
|---|---|---|---|
| UNIT-01 消息接收边界 | 三方回调消息进入 -> 识别是否属于单渠道/单 bot 样板入口 -> 产生已接收或范围外记录 | 无 | 全渠道接入、渠道平台治理、通用 bot 管理 |
| UNIT-02 前置处理与场景确认 | 已接收消息 -> 判断消息内容和场景触发条件是否足以继续 -> 产生前置通过或前置阻断结果 | UNIT-01 | 完整清洗平台、风控平台、通用规则中心 |
| UNIT-03 上下文取用 | 前置通过消息 -> 取用当前单场景必要上下文 -> 产生上下文可用或上下文不足结果 | UNIT-02 | 完整上下文平台、跨场景记忆、权限平台 |
| UNIT-04 单 bot agent 调度 | 上下文可用 -> 限定调度单 bot agent -> 产生已调度或未调度记录 | UNIT-03 | 完整调度平台、多 bot 编排、灰度平台 |
| UNIT-05 响应生成 | 已调度请求 -> 生成与原消息和上下文一致的单次响应 -> 产生响应结果或生成受阻原因 | UNIT-04 | 通用对话平台、语言选型、重写方案 |
| UNIT-06 可观察结果记录 | 各阶段结果产生 -> 汇总链路状态和原因 -> 验收者可追溯成功、阻断或排除位置 | UNIT-01~05 | 观测平台、计费平台、配置平台 |

**示例驱动 AC**
- UNIT-01 AC-01：输入为已选渠道、已选 bot、样板场景消息；预期为记录“已接收”。边界：消息内容存在但很短仍进入前置处理。失败模式：非已选渠道消息被标记范围外，后续 UNIT 不执行。
- UNIT-01 AC-02：输入为已选渠道但目标 bot 不是本期单 bot；预期为记录“非本期 bot”。边界：bot 标识缺失时记录入口信息不足。失败模式：不得把未知 bot 消息继续送入样板链路。

- UNIT-02 AC-01：输入为“[样板场景触发语] + 明确业务诉求”；预期为前置通过。边界：表达不标准但能判断为样板场景时继续。失败模式：空消息或无法判断场景时前置阻断。
- UNIT-02 AC-02：输入为同渠道同 bot 但非样板场景诉求；预期为记录“场景不在本期范围”。边界：同时包含样板和非样板诉求时只保留样板场景处理依据。失败模式：不得把非目标场景扩展进本期。

- UNIT-03 AC-01：输入为前置通过消息且当前场景必要上下文存在；预期为形成“上下文可用”结果。边界：非必要上下文缺失不阻断。失败模式：关键上下文缺失时记录“上下文不足”，不进入调度。
- UNIT-03 AC-02：输入为需要跨场景或完整历史上下文的消息；预期为标记超出本期上下文边界。边界：只需当前场景上下文时仍可继续。失败模式：不得临时扩大为完整上下文平台。

- UNIT-04 AC-01：输入为上下文可用的样板请求；预期为调度到单 bot agent，并记录已调度。边界：同一请求只允许落到本期单 bot。失败模式：无法确认目标 bot 时记录未调度。
- UNIT-04 AC-02：输入为需要多 bot 协作的诉求；预期为标记超出本期调度范围。边界：单 bot 可独立处理的部分可继续。失败模式：不得引入通用调度或多 bot 编排。

- UNIT-05 AC-01：输入为已调度请求、原消息和可用上下文；预期为生成与样板场景一致的响应结果。边界：响应可简短，但必须覆盖用户核心诉求。失败模式：不得生成与上下文冲突或无依据的答复。
- UNIT-05 AC-02：输入为 agent 无法基于上下文给出可靠响应；预期为记录生成受阻原因。边界：可说明缺少的业务信息。失败模式：不得伪造确定结论。

- UNIT-06 AC-01：输入为一次完整成功链路；预期为可追溯接收、前置、上下文、调度、响应生成各阶段结果。边界：阶段耗时或展示形式由下游设计收口。失败模式：任一阶段结果缺失时不能作为可验收样板记录。
- UNIT-06 AC-02：输入为任一阶段阻断链路；预期为记录阻断阶段、原因和未继续执行的后续阶段。边界：范围外与失败要区分。失败模式：不得只记录“失败”而不说明业务阶段和原因。
