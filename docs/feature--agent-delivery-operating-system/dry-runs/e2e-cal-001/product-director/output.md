结论：本次仅做 Stage 1 eval/dry-run。D-S1 只基于 Eval prompt 收集候选线索，不进入真实 `qft-pai`、不写业务 JSON、不运行代码；当前停在 D-S2 关键假设验证，不进入语言选型、架构设计、PRD、UNIT 或 AC。

**D-S1 候选线索**
已知线索：三方消息回调 → 前置消息处理 → 上下文处理 → agent 调度 → 响应处理，这条主流程被描述为“维护不动”。老板诉求是通用、高可用、高性能、易维护、易观测的 agent 管理调度系统。
未闭合缺口：“维护不动”到底是变更成本、线上故障、性能瓶颈、观测缺口，还是人员知识沉淀问题，目前没有证据。
风险线索：“新语言重写”是方案，不是根因；现在不能把它当成基线方向。

**D-S2 问题澄清**
方案线索：直接用新语言重写主流程。
真实痛点：候选判断不是“语言不合适”，而是核心消息链路职责、状态、异常、调度和观测边界没有稳定收口，导致新增三方、调整 agent、变更响应策略时都要碰主链路。
现有处理方式：候选是继续在原主流程里叠逻辑、补兼容、靠熟人理解链路、线上问题靠日志和经验排查。
处理代价：变更回归风险高，故障定位慢，性能瓶颈难归因，agent 调度策略难演进，最终拖累消息响应稳定性和业务迭代速度。

我的默认根问题判断：当前要解决的不是“换一门语言”，而是“把 agent 消息主链路从不可控的耦合流程，收口成可演进、可观测、可治理的业务调度能力”。
