## 本次复审目标

本次不是重做首轮评审，而是检查：Claude 在首轮评审指出的关键阻塞项后，是否已完成系统性修复，是否足以把结论从“不通过正式评审”提升到更接近可批准的状态。

本轮只聚焦 4 类首轮 blocker：

1. reviewer 外部依赖契约
2. 统一 findings schema
3. fail-close 状态机
4. baseline / 恢复语义

## 二次复审结论

**结论：有条件通过候选。**

与首轮评审相比，这一版 design 已经出现实质性改善，不再是“只有方向、没有契约”的状态。当前更准确的判断是：

1. 首轮最核心的设计缺口已经大面积补齐。
2. 该文档已经接近可作为实现输入使用。
3. 但在正式给出“通过”结论前，仍建议保留 2 个待确认点：
   - `codex:adversarial-review` / `codex-companion.mjs` 主路径能力是否真实可用
   - DECEPTION 是否应该保留独立终态，而不只是附着在普通 finding schema 上

因此，这份二次复审文档给出的不是“完全通过”，而是：

> **设计已由“不通过”提升到“有条件通过候选”；若上述两个待确认点确认无硬伤，可进一步转为正式通过。**

## 关闭的 blocker

### 1. baseline / 恢复语义已从口号升级为契约

首轮评审认为 baseline 保护只有“dirty 时 stash，报告里带 stash SHA”，不足以支撑可恢复基线。当前版本已补入：

- `baseline_ref`
- `stash_ref`
- `staged_stash_ref`
- 正常退出时的 `git stash pop`
- stash 冲突时不自动解决、报告冲突文件
- 用户中止/异常终止时保留现场并提示手动恢复
- 禁止 `git reset --hard` / `git checkout .`

见 `docs/review-fix-loop/2026-04-03-redesign/design.md:48-71`。

我的判断：这一项已经不再是阻塞。它未必是最优实现，但已经形成了**可恢复语义**，不再是首轮那种“只有 stash 口号，没有恢复闭环”的状态。

### 2. fail-close 状态机已经补出主异常矩阵

首轮评审认为文档只有 happy path，没有异常终态。当前版本已显式补出异常矩阵，覆盖：

- 工具不可用
- 输出非 JSON / 缺关键字段
- finding 不可定位
- stash 冲突
- 验证命令失败
- 验证命令发现错误
- 用户中止
- 超时
- 路径切换禁止静默降级

见 `docs/review-fix-loop/2026-04-03-redesign/design.md:72-90`。

我的判断：这项也已从 blocker 降为可接受设计。原因不是它已经完美，而是**状态机终于具备负路径**，并且明示“不继续修复、不静默切换路径、保留现场”。这已经满足设计层的最低可靠性要求。

### 3. finding schema 已从自由文本回到机器可消费结构

首轮评审最担心的是统一 finding schema 退化成 `location` 字符串，导致排序、修复、跨轮比对都站不住。当前版本已改成：

- `path`
- `line`
- `end_line`
- `severity`
- `description`
- `recommendation`
- `dimension`（可选）

并补了字段约束和跨轮追踪规则，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:177-200`。

我的判断：这一项已实质关闭 blocker。尤其是它已经明确：

- `dimension` 是附加语义，不再替代机器字段
- 代码路径和文档路径可以在同一统一 schema 上落地
- 跨轮追踪至少有了明确启发式

我仍然会提醒：后续实现时，`±5 行视为同一 finding` 这个规则可能需要验证，但这是实现精度问题，不再是设计是否成立的问题。

### 4. 影响范围与迁移映射已明显补强

首轮评审认为 blast radius 被严重低估。当前版本已经把受影响对象提升到运行时、门禁、hook、contract 级，并新增了迁移映射表，明确：

- 哪些旧组件被吸收
- 哪些被丢弃
- 哪些需要替换
- 哪些需要在删除前确认无调用方

见 `docs/review-fix-loop/2026-04-03-redesign/design.md:293-339`。

我的判断：这项也已明显改进。至少它不再把迁移理解成“删目录 + 清引用”，而是把范围提升到了真实的工程层面。

## 仍保留的待确认点

### A. `code-review-fix` 主路径能力仍建立在未被当前变更证明的前提上

当前代码路径仍然建立在：

- `codex:adversarial-review`
- `codex-companion.mjs`

之上，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:105-117`、`:248-255`。

虽然文档这次已经补了“外部依赖契约”，但这里仍有一个残余问题：

> 设计里把它写成正式依赖，不等于当前仓库/运行时已经证明这条能力真实、稳定、可调用。

所以这项我不再把它当 blocker，但会保留为**实现前 gate**：

- 如果这条能力真实存在且可稳定调用，那么当前设计可以继续推进
- 如果它实际上只是设想能力，那设计还需要再收敛到仓库当前真实能力上

### B. DECEPTION 语义已补强，但是否需要独立终态仍值得保留

当前版本已经补了：

- DECEPTION 不进入自动修复
- 需用户介入
- 可通过 `severity=critical + dimension 含 DECEPTION` 来表达

见 `docs/review-fix-loop/2026-04-03-redesign/design.md:220`、`:334-339`。

这比首轮强很多，也解决了“DECEPTION 语义丢失”的主要问题。

但我保留一个设计层面的疑问：

> DECEPTION 现在仍然是普通 finding schema 上叠加的约束，而不是独立 verdict / 独立终态。

这未必错，但它仍是一个应该被显式确认的设计选择。我的建议是：

- 如果团队接受“普通 finding schema + 特殊修复约束”这种方式，那么这项可以视为通过
- 如果团队要求 DECEPTION 保持独立安全语义，那应进一步提升为独立 verdict 或终态
