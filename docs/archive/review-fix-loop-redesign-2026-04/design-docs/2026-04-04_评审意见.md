## 评审方法

本次评审综合了以下视角：

- 主评审：架构、状态机、失败闭环、验收证据
- 专题评审：收敛标准与 success criteria
- Challenger 1：可靠性观点反驳
- Challenger 2：价值/复杂度观点反驳
- 现状核对：旧 skill、运行时、门禁、hook、contract 级影响范围

目标不是附和单一判断，而是收敛出“哪些点必须坚持、哪些点被高估、哪些点应后移到实现验证”。

## 结论

**结论：当前版本不建议直接进入实现验收；需先补设计契约后再实现。**

这份 design 的方向是对的，但晚到的架构、fail-close、独立审查结论把整体判断进一步收紧了：它现在更准确的定位不是“有条件通过并可先做 MVP”，而是**“方向正确，但契约未闭合，按当前文本直接实现会把关键风险留到实现期临场决策”**。

收敛后的最终判断是：

1. 设计方向通过：拆 skill、文档动态维度、用户显式选评审方式，这三个方向都成立。
2. 当前文本不通过正式评审：至少在外部 reviewer 契约、统一 findings schema、fail-close 状态机、baseline 恢复语义上仍有阻塞缺口。
3. 因此不建议把当前文档直接作为实现输入，更不应把它当成“替代旧方案”的验收契约。
4. 正确动作是：先补设计，再实现；不是先实现再靠代码补齐设计缺口。

换句话说，这不是“方向错了”，而是**“方向对，但还没到可安全开工的设计完成度”**。

## 正面判断

### 1. 迁移动机成立，且已被现状证实

现有 `review-fix-loop` 确实把代码与文档两类对象塞进同一循环：代码路径跑测试/静态检查，文档路径则标注“无可执行验证”，说明两类对象共享了同一 orchestration，但验证逻辑本质不同，见 `claude/skills/review-fix-loop/SKILL.md:39-41`。同时，现有实现确实依赖本仓库自定义 JSON schema 与校验脚本，而不是直接消费现成插件产物，见 `claude/skills/review-fix-loop/SKILL.md:32-37`、`claude/skills/review-fix-loop/references/execution-spec.md:15-34`、`claude/skills/review-fix-loop/references/review-schema.md:1-19`。

对应地，design 对旧方案三类根因的判断是成立的：代码/文档混评、额外 schema/校验脚本复杂度、固定维度不适配 leader 模式，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:3-4`。

### 2. 拆成 `code-review-fix` / `doc-review-fix` 是正确方向

设计把代码与文档明确拆成两个独立 skill，并承认它们在评审引擎、评审维度、验证方式、修复范围、收敛标准上都不同，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:24-34`、`:90-99`。这不是目录重命名，而是把两个本来就不同的状态机拆开。

### 3. 文档评审改为“动态发现维度”是合理的

设计明确指出代码插件的攻击面不适合文档场景，文档评审需要自定义 prompt 和从内容中涌现维度，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:101-109`。这比沿用固定攻击面更符合文档评审的真实目标。

### 4. “去脚本化”方向正确，但不能连好契约一起丢掉

设计希望去掉旧的 baseline 脚本和 JSON 校验脚本，以 `git stash` 和结构化 findings 取代额外脚本，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:173-175`。这个方向本身是加分项；但当前文档对“异常时怎么停、怎么报、怎么恢复”写得不够硬，因此只能说“简化方向正确”，不能说“新契约已经完整”。

## 主要问题

### P1. 影响范围被低估，不能只写成“清理引用”

设计把淘汰计划主要描述为删除旧目录、删除旧 agent、grep 清理引用，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:185-205`。但现状显示，影响范围已经扩到运行时、门禁和 contract：

- 安装 quick check 直接要求 `review-fix-loop` 运行时文件存在，见 `install.sh:1248-1253`
- runtime integrity 直接校验 `review-fix-loop`、`codex-doc-review`、`codex-doc-reviewer` 的存在/不存在关系，见 `tests/test-runtime-integrity.sh:179-205`
- single-source layout 把这两个旧 skill 和一个旧 agent 当成唯一允许的 claude-only source，见 `tests/test-single-source-layout.sh:57-68`
- 测试总入口显式编排 `test-codex-doc-review-*` 与 `test-review-fix-loop-skill.sh`，见 `tests/run-all.sh:15-18`、`:49-52`、`:100-107`
- shared hook 已包含整套 `codex-doc-review` 上下文解析逻辑，见 `shared/hooks/lib/common.sh:508-690`
- contract 链路存在 `codex-doc-review` 节点及其产物消费者，见 `contracts/skill-chain.yaml:61-81`

因此，“删除旧 skill + 清理引用”不足以表达 blast radius。这里更准确的说法应是：本次迁移会波及 skill source、安装校验、运行时完整性测试、布局门禁、shared hooks、contract registry。

### P1. fail-close 契约没有写完整，且当前应按阻塞处理

设计定义了共同交互模型与终止条件，但对异常矩阵写得偏薄，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:39-45`、`:60-74`、`:101-127`。晚到的 `contract-reviewer`、`arch-reviewer` 与独立审查结论一致认为：这一项不能再按“实现约束待补”弱化处理，而应视为**阻塞**。

当前缺失的关键点包括：

- `codex:adversarial-review` 或 `codex exec --json` 不可用怎么办
- agent 自评审输出非 JSON / 缺字段怎么办
- `location` 无法定位到文件与行号怎么办
- `git stash` / 恢复冲突怎么办
- 自动发现验证命令失败或发现错误命令怎么办
- codex 路径失败后是否允许静默切到 agent，自评审失败后是否允许静默切到 codex
- reviewer 输出非法、JSON 解析失败、用户中止时进入哪个终态，最终报告要保留哪些错误证据

更重要的是，代码路径当前把 `codex:adversarial-review --scope auto --wait "${focus_text}"` 和 `codex-companion.mjs` 当作既有前提，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:60-63`、`:167-169`；但 design 没给出 capability contract、错误语义、超时/重试/停止规则。对于修复循环来说，这已经不是“细节后补”，而是主路径依赖未闭合。

因此，本项的最终口径应是：**当前设计不满足 fail-close，属于阻塞，不宜带着这个缺口进入实现。**

### P1. finding 结构退化，且与修复状态机自相矛盾

当前旧方案的 finding 契约是 `file + line_start + line_end + severity + description + recommendation`，见 `claude/skills/review-fix-loop/references/review-schema.md:1-19`。而 redesign 统一格式退化为 `dimension + severity + location + description + recommendation`，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:111-122`。

这个变化带来三个问题：

1. `location` 只是字符串，无法稳定排序、定位、对比同一 finding 是否持续存在。
2. 设计又在代码路径中要求“同文件内按行号降序修复”，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:66-69`；如果最终统一 schema 不保留结构化 `path/range`，这条修复策略本身就缺支撑。
3. design 前文对代码路径的描述仍然是 `file + line + severity + recommendation`，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:60-62`；也就是说，文档内部已经出现“代码引擎输出结构”和“统一 finding 结构”不一致的问题。

因此，这里不是单纯的“字段名不同”，而是**统一 schema 与修复状态机自相矛盾**。这一点会直接影响排序、去重、跨轮比对、不收敛判定与自动修复定位，属于必须先补齐的设计缺口。

### P1. 收敛标准与最终报告还不足以支撑真实验收

设计对 code/doc 两类对象分别定义了通过条件，这是优点；但验收视角看，当前闭环还不够硬：

- 代码 skill 只修 `high+`，但最终报告仅在非通过时列剩余 findings，意味着 medium/low 可能在“通过”时被隐藏，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:66-83`、`:171-172`
- 文档 skill 用“连续两轮零 findings”作为通过条件，这对 MVP 是可接受的，但若第二轮维度缩水，仍可能浅通过，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:107-109`、`:124-140`
- success criteria 主要证明“能跑过一轮”，但没有把应保留的证据写成机械可验证输出，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:177-183`

Acceptance 专题评审的结论是：当前文档还不足以证明“稳定闭环成立”，只能证明“流程骨架成立”。这个判断我保留。

### P1. baseline、DECEPTION 与旧契约迁移都没有闭环

设计写到“淘汰 `codex-doc-review`，迁移 DECEPTION 模式”，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:11-13`、`:141-145`、`:175`。但晚到的架构评审指出，当前问题不只是“替代关系写轻了”，而是**baseline、DECEPTION、旧契约迁移都没有形成闭环**。

具体包括：

- baseline 只剩 `dirty 时 stash / clean 时跳过` 和报告里的 `基线 stash SHA`，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:41-45`、`:76-83`、`:129-137`、`:174-175`；没有起始基线标识、恢复命令、循环新增文件、stash apply 失败后的恢复分支
- DECEPTION 虽然迁移了模式知识，但统一 severity 只有 `critical|high|medium|low`，且文档路径声明“所有级别都修”，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:96-99`、`:111-145`、`:171-175`；这意味着 DECEPTION 在新设计里没有单独 severity、单独 verdict，也没有“需用户介入/禁止自动修复”的处置落点
- 现有 `codex-doc-review` 不只是一个 guide 文件，而是一整套 hard-gate、I/O 契约、状态码、canonical 报告和 agent 契约，见 `claude/skills/codex-doc-review/SKILL.md:18-25`、`:40-52`、`:79-105`，`claude/agents/codex-doc-reviewer.md:17-30`，以及 `claude/skills/codex-doc-review/references/review-guide-base.md:33-79`

所以 redesign 不能只迁移“知识点”，而必须明确：哪些旧契约被保留、哪些被丢弃、哪些被新 skill 吸收、哪些状态要继续保留为独立终态。否则实现时会把旧系统的安全语义和恢复语义一起丢掉。

另外，独立审查还指出一个更严重的问题：design 把 `review-fix-loop-protocol.md`、`review-iteration-protocol.md`、`team-review-protocol.md` 视为仍存在且“被其他 skill 引用，不在本次改动范围”，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:16-17`、`:191-193`；但当前仓库基线可能已不再如此。这说明设计对迁移基线的判断本身也需要重新核对，不能直接沿用。

因此，这一项应提升为 P1：它不是“描述轻重”的问题，而是**迁移基线与安全语义都可能已经过时，必须先校正再设计实现。**

## 对 challenger 观点的收敛

### 1. 关于“现在就能直接开工”

我不再保留“接受一半”的说法，最终改为：**当前文本不应直接开工。**

原因不是方向不清，而是主路径契约没有闭合：

- 文档已经清晰到足以表达设计意图，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:24-45`、`:56-140`、`:199-205`
- 但它还不是足以驱动安全实现的设计，因为外部 reviewer capability contract、统一 schema、fail-close 状态机、baseline 恢复语义都还没补齐

因此最终结论不再是“可以做，但别直接拿去验收”，而是：**先补 design，再开工。**

### 2. 关于“stash / JSON 异常不算阻塞”

我撤回这个修正。

晚到的 `contract-reviewer`、`arch-reviewer` 和独立审查都给出了更强证据：当前缺的不是局部实现细节，而是会直接影响 working tree 安全与循环边界的主契约。因此它们应恢复为**阻塞项**。

设计虽然给出了 dirty 时 stash、clean 时跳过、最终报告回显 stash SHA 的最小骨架，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:43-45`、`:82`、`:136`；但缺失的恢复命令、stash apply 失败语义、非法 reviewer 输出终态、JSON 解析失败 stop contract，已经足以让实现阶段出现静默降级、误判通过或破坏工作树的空间。

因此这一项的最终口径是：**stash / JSON / reviewer output 异常当前都应按阻塞处理，不宜降级为实现期再补的细节。**

### 3. 关于“count-based 不收敛判定是否可接受”

我接受 challenger 对定位的修正，但保留对强度的质疑。

- 作为 bounded loop 的保险丝，`连续 2 轮 findings 数量不减少` 可以先用，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:74`、`:127`
- 但它不适合作为“问题是否真正解决”的核心证明

所以这条可以先保留为 MVP 终止条件，但不应当被误用为质量证明。

### 4. 关于“双零 findings”是否足够

我接受 challenger 的基本判断：对无可执行验证的文档场景，连续两轮零 findings 是合理的 MVP 下限，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:124-126`。如果后续需要增强，更合理的方向是增加第二轮视角差异，而不是机械地再加第三轮、第四轮同质重跑。

## 必须补齐的修改项

### 0. 先校正迁移基线与主路径依赖

在进入实现前，先补两项设计前置核对：

- 校正 `code-review-fix` 主路径依赖：`codex:adversarial-review`、`codex-companion.mjs`、`codex exec --json` 三者到底谁是正式依赖，真实输入/输出/错误语义是什么，不能再把能力当既有前提直接写入设计，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:60-63`、`:94`、`:167-169`
- 重新核对迁移基线：design 当前把部分 shared protocols 当作仍存在且被引用，但独立审查已提示这部分基线可能过时；实现前必须先校正“现有真相”，再决定哪些属于本期不交付，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:16-17`、`:191-193`

### A. 把影响范围提升到运行时/门禁/contract 级

建议在 design 的淘汰计划和 success criteria 中显式列出以下受影响对象：

- `install.sh:1248-1253`
- `tests/test-runtime-integrity.sh:179-205`
- `tests/test-single-source-layout.sh:57-68`
- `tests/run-all.sh:15-18`、`:49-52`、`:100-107`
- `shared/hooks/lib/common.sh:508-690`
- `contracts/skill-chain.yaml:61-81`

否则实现计划会系统性低估工作量与验收面。

### B. 给两条新 skill 补最小 fail-close 异常矩阵

至少要定义：

- 工具不可用
- 输出非 JSON / 缺关键字段
- `location` 不可定位
- stash / 恢复冲突
- 验证命令自动发现失败
- reviewer 输出非法、用户中止、超时、权限不足时进入哪个终态
- 一条路径失败后是否允许切另一条路径（默认应禁止静默切换）

这里不能只写“失败就报错”，而要明确：异常发生时终止 run、报告原因、保留哪些现场信息、不继续修复、不静默切换路径。

### C. 把 finding 恢复成可解析、可追踪结构

最低要求应包含：

- `path`
- `line` 或 `range`
- `severity`
- `description`
- `recommendation`

如果还要做跨轮对比，再补一个 `finding_id` 或稳定 `fingerprint`。否则后面的“按行号修复”“判断同一问题是否仍存在”“不收敛统计”都会变弱。

另外，`dimension` 可以保留，但它应作为附加语义字段，而不能替代 `path/range` 这类机器字段。

### D. 把最终报告和 success criteria 改成证据导向

建议新增或显式要求：

- 各轮 findings 统计
- 最终 residual findings（即使通过也要保留 non-blocking 摘要）
- code 路径实际执行的验证命令与退出码
- doc 路径每轮评审维度列表
- 删除旧 skill 后 grep / 测试 / contract 校验的通过证据

## 可后移到实现验证的项

以下问题应进入实现验证或后续测试设计，不必阻塞 design 通过：

1. `focus` 文本对 `codex:adversarial-review` 的传递效果，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:211`
2. 自评审 agent 与 codex 路径的实际发现能力差距，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:212`
3. 文档评审自定义 prompt 的 JSON 稳定性，见 `docs/review-fix-loop/2026-04-03-redesign/design.md:213`
4. 文档第二轮是否需要增加 reviewer 多样性，而不是单纯重复同一路径

## 建议验收结论

建议给 Claude 的验收口径如下：

> 设计方向认可，但当前 design **不通过正式评审**。请先补齐 reviewer 外部依赖契约、统一 findings schema、fail-close 状态机、baseline 恢复语义，并重新核对迁移基线与影响范围；补完后再进入实现与验收。

## 最终一句话

**这份 redesign 方向是对的，但当前文本还没到可安全开工的设计完成度；先补 design，再实现。**
