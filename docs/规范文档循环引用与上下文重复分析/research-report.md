# 规范文档循环引用与上下文重复分析 调研报告

## 一页判断
- 当前结论：部分成立
- 是否符合当前目标：高
- 一句话判断：`rules/` 与 `reference/` 之间确实存在多条双向引用回路，但仓库当前运行时没有证据表明会自动递归展开这些文档正文；真正存在的风险是多层入口反复指向同一规则，造成“同一约束被多次强调”的认知重复，而不是安装器把同一文件无限重复注入上下文。
- 最大收益：当前分层把 MUST 规则源与补充指南分开，便于裁决优先级和维护责任划分。
- 最大风险：同一 reference 在 `assistant`、`rules`、`skills` 三层都可能再次出现，模型若逐层读取，可能出现权重放大、维护漂移和“看起来像重复加载”的体验。
- 不适用场景：如果前提是假设运行时存在 Markdown 链接递归加载器，这份结论不适用；本报告没有找到这样的实现。
- 结论翻转条件：若后续发现运行时会自动遍历并展开 `补充细则` 指向的文档正文，或 live probe 证明模型会在单次任务中无条件递归读取整条引用链，则应把风险等级上调为高。

## 优缺点速览
| 对象/论点 | 核心优势 | 核心短板 | 适用场景 | 不适用场景 |
|-----------|---------|---------|---------|-----------|
| `rules -> reference` 分层 | 优先级清晰，MUST 与指南职责分离 | 同一主题容易在多层再次被提及 | 需要明确“规则源 / 补充细则”边界的体系化规范 | 追求最小上下文、极低重复度的极简提示体系 |
| `runtime-catalog` 装配 | 统一渲染入口，按 target 控制可见项，避免手写漂移 | catalog 允许同一 reference 被多个 target 重复暴露 | 需要双端安装、平台差异隔离、可测试渲染 | 需要运行时自动去重和全局唯一曝光的场景 |
| 当前 skill 层引用方式 | 让 skill 在局部任务里显式声明依赖的规则与 reference | 可能与入口层、rules 层形成三层重复提醒 | 高风险流程、需要显式提醒关键规则的 skill | 已有稳定全局自动装载且不希望重复提醒的 skill |

## 采纳速览
- 现在该做什么：小范围试点
- 采纳前必须补的验证：对“模型在一次真实任务里会不会顺着 assistant -> rules -> reference -> skill 多跳读取”做行为级 probe；对重复指向最多的主题做一次上下文预算审计
- 最匹配的点：仓库已经有 `runtime-catalog`、运行时 probe 与多项 integrity/noise 测试，适合继续做结构化收敛
- 最不匹配的点：当前没有“全局去重策略”或“重复暴露预算”规则，skill 层也可再次声明相同依赖

## 调研背景
- 调研触发：用户担心 `硬编码治理规范.md`、`代码规范.md` 等规范文档互相引用，可能导致重复加载与上下文冗余
- 决策目标：判断这种担心在当前仓库里到底发生在哪一层，并明确是否已经影响运行时上下文
- 关键约束：只接受带代码和测试证据的判断；不把文档自述直接当结论；必须同时纳入反方挑战

## 检索路径与覆盖证明
- 名称归一化：本次对象为仓库内固定实体，覆盖 `rules/`、`reference/`、`runtime-catalog`、安装器、探针、契约测试、部分 `skills/`
- 已查对象类型：规则文档、参考文档、运行时 catalog、安装脚本、渲染器、探针脚本、完整性测试、skill 提示
- 已查 discovery 入口：`shared/`、`tools/`、`tests/`、`docs/`、安装后临时运行时产物
- 已排除候选：未把 `docs/archive/`、第三方社区 skill 正文、与本论点无关的评测结果纳入主结论，因为它们不决定当前运行时装配机制
- 剩余盲区：未运行依赖真实本机鉴权的 live Codex/Claude probe，因此“模型在真实一次会话里跨层读取多少跳”仍是待验证项

## 项目上下文
- 技术栈：Bash 安装器 + Python 渲染/校验脚本 + Markdown 规范/skill 体系 + shell tests
- 已有相关实现：`install.sh` 负责构建 `.claude/.codex` 运行时；`tools/community/render_runtime_contract.py` 负责把 catalog 渲染为 Runtime Contract；`tools/dev/probe-*-capabilities.sh` 与多项 `tests/test-*.sh` 负责运行时采证与完整性校验
- 约束条件：运行时强调 rules 优先于 reference；reference 作为补充细则保留绝对路径，不作为相对路径硬依赖

## 拆解对象概览
- 对象类型：项目方法 / 运行时文档装配机制
- 原始观点：文档循环引用会重复加载内容，导致上下文里出现重复信息
- 需要回答的问题：文档层有没有循环；运行时有没有自动重复展开；真正的重复风险发生在哪一层

## 核心论点拆解

### 论点 1：文档层确实存在循环引用，但主要是“规则源 <-> 指南”的语义回指

支持证据：
- `shared/rules/代码规范.md` 在 Runtime Contract 和正文中指向 `reference/代码质量.md`、`reference/硬编码治理规范.md`、`reference/性能效率.md`、`reference/测试规范.md`、`reference/代码复用.md`
- `shared/reference/硬编码治理规范.md` 明确写出 MUST 来自 `rules/代码规范.md`
- `shared/reference/代码质量.md` 多次回指 `rules/代码规范.md`，并再回指 `rules/铁律.md`
- 扫描结果存在多条闭环：`rules/代码规范.md -> reference/硬编码治理规范.md -> rules/代码规范.md`、`rules/代码规范.md -> reference/代码质量.md -> rules/代码规范.md`、`rules/铁律.md -> reference/测试规范.md -> rules/铁律.md`

反方挑战：
- 这些闭环没有被任何求值器当作依赖图执行，它们只是让人类/模型知道“规则源在哪里、补充细则在哪里”

判定：
- 成立，但属于“文档图存在回路”，不是“程序求值存在循环依赖”

### 论点 2：当前运行时没有发现自动递归展开这些回路的机制

支持证据：
- `install.sh` 先复制 `shared/assistant.md`、`shared/rules`、`shared/reference`，再调用 `render_runtime_contract`
- `render_runtime_contract.py` 对 `runtime_link` 的处理只是输出一条文本：`补充细则：\`$HOME/.../reference/xxx.md\``
- `runtime-catalog.json` 的 entry 是按 target 明确列出的，不是扫描 Markdown 后自动追链接
- 安装到临时目录后的 `AGENTS.md` 与 `rules/代码规范.md` 均表现为“一层摘要 + 绝对路径”，没有把 `reference/*.md` 正文内联进来

反方挑战：
- 运行时没有自动递归展开，不等于模型在执行任务时不会自行继续读取更多文件

判定：
- “自动重复加载正文”这一强论点不成立；“模型可能被再次引导去读同一主题文档”这一弱论点成立

### 论点 3：真实存在的重复更像“多层重复暴露”和“权重放大”

支持证据：
- `runtime-catalog.json` 里 `reference/测试规范.md` 同时挂在 `assistant`、`rules/铁律.md`、`rules/代码规范.md`
- `reference/代码质量.md`、`reference/硬编码治理规范.md`、`reference/性能效率.md` 同时挂在 `assistant` 与 `rules/代码规范.md`
- `shared/skills/developer/SKILL.md` 又声明“自动加载（不展开）：rules/铁律.md + rules/代码规范.md + reference/测试规范.md”
- 文档内部也有局部重复：`reference/代码质量.md` 对 `rules/代码规范.md` 有 4 次回指；`rules/代码规范.md` 对 `reference/代码质量.md` 有 2 次回指；`reference/硬编码治理规范.md` 对 `rules/代码规范.md` 有 2 次回指

反方挑战：
- 这类重复有一部分是有意强化关键约束，未必应该被全部消除

判定：
- 成立。问题不在“无限递归”，而在“同一约束被多层重复提及，可能改变模型注意力分配并增加维护成本”

### 论点 4：风险应分层看待，而不是一刀切说“有循环就有上下文污染”

支持证据：
- 渲染器层：未发现自动递归展开，风险低
- 运行时合同层：同一 reference 被多个 target 暴露，风险中
- skill 层：局部任务可再次声明相同依赖，风险中
- 维护层：同一主题在不同层被改写或重复表述，未来最容易出现漂移，风险中高

反方挑战：
- 如果真实代理大多只读入口文档，很多结构重复不会变成执行时问题

判定：
- 成立。当前更像“信息架构重复风险”而不是“实现层死循环风险”

## 论点挑战总表
| 论点 | 最强支持证据 | 最强反方挑战 | 当前判定 | 对我们的启示 |
|------|-------------|-------------|---------|-------------|
| 文档回路存在 | 扫描到多条 `rules <-> reference` 闭环 | 回路不等于 loader 递归 | 成立 | 必须把“图结构”与“执行机制”分开 |
| 会自动重复加载正文 | 未找到递归展开实现 | 模型仍可能多跳读取 | 不成立 | 不要把结构风险夸大成实现事实 |
| 不存在任何重复问题 | catalog 与 skills 都会再次暴露同一 reference | 一部分重复是故意强化 | 不成立 | 需要区分“强化性重复”和“维护性重复” |
| 核心风险是信息架构重复 | 同一 reference 在多 target 和 skill 重复出现 | 若模型读取深度有限，影响会被高估 | 部分成立 | 后续应做行为 probe 和重复预算治理 |

## 吸收建议
### 可以直接吸收
| 论点/做法 | 适用条件 | 如何吸收 |
|-----------|---------|---------|
| 把文档层回路与运行时装配分层判断 | 所有规范体系调研 | 以后讨论“重复加载”时，先问是 source graph、runtime assembly 还是 agent read path |
| 保留 `rules` 作为真源、`reference` 作为细则 | 需要优先级裁决的规范体系 | 继续保持 source of truth 分层，但减少无必要回指 |

### 改写后吸收
| 原始说法 | 改写后的做法 | 改写原因 |
|---------|-------------|---------|
| “循环引用会导致上下文重复污染” | “循环引用会提高多层重复暴露概率，但当前未证实存在自动递归正文展开” | 避免把结构问题误报为实现事实 |
| “只要没有 literal duplicate load 就不是问题” | “即使无自动重复展开，多层重复指向仍可能造成认知重复和维护漂移” | 避免低估信息架构风险 |

### 不采纳
| 论点/做法 | 不采纳理由 |
|-----------|-----------|
| 仅凭文档互链就判定运行时必然重复加载 | 缺少渲染器、安装器、probe 证据支撑 |
| 仅凭当前无递归 loader 就断言完全无风险 | 忽略了 assistant/rules/skills 三层重复暴露 |

## 落地行动项
- [高] 给 `runtime-catalog` 增加“重复暴露审计”脚本，统计同一 `runtime_path` 被多少 target 暴露，并标注是否属于故意强化
- [高] 为 `assistant -> rules -> reference` 增加一次真实多跳行为 probe，验证模型是否会在单次任务里跨层重复读取
- [中] 对 `代码规范 / 代码质量 / 硬编码治理规范` 做一次“最小必要回指”清理，减少同文件内重复提及同一路径的次数
- [中] 为 skill 层建立“重复依赖声明白名单”，明确哪些全局规则允许再次显式强调
- [低] 在文档规范或运行时规范里补一条“重复暴露预算/去重原则”，防止后续继续膨胀
