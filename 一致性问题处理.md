⏺ 核心思想是：skill 不是文档，是给 LLM 建立“下一步动作模型”的执行环境。
  所以每句话都应该降低决策熵，而不是增加一个模型需要解释、排除、联想的对象。

  你说“每一个字每句话 LLM 都会去理解”这个判断基本成立，但要再精确一点：

  LLM 不只是逐字执行，它会把所有 token 共同压成一个“当前任务世界”。
  你写：

  ▎ 不生成 PM co-creation ledger

  它不只是得到一个禁止项，还会得到几个副作用：

  1. PM co-creation ledger 被激活了：模型知道这里有个看起来很正式的 artifact
  名。
  2. 历史结构被召回了：它会推断“这个东西可能曾经存在，和当前任务有关”。
  3. 注意力被分散：它要判断
  ledger、issue_ledger、review_conclusion、delivery_confirmation 之间的关系。
  4. 禁止句不等于闭集：它只禁止这个 ledger，不自动禁止其他自造字段。
  5. 负面指令会变成候选空间的一部分：尤其是长名词、正式名词、路径、字段名，都会
  有“存在感”。

  所以最佳实践不是“把所有错误都禁止一遍”，而是：

  ▎ 只描述当前合法世界；只有当错误会真实进入输入或高频复发时，才命名错误。

  brainstorming skill 给的参考很明显。它的主路径是：

  - Explore project context
  - Ask clarifying questions
  - Propose approaches
  - Present design
  - Write design doc
  - User reviews spec
  - Invoke writing-plans

  这是正向流程闭集。模型看到的是“我接下来该做什么”。

  它也有负面内容，比如：

  ▎ Do NOT invoke any implementation skill...

  这个不是废话，因为它满足几个条件：

  1. 这是高风险分叉：一旦实现了，就越过了用户审批。
  2. 这是模型天然会犯的错：用户说“做个东西”，模型容易直接写代码。
  3. 它保护的是流程边界，不是召回一个废弃 artifact。
  4. 它后面还有正向终点：terminal state is invoking writing-plans。

  也就是说，brainstorming 的负面指令不是“不要生成某个已经不存在的东西”，而是阻断
  一个真实、常见、高代价的错误动作。

  我会把 skill 写作的核心原则压成这几条：

  1. 主路径写正向动作，不写历史债务
  写“PM 状态写入这些字段”，不要写“不要生成旧 ledger”。
  2. 用闭集替代禁止项
  好写法：
  ▎ PM 状态只写入：issue_ledger、review_conclusion、brief.json.delivery_confirma
  tion。
  ▎ 差写法：
  ▎ 不要写入 PM co-creation ledger。
  3. 命名即激活
  不要在主流程里命名已经不存在的对象、废弃目录、失败产物、旧字段。除非当前输入里
  会出现它，需要模型识别并迁移。
  4. 负面规则只用于高风险边界
  值得写 Do not 的通常是：写代码前必须审批、不能 mock
  验收、不能删除测试、不能改镜像源、不能推送远端。
  不值得写的是：某个已经清掉的旧 artifact 名。
  5. 错误模式放 eval，不放主提示
  如果担心模型又生成 ledger，应该用测试检查“输出没有新增 ledger 字段”，而不是在
  skill 正文里天天喊 ledger。
  6. Why 只解释会改变执行判断的原因
